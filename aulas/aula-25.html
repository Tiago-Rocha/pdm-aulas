Às 16:40, logo a seguir ao projeto. Dois minutos. As duas coisas viajam pelo mesmo cano: a app junta as linhas, manda-as em lotes para a API do curso e a API passa-as ao OpenObserve, na mesma stream apps. O que as separa é o campo kind: log ou event. Não precisam de dois servidores para ter as duas coisas; precisam de as distinguir no código, para no fim não terem um monte de linhas onde o erro se perde entre os toques. Os eventos têm um nome por ação, no passado, em snake_case, sempre igual: é com ele que se conta. As apps grandes usam ferramentas diferentes para cada lado: o Spotify ou a Revolut medem com analytics o que as pessoas fazem e apanham os crashes com o Crashlytics ou o Sentry. Um exemplo com as duas: alguém abre a previsão de uma ilha e a app rebenta. Abrir a previsão é um evento de analytics (forecast_opened, com a ilha); o rebentar é um erro, uma linha de log. E a linha do erro leva o last_event: o que a pessoa tinha acabado de fazer.

A ideia: Uma linha, no initState do ecrã da previsão. O resto junta-se pelo caminho, e é com isso que no OpenObserve se conta e filtra.

Está em lib/screens/forecast_screen.dart: o initState corre uma vez, quando o ecrã abre, e é aí que se diz "abriram a previsão desta ilha". O nome vai no passado e em snake_case, sempre igual: é com ele que se conta. Como funciona por dentro (lib/telemetry/analytics.dart e telemetry.dart), para quem perguntar. Além destes campos, cada linha leva version (o commit do deploy), platform e run (um por arranque): o analytics.event põe a linha na mesma fila dos logs, com kind event; a fila junta a versão, a plataforma e o run e vai para a API em lotes de cinco em cinco segundos; sem rede, guarda. A API acrescenta quem mandou e passa ao OpenObserve. O analytics também guarda o último evento como texto (forecast_opened island=corvo): se a seguir houver um erro, a linha do erro leva last_event. É o que o Sentry chama breadcrumb, o rasto de migalhas. O log.info('islands loaded', {'count': islands.length}) faz o mesmo com kind log.

  • Procurem as vossas linhas pelo nome: o que fizeram, em que ilha e em que versão.

No OpenObserve, o dashboard "PDM · a API e a app ao vivo", com 1 hora e atualização de 10 em 10 segundos. Separador "App: analytics": arranques, previsões abertas, favoritos, "Onde estou?", as ilhas mais abertas e os últimos eventos com o nome de quem os fez. Onde a magia acontece: um teste em três partes

test('offline, load keeps the error for the screen', () async {
  final repository = FakeForecastRepository()..failing = true;
  final notifier = ForecastNotifier(repository);

  await notifier.load();

  expect(notifier.error, contains('Sem ligação'));
});

A ideia: Preparar, fazer, verificar. O nome diz, numa frase, o que devia acontecer.

Está em test/state/forecast_notifier_test.dart. As três partes vão separadas por uma linha em branco; quando falha, lês o nome e sabes o que se partiu. Preparar: um repositório falso que falha, como um telemóvel sem rede, e o notifier com ele. Fazer: uma coisa só, o load. Verificar: o erro ficou guardado para o ecrã mostrar. O expect compara o que aconteceu com o que devia acontecer; contains, isNull, isTrue, closeTo são os matchers. Não há rede, nem ecrã, nem telemóvel: corre em milissegundos. Se o load não apanhasse a exceção, o teste falhava com a exceção e o nome do teste, e não com "expected ... but was null".

Primeiro vermelho, depois verde

Se corrigem primeiro e o teste passa à primeira, não há garantia de que apanhe o bug: pode estar a testar outra coisa, ou o mesmo caminho que já funcionava. Por isso a ordem: vê-lo falhar com o bug, corrigir, vê-lo passar. A partir daí o teste fica no repositório para sempre: se alguém voltar a partir a mesma coisa daqui a um ano, o CI fica vermelho antes de chegar às pessoas. Chama-se teste de regressão. Cada ficheiro de teste já tem um teste vizinho do bug; o mais rápido é copiar esse e mudar o caso. Se o teste novo não falhar com o bug, não está a testar o bug: voltem ao log.

Integração contínua: o CI

  • Mundo real: GitHub Actions, Codemagic e Bitrise para Flutter; para iPhone o CI precisa de um Mac.
O ficheiro é .github/workflows/ci.yml, tem duas partes. A primeira, test, corre em cada pull request e em cada push para o main: instala o Flutter, flutter pub get, flutter analyze, flutter test. A segunda, deploy, só corre depois de um merge e só se a primeira passou: flutter build web com o clientId da app desta aula e a versão igual ao commit, e publica no GitHub Pages. A versão publicada é o commit: nos logs, a coluna version muda quando a correção chega. Os segredos (clientId e clientSecret) estão nas definições do repositório, não no código. Mostra no GitHub um PR com o visto verde e um com a cruz vermelha, e o separador Actions com o log de um teste a falhar. Com o CI vermelho não há merge, nem a cinco minutos da review: um merge vermelho parte o main de todos os colegas, e na review o que conta é o que funciona. Melhor apresentar menos e verde. Nos projetos, o CI entra na sprint 3: é este ficheiro, só com a parte test.
