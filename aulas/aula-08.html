Estado: do setState às arquiteturas

Teoria: o que é estado numa app, onde deve viver, e comparação entre setState, Provider, BLoC e Riverpod. Prática: StatefulWidget, ciclo de vida do State, campos de texto, formulários com validação e pesquisa numa lista.

Estado efémero vs estado de aplicação

Efémero (de um widget)De aplicação (partilhado)
ExemplosSeparador selecionado, texto meio escrito, posição de scroll, se um cartão está expandidoUtilizador autenticado, favoritos, unidade de temperatura, previsões carregadas, carrinho de compras
Quem precisa deleUm widget e os filhosVários ecrãs, sem relação de parentesco

Para os testes: estado efémero fica no widget com setState; estado de aplicação fica fora da árvore e é partilhado.

Volta à pergunta do quadro: o interruptor °C/°F. É efémero? Não: o ecrã de previsão, o detalhe e o widget de ecrã inicial precisam todos dele. Exemplo prático: pergunta onde vive o "carrinho" numa app de compras. Todos percebem que não pode ser no botão "adicionar".

O problema dos cinco níveis

  • A unidade de temperatura é escolhida em EcraDefinicoes e usada em CartaoLocalidade, que está dentro de ListaLocalidades, dentro de EcraPrevisao, dentro de Shell, dentro de TempoApp.
  • Com setState só, a variável tem de subir até ao antepassado comum (TempoApp) e descer por parâmetro através de cinco construtores que não a usam para nada. Chama-se prop drilling.
  • Cada widget intermédio passa a depender de algo que não é seu. Acrescentar um campo novo obriga a mexer em cinco ficheiros.
  • E quando a unidade muda, setState em TempoApp reconstrói a app inteira, não só os cartões.

A resposta a este problema é a razão de existirem as bibliotecas de gestão de estado. Todas resolvem a mesma coisa: pôr o estado num sítio acessível e reconstruir só quem o lê.

setState: quando chega e quando deixa de chegar

  • Chega quando o estado é de um ecrã ou de um widget e ninguém mais precisa dele: um contador, um formulário, um painel que abre e fecha, um filtro de pesquisa local.
  • Chega para protótipos e para ecrãs isolados. Não é "má prática"; é a ferramenta mais simples e o Flutter foi desenhado para ela.
  • Deixa de chegar quando dois ecrãs sem parentesco precisam do mesmo dado, quando o estado tem de sobreviver à navegação, ou quando queres testar a lógica sem construir widgets.
  • Deixa de chegar quando o build reconstrói uma árvore grande por causa de um booleano.

Para os testes: setState marca o widget como sujo e agenda um rebuild do seu subtree no próximo frame. Não reconstrói a app inteira, mas reconstrói tudo abaixo.

ChangeNotifier, Provider e InheritedWidget

  • InheritedWidget é o mecanismo do próprio Flutter para pôr um valor na árvore e deixar qualquer descendente lê-lo com context. Theme.of(context) e MediaQuery.of(context) são isto.
  • ChangeNotifier é uma classe com notifyListeners(). O teu estado estende-a: class Definicoes extends ChangeNotifier { bool fahrenheit = false; void alternar() { fahrenheit = !fahrenheit; notifyListeners(); } }.
  • Provider junta os dois: põe o notifier na árvore e context.watch<Definicoes>() reconstrói só o widget que o chamou quando há notifyListeners.
  • Resolve os cinco níveis: o CartaoLocalidade lê a unidade diretamente; os intermédios nem sabem que existe.
  • É recomendado pela equipa do Flutter para começar e é o que vamos usar no projeto.

Para os testes: Provider é um InheritedWidget com açúcar; ChangeNotifier avisa os ouvintes; watch reconstrói, read não.

BLoC, Cubit e Riverpod

AbordagemComo funcionaQuando faz sentido
setStateO State guarda e reconstrói o subtreeEcrã isolado, poucos widgets, protótipos
Provider + ChangeNotifierObjeto observável na árvore; watch reconstrói só quem lêVários ecrãs partilham estado; equipas pequenas; o nosso projeto
BLoC / CubitEventos entram, estados imutáveis saem por um Stream; cada transição é previsível e testável; mais ficheirosEquipas grandes, requisitos fortes de teste, apps bancárias
RiverpodProviders globais e tipados, sem depender do BuildContext; erros apanhados em compilaçãoQuem já domina Provider e quer mais segurança e composição

Todas fazem a mesma coisa por baixo: um objeto que guarda estado e avisa quem o observa. A diferença está na cerimónia e nas garantias.

Analogia Onde fica a lista de compras. Um post-it no frigorífico de um quarto: só quem entra nesse quarto o vê (setState). Um quadro na cozinha que toda a casa consulta e que avisa quando muda (ChangeNotifier com Provider). Um livro de registos com todas as alterações, datadas e assinadas (BLoC: eventos e estados). O quadro chega para a maioria das casas.

Fluxo unidirecional e imutabilidade

  • Um só sentido: a UI dispara uma ação (toque, texto) → a ação muda o estado → a UI reconstrói a partir do estado novo. A UI nunca muda o estado diretamente nem o estado toca na UI.
  • Com um só sentido, qualquer ecrã é uma função do estado: dado o mesmo estado, vês o mesmo ecrã. É o que torna testes e depuração possíveis.
  • Imutável: em vez de mudar um campo de Previsao, crias uma nova com copyWith. Um objeto que ninguém altera pode ser partilhado, comparado e guardado num histórico sem sustos.
  • O Definicoes do slide anterior é mutável por dentro (é um ChangeNotifier), mas o que expõe são valores. BLoC e Riverpod levam a imutabilidade até ao fim.

Para os testes: fluxo unidirecional é ação → estado → UI; imutabilidade significa criar cópias com copyWith em vez de alterar objetos.

Analogia Não se rabisca o quadro da cozinha. Escreve-se um quadro novo com a alteração (copyWith) e substitui-se o antigo. Quem estava a olhar para o antigo percebe que mudou, porque o objeto é outro; e o antigo pode ficar guardado num histórico.

Critério para escolher, e o que vamos usar

  • Quantos ecrãs partilham o estado? Um: setState. Vários: Provider ou acima.
  • Precisas de testar a lógica sem widgets? Então a lógica tem de viver fora dos widgets: Provider, BLoC ou Riverpod.
  • Tamanho da equipa e do projeto. Três pessoas e 10 ecrãs: Provider. Vinte pessoas e 200 ecrãs: BLoC ou Riverpod pelas regras que impõem.
  • O que a equipa já sabe pesa mais do que o que está na moda.
  • No projeto usamos setState para estado efémero e Provider com ChangeNotifier para o resto: é simples, é o recomendado no guia de arquitetura do Flutter, e dá para chegar a BLoC mais tarde sem reescrever tudo.
Hoje só setState. Provider entra na aula 13, quando tivermos dados da API para partilhar.

1. StatelessWidget vs StatefulWidget

class SeletorUnidade extends StatefulWidget {
  const SeletorUnidade({super.key});

  @override
  State<SeletorUnidade> createState() => _SeletorUnidadeState();
}

class _SeletorUnidadeState extends State<SeletorUnidade> {
  bool _fahrenheit = false;                     // o estado vive aqui, não no widget

  @override
  Widget build(BuildContext context) {
    final t = _fahrenheit ? 21.0 * 9 / 5 + 32 : 21.0;
    return Column(
      children: [
        Text('${t.toStringAsFixed(0)} ${_fahrenheit ? '°F' : '°C'}'),
        Switch(
          value: _fahrenheit,
          onChanged: (v) => setState(() => _fahrenheit = v),   // muda e pede rebuild
        ),
      ],
    );
  }
}

1. Stateful: o que interessa

  • O widget continua imutável. O que muda é o objeto State, que o Flutter cria uma vez e mantém vivo entre rebuilds. É por isso que o hot reload preserva o que escreveste.
  • setState(() { ... }) faz duas coisas: executa a alteração e marca o widget para reconstruir no próximo frame. Alterar a variável sem setState muda o valor, mas o ecrã não acompanha.
  • Só o subtree deste widget é reconstruído. Quanto mais abaixo estiver o StatefulWidget, menos trabalho.
  • O Switch não guarda nada: mostra value e avisa em onChanged. Todos os controlos Material são assim: controlled widgets.
  • Atalho no VS Code: escreve stful e carrega em Tab.

2. Ciclo de vida do State

class _PesquisaState extends State<Pesquisa> {
  late final TextEditingController _controlador;
  Timer? _debounce;

  @override
  void initState() {
    super.initState();                       // 1. uma vez, antes do primeiro build
    _controlador = TextEditingController();
    _controlador.addListener(_aoEscrever);
  }

  void _aoEscrever() {                       // 2. cada tecla: espera 300 ms antes de filtrar
    _debounce?.cancel();
    _debounce = Timer(const Duration(milliseconds: 300), () => setState(() {}));
  }

  @override
  void dispose() {
    _debounce?.cancel();
    _controlador.dispose();                  // 4. liberta; sem isto, fuga de memória
    super.dispose();
  }

  // 3. build corre entre initState e dispose, tantas vezes quantas forem precisas
}
Mostra o erro que aparece se chamares setState depois do dispose (um Timer que dispara depois de sair do ecrã). É o crash mais comum nos projetos de anos anteriores. Dá 10 minutos a este bloco.

2. Ciclo de vida: o que interessa

MétodoQuando correPara quê
initStateUma vez, quando o State é criadoCriar controllers, subscrever streams, lançar o primeiro pedido
didChangeDependenciesDepois do initState e sempre que um InheritedWidget de que dependes muda (tema, locale)Ler Theme.of ou MediaQuery.of, que não podem ser lidos no initState
buildSempre que é preciso desenharSó descrever a UI. Nada de pedidos de rede aqui
didUpdateWidgetQuando o pai reconstrói com parâmetros novosReagir a um parâmetro que mudou (nova localidade selecionada)
disposeUma vez, quando o widget sai da árvoreLibertar controllers, timers, subscrições, focus nodes

Para os testes: tudo o que crias em initState libertas em dispose; build pode correr muitas vezes e não deve ter efeitos secundários.

3. TextField e pesquisa numa lista

String _filtro = '';                          // estado: o que o utilizador escreveu

List<String> get _filtradas => localidades   // de lib/dados.dart
    .where((l) => l.toLowerCase().contains(_filtro.toLowerCase()))
    .toList();

@override
Widget build(BuildContext context) {
  return Column(
    children: [
      TextField(
        decoration: const InputDecoration(
          prefixIcon: Icon(Icons.search),
          hintText: 'Pesquisar localidade',
          border: OutlineInputBorder(),
        ),
        onChanged: (texto) => setState(() => _filtro = texto),
      ),
      Expanded(
        child: ListView(
          children: [for (final l in _filtradas) ListTile(title: Text(l))],
        ),
      ),
    ],
  );
}

3. Pesquisa: o que interessa

  • Para reagir ao texto chega onChanged. Precisas de um TextEditingController quando queres ler o texto noutro sítio, limpá-lo (botão X) ou pôr um valor inicial. E aí, dispose.
  • A lista filtrada é um getter calculado a partir do estado. Não guardes a lista filtrada como estado: são dois valores que podem ficar dessincronizados.
  • Filtrar 100 localidades a cada tecla é instantâneo. Filtrar 100 000, ou pedir à API, exige o debounce do slide anterior.
  • O Expanded à volta do ListView é obrigatório: sem ele, altura infinita dentro da Column.
  • InputDecoration controla o aspeto: ícone, hint, label, borda, texto de ajuda e de erro.

4. Form, TextFormField e validação

final _chave = GlobalKey<FormState>();

Form(
  key: _chave,
  child: Column(
    children: [
      TextFormField(
        decoration: const InputDecoration(labelText: 'Nome da localidade'),
        validator: (v) {
          if (v == null || v.trim().isEmpty) return 'Obrigatório';
          if (v.trim().length < 3) return 'Pelo menos 3 letras';
          return null;                                  // null significa válido
        },
      ),
      FilledButton(
        onPressed: () {
          final form = _chave.currentState!;
          if (form.validate()) {                        // corre todos os validators
            ScaffoldMessenger.of(context).showSnackBar(
              const SnackBar(content: Text('Formulário válido')),
            );
          }
        },
        child: const Text('Guardar'),
      ),
    ],
  ),
)

4. Formulários: o que interessa

  • Form agrupa campos; GlobalKey<FormState> dá acesso ao estado do formulário a partir do botão. É dos poucos usos legítimos de GlobalKey.
  • Cada TextFormField tem um validator que devolve uma mensagem de erro ou null. validate() corre todos, mostra os erros por baixo dos campos e devolve true se estiver tudo bem.
  • autovalidateMode: AutovalidateMode.onUserInteraction valida enquanto o utilizador escreve, depois da primeira tentativa. Sem isto, só valida ao submeter.
  • keyboardType: TextInputType.number e textInputAction: TextInputAction.next mudam o teclado do telemóvel. Em mobile, isto é UX.
  • onSaved e form.save() copiam os valores para variáveis quando não queres um controller por campo.

Para os testes: um validator devolve null quando o valor é válido e uma String com o erro quando não é.

5. Switch, Checkbox e Slider ligados a estado

bool _notificacoes = true;
double _raio = 25;
bool _fahrenheit = false;

SwitchListTile(
  title: const Text('Avisos meteorológicos'),
  value: _notificacoes,
  onChanged: (v) => setState(() => _notificacoes = v),
),
CheckboxListTile(
  title: const Text('Mostrar em Fahrenheit'),
  value: _fahrenheit,
  onChanged: (v) => setState(() => _fahrenheit = v ?? false),
),
ListTile(
  title: Text('Raio de pesquisa: ${_raio.round()} km'),
  subtitle: Slider(
    value: _raio,
    min: 5,
    max: 100,
    divisions: 19,
    label: '${_raio.round()} km',
    onChanged: (v) => setState(() => _raio = v),
  ),
),

Todos seguem o mesmo contrato: value vem do estado, onChanged muda o estado com setState. O widget nunca guarda nada.
