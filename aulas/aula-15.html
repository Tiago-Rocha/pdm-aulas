Do JSON ao modelo

O GET /v1/trails da API devolve uma lista de trilhos. Cada um chega assim (encurtado):

{
  "id": "montanha-do-pico",
  "name": "Montanha do Pico",
  "islandId": "pico",
  "distanceKm": 7.6,
  "duration": "7 h"
}

Três peças para o pôr na app: o modelo Trail, o fromJson que lê um mapa, e o repository que lê a lista. É o mesmo caminho das ilhas, agora com trilhos.

Antes do jogo, pergunta: "que campos do JSON a app precisa para mostrar uma lista de trilhos?". O distanceKm é a armadilha: 7.6 parece sempre double, mas a API pode mandar 7.

Jogo: do JSON ao modelo

Três exercícios de ordenar. No modelo, as linhas certas prendem-se; os campos podem vir por qualquer ordem, tal como os required. No fromJson, os quatro campos também. A lista é igual à das ilhas no HttpForecastRepository.

Estado da turma

Quem acabar pode abrir a API em /docs e ver o JSON de um trilho a sério.

Definição de pronto

Uma issue só fecha quando o pull request cumpre tudo isto. Se falha um ponto, não está pronta, por muito que "funcione no meu portátil".

  1. Corre no telemóvel, não só no Chrome ou no emulador.
  2. flutter analyze sem avisos.
  3. Trata os estados de carregamento, erro e vazio.
  4. Foi revisto e aprovado por outro membro do grupo.
Para os testes "Pronto" é uma lista objetiva, não uma opinião.

Jogo: está pronto?

Um cenário de cada vez, todos ao mesmo tempo. Esperem por todos: revemos cada resposta juntos.

  1. Lê o cenário e vota sozinho.
  2. Discute com o colega do lado: porquê essa resposta? Convence-o, ou deixa-te convencer.
  3. Vota outra vez. Só depois vês a resposta.
Vão todos ao mesmo ritmo: diz "cenário 1", deixa votar, dá um minuto de discussão aos pares, segunda votação, e passa ao painel do slide seguinte. A primeira votação é a que conta no painel dos pontos; o que interessa é a mudança entre a primeira e a segunda. Se a primeira votação já tiver mais de 70% certos, não vale a pena discutir: passa ao seguinte.

Está pronto? A turma

Compara as duas barras de cada cenário: se a segunda votação tem mais respostas certas, a discussão funcionou. O cenário dos avisos do analyze costuma dividir a turma: vale a pena ouvir quem diz "são só avisos".

Contrato primeiro

A API já está feita. O que falta é o código de cada um, e num grupo o maior atraso é esperar pelo colega. Por isso, antes de programar, o grupo combina o contrato: o modelo e a interface do repository. Depois cada um trabalha do seu lado.

A Anafaz o ecrã dos trilhos contra o FakeTrailRepository
O contratoTrailRepository: o que se pode pedir, sem dizer como
O Ruifaz o HttpTrailRepository, que chama a API

É o que fizemos nas aulas de camadas, agora a dois: o fake passa a ser a forma de não esperar pelo colega.

Jogo: o contrato

A pares: um é a Ana, o outro é o Rui. Um exercício de cada vez, e esperem por todos: revemos cada resposta juntos antes do seguinte.

Três exercícios de ordenar: a interface (as linhas certas prendem-se), o fake e a ordem do trabalho num grupo de dois. Os dois métodos da interface podem trocar entre si, tal como os dois métodos do fake e os passos da Ana e do Rui, que acontecem ao mesmo tempo. No terceiro, repara que a revisão do pull request é a definição de pronto de há bocado. O painel do slide seguinte mostra quem já acabou.

Estado da turma

Uma linha por aluno, uma coluna por exercício. Verde com ✓: resolvido; o ponto diz se acertou na pergunta. "Sem verificar há X min": está parado, vai lá.

Onde ficámos

  3. O contrato primeiro deixa dois colegas trabalhar ao mesmo tempo: um contra o fake, outro contra a API.
