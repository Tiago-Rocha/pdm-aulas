Build e assinatura

Teoria: assinatura de aplicações no Android e no iOS, versionamento aceite pelas lojas, flavors e ambientes, segredos de build. Prática: build de release assinado com uma chave do grupo, app bundle, versionamento e flavors dev e prod.

Repo: pdm-aula-31
Pergunta quem já tem o JDK acessível na linha de comandos (keytool). Em Windows, o keytool está em C:\Program Files\Android\Android Studio\jbr\bin; quem não o tiver no PATH usa o caminho completo. Mostra o teu keystore de produção no gestor de palavras-passe (sem abrir) para deixar claro onde é que uma chave real vive.

No fim desta aula consegues

  • Explicar o que uma assinatura digital prova numa app e o que acontece quando a chave se perde, no Android e no iOS.
  • Criar um keystore, ligá-lo ao Gradle com key.properties fora do repositório e gerar um app bundle assinado.
  • Distinguir versionName de versionCode e aplicar as regras das lojas ao version do pubspec.yaml.
  • Configurar flavors dev e prod com application id e ícone diferentes, e injetar configuração de build com --dart-define.
  • Descrever certificados, provisioning profiles e automatic signing no iOS.

Assinatura: porque existe (1 de 2)

  • Assinar é calcular um resumo (hash) do pacote e cifrá-lo com uma chave privada. O certificado com a chave pública viaja dentro do pacote.
  • Prova duas coisas: quem construiu a app (a mesma chave é o mesmo autor) e que o pacote não foi alterado depois de assinado.
  • O sistema operativo só aceita uma atualização se o package name e a chave forem os mesmos da versão instalada. É isto que impede uma app falsa de substituir a tua.
  • Não prova que a app é segura, nem que o código presta. Prova identidade e integridade, mais nada.
  • Toda a app instalada num telemóvel está assinada, incluindo as de debug: o Flutter usa ~/.android/debug.keystore, gerado na primeira compilação, diferente em cada máquina.

Para os testes: a assinatura prova autoria e integridade; não prova qualidade nem segurança.

Analogia A assinatura é o selo de um notário. Prova quem fez a app (a mesma chave é o mesmo autor) e que ninguém a alterou pelo caminho (o hash bate certo). Não diz nada sobre o conteúdo do documento: um contrato mau com selo continua a ser um contrato mau.
Exemplo real que já apanhou grupos: o colega A instala a app de debug no telemóvel do colega B; depois B tenta correr flutter run e recebe INSTALL_FAILED_UPDATE_INCOMPATIBLE, porque a chave de debug de cada portátil é diferente. A solução é desinstalar. Isto é a assinatura a funcionar.

Quem o perde nunca mais consegue assinar uma atualização como sendo a mesma app: para o sistema, uma app com outro carimbo é outra app. O Play App Signing é a Google a guardar uma cópia do carimbo final; a tua upload key é um carimbo secundário que, se se perder, se substitui.

Android: keystore, key.properties, signingConfigs

  • Keystore (.jks): ficheiro com o par de chaves, protegido por palavra-passe. Cada chave lá dentro tem um alias. Cria-se uma vez com keytool.
  • android/key.properties: quatro linhas com o caminho do keystore, o alias e as palavras-passe. O Gradle lê-o. Vai para o .gitignore.
  • signingConfigs em android/app/build.gradle.kts: diz ao Gradle que o build type release assina com essa chave.
  • Sem isto, flutter build appbundle assina com a chave de debug e a Play Console recusa o upload.
  • Em CI, o keystore entra como secret em base64 e o key.properties é escrito no momento do build.

Para os testes: o keystore assina; o key.properties só diz onde ele está e como abri-lo. Nenhum dos dois entra no git.

iOS: certificados e provisioning profiles (1 de 2)

  • Certificado de desenvolvimento: por programador, para correr no teu iPhone. Certificado de distribuição: por equipa, para TestFlight e App Store. Ambos emitidos pela Apple a partir de um pedido (CSR) e válidos um ano.
  • A chave privada do certificado fica no Keychain do Mac que fez o pedido. Para outra máquina ou para CI exporta-se em .p12.
  • App ID / bundle identifier: registado em developer.apple.com, em notação DNS invertida (pt.uac.tempoacores). As capacidades (push, associated domains) ficam-lhe associadas.
  • Provisioning profile = certificado + App ID + lista de dispositivos (em desenvolvimento e ad hoc) + entitlements. Vai embutido no .ipa.
  • Um Apple ID gratuito chega para correr no próprio iPhone: perfil de 7 dias, sem TestFlight nem loja. A conta paga custa 99 USD por ano.
Analogia No iOS há ainda o registo notarial da Apple. O certificado é a identidade do notário (quem és); o provisioning profile é o registo de em que dispositivos e para que app o selo vale. Sem os dois o Xcode não assina, e o selo final que chega à loja é o da própria Apple.

iOS: bundle id e automatic signing (2 de 2)

  • Automatically manage signing no Xcode cria certificados, App ID e perfis por ti. Chega para quase todos os projetos, incluindo o vosso.
  • Assinatura manual só quando precisas de controlar o perfil: CI, extensões (widgets, notificações ricas), várias equipas. Nesse mundo usa-se fastlane match, que guarda os certificados cifrados num repositório privado.
  • O bundle id é único no mundo e não muda depois de publicado. Escolhe-o bem à primeira.
  • flutter build ipa gera o ficheiro .ipa; o upload faz-se com o Transporter ou com xcrun altool. Só em macOS.
  • O versionamento é o mesmo que no Android: vem do pubspec.yaml, como vais ver a seguir.

Para os testes: no iOS quem assina a app que chega à loja é a Apple; o teu certificado de distribuição só te autoriza a fazer o upload.

Mostra o Xcode: Runner → Signing & Capabilities → Team. Mostra também developer.apple.com → Certificates, IDs & Profiles com a tua conta, para verem que os três objetos existem mesmo. Não gastes mais de 5 minutos: quem não tem Mac não vai fazer isto.

Versionamento: version: 1.2.3+45

No pubspec.yamlAndroidiOSQuem o vê
1.2.3 (antes do +)versionNameCFBundleShortVersionStringO utilizador, na loja e nas definições
45 (depois do +)versionCodeCFBundleVersionA loja, para ordenar builds
  • O Flutter copia os dois valores para o Gradle (flutter.versionName, flutter.versionCode) e para o Xcode (Generated.xcconfig) em cada build. O pubspec é a fonte única.
  • Na linha de comandos podes sobrepor: --build-name=1.2.4 --build-number=46. É o que o CI faz com o número da execução.
  • Segue semver no nome: major quando partes compatibilidade, minor quando acrescentas, patch quando corriges.

Versionamento: regras das lojas

  • Play: o versionCode é um inteiro que tem de ser estritamente maior do que qualquer um já carregado para a app, em qualquer track. Máximo 2 100 000 000. Não se reutiliza nunca.
  • App Store: dentro da mesma versão (1.2.3) o build number tem de subir; o TestFlight recusa um build repetido. Uma versão nova pode recomeçar o build em 1, mas ninguém o faz.
  • O nome de versão pode repetir-se entre uploads (vários builds da 1.2.3 em teste); o código nunca.
  • No telemóvel, instalar um versionCode menor do que o instalado dá INSTALL_FAILED_VERSION_DOWNGRADE. É o mesmo mecanismo que impede que um utilizador seja "atualizado" para trás.
  • Estratégia simples para o projeto: 1.0.0+N, com N a subir a cada build que sai do portátil para outra pessoa.

Para os testes: versionName é para humanos e pode repetir-se; versionCode é para a loja e nunca pode descer nem repetir.

Flavors e ambientes

  • Porquê: a app de dev fala com a API de dev, a de prod com a de prod; as duas instalam-se lado a lado no mesmo telemóvel; o ícone diz qual é qual; a de prod não tem logs nem menus escondidos.
  • Android: productFlavors no Gradle, com applicationIdSuffix (.dev) e source sets por flavor (src/dev/res) para ícone e nome.
  • iOS: schemes e configurations (Debug-dev, Release-prod) com ficheiros .xcconfig. Mais trabalho manual; há packages que o automatizam.
  • Flutter: flutter run --flavor dev. O nome do flavor tem de existir nas duas plataformas se compilas as duas.
  • Dois ambientes chegam para o projeto. Em empresas vês dev, staging e prod, raramente mais.

Para os testes: um flavor muda a identidade da app (id, nome, ícone) e a configuração de build; não muda o código Dart.

--dart-define para configuração e segredos de build

  • --dart-define=API_URL=https://... na linha de comandos e String.fromEnvironment('API_URL') no código. É uma constante de compilação: existe também bool.fromEnvironment e int.fromEnvironment.
  • Com muitas chaves: --dart-define-from-file=env/prod.json. O ficheiro de prod vai para o .gitignore e para os secrets do CI.
  • O valor entra no binário como texto. A ofuscação (--obfuscate) dificulta mas não impede que alguém o extraia de um APK. Serve para configuração e chaves de baixo risco (URL, chave de mapas com restrição por package), não para segredos que dariam acesso a dados.
  • O segredo do grupo para a API do curso fica onde já está: obtido em runtime e guardado no flutter_secure_storage, como fizemos na aula 17.
  • Flavor e dart-define combinam-se: o flavor muda a identidade da app, o dart-define muda o que o Dart lê.

Para os testes: --dart-define injeta valores em tempo de compilação; tudo o que entra no binário pode ser lido por quem o descompilar.

Antes de começar Confirma que keytool responde no terminal. Se não, usa o caminho completo: em macOS e Linux $(/usr/libexec/java_home)/bin/keytool ou o JDK do Android Studio; em Windows "C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe".
Faz o passo 1 ao vivo no teu portátil para o keystore do repo da aula, e deixa o teu ecrã visível. As perguntas do keytool (nome, organização, cidade) confundem: diz-lhes que podem responder qualquer coisa, só o alias e as palavras-passe importam.

1. Criar o keystore e o key.properties

  1. Gera a chave, fora da pasta do projeto. Guarda as duas palavras-passe no gestor de palavras-passe do grupo. 
    keytool -genkey -v -keystore ~/tempo-acores-upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
  2. Escreve o key.properties dentro de android/, com o caminho absoluto do keystore. 
    storePassword=a-tua-palavra-passe
keyPassword=a-tua-palavra-passe
keyAlias=upload
storeFile=/Users/eu/tempo-acores-upload.jks
  3. Protege os dois no git antes de fazeres qualquer commit. 
    android/key.properties
**/*.jks
**/*.keystore

2. signingConfigs no build.gradle.kts

import java.util.Properties
import java.io.FileInputStream

val keystoreProperties = Properties()
val keystorePropertiesFile = rootProject.file("key.properties")
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(FileInputStream(keystorePropertiesFile))
}

android {
    // ...namespace, compileSdk, defaultConfig ficam como estão
    signingConfigs {
        create("release") {
            keyAlias = keystoreProperties["keyAlias"] as String
            keyPassword = keystoreProperties["keyPassword"] as String
            storeFile = keystoreProperties["storeFile"]?.let { file(it) }
            storePassword = keystoreProperties["storePassword"] as String
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")   // TODO 1: era "debug"
        }
    }
}

3. Gerar, instalar e verificar o release

  1. App bundle para a loja. Fica em build/app/outputs/bundle/release/app-release.aab. 
    flutter build appbundle --release
  2. APK de release para instalar no telemóvel. Desinstala primeiro a versão de debug: a chave é outra e o Android recusa a atualização. 
    flutter build apk --release
adb uninstall pt.uac.tempoacores
adb install build/app/outputs/flutter-apk/app-release.apk
  3. Verifica quem assinou. O keytool lê o certificado de dentro do APK. Compara o SHA-256 com o do teu keystore. 
    keytool -printcert -jarfile build/app/outputs/flutter-apk/app-release.apk
keytool -list -v -keystore ~/tempo-acores-upload.jks -alias upload

5. Flavors dev e prod no Android

android {
    // ...
    flavorDimensions += "ambiente"
    productFlavors {
        create("dev") {
            dimension = "ambiente"
            applicationIdSuffix = ".dev"          // pt.uac.tempoacores.dev
            versionNameSuffix = "-dev"
            resValue("string", "app_name", "Tempo Açores DEV")
        }
        create("prod") {
            dimension = "ambiente"
            resValue("string", "app_name", "Tempo Açores")
        }
    }
}
  • No AndroidManifest.xml, android:label="@string/app_name" passa a usar o valor do flavor.
  • Ícone diferente: copia android/app/src/main/res/mipmap-* para android/app/src/dev/res/mipmap-* e troca as imagens. O source set do flavor sobrepõe-se ao main.
  • Corre com flutter run --flavor dev. As duas apps ficam instaladas ao mesmo tempo, com nomes e ícones diferentes.

7. iOS, para quem tem Mac

  1. Abre o projeto no Xcode com open ios/Runner.xcworkspace. Nunca o .xcodeproj: o workspace é o que tem os pods.
  2. Runner → Signing & Capabilities. Marca Automatically manage signing e escolhe a tua equipa. Sem conta paga aparece "Personal Team" com o teu Apple ID.
  3. Bundle identifier único: pt.uac.pdm.tempoacores.grupoN. O Xcode cria o App ID e o perfil sozinho.
  4. Liga o iPhone e corre flutter run. No telemóvel, Definições → Geral → VPN e gestão de dispositivos → confiar no programador.
  5. Limites da conta gratuita: o perfil expira em 7 dias, máximo 3 apps, sem push e sem TestFlight. flutter build ipa só com conta paga.
Exercício 7 Quem tem Mac e iPhone: app a correr no iPhone com automatic signing. Quem tem Mac sem iPhone: flutter run no simulador não precisa de assinatura, mas faz na mesma os passos 1 a 3 para veres o que o Xcode gera.
