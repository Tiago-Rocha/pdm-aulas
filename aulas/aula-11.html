Qualidade: lints, organização e git flow

Teoria: qualidade de código: lints, organização por funcionalidade, extração de widgets e revisão de código; fluxo de git para equipas com branch por tarefa, pull request pequeno e revisão por um colega. Prática: refactor guiado do mini-projeto e resolução de um conflito de merge.

Repositório: pdm-aula-11
Pergunta quem já tem o mini-projeto a compilar e quem já fez push. Pede a dois alunos que mostrem a app: 1 minuto cada, sem comentários de código ainda. Depois pergunta: "se eu te pedisse para acrescentar um separador Avisos, em quantos ficheiros mexias?" A resposta é o ponto de partida da aula.

No fim desta aula consegues

  • Configurar analysis_options.yaml com lints estritos e explicar porque cada aviso importante existe.
  • Organizar um projeto Flutter por funcionalidade e dizer o que ganha face à organização por camada.
  • Extrair widgets reutilizáveis com parâmetros nomeados e construtores const.
  • Rever o código de um colega com comentários úteis sobre nomes, erros, dispose e null safety.
  • Trabalhar com branch por tarefa, pull requests, commits convencionais, e resolver um conflito de merge.

Lints: o compilador que te conhece

  • O analisador do Dart apanha erros de tipo. Os lints vão mais longe: apanham código que compila mas está errado, é lento ou vai dar problemas. São regras, e escolhes quais.
  • flutter_lints vem com o flutter create: as regras recomendadas pela equipa do Flutter. Poucas, consensuais, sem falsos positivos.
  • very_good_analysis (Very Good Ventures) é o conjunto estrito usado na indústria: 200 e tal regras, incluindo estilo, documentação e trailing commas. Mais ruído no início, menos discussões em revisão de código.
  • A configuração vive em analysis_options.yaml na raiz. O VS Code mostra os avisos ao escrever; flutter analyze mostra-os todos; o CI (aula 25) recusa PRs com avisos.
  • Zero avisos é a definição de pronto no projeto. Não porque cada aviso é grave, mas porque um projeto com 200 avisos esconde os 3 que interessam.

Para os testes: lints são regras de análise estática configuradas em analysis_options.yaml; flutter_lints é o conjunto base, very_good_analysis o estrito.

Abre o mini-projeto da solução com very_good_analysis ligado e mostra a lista de avisos: são dezenas. Pergunta quais é que os alunos acham que importam. Depois mostra o mesmo com flutter_lints: quase nenhum. A diferença é a conversa deste slide e do seguinte.

analysis_options.yaml

include: package:flutter_lints/flutter.yaml   # ou package:very_good_analysis/analysis_options.yaml

analyzer:
  language:
    strict-casts: true          # nada de dynamic a passar por String sem cast explícito
    strict-inference: true
    strict-raw-types: true      # List sem <T> é aviso
  errors:
    unused_import: error        # sobe de aviso para erro
    use_build_context_synchronously: error
  exclude:
    - "**/*.g.dart"             # código gerado não se analisa

linter:
  rules:
    prefer_const_constructors: true
    prefer_final_locals: true
    avoid_print: true
    require_trailing_commas: true
    always_declare_return_types: true
    avoid_dynamic_calls: true

include herda um conjunto; analyzer.errors muda a gravidade; linter.rules liga ou desliga regras uma a uma. A lista completa está em dart.dev/tools/linter-rules.

Avisos que interessam, e porquê

RegraPorque existe
prefer_const_constructorsUm widget const é criado uma vez e reutilizado em todos os rebuilds. Menos trabalho por frame; menos jank.
use_build_context_synchronouslyUsar o context depois de um await pode apontar para um widget que já não existe. Crash intermitente, difícil de reproduzir.
avoid_printprint fica no binário de release e vai para os logs do sistema. Usa debugPrint ou um logger que se desliga em produção.
strict-casts e avoid_dynamic_callsJSON é dynamic; sem casts explícitos o erro aparece em runtime no telemóvel do utilizador, não na compilação.
unused_import, unused_local_variable, dead_codeRuído que esconde bugs e confunde quem lê. Se não é usado, apaga-se.

Para os testes: use_build_context_synchronously existe porque o widget pode ter sido destruído durante o await; const evita reconstruções.

Organização: por camada ou por funcionalidade

Por camada

lib/
  models/      previsao.dart, localidade.dart, aviso.dart
  services/    previsoes_locais.dart, api_client.dart
  ui/          ecra_lista.dart, ecra_detalhe.dart,
               ecra_avisos.dart, ecra_definicoes.dart
  widgets/     previsao_card.dart, dia_chip.dart

Simples de começar. Com 30 ecrãs, cada funcionalidade está espalhada por quatro pastas e uma alteração toca em todas.

Por funcionalidade

lib/
  app/           app.dart, router.dart, tema.dart
  previsao/      modelos/, dados/, ui/
  avisos/        modelos/, dados/, ui/
  definicoes/    ui/
  partilhado/    widgets/, extensoes/, l10n/

Cada pasta é uma funcionalidade completa, com as suas camadas dentro. Uma equipa por pasta; apagar uma funcionalidade é apagar uma pasta.

Para os testes: por camada agrupa pelo tipo de código; por funcionalidade agrupa pelo que a app faz. O projeto usa por funcionalidade com camadas dentro de cada uma, que é o que o guia de arquitetura do Flutter recomenda.

Widgets reutilizáveis

  • Extrai quando repete ou quando um build passa de 50 linhas. Um build de 300 linhas não se lê, não se testa e reconstrói tudo de cada vez.
  • Classe, não método. Widget _cartao() dentro do State parece mais curto, mas não pode ser const, reconstrói sempre, e não aparece no inspector. class PrevisaoCard extends StatelessWidget resolve os três.
  • Parâmetros nomeados e required: PrevisaoCard(previsao: p, onTap: abrir) lê-se sem abrir a classe. Dados de entrada como campos final; ações como callbacks VoidCallback ou ValueChanged<T>.
  • Construtor const sempre que os campos são finais. O lint prefer_const_constructors avisa-te onde podes usá-lo.
  • Ficheiros pequenos: um widget público por ficheiro, nome do ficheiro em snake_case igual ao da classe. previsao_card.dart tem PrevisaoCard.
  • O widget não sabe de onde vêm os dados nem para onde vai a navegação. Recebe valores e devolve eventos. É o que o torna reutilizável e testável.

Para os testes: extrai widgets para classes, não para métodos: permitem const, evitam rebuilds e aparecem no inspector.

Code review: o que procurar

ProcuraExemplo de comentário
Nomes que dizem o que a coisa é"lista2 → localidadesFiltradas? Assim quem lê não precisa de abrir o where."
Estados de erro e vazio tratados"Se o JSON falhar, o FutureBuilder fica em branco. Um Text com a mensagem e um botão de repetir?"
dispose para cada controller, timer e subscrição"O _controlador criado no initState não é libertado. Fuga de memória a cada abertura do ecrã."
Null checks com ! e casts a esconder problemas"Este json['tMax']! falha quando o campo faltar. ?? 0 ou uma FormatException com o nome do campo?"
Widgets grandes e código repetido"Este build tem 140 linhas e o cartão aparece três vezes. Extrair PrevisaoCard?"
Projeta um ficheiro de 150 linhas do starter e faz a revisão ao vivo com a turma: eles apontam, tu escreves o comentário. 5 minutos. Reparem que cada comentário termina com uma pergunta ou uma sugestão concreta, nunca com "isto está mal".

Code review: como comentar

  • Comenta o código, não a pessoa. "Este método faz duas coisas" em vez de "fizeste isto mal".
  • Pergunta antes de afirmar. "Há razão para o Future ser criado no build?" Às vezes há, e aprendes; às vezes não, e o autor corrige sem se sentir atacado.
  • Sugere, com código quando ajuda. O GitHub tem "suggestion" blocks que o autor aceita com um clique.
  • Distingue o que bloqueia do que é gosto. "bloqueante: crash sem rede" vs "nit: prefiro final aqui". Um PR não fica parado por causa de vírgulas.
  • Elogia o que está bem. Uma revisão só com problemas ensina menos do que uma que diz "esta extração ficou limpa, faz o mesmo no detalhe".
  • Rever é ler com atenção, não correr. Se não percebes um bloco, o comentário é "não percebi isto; consegues explicar ou simplificar?". Provavelmente mais ninguém percebe.

Para os testes: uma boa revisão distingue bloqueante de opcional, comenta o código e não o autor, e termina com uma sugestão concreta.

Git para equipas (1 de 2): branches e pull requests

  • main protegido. Ninguém faz push direto. Tudo entra por pull request revisto. No GitHub: Settings → Branches → "Require a pull request before merging". No projeto de grupo é obrigatório.
  • Um branch por tarefa, curto, com nome que diz o que é: feat/detalhe-aviso, fix/overflow-landscape, chore/lints. Nasce de main e morre depois do merge.
  • PR pequeno. Menos de 300 linhas, uma coisa só. Um PR de 2000 linhas não é revisto; é aprovado sem ler. Divide antes de abrir.
  • Descrição: o quê, porquê, como testar, captura de ecrã se for UI. O título vira a mensagem do commit de merge.
  • Revisão de um colega antes de entrar. Quem escreveu não aprova o próprio PR. O CI (aula 25) corre analyze e test e bloqueia se falhar.

Para os testes: branch por tarefa a partir de main, PR pequeno revisto por outra pessoa, main protegido sem push direto.

Analogia Um commit é uma fotografia de todo o projeto com legenda e data; não se apaga nenhuma e pode-se voltar a qualquer uma. Um branch é um caderno à parte onde se experimenta sem estragar o caderno principal. O pull request é pedir a um colega que leia o caderno antes de o conteúdo ser copiado para o principal.

Git para equipas (2 de 2): commits, rebase e conflitos

  • Conventional commits: tipo(âmbito): descrição no imperativo, até 72 caracteres. Tipos: feat, fix, refactor, docs, test, chore. Exemplo: feat(avisos): detalhe de aviso com localidades afetadas. Permite gerar changelogs e perceber o histórico sem abrir diffs.
  • Merge junta dois históricos com um commit de merge: preserva tudo, mas o grafo fica com laços. Rebase reescreve os teus commits por cima do main atual: histórico linear, mas nunca em commits que já foram partilhados.
  • Regra do projeto: git pull --rebase no teu branch para atualizar; "Squash and merge" no GitHub para entrar em main. Um commit limpo por PR.
  • Conflitos acontecem quando dois branches mudam as mesmas linhas. Não são um erro: são o git a pedir-te para decidir. Abres o ficheiro, escolhes, apagas as marcas, git add, continuas.
  • Conflitos grandes são sintoma de PRs grandes ou de dois membros a mexer no mesmo ficheiro. Divide o trabalho por funcionalidade (pasta) e desaparecem quase todos.

Para os testes: rebase reescreve o histórico e não se faz em commits partilhados; um conflito resolve-se editando o ficheiro, apagando as marcas e fazendo git add.

1. Ligar lints estritos e corrigir

flutter pub add --dev very_good_analysis
flutter analyze
dart fix --dry-run          # o que o dart consegue corrigir sozinho
dart fix --apply
flutter analyze
include: package:very_good_analysis/analysis_options.yaml

linter:
  rules:
    public_member_api_docs: false     # documentar tudo é demais para uma app; fica para packages

  • dart fix corrige o mecânico: const em falta, imports não usados, trailing commas. O resto corrige-se manualmente, um aviso de cada vez.
  • Desligar uma regra é legítimo quando tens uma razão e a escreves ao lado. Desligar uma regra porque dá muitos avisos não é razão.

2. Extrair widgets

class PrevisaoCard extends StatelessWidget {
  const PrevisaoCard({
    required this.previsao,
    this.selecionado = false,
    this.onTap,
    super.key,
  });

  final Previsao previsao;
  final bool selecionado;
  final VoidCallback? onTap;                     // ação: quem usa decide o que faz

  @override
  Widget build(BuildContext context) {
    final cores = Theme.of(context).colorScheme;
    return Card(
      color: selecionado ? cores.primaryContainer : null,
      child: InkWell(
        onTap: onTap,
        child: Padding(
          padding: const EdgeInsets.all(12),
          child: Text('${previsao.dia.day}: ${previsao.tMin.round()}° a ${previsao.tMax.round()}°'),
        ),
      ),
    );
  }
}

2. Extrair: o que interessa

  • O VS Code faz a extração: seleciona o widget, Ctrl+. → "Extract Widget", dá o nome. Depois moves o resultado para o ficheiro certo e trocas os campos capturados por parâmetros.
  • Ordem dos parâmetros: os required primeiro, os opcionais depois, super.key no fim. É a convenção do very_good_analysis.
  • O widget não importa go_router nem dados.dart. Recebe uma Previsao e um onTap. Quem o usa decide para onde navegar.
  • Depois de extrair, o build do ecrã fica com 30 linhas que se leem como um índice: cabeçalho, fila de dias, cartão do dia. É o objetivo.

3. Branch, pull request e revisão

cd ~/pdm-miniprojeto                       # o teu repositório, não o starter
git switch -c chore/lints-e-estrutura
flutter pub add --dev very_good_analysis   # repete os passos 1 e 2 no teu projeto
git add -A
git commit -m "chore: liga very_good_analysis e organiza por funcionalidade"
git push -u origin chore/lints-e-estrutura
gh pr create --fill --base main            # ou o botão "Compare & pull request" no GitHub
  1. No GitHub, Settings → Branches → adiciona uma regra para main com "Require a pull request before merging" e "Require approvals: 1".
  2. Adiciona um colega como colaborador do teu repositório e pede-lhe revisão no PR. Ele faz o mesmo contigo.
  3. Revê o PR do colega: pelo menos dois comentários com a tabela do slide 8, um bloqueante e um "nit". Aprova só depois de ele responder.
  4. Faz "Squash and merge" do teu PR quando estiver aprovado. Apaga o branch.
Exercício 3 PR aberto, revisto por um colega com dois comentários, respondido, aprovado e merged. O main do teu mini-projeto fica com os lints ligados e a estrutura nova.
Faz pares na hora: quem está ao lado. Dá 25 minutos. A confusão típica é o colaborador não conseguir comentar porque o repositório é privado e ainda não aceitou o convite; verifica o e-mail. Mostra um PR bem descrito de um projeto real como exemplo.

4. Simular e resolver um conflito

git switch main && git pull
git switch -c feat/titulo-pt     # muda o título em lib/app/app.dart para 'Tempo Açores' e commita
git switch main
git switch -c feat/titulo-en     # muda a MESMA linha para 'Azores Weather' e commita
git switch main && git merge feat/titulo-pt      # entra sem conflito
git merge feat/titulo-en                            # CONFLICT (content): lib/app/app.dart
      title: 'Tempo Açores',
<<<<<<< HEAD
      // versão que está em main
=======
      title: 'Azores Weather',
>>>>>>> feat/titulo-en
  1. Abre o ficheiro. O VS Code mostra "Accept Current", "Accept Incoming", "Accept Both". Decide: aqui, o título vem do .arb, por isso nenhuma das duas está certa.
  2. Escreve a versão final, apaga as três marcas, guarda. flutter analyze para confirmar que compila.
  3. git add lib/app/app.dart e git commit. Se estivesses num rebase: git rebase --continue.
Exercício 4 Provoca e resolve o conflito acima no teu repositório. Depois apaga os dois branches. Se ficares perdido a meio: git merge --abort volta ao estado anterior, sempre.
Deixa-os provocar o conflito sozinhos; é o momento em que percebem que não é grave. Circula e mostra o git merge --abort a quem entrar em pânico. Dá 15 minutos. Se sobrar tempo, mostra o mesmo com rebase e o --force-with-lease no push.

5. dart format e format-on-save

dart format lib test                 # formata tudo; sem argumentos, o projeto inteiro
dart format --set-exit-if-changed .  # no CI: falha se algo não estiver formatado
{
  "editor.formatOnSave": true,
  "[dart]": {
    "editor.formatOnSave": true,
    "editor.rulers": [80],
    "editor.codeActionsOnSave": { "source.fixAll": "explicit" }
  },
  "dart.lineLength": 80
}
  • O formatador do Dart não tem opções de estilo. Acabam as discussões sobre chavetas e indentação: todos têm o mesmo código.
  • A trailing comma decide o formato: com vírgula no fim, um argumento por linha; sem ela, tudo numa linha. É por isso que require_trailing_commas está ligado.
  • Commita o .vscode/settings.json: a equipa inteira fica com a mesma configuração.
Exercício 5 Liga format-on-save, corre dart format . no mini-projeto e commita o resultado num PR próprio, chore: formata com dart format. É um PR pequeno e simples de rever.
