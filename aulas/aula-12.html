Teoria: camada de rede: HTTP, JSON, códigos de estado, timeouts, retries e interceptors; catálogo de APIs e OpenAPI. Prática: ligação da app à API do curso e apresentação das localidades dos Açores obtidas do servidor.

Antes de começar, abre o Swagger da API no projetor e confirma que responde. Pergunta quem já usou fetch ou axios na web: quase todos. HTTP em 10 minutos (1 de 2): métodos e idempotência

  • Um pedido é método + URL + headers + corpo (opcional). A resposta é código + headers + corpo.
  • GET lê e nunca altera. POST cria ou executa. PUT substitui. PATCH altera parte. DELETE apaga.
  • Idempotente: repetir o pedido dá o mesmo resultado. GET, PUT e DELETE são; POST não é.
  • Por isso um GET que falhou pode ser repetido às cegas. Um POST repetido pode criar dois favoritos, ou cobrar duas vezes.
  • Exemplo real: a app do IPMA faz GET à previsão; um pagamento MB WAY é um POST que a app nunca repete sozinha.

Para os testes: a idempotência decide o que a app pode repetir automaticamente quando a rede falha.

Analogia Um restaurante. O menu é a documentação da API (o contrato OpenAPI); o pedido é o request, com método, URL e headers; a cozinha é o servidor. O prato chega numa caixa etiquetada (a resposta JSON, Content-Type: application/json) com um código na tampa: 200 está tudo bem, 404 não há, 500 a cozinha avariou, 429 pedidos a mais. A app não come da caixa: tira o conteúdo para o prato, que é o modelo Dart.
Pergunta: "se o pedido de pagamento deu timeout, o dinheiro saiu ou não?" A resposta é "não sabes", e é isso que torna o POST perigoso de repetir. Voltamos a isto na aula 14 com as chaves de idempotência.

HTTP em 10 minutos (2 de 2): códigos, headers, JSON

CódigoSignificaO que a app faz
2xx (200, 201, 204)Correu bem; 204 não traz corpoUsa os dados
400, 404, 422O pedido está errado ou o recurso não existeBug nosso ou estado vazio; não repetir
401, 403Sem token válido / sem permissãoRenovar token ou fazer login; 403 não adianta repetir
429Demasiados pedidosEsperar o Retry-After e repetir
5xxErro do servidorRepetir com backoff, mostrar dados antigos
  • Headers do dia a dia: Content-Type: application/json, Accept, Authorization, Cache-Control, ETag.
  • O corpo é JSON em UTF-8: objetos, listas, números, strings, booleanos e null. Tudo o que vem de fora pode faltar.

Para os testes: 4xx é culpa do pedido, 5xx é culpa do servidor, 429 não é culpa de ninguém: é um limite.

Catálogo de APIs e OpenAPI

  • Contrato: um ficheiro openapi.yaml descreve rotas, parâmetros, esquemas de dados e códigos de resposta. É a fonte de verdade.
  • Swagger UI: página gerada a partir do contrato onde experimentas cada rota sem escrever código. A API do curso tem uma em /docs.
  • Geração de clientes: openapi-generator produz o código Dart a partir do contrato. Nós escrevemos à mão para perceber o que está lá dentro.
  • Versionamento no URL: /v1. Quando algo muda de forma incompatível nasce /v2 e /v1 vive mais uns meses. Vais migrar na aula 28.
  • Catálogo: uma empresa tem dezenas de APIs (Apigee, Postman, Backstage). Como cliente, lês o contrato antes de escrever a primeira linha.

Para os testes: código de cliente que não bate certo com o contrato OpenAPI é um bug do cliente.

Mostra o Swagger da API do curso ao vivo: expande GET /v1/locations, carrega em "Try it out", mostra a resposta. Dois minutos que poupam muitas perguntas na prática.

Timeouts, retries e cancelamento

  • Na web, um pedido pendurado é uma tab que gira. Em mobile é uma app "morta" e uma avaliação de uma estrela.
  • Timeout: sem ele um pedido pode esperar minutos. Valores típicos: 10 s para ligar, 15 a 30 s no total.
  • Retry com backoff: 1 s, 2 s, 4 s, com aleatoriedade. Só para falhas transitórias (timeout, 5xx, 429) e só em pedidos idempotentes. Detalhe na aula 14.
  • Cancelamento: o utilizador saiu do ecrã; a resposta chega para um widget que já não existe. É a origem do erro setState() called after dispose().
  • Porquê mais em mobile: a rede muda (Wi-Fi para 4G a meio), túneis, ecrã bloqueado, o sistema suspende a app com o pedido a meio.

Para os testes: timeout limita a espera, retry repete falhas transitórias, cancelamento evita trabalho para ecrãs que já não existem.

Interceptors e cliente HTTP único

  • Um interceptor vê todos os pedidos e respostas num só sítio: acrescenta headers, regista logs, renova o token, mede tempos.
  • Headers comuns: Authorization: Bearer …, X-Platform (android/ios), X-App-Version. Permitem ao backend saber que versão está a falhar e onde.
  • Um só cliente na app: reutiliza ligações (keep-alive), tem a configuração num sítio e troca-se por um fake nos testes.
  • Com http: uma subclasse de BaseClient que sobrepõe send. Com dio: InterceptorsWrapper com onRequest, onResponse, onError.
  • Logging só em debug. Um token impresso na consola de release acaba num crash report.

Para os testes: o interceptor é o ponto único de passagem; é onde vivem autenticação, logs e retries.

A API do curso

Base URL https://api.pdm.example (URL real na página API). Swagger em /docs. Envolve os dados abertos do IPMA e acrescenta autenticação, favoritos e telemetria.

EndpointDevolve
POST /v1/auth/tokenJWT a partir de client_id e secret do grupo
GET /v1/locationsLocalidades dos Açores com id, nome, ilha e coordenadas
GET /v1/forecast/{locationId}Previsão a 5 dias de uma localidade
GET /v1/warnings · GET /v1/seismicAvisos meteorológicos · sismos recentes
GET/POST/DELETE /v1/me/favoritesFavoritos do grupo autenticado (aula 17)
Transparência Cada pedido leva Authorization: Bearer, X-Platform e X-App-Version. O backend conta pedidos por grupo para dar feedback, não para avaliar por volume. O docente pode ligar um modo caos por grupo (latência, 429, 500): é assim que treinamos resiliência na aula 14.
Deixa claro que o modo caos é anunciado e não é partida: os grupos sabem quando está ligado. Hoje usam-se o client-id e o segredo da turma; os de grupo chegam na aula 15.

Do JSON ao objeto Dart

A resposta chega como texto: uma String com JSON no corpo e Content-Type: application/json no header. Até ser um objeto que a app pode usar passa sempre pelos mesmos dois passos: descodificar e tipar.

// O corpo de GET /v1/forecast/3 é texto. Uma previsão, resumida:
// {
//   "locationId": 3,
//   "atualizadoEm": "2026-10-12T15:00:00Z",
//   "dias": [ { "data": "2026-10-12", "tMin": 17.2, "tMax": 22.8, "tipo": "chuva" } ]
// }
final corpo = utf8.decode(resposta.bodyBytes);        // String
final previsao = Previsao.fromJson(                   // Previsao, tipada
  jsonDecode(corpo) as Map<String, dynamic>,          // Map, sem tipos verificados
);
previsao.dias.first.tMin;                             // double, não dynamic
Analogia JSON é texto com etiquetas, como um formulário preenchido à mão. jsonDecode transforma o texto num dicionário (Map<String, dynamic>): já se consegue ler por chave, mas nada é verificado. Previsao.fromJson passa o formulário a limpo para uma ficha tipada: cada campo no sítio certo, com o tipo certo, e um erro claro se faltar algo. A partir daí o resto da app trabalha com fichas, nunca com texto.

1. Um pedido com o package http

import 'dart:convert';
import 'package:http/http.dart' as http;

const baseUrl = 'https://api.pdm.example'; // URL real na página API

Future<List<Localidade>> obterLocalidades() async {
  final uri = Uri.parse('$baseUrl/v1/locations');
  final resposta = await http.get(uri).timeout(const Duration(seconds: 10));

  if (resposta.statusCode != 200) {
    throw ApiException('GET /v1/locations devolveu ${resposta.statusCode}',
        statusCode: resposta.statusCode);
  }

  final json = jsonDecode(utf8.decode(resposta.bodyBytes)) as List<dynamic>;
  return json
      .map((e) => Localidade.fromJson(e as Map<String, dynamic>))
      .toList();
}

1. Um pedido: o que interessa

  • http.get devolve um Future<Response>. Só com await tens o statusCode e o body.
  • .timeout(…) lança TimeoutException se a resposta não chegar. Sem isto, um túnel deixa a app à espera para sempre.
  • jsonDecode devolve dynamic: uma List ou um Map<String, dynamic>. O as confirma o que esperas e falha cedo se não for.
  • utf8.decode(bodyBytes) em vez de body evita acentos estragados quando o servidor não declara o charset.
  • Verifica sempre o código de estado antes de tocar no corpo. Um 500 também tem corpo, e não é o que esperas.

2. Modelos a partir de JSON, com validação

class Localidade {
  final int id;
  final String nome;
  final String ilha;

  const Localidade({required this.id, required this.nome, required this.ilha});

  factory Localidade.fromJson(Map<String, dynamic> json) {
    final id = json['id'];
    final nome = json['nome'];
    if (id is! int || nome is! String) {
      throw const FormatException('Localidade sem id ou nome');
    }
    return Localidade(id: id, nome: nome, ilha: json['ilha'] as String? ?? 'desconhecida');
  }

  Map<String, dynamic> toJson() => {'id': id, 'nome': nome, 'ilha': ilha};
}

class ApiException implements Exception {
  const ApiException(this.mensagem, {this.statusCode});
  final String mensagem;
  final int? statusCode;
  @override
  String toString() => 'ApiException($statusCode): $mensagem';
}

2. Modelos: o que interessa

  • fromJson é um factory: valida e constrói. Se o JSON está mal, lança FormatException com uma mensagem que diz o que faltou.
  • is! promove o tipo: depois do if, o compilador sabe que id é int. Sem !, sem as às cegas.
  • Campos opcionais com valor por defeito (?? 'desconhecida'); campos obrigatórios falham cedo. Decide caso a caso.
  • A exceção própria (ApiException) leva o statusCode: na aula 14 a UI escolhe a mensagem por código.
  • Regra: a app nunca deve falhar porque o servidor mandou um campo a mais ou a menos. Testa com JSON estragado.

3. FutureBuilder: o primeiro ecrã ligado à API

class _LocalidadesScreenState extends State<LocalidadesScreen> {
  late final Future<List<Localidade>> _futuro = obterLocalidades();

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<Localidade>>(
      future: _futuro,
      builder: (context, snapshot) {
        if (snapshot.connectionState != ConnectionState.done) {
          return const Center(child: CircularProgressIndicator());
        }
        if (snapshot.hasError) {
          return Center(child: Text('Não foi possível carregar: ${snapshot.error}'));
        }
        final lista = snapshot.data ?? const <Localidade>[];
        return ListView.builder(
          itemCount: lista.length,
          itemBuilder: (_, i) => ListTile(
            title: Text(lista[i].nome),
            subtitle: Text(lista[i].ilha),
          ),
        );
      },
    );
  }
}

3. FutureBuilder: o que interessa

  • connectionState é waiting enquanto o Future corre e done quando termina, com hasData ou hasError.
  • O Future cria-se uma vez, num campo do State. Se o criares dentro de build, cada rebuild faz um pedido novo à API.
  • snapshot.data é nullable. ?? const [] em vez de !.
  • Mostrar snapshot.error cru serve para aprender; em produção a mensagem é escolhida pela app (aula 14).
  • FutureBuilder chega para um ecrã isolado. Segunda movemos isto para um notifier, para partilhar entre ecrãs e testar sem rede.

4. ApiClient: base URL, headers e timeout num só sítio

class ApiClient {
  ApiClient({required this.baseUrl, http.Client? client, this.token})
      : _client = client ?? http.Client();

  final String baseUrl;
  final http.Client _client;
  String? token;

  Map<String, String> get _headers => {
        'Accept': 'application/json',
        'X-Platform': defaultTargetPlatform.name,
        'X-App-Version': '1.0.0',
        if (token != null) 'Authorization': 'Bearer $token',
      };

  Future<dynamic> get(String caminho) async {
    final resposta = await _client
        .get(Uri.parse('$baseUrl$caminho'), headers: _headers)
        .timeout(const Duration(seconds: 10));
    if (resposta.statusCode >= 400) {
      throw ApiException('GET $caminho falhou', statusCode: resposta.statusCode);
    }
    return jsonDecode(utf8.decode(resposta.bodyBytes));
  }
}

4. ApiClient: o que interessa

  • Uma instância para toda a app, criada no main e passada por construtor a quem precisa. Segunda o Provider trata da distribuição.
  • O http.Client é injetável: nos testes passas um MockClient do package http/testing e não há rede.
  • defaultTargetPlatform.name (de package:flutter/foundation.dart) dá android ou iOS. A versão vem do package_info_plus no projeto.
  • Os erros 4xx e 5xx viram ApiException com statusCode. TimeoutException e SocketException (sem rede) passam como estão. Tratamos os três na aula 14.
  • O token é mutável de propósito: hoje é atribuído no arranque; na aula 17 passa a ser renovado por um interceptor.

// Em ApiClient
Future<Map<String, dynamic>> post(String caminho, {Object? body}) async {
  final resposta = await _client
      .post(Uri.parse('$baseUrl$caminho'),
          headers: {..._headers, 'Content-Type': 'application/json'},
          body: jsonEncode(body))
      .timeout(const Duration(seconds: 10));
  if (resposta.statusCode >= 400) {
    throw ApiException('POST $caminho falhou', statusCode: resposta.statusCode);
  }
  return jsonDecode(utf8.decode(resposta.bodyBytes)) as Map<String, dynamic>;
}

5. Token e previsão: o que interessa

  • POST /v1/auth/token recebe JSON com client_id e secret e devolve access_token: um JWT que expira. Vemos o que tem dentro na aula 17.
  • O segredo entra pela linha de comandos com --dart-define e String.fromEnvironment. Nunca no código, nunca no git. Porquê, na aula 18.
  • Com o token no ApiClient, todos os pedidos seguintes levam Authorization: Bearer sem mais código.
  • Um 401 significa token em falta ou expirado. Hoje resolve-se reiniciando a app; na aula 17 fica automático.
  • Spread {..._headers, 'Content-Type': …}: um mapa novo com os headers comuns mais um. Idiomático em Dart.
