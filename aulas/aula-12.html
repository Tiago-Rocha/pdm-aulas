Futures, HTTP e JSON

Como uma app vai buscar dados a um servidor sem congelar: Future e async/await, pedidos HTTP, JSON convertido em objetos Dart e o FutureBuilder. Pelo meio, lemos juntos a documentação Swagger da API do curso e experimentamos pedidos no browser.

Aula de teoria, sem prática dos alunos nem trabalho para casa. Tempos de referência: Future e HTTP até às 16:30; API do curso e Swagger até às 16:45; prática no Swagger (parte 1, o token, até às 16:55; parte 2, caça ao erro e correção, até às 17:25); JSON, parsing, FutureBuilder e Streams até ao fim. Hoje os alunos não escrevem código: usam a API no browser ou no Postman. A entrega do mini-projeto Trilhos fechou às 16:00, no início desta aula.

No fim desta aula consegues

  • Explicar o que é um Future e porque um pedido à rede nunca pode bloquear a app.
  • Ler um pedido e uma resposta HTTP: método, URL, headers, corpo e código de estado.
  • Ler a documentação Swagger de uma API: operações, parâmetros, respostas, schemas e erros.
  • Converter JSON em objetos Dart com fromJson e saber onde o parsing costuma partir.
  • Mostrar dados da rede com FutureBuilder: a carregar, erro e dados.
  • Distinguir um Future (um valor) de uma Stream (muitos valores ao longo do tempo).

Um valor que ainda não chegou

  • Um pedido à rede demora 50 ms no Wi-Fi da escola e 5 s num túnel. A app não pode ficar parada à espera.
  • O Dart corre a tua app numa só linha de execução, que também desenha o ecrã. Se ela esperar, o ecrã congela: nem scroll, nem animações, nem toques.
  • Por isso http.get não devolve a resposta: devolve um Future<Response>, uma promessa de que a resposta vem mais tarde.
  • Um Future está num de três estados: por completar, completo com um valor ou completo com um erro.
print('1. antes do pedido');
final future = http.get(url); // o pedido parte, a app continua
print('2. o pedido já partiu');
final response = await future; // aqui a função para até chegar a resposta
print('3. chegou: ${response.statusCode}');
Pergunta à turma Enquanto esta função está parada no await, o utilizador consegue fazer scroll na app?
Respostas às perguntas. Sim. O await suspende esta função, não a app: a linha de execução volta ao event loop e continua a desenhar frames e a tratar toques. Quando a resposta chega, a função retoma na linha seguinte. É igual ao async/await do JavaScript, que muitos já usaram com fetch: um Future é uma Promise.

async e await

Future<List<Island>> fetchIslands(String token) async {
  final response = await http.get(
    Uri.parse('$baseUrl/v1/islands'),
    headers: {'Authorization': 'Bearer $token'},
  );
  final list = jsonDecode(response.body) as List<dynamic>;
  return list
      .map((item) => Island.fromJson(item as Map<String, dynamic>))
      .toList();
}
  • async marca a função: ela devolve sempre um Future, mesmo que o return devolva uma lista.
  • await só se usa dentro de uma função async. Lê-se de cima para baixo como código normal.
  • Um erro dentro da função (sem rede, JSON errado) completa o Future com erro. Apanha-se com try/catch à volta do await.
  • Esquecer o await é o erro mais comum: ficas com um Future na mão em vez da resposta.
Mostra o erro de esquecer o await: final response = http.get(...) e depois response.body não compila, porque Future não tem body. O compilador apanha a maior parte destes casos; o caso perigoso é uma função que devolve Future<void> chamada sem await, que corre "em paralelo" sem ninguém ver o erro. A lint unawaited_futures avisa.

HTTP em 10 minutos (1 de 2): pedido e resposta

  • GET lê e nunca altera. POST cria. PUT substitui. DELETE apaga.
  • Idempotente: repetir o pedido dá o mesmo resultado. GET, PUT e DELETE são; POST não é. Um GET que falhou pode repetir-se; um POST repetido pode criar dois relatos, ou cobrar duas vezes.

Para os testes: a idempotência decide o que a app pode repetir sozinha quando a rede falha.

Abre as ferramentas do Chrome (separador Network) numa página qualquer e mostra um pedido a sério: método, URL, headers, código e corpo. Os alunos de DAW já viram isto na web; em mobile é exatamente o mesmo protocolo. Pergunta: "se o pedido de pagamento deu timeout, o dinheiro saiu ou não?" A resposta é "não sabes", e é isso que torna o POST perigoso de repetir.

A seguir vêm três slides sobre o Swagger. Se preferires, faz tudo ao vivo no projetor em vez das capturas.

Ler o Swagger (1 de 4): o mapa da API

  • O Swagger é uma página gerada a partir do contrato OpenAPI (/openapi.json): um ficheiro que descreve cada rota, os parâmetros, os dados e os erros. É a fonte de verdade.
  • As operações vêm agrupadas por tema. Cada linha é um método e um caminho: GET /v1/islands.
  • O cadeado diz que a operação precisa de token. O botão Authorize guarda o token para todos os pedidos da página.
Abre https://api-pdm.sublimecipher.com/docs no projetor e percorre a página de cima a baixo: os quatro grupos (Autenticação, Ilhas e trilhos, Previsão, Relatos) e, no fim, a secção Schemas. Clica em /openapi.json para mostrarem que o Swagger é só uma forma bonita de ler esse ficheiro. Ferramentas como o openapi-generator geram o código do cliente a partir dele; nós escrevemos à mão para perceber o que lá está.

Ler o Swagger (2 de 4): uma operação

  • Parameters: o que tens de mandar. id é obrigatório (* required), é texto e vai no caminho (path): /v1/islands/sao-miguel/forecast. Outros vão na query: /v1/trails?islandId=faial.
  • Try it out e Execute fazem o pedido a sério. O Swagger mostra o curl, o URL, o código e o corpo da resposta. Se o curl não tiver a linha Authorization: Bearer, faltou o Authorize.
  • Responses: uma entrada por código possível (200, 401, 404, 502), cada uma com um exemplo. É a lista de casos que a tua app tem de tratar.
Ao vivo: Try it out em POST /v1/auth/token com a conta Docente (~/.config/pdm-api/docente.json; não mostres o segredo no ecrã), copia o accessToken, Authorize, e depois Execute em GET /v1/islands/pico/forecast. Mostra o curl gerado: é o mesmo pedido que o código Dart vai fazer, com o header Authorization. Atenção: o curl mostra o token no ecrã; dura uma hora e é só da conta Docente.

Ler o Swagger (3 de 4): o schema

  • Schema (ao lado de Example Value) é a forma exata da resposta. O * vermelho quer dizer que o campo vem sempre.
  • Os tipos dizem como ler cada campo em Dart: string, integer, number, objetos dentro de objetos ({ }) e listas ([Day]). Enum é a lista fechada de valores: dá um enum em Dart.
Liga ao modelo: este schema é, campo a campo, o DayForecast que vamos escrever daqui a pouco. Pergunta: "o tMin é integer ou number?" É number, por isso em Dart lê-se como num e passa a double (o slide "Onde o parsing parte" explica porquê). O category tem os mesmos cinco valores do enum WeatherType das aulas.

Ler o Swagger (4 de 4): os erros

  • Cada código que a operação pode devolver tem uma entrada: em /v1/islands/{id}/forecast são 200, 401, 404 e 502.
  • Os erros têm sempre a mesma forma: code para o programa decidir (not_found, unauthorized...), message para mostrar à pessoa.
  • A lista de códigos é a lista de casos que o ecrã tem de tratar. Se o Swagger diz que pode vir 502, a app tem de ter o que mostrar quando vier.
O 502 aparece quando o IPMA não responde e a API não tem previsão guardada: não é culpa da app nem do aluno, e a app deve dizer "tenta daqui a pouco". Os códigos possíveis da API estão todos na página API do site, na tabela de erros.

Parte 1: toda a gente com token

Faz
  1. Abre https://api-pdm.sublimecipher.com/docs. O teu clientId e o teu clientSecret estão na issue #1 do teu repositório pdm-miniprojeto.
  2. Abre POST /v1/auth/token, carrega em Try it out, cola os dois no pedido e carrega em Execute. Tem de dar 200 e um accessToken.
  3. Sobe ao topo da página, carrega no botão verde Authorize e cola só o token, sem a palavra "Bearer" nem aspas. Os cadeados fecham.
  4. Abre GET /v1/me, Try it out, Execute: tem de aparecer o teu nome. Quando aparecer, mão no ar.
Com o Postman O mesmo endereço; no separador Authorization escolhe Bearer Token e cola o token. Mais rápido: no Swagger, copia o curl que aparece depois do Execute e, no Postman, carrega em Import e cola-o.

Ninguém passa à parte 2 sem o nome no ecrã.

Dez minutos, e só se avança quando toda a gente tiver o nome no ecrã. Os problemas mais comuns: colar "Bearer eyJ..." no Authorize (o Swagger acrescenta o Bearer sozinho e fica "Bearer Bearer", que dá 401 "Token inválido."); trocar o clientId com o clientSecret (401 "clientId ou clientSecret errados."); copiar o token com aspas ou com espaços; esquecer o Authorize (401 "Falta o header Authorization..."). O token dura uma hora: chega para a aula. Quem não tiver a issue #1 no repositório não recebeu credenciais: usa GET /admin/students para confirmar.

Resposta à pergunta. O backend, porque é ele que não cumpre o contrato. Do JSON ao objeto Dart

A resposta chega como texto. Até ser um objeto que a app pode usar passa sempre pelos mesmos dois passos: descodificar e dar tipos.

Os dois passos são sempre os mesmos, seja qual for a API. O jsonDecode não sabe nada da previsão nem das ilhas; quem sabe é o fromJson, que escrevemos para cada modelo.

Uma ilha: do JSON ao Island

{
  "id": "sao-miguel",
  "name": "São Miguel",
  "imageUrl": "https://api-pdm.sublimecipher.com/static/islands/sao_miguel.jpg",
  "trailCount": 3
}
factory Island.fromJson(Map<String, dynamic> json) {
  return Island(
    id: json['id'] as String,
    name: json['name'] as String,
    imageUrl: json['imageUrl'] as String,
  );
}
O trailCount vem no JSON e o modelo ignora-o: o fromJson lê só o que a app usa. Se a API acrescentar campos, a app não parte; se tirar ou mudar um que a app lê, parte. Pergunta frequente: "porque não uso json_serializable ou freezed?" Podes, no projeto: geram este código. Hoje escrevemos à mão para perceber o que o gerador faz.

JSON com objetos dentro de objetos

{
  "date": "2026-10-14",
  "weatherType": {
    "id": 7,
    "description": "Aguaceiros/chuva fracos",
    "category": "rain"
  },
  "tMin": 20.0,
  "tMax": 24.2,
  "rainChance": 57,
  "wind": {
    "direction": "SW",
    "class": 2,
    "description": "Moderado"
  }
}
  • Um objeto dentro de outro é mais um Map; uma lista é uma List<dynamic> que se percorre com map.
  • O JSON não tem datas nem enums: vêm como texto, e o fromJson converte (DateTime.parse, values.byName).

Um dia: DayForecast.fromJson

factory DayForecast.fromJson(Map<String, dynamic> json) {
  final weather = json['weatherType'] as Map<String, dynamic>;
  final wind = json['wind'] as Map<String, dynamic>;
  return DayForecast(
    date: DateTime.parse(json['date'] as String),
    type: WeatherType.values.byName(weather['category'] as String),
    tMin: (json['tMin'] as num).toDouble(),
    tMax: (json['tMax'] as num).toDouble(),
    rainChance: json['rainChance'] as int,
    windClass: wind['class'] as int,
  );
}
  • O modelo da app não tem de ser igual ao JSON. O IPMA não dá o vento em km/h, só a classe: o windKmh das aulas passa a windClass.
Liga ao enum WeatherType das aulas 5 a 11: os nomes (sunny, partlyCloudy, cloudy, rain, storm) foram escolhidos para coincidir com o category da API, e por isso o byName funciona sem tabela de conversão. A previsão inteira é um Forecast com location e uma lista days, cada um um DayForecast.fromJson.

Pergunta à turma Se a API mandar "category": "fog" num só dia, o que vê o utilizador no ecrã da previsão?
Respostas às perguntas. O ecrã de erro, para a previsão toda: o byName lança um erro, o fromJson da lista inteira falha, o Future completa com erro e o FutureBuilder mostra o ramo de erro. Um valor inesperado num dia estraga os cinco dias. Por isso, para enums vindos de fora, vale a pena ter um valor por omissão em vez de falhar. Os acentos: o package http lê o corpo como UTF-8 quando o Content-Type é JSON; com outros tipos, usa utf8.decode(response.bodyBytes), ou aparece "SÃ£o Miguel".

O pedido completo, com erros

void _check(http.Response response) {
  if (response.statusCode >= 200 && response.statusCode < 300) return;
  final body = jsonDecode(response.body) as Map<String, dynamic>;
  final error = body['error'] as Map<String, dynamic>;
  throw ApiException(response.statusCode, error['message'] as String);
}

Future<List<Island>> fetchIslands(String token) async {
  final response = await http
      .get(
        Uri.parse('$baseUrl/v1/islands'),
        headers: {'Authorization': 'Bearer $token'},
      )
      .timeout(const Duration(seconds: 10));
  _check(response);
  final list = jsonDecode(response.body) as List<dynamic>;
  return list
      .map((item) => Island.fromJson(item as Map<String, dynamic>))
      .toList();
}
  • O http não lança erro num 404 ou num 500: a resposta chega na mesma. Quem verifica o statusCode és tu.
  • Sem timeout, um pedido num túnel pode ficar pendurado minutos. Com ele, ao fim de 10 s o Future completa com erro.
Mostra o resultado real dos dois erros, que estão no código de demonstração: GET /v1/islands/atlantida/forecast dá "404: Não há nenhuma ilha com o id "atlantida"." e um token com segredo errado dá "401: clientId ou clientSecret errados.". O ApiException é uma classe nossa com statusCode e message; mais à frente a app decide o que fazer por código (aula de resiliência).

O token e o segredo

Future<String> fetchToken(String clientId, String clientSecret) async {
  final response = await http.post(
    Uri.parse('$baseUrl/v1/auth/token'),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode({'clientId': clientId, 'clientSecret': clientSecret}),
  );
  _check(response);
  final json = jsonDecode(response.body) as Map<String, dynamic>;
  return json['accessToken'] as String;
}
const clientId = String.fromEnvironment('CLIENT_ID');
const clientSecret = String.fromEnvironment('CLIENT_SECRET');

FutureBuilder: o ecrã que espera

class _IslandsScreenState extends State<IslandsScreen> {
  late final Future<List<Island>> _islands;

  @override
  void initState() {
    super.initState();
    _islands = fetchIslands(widget.token); // once, not in build
  }

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<Island>>(
      future: _islands,
      builder: (context, snapshot) {
        if (snapshot.connectionState != ConnectionState.done) {
          return const Center(child: CircularProgressIndicator());
        }
        if (snapshot.hasError) {
          return Center(child: Text('${snapshot.error}'));
        }
        final islands = snapshot.data!;
        return ListView.builder(
          itemCount: islands.length,
          itemBuilder: (context, i) => ListTile(
            leading: Image.network(islands[i].imageUrl, width: 56),
            title: Text(islands[i].name),
          ),
        );
      },
    );
  }
}

FutureBuilder: o que interessa

  • O builder corre de novo cada vez que o Future muda de estado. O snapshot diz em que estado está.
  • Três ramos, sempre: a carregar (connectionState), erro (hasError, error) e dados (data). Os três estados do Future, desenhados.
  • O Future cria-se uma vez, no initState. Se escreveres future: fetchIslands(token) dentro do build, cada rebuild faz um pedido novo.
  • Image.network em vez de Image.asset: a fotografia também vem da rede, e o Flutter guarda-a em cache.
  • Para voltar a pedir (botão "Tentar de novo"), atribui um Future novo dentro de setState.
Pergunta à turma O build de um ecrã corre quantas vezes? E quantos pedidos fazia o servidor se o Future fosse criado lá dentro?
Respostas às perguntas. Muitas e sem controlo: cada setState, cada mudança de tema ou de tamanho de letra, cada vez que o teclado abre ou o ecrã roda, e cada hot reload. Com o Future no build, cada uma é um pedido novo e o ecrã volta a mostrar o "a carregar". Demonstração ao vivo: muda future: _islands para future: fetchIslands(widget.token), faz hot reload três vezes e mostra no separador Network do Chrome os pedidos repetidos.

Código de demonstração em ../pdm-aula-12 (local, sem remote). Corre com flutter run -d chrome --dart-define=CLIENT_ID=... --dart-define=CLIENT_SECRET=... com a conta Docente de ~/.config/pdm-api/docente.json.

E se os dados não param de chegar?

Future<T>Stream<T>
Quantos valoresUm, uma vezMuitos, ao longo do tempo
Como se esperaawaitawait for ou listen
WidgetFutureBuilderStreamBuilder
ExemplosA previsão de hoje, o token, uma fotografiaA posição do GPS, mensagens de chat, cotações, um autocarro em movimento
  • Um Future é uma encomenda: chega uma vez. Uma Stream é uma assinatura: chega sempre que há uma edição nova, até cancelares.
  • De onde vêm os dados em tempo real: polling (a app pergunta de X em X segundos), Server-Sent Events ou WebSockets (o servidor envia quando há novidades).
  • O StreamBuilder tem o mesmo snapshot do FutureBuilder, mas o builder corre de novo a cada valor novo.
O polling é o mais simples e o que mais gasta: com 1000 telemóveis a perguntar de 5 em 5 segundos, são 200 pedidos por segundo, quase todos com a mesma resposta. Com WebSockets, o servidor pergunta uma vez e envia a todos. É uma das perguntas a fazer ao desenhar uma app em tempo real.
