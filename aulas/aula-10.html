Acessibilidade é obrigatória, e é boa engenharia

  • Lei: o European Accessibility Act está em vigor desde junho de 2025. Apps de comércio, banca, transportes e serviços ao consumidor na UE têm de ser acessíveis. Multas e retirada do mercado são reais.
  • Lojas: a Apple e a Google avaliam acessibilidade nas revisões de destaque e nas rejeições. A Apple publica "Accessibility Nutrition Labels" desde 2025.
  • Pessoas: cerca de 1 em cada 6 pessoas tem alguma deficiência. E todos usamos o telemóvel ao sol, com uma mão, com o ecrã partido, ou com a letra do sistema aumentada.
  • Engenharia: uma app acessível tem widgets com nomes, estrutura clara e sem cor como único sinal. Isso é o mesmo que uma app testável e fácil de manter.
  • O Flutter já faz muito sozinho: botões, textos e campos ganham semântica automaticamente. Tu tratas do que falta.

Para os testes: o European Accessibility Act (2025) obriga apps de serviços ao consumidor na UE a serem acessíveis; a semântica no Flutter é gerada automaticamente para os widgets Material e completada com Semantics.

Liga o TalkBack no teu telemóvel ao vivo e navega dois ecrãs da solução da aula 9 sem olhar. Os alunos ouvem "botão" sem nome no ícone da estrela. É a demonstração mais eficaz de toda a aula; 3 minutos.

Semantics no Flutter

// O Flutter gera semântica para Text, botões e campos. Tu acrescentas o que falta:
IconButton(
  icon: const Icon(Icons.star_border),
  tooltip: 'Adicionar aos favoritos',        // lido pelo leitor de ecrã e mostrado em long press
  onPressed: adicionar,
),

Semantics(
  label: 'Ponta Delgada, 21 graus, céu limpo',
  button: true,
  child: ExcludeSemantics(                   // o ícone e os textos já estão no label
    child: CartaoLocalidade(previsao: p),
  ),
),

Image.asset('assets/img/sao_miguel.jpg', semanticLabel: 'Lagoa das Sete Cidades'),

MergeSemantics(                              // dois textos lidos como um só
  child: Row(children: const [Text('Mín '), Text('17°')]),
),
  • Ordem de foco: o leitor segue a ordem da árvore. Se o layout visual não bate certo, Semantics(sortKey: OrdinalSortKey(1)) corrige.
  • Testa com TalkBack (Android: Definições → Acessibilidade) ou VoiceOver (iOS: triplo clique no botão lateral). Cinco minutos de utilização com o ecrã tapado revelam mais do que a leitura da documentação.
Analogia O leitor de ecrã é um guia que descreve a sala a quem não vê. Um botão só com ícone é um objeto sem nome: o guia diz "botão" e mais nada. A etiqueta semântica (tooltip, label) dá-lhe o nome; MergeSemantics junta várias peças numa só descrição.
Pergunta: o que ouve o leitor de ecrã num cartão com ícone de sol, "Ponta Delgada" e "21°"? Sem Semantics: três elementos separados, o ícone sem nome. Com o label: uma frase. Mostra no DevTools o "Show semantics" para verem a árvore semântica.

Contraste, toque e letra grande

  • Contraste: 4,5:1 para texto normal, 3:1 para texto grande e ícones (WCAG AA). O ColorScheme.fromSeed garante os pares x/onX; cores à mão são a fonte dos problemas. Verifica com o Accessibility Scanner (Android) ou o inspector do Xcode.
  • Alvos de toque: 48 dp no mínimo. IconButton e ListTile já cumprem; um GestureDetector à volta de um ícone de 20 dp não. MaterialTapTargetSize.padded é o valor por defeito do tema.
  • Letra grande: o utilizador pode pôr o texto a 200%. MediaQuery.textScalerOf(context) diz-te o fator. Layouts com alturas fixas (SizedBox(height: 40) à volta de um Text) partem; usa Wrap, Expanded, FittedBox ou deixa a altura livre.
  • Testa com a letra do sistema no máximo. Se um cartão fica com texto cortado, é um bug, não uma preferência estranha.
  • Cor não é sinal: um aviso "vermelho" precisa também de ícone ou texto. Daltonismo afeta 8% dos homens.

Para os testes: contraste mínimo 4,5:1, alvo mínimo 48 dp, e o layout tem de sobreviver a textScaler de 2,0.

i18n (1 de 2): gen-l10n e ficheiros .arb

# pubspec.yaml
dependencies:
  flutter_localizations:
    sdk: flutter
  intl: any                     # a versão que o SDK fixar
flutter:
  generate: true                # corre gen-l10n em cada pub get

# l10n.yaml (na raiz do projeto)
arb-dir: lib/l10n
template-arb-file: app_pt.arb
output-localizations-file: app_localizations.dart
{
  "@@locale": "pt",
  "tituloApp": "Tempo Açores",
  "pesquisar": "Pesquisar localidade",
  "previsaoDias": "{n, plural, =1{Previsão para 1 dia} other{Previsão para {n} dias}}",
  "@previsaoDias": {"placeholders": {"n": {"type": "int"}}},
  "atualizadoHa": "Atualizado há {minutos} min",
  "@atualizadoHa": {"placeholders": {"minutos": {"type": "int"}}}
}
Analogia Não se escreve o texto na parede; escreve-se numa placa que se pode trocar. Os ficheiros .arb são as placas em cada língua, e gen-l10n faz o suporte onde a placa encaixa (AppLocalizations). O locale do telemóvel escolhe a placa.

i18n (2 de 2): usar as strings

import 'l10n/app_localizations.dart';                       // gerado em lib/l10n/

MaterialApp.router(
  routerConfig: router,
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,     // [pt, en], lidos dos .arb
  onGenerateTitle: (context) => AppLocalizations.of(context)!.tituloApp,
)

// num widget
final l10n = AppLocalizations.of(context)!;
Text(l10n.tituloApp);
Text(l10n.previsaoDias(5));                                  // Previsão para 5 dias
Text(l10n.atualizadoHa(12));                                 // Atualizado há 12 min
  • O ficheiro modelo (app_pt.arb) define as chaves; cada outra língua é um .arb com as mesmas chaves. Faltar uma chave dá aviso ao gerar, não crash em runtime.
  • Plurais com ICU: =0, =1, other. Em português "1 dia" e "2 dias"; noutras línguas há mais formas, e o formato trata delas.
  • A língua vem do sistema. Para forçar, locale: const Locale('en') no MaterialApp (útil para testar).

Para os testes: as strings vivem em ficheiros .arb, uma língua por ficheiro; gen-l10n gera a classe AppLocalizations; nunca há texto visível hard-coded nos widgets.

Formatos com intl, e RTL em uma frase

import 'package:intl/intl.dart';
import 'package:intl/date_symbol_data_local.dart';

await initializeDateFormatting('pt_PT');               // uma vez, no main, antes do runApp

final hoje = DateTime(2026, 10, 6);
DateFormat.EEEE('pt_PT').format(hoje);                 // terça-feira
DateFormat('d MMM', 'pt_PT').format(hoje);             // 6 out.
DateFormat.yMMMMd('en').format(hoje);                  // October 6, 2026
NumberFormat('0.0', 'pt_PT').format(21.456);           // 21,5
NumberFormat.decimalPattern('en').format(1234.5);      // 1,234.5

// Melhor: o locale do ecrã, não um fixo
final locale = Localizations.localeOf(context).toString();
DateFormat.EEEE(locale).format(hoje);
  • Datas, números, moedas e unidades mudam de língua para língua: a vírgula decimal, a ordem dia/mês, o nome do dia. Nunca os montes à mão com '$dia/$mes'.
  • RTL: árabe e hebraico escrevem-se da direita para a esquerda; o Flutter espelha o layout sozinho se usares EdgeInsetsDirectional e start/end em vez de left/right.

Para os testes: intl formata datas e números por locale; initializeDateFormatting é obrigatório para locales que não sejam inglês.

Passo 1: carregar JSON dos assets

import 'dart:convert';
import 'package:flutter/services.dart';

class PrevisoesLocais {
  Future<List<Localidade>> carregar() async {
    final texto = await rootBundle.loadString('assets/previsoes.json');
    final json = jsonDecode(texto) as Map<String, dynamic>;
    final lista = json['localidades'] as List<dynamic>;
    return lista
        .map((e) => Localidade.fromJson(e as Map<String, dynamic>))
        .toList();
  }
}

// no ecrã da lista
FutureBuilder<List<Localidade>>(
  future: _futuro,                              // criado uma vez no initState, nunca no build
  builder: (context, snapshot) {
    if (snapshot.hasError) return Text('Erro: ${snapshot.error}');
    if (!snapshot.hasData) return const Center(child: CircularProgressIndicator());
    final localidades = snapshot.data!;
    return ListaLocalidades(localidades: localidades);
  },
)
Erro clássico: criar o Future dentro do build; a cada rebuild volta a ler o ficheiro e o ecrã pisca. Mostra-o de propósito e corrige com initState. Segundo erro: o ficheiro não está declarado em pubspec.yaml e o loadString lança "Unable to load asset".

Passo 1: o que interessa

  • rootBundle.loadString lê um ficheiro declarado em pubspec.yaml na secção assets:. É assíncrono porque em release os assets vêm de dentro do binário.
  • Os modelos Localidade e Previsao com fromJson são os da aula 4, com a validação do trabalho de casa: um campo em falta lança FormatException com o nome do campo.
  • FutureBuilder desenha os estados do Future: a carregar, com erro, com dados. É a versão mínima dos quatro estados da aula 6; na aula 14 fazemos melhor.
  • O Future cria-se uma vez (initState) e guarda-se num campo. Criá-lo no build repete a leitura a cada rebuild.
  • A classe PrevisoesLocais é a única que sabe de onde vêm os dados. Na aula 12 troca-se por uma que fala com a API sem mexer nos ecrãs.
