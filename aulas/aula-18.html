O programa: toda a gente leva um para casa

// flutter run --dart-define=CLIENT_SECRET=...
const clientSecret = String.fromEnvironment('CLIENT_SECRET');
  • O --dart-define tira o segredo do repositório. Não o tira do APK: o valor é compilado para o libapp.so.
  • Por isso um segredo de app vale pouco: só dá a pulseira de visitante. O que protege a conta da Ana é o login dela.
Pergunta à turma Então para que serve o --dart-define, se o segredo acaba no APK?
Respostas às perguntas. Serve para o segredo não ir para o GitHub, onde fica para sempre e onde qualquer colaborador, ou um repositório que um dia passe a público, o expõe. E para cada grupo ter o seu sem mexer no código. O APK só chega a quem o instala; o repositório chega a toda a gente que alguma vez lhe tenha acesso. Em produção, as apps não levam segredo nenhum (é o PKCE de ontem) e o servidor pode revogar um segredo que vaze.

A memória do festival: o git

git log -S "o-segredo-do-grupo" --oneline
  • Nunca no repositório: o clientSecret, a keystore de assinatura (*.jks) e o key.properties. O android/.gitignore do projeto já ignora os dois últimos.
  • Se um segredo entrou num commit, conta como publicado: pede um novo e muda-o. Apagar o commit não chega: quem já fez pull tem uma cópia.
O git log -S procura commits que acrescentaram ou tiraram aquele texto. Vão usá-lo daqui a pouco no repositório do grupo, com o segredo verdadeiro. Funciona igual no PowerShell e no terminal do Mac.

A fila: falar ao ouvido do porteiro

  • HTTPS sempre. O Android bloqueia http:// desde a versão 9; o iOS também (App Transport Security). Desligar isto "para testar" é dos erros mais comuns.
  • Nunca aceitar qualquer certificado: badCertificateCallback a devolver true deixa entrar um porteiro falso.
  • Certificate pinning: a app traz o crachá do porteiro verdadeiro e confere-o. Protege de quem controla a rede; custa caro: quando o certificado do servidor muda, as apps antigas deixam de funcionar. Vale a pena em bancos e saúde, não na Tempo Açores.
Se perguntarem como alguém lê o tráfego: num Wi-Fi aberto qualquer pessoa na rede vê os pacotes, e quem gere o router vê tudo. Com HTTPS vê o endereço do servidor mas não o que se diz.

A revista à entrada: só o que é preciso

  • Pede a permissão quando a pessoa toca na funcionalidade, e diz porquê numa frase antes do pedido do sistema.
  • Pede a menor: localização aproximada chega para "a ilha mais próxima". Se a pessoa recusar, a app continua a funcionar sem isso.
  • As lojas rejeitam permissões que a app não justifica.
Atenção Em debug, o Flutter acrescenta a permissão INTERNET sozinho. No APK de release, só a tem se estiver em android/app/src/main/AndroidManifest.xml. Sem ela, o APK que vão entregar não tem rede.
A permissão INTERNET não aparece ao utilizador (é "normal", não "perigosa"), mas tem de estar declarada. O template do projeto não a tem no manifesto principal: vão acrescentá-la na verificação da sprint.

O bar do festival tem um só barman

No barNa app
O barmanA thread de UI: corre o build, os toques e as animações
Um cliente servidoUm frame: 16 ms a 60 fps, 8 ms a 120 fps
A fila paradaJank: o ecrã congela ou salta
Um segundo barman, noutro balcãoUm isolate, com compute()
Copos já cheiosWidgets const
Servir só quem está ao balcãoListView.builder
O Dart tem uma só thread por isolate: a app inteira corre num barman. Tudo o que ele faz de seguida, sem pausa, a fila espera. Volta a esta tabela no fim da parte de performance.

async não chama outro barman

// before: the UI thread decodes 5 MB, the queue stops
return jsonDecode(response.body);

// after: a second isolate decodes it, the UI keeps going
return compute(jsonDecode, response.body);
  • await http.get(...) não trava: esperar pela rede não é trabalhar, e o barman serve outros entretanto.
  • jsonDecode de 5 MB trava, mesmo dentro de uma função async: são 120 ms de contas seguidas.
  • O segundo barman tem a caixa dele (memória separada): recebe texto e números, devolve dados. Não vê o BuildContext nem os notifiers.
A pergunta clássica do teste: "meter o jsonDecode numa função async resolve o jank?" Não: o async só liberta o barman nos await. Criar um isolate custa alguns milissegundos: para as respostas da API do curso, que são pequenas, não compensa. É para JSON grande, imagens, cálculos.

Copos já cheios: const e widgets pequenos

  • setState e notifyListeners reconstroem o widget e tudo o que está por baixo. Quanto mais alto, mais trabalho.
  • Parte o ecrã em widgets pequenos: o que muda fica num widget só dele.
  • const Text('Ilhas') é criado uma vez e nunca mais se reconstrói. O flutter analyze avisa onde falta.
  • Com Provider: context.select em vez de context.watch, para só reconstruir quando muda o valor que o widget usa.
O DevTools mostra quantas vezes cada widget se reconstrói (Rebuild stats, no separador Performance). Não é para usar hoje; é para saberem que existe.

Verificação de segurança: 5 minutos, no repositório do grupo

git log -S "o-clientSecret-do-grupo" --oneline
git grep -n "http://"
git grep -n "uses-permission" -- android
  1. O primeiro comando não pode mostrar nada. Se mostrar um commit, o segredo foi publicado: pede um novo no issue das credenciais.
  2. O segundo também não: tudo em https://.
  3. O terceiro tem de mostrar a INTERNET em android/app/src/main/AndroidManifest.xml. Se só aparecer em debug e profile, falta no release.
Faz Corre os três comandos. Se faltar a INTERNET, acrescenta num PR, logo a seguir a <manifest ...>: <uses-permission android:name="android.permission.INTERNET"/>
Os comandos são do git e funcionam no PowerShell. O segredo vai entre aspas, sem o escrever em mais lado nenhum. O template do projeto só tem a INTERNET nos manifestos de debug e profile, por isso todos os grupos vão precisar da linha.
