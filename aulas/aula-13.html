Arquitetura por camadas e gestão de estado

Hoje a app vai buscar as ilhas à API do curso, escrita por ti. Partimos de um ecrã que faz tudo sozinho (pedido, JSON e estados) e arrumamos cada coisa na sua camada: um repository para os dados, um notifier para o estado e o Provider para os ligar ao ecrã.

Na última aula não houve código dos alunos, só Swagger: hoje é a primeira vez que cada um corre a app contra a API, com as suas credenciais. O clone e as credenciais são o ponto onde a aula pode encalhar; não avances para o passo 1 sem toda a gente com a lista de ilhas no ecrã. Antes da aula, confirma que os erros de propósito da caça ao erro estão desligados (pdm-bugs off): com eles ligados, a lista chega com oito ilhas.

No fim desta aula consegues

  • Explicar porque se separa uma app em camadas e o que cada camada pode conhecer.
  • Escrever um repository com uma interface e uma implementação HTTP.
  • Guardar o estado de um ecrã (a carregar, erro, dados) num ChangeNotifier.
  • Ligar o notifier ao ecrã com o Provider: context.watch, context.read e Consumer.
  • Injetar dependências pelo construtor e trocar a API por um repository a fingir sem mexer no ecrã.
  • Partilhar estado entre dois ecrãs.

Pergunta à turma Que ficheiros mudas se a API mudar o caminho para /v2/islands? E se quiseres mostrar a app numa demonstração sem rede? E se o mapa também precisar das ilhas?
Respostas às perguntas. As três respostas são o mesmo ficheiro, o ecrã. O caminho está no _load; para mostrar sem rede só há uma maneira, que é mexer no ecrã; e um segundo ecrã que precise das ilhas copia o _load e faz um segundo pedido. Um ficheiro com muitas razões para mudar é o sinal de alarme: cada alteração pequena obriga a mexer no ecrã, e é aí que os erros aparecem. Hoje cada uma destas razões passa a ter o seu ficheiro.

Porquê camadas

  • Trocar a fonte dos dados. A API muda de versão, os dados passam a vir também de uma cache no telemóvel: muda um ficheiro, e os ecrãs ficam iguais.
  • Mostrar sem rede. Um repository a fingir, com dados fixos, deixa desenvolver e demonstrar o ecrã sem API e sem credenciais. Mais à frente, é também o que torna os testes automáticos possíveis.
  • Reutilizar. A lista de ilhas aparece na lista, nos favoritos e, um dia, no mapa: um só sítio sabe ir buscá-la.
  • Cada pessoa no seu ficheiro. No projeto de grupo, quem faz o ecrã e quem faz os pedidos não mexem no mesmo ficheiro ao mesmo tempo.

Numa app grande (a do banco, a do Spotify) o ecrã pede "a conta" e não sabe se ela veio da rede, da cache ou do disco.

Para os testes: as camadas existem para isolar mudanças; o ecrã não deve conhecer HTTP nem JSON.

Repository: uma interface, várias implementações

/// What the app can ask for. The screens only see this.
abstract class ForecastRepository {
  Future<List<Island>> fetchIslands();
  Future<Forecast> fetchForecast(String islandId);
}
  • A interface diz o quê: as ilhas, a previsão de uma ilha. Uma abstract class sem corpo nos métodos.
  • Cada implementação diz como: HttpForecastRepository pede à API; FakeForecastRepository devolve dados fixos; mais à frente, uma com cache no telemóvel.
  • Quem usa recebe um ForecastRepository e não sabe qual dos três é.
  • O JSON não passa daqui para cima. O fromJson converte a forma da API (o DTO) na forma da app (o modelo); se a API mudar um nome, muda o fromJson, e o resto da app fica igual.
Analogia O balcão de uma loja. Pedes "uma previsão do Pico" ao balcão e não sabes se veio do armazém (a cache) ou do fornecedor (a API). A loja pode mudar de fornecedor sem tu dares por isso; e numa formação, um balcão a fingir responde sempre o mesmo.

Para os testes: repository = uma interface com várias implementações; o ecrã depende da interface, nunca da implementação.

Injeção de dependências: quem usa não cria

final ForecastRepository repository = useFake
    ? FakeForecastRepository()
    : HttpForecastRepository(
        ApiClient(clientId: clientId, clientSecret: clientSecret),
      );
  • O HttpForecastRepository recebe o ApiClient no construtor; o ForecastNotifier recebe o repository no construtor. Nenhum deles cria aquilo de que precisa.
  • Quem cria é o main, num só sítio. É aí que se escolhe a API ou o fake, e as credenciais.
  • O contrário, um ApiClient() criado dentro do notifier ou uma variável global que todos usam, é uma dependência escondida: não se troca, e não se vê quem depende de quem.
  • Para levar os objetos até aos widgets usamos o Provider. Há outras ferramentas (get_it, Riverpod); a regra do construtor é a mesma.
Pergunta à turma Se o HttpForecastRepository criasse o seu próprio ApiClient lá dentro, o que deixava de ser possível?

Para os testes: injeção de dependências = receber pelo construtor em vez de criar; permite trocar uma peça sem mexer em quem a usa.

Respostas às perguntas. Escolher as credenciais (e o endereço da API) do lado de fora: teriam de estar escritas dentro do repository. Partilhar um só ApiClient, e portanto um só token, entre vários repositories: cada um pedia o seu. E trocar o ApiClient por outro, por exemplo um que responde sem rede para um teste. Analogia rápida, se ajudar: uma máquina de café recebe a cápsula, não planta o café.

Quando chega o Provider

SituaçãoEscolha
Estado de um só widget: um cartão aberto, um campo de pesquisa, um separadorsetState
Dados da rede, ou estado partilhado por vários ecrãs, numa equipa pequenaChangeNotifier + Provider (o projeto)
Muitos eventos, regras de teste fortes, equipas grandesBLoC ou Riverpod
  • O Provider chega quando o estado sai de um só widget: quando dois ecrãs precisam dele, quando tem de sobreviver à navegação, ou quando a lógica deve viver fora dos widgets.
  • A recomendação da equipa do Flutter: começar simples, com camadas e injeção pelo construtor, e só depois trocar de ferramenta se for preciso. Com as camadas feitas, trocar o ChangeNotifier por BLoC é mexer numa camada; sem elas, é reescrever ecrãs.

1. O repository: o pedido sai do ecrã

/// How: HTTP to the course API, through the ApiClient.
class HttpForecastRepository implements ForecastRepository {
  HttpForecastRepository(this._api); // injected, not created here

  final ApiClient _api;

  @override
  Future<List<Island>> fetchIslands() async {
    final list = await _api.get('/v1/islands') as List<dynamic>;
    return list
        .map((item) => Island.fromJson(item as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Forecast> fetchForecast(String islandId) async {
    final json = await _api.get('/v1/islands/$islandId/forecast');
    return Forecast.fromJson(json as Map<String, dynamic>);
  }
}
  • O fetchIslands é o _load do ecrã, mudado de sítio: o caminho e o fromJson vivem agora aqui.
  • implements ForecastRepository obriga a escrever os dois métodos da interface, com @override. Se faltar um, o código não compila.
  • O fetchForecast fica pronto para mais à frente: hoje ninguém o chama.
A interface (slide da teoria) fica no mesmo ficheiro, por cima desta classe, com os dois imports: api_client.dart e models.dart. O _api com sublinhado é privado: fora do ficheiro ninguém lhe chega, e o construtor HttpForecastRepository(this._api) preenche-o na mesma.

2. ForecastNotifier: o estado sai do ecrã

/// The state of the islands screen. Knows the repository, not the widgets.
class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repository); // injected, not created here

  final ForecastRepository _repository;

  bool isLoading = false;
  String? error;
  List<Island> islands = const [];

  Future<void> load() async {
    isLoading = true;
    error = null;
    notifyListeners(); // the screen shows the spinner
    try {
      islands = await _repository.fetchIslands();
    } catch (e) {
      error = '$e';
    } finally {
      isLoading = false;
      notifyListeners(); // the screen shows the islands or the error
    }
  }
}
  • Os três estados do FutureBuilder passam a ser três campos: isLoading, error e islands.
  • O notifier não conhece widgets nem BuildContext. Importa foundation.dart, não material.dart.
Pergunta à turma Porque há dois notifyListeners()? O que vê o utilizador ao carregar em "Tentar de novo" se tirares o primeiro?
Respostas às perguntas. O primeiro mostra o "a carregar" logo que o pedido parte; o segundo, no finally, mostra o resultado, seja ele as ilhas ou o erro. Sem o primeiro, depois de "Tentar de novo" a mensagem de erro fica no ecrã até a resposta chegar: parece que o botão não fez nada, e o utilizador carrega outra vez e faz dois pedidos. O '$e' mostra a mensagem da API (401: ...) ou a do Dart (um timeout); mensagens de erro escritas para pessoas ficam para amanhã.

Com o Consumer só o botão do contador volta a correr o build; com o FavoriteButton só as estrelas. As duas formas funcionam; esta faz menos trabalho, e o FavoriteButton ainda serve nos dois ecrãs. Se houver tempo, mostra no DevTools, com "Highlight repaints", o que pisca a cada toque.

Onde ficámos

  1. ForecastRepository com a interface e o HttpForecastRepository, que recebe o ApiClient: o pedido e o JSON saem do ecrã (passo 1).
