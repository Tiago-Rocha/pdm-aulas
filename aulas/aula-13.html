Arquitetura por camadas e gestão de estado

Teoria: separação da app em camadas (apresentação, domínio, dados), padrão repository e injeção de dependências; critérios para escolher entre arquiteturas simples e complexas. Prática: repository, notifier e Provider a ligar a interface aos dados.

Repositório: pdm-aula-13
Começa por pedir a dois alunos que mostrem o ecrã de detalhe do TPC. Pergunta: "onde está a chamada HTTP?" A resposta (dentro do widget) é o problema que a aula resolve. Não gastes mais de cinco minutos aqui.

No fim desta aula consegues

  • Explicar porque separar apresentação, domínio e dados, e o que cada camada pode conhecer.
  • Escrever um repository com interface e implementação, e distinguir DTO de modelo de domínio.
  • Injetar dependências por construtor e distribuí-las com o Provider, sem singletons escondidos.
  • Modelar o estado de um ecrã num ChangeNotifier e ligá-lo à UI com watch, read, Consumer e Selector.
  • Testar um notifier trocando o repository por um fake.

Porquê camadas

  • Um widget que importa package:http é um sinal de alarme: a UI sabe demasiado.
  • Testar sem rede. Um teste que precisa de Wi-Fi não é um teste, é uma lotaria. Com camadas, substitui-se a fonte de dados por um fake.
  • Trocar a fonte. API v1 para v2 (aula 28), ficheiro local nos testes, cache em disco na aula 16. Os ecrãs não mudam.
  • Reutilizar. A lista de localidades aparece no ecrã inicial, nos favoritos e no mapa. Um pedido, três ecrãs.
  • Exemplo real: na app do Spotify ou do Nubank a UI pede "dá-me a conta" e não sabe se veio da rede, da cache ou do disco.

Para os testes: as camadas existem para isolar mudanças; a UI não deve conhecer HTTP nem JSON.

UI → Notifier → Repository → DataSource

CamadaResponsabilidadeSó conhece
UI (widgets)Mostrar o estado, disparar açõesO notifier
ViewModel / NotifierEstado do ecrã (loading, dados, erro) e lógica de apresentaçãoO repository
RepositoryDecidir de onde vêm os dados, converter DTO em modeloData sources
DataSourceFalar com a API, a base de dados, as preferênciasHTTP, SQL, ficheiros
  • Regra de dependência: as setas apontam só para baixo. Uma camada nunca importa a que está acima.
  • Os nomes variam (MVVM, Clean Architecture, "camadas"); a ideia é a mesma: apresentação, domínio, dados.

Para os testes: a UI depende do domínio, nunca dos dados; o repository é a fronteira entre os dois.

Desenha as quatro caixas no quadro com setas para baixo. Depois pergunta: "o widget pode chamar o ApiClient diretamente?" Não. "O repository pode conhecer o BuildContext?" Não. Estas duas perguntas aparecem no teste.

Repository: uma interface, várias fontes

  • Uma interface (abstract class PrevisaoRepository) e várias implementações: remota, com cache, fake para testes.
  • O repository esconde a origem: previsao(id) devolve uma Previsao, venha da rede, do disco ou de memória.
  • DTO (Data Transfer Object): a forma do JSON tal como a API a manda. Muda quando a API muda.
  • Modelo de domínio: a forma que a app quer, com tipos ricos (DateTime, enum, double). Estável.
  • A conversão vive num só sítio (PrevisaoDto.toDomain()). Quando a API v2 renomear campos, só o DTO muda.

Para os testes: o DTO reflete a API, o modelo reflete a app; o repository converte um no outro.

Analogia Um balcão único. O ecrã pede "previsão da Horta" ao balcão e não sabe nem quer saber se veio do armazém (a cache) ou do fornecedor (a API). Trocar de fornecedor não muda o ecrã. Testar é pôr um balcão a fingir (o fake) que responde sempre o mesmo.

Injeção de dependências

  • Injetar = quem usa não cria. PrevisaoNotifier(repository) recebe o repository por construtor em vez de o construir lá dentro.
  • Um singleton global escondido (ApiClient.instance) é uma dependência invisível: não se troca nos testes e não se sabe quem depende de quem.
  • Provider: Provider<PrevisaoRepository>(create: …) na raiz da árvore; os widgets pedem com context.read. É o que usamos no projeto.
  • get_it: um service locator. Simples, mas esconde dependências. Aceitável em apps pequenas; evita-o em código que queres testar.
  • Regra: construtor sempre; Provider para levar as instâncias até aos widgets; nunca ApiClient() dentro de um notifier.

Para os testes: injeção por construtor permite trocar o repository por um fake sem tocar no código que está a ser testado.

Simples vs complexo: quando escalar

SituaçãoEscolha
Estado de um só widget: tab ativa, checkbox, animaçãosetState
Estado partilhado por vários ecrãs, equipa pequenaChangeNotifier + Provider (o nosso projeto)
Muitos eventos, histórico auditável, equipas grandesBLoC / Cubit
Providers globais tipados, sem BuildContext, muitos derivadosRiverpod
  • O guia de arquitetura da Google para Flutter recomenda MVVM, repositories e injeção por construtor: "começa simples, escala quando for necessário".
  • Mudar de ChangeNotifier para BLoC mais tarde é fácil se as camadas existirem. O contrário é mais difícil.

Para os testes: a arquitetura certa é a mais simples que resolve o problema atual, com fronteiras que deixam crescer.

Analogia Onde fica a lista de compras. Um post-it no frigorífico de um quarto (setState: só esse ecrã o vê); um quadro na cozinha que toda a casa consulta e que avisa quando muda (ChangeNotifier + Provider); um livro de registos com todas as alterações datadas e quem as fez (BLoC: eventos e estados). O quadro chega para a maioria das casas.
Pergunta à turma: "o formulário de definições com dois switches precisa de Provider?" Não, setState chega. "E os favoritos, que aparecem em três ecrãs?" Sim. O critério é quantos ecrãs partilham o estado.

1. PrevisaoRepository: interface e implementação

abstract class PrevisaoRepository {
  Future<List<Localidade>> localidades();
  Future<Previsao> previsao(int localidadeId);
}

class PrevisaoRepositoryApi implements PrevisaoRepository {
  PrevisaoRepositoryApi(this._api);   // injetado por construtor

  final ApiClient _api;

  @override
  Future<List<Localidade>> localidades() async {
    final json = await _api.get('/v1/locations') as List<dynamic>;
    return json
        .map((e) => Localidade.fromJson(e as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Previsao> previsao(int localidadeId) async {
    final json = await _api.get('/v1/forecast/$localidadeId') as Map<String, dynamic>;
    return Previsao.fromJson(json);
  }
}

1. Repository: o que interessa

  • A interface diz o quê (localidades, previsão); a implementação diz como (HTTP, caminhos, JSON). A UI só vê a interface.
  • O ApiClient entra pelo construtor. Nos testes entra um MockClient; na aula 16 entra também uma base de dados.
  • O JSON não sai desta camada. Quem chama localidades() recebe List<Localidade> e nunca vê um Map.
  • No starter o DTO e o modelo estão na mesma classe (fromJson). Quando a API mudar de forma, separa-os.
  • Nome da implementação diz a fonte: …Api, …Cache, …Fake. Vais ter as três.
Exercício 1 Cria AvisosRepository com o método Future<List<Aviso>> avisos() e a implementação AvisosRepositoryApi sobre GET /v1/warnings. O teste test/avisos_repository_test.dart usa um MockClient e tem de passar.

2. PrevisaoNotifier: o estado do ecrã

class PrevisaoNotifier extends ChangeNotifier {
  PrevisaoNotifier(this._repo);

  final PrevisaoRepository _repo;

  bool aCarregar = false;
  String? erro;
  List<Localidade> localidades = const [];

  Future<void> carregar() async {
    aCarregar = true;
    erro = null;
    notifyListeners();
    try {
      localidades = await _repo.localidades();
    } on ApiException catch (e) {
      erro = e.mensagem;
    } catch (_) {
      erro = 'Algo correu mal. Tenta de novo.';
    } finally {
      aCarregar = false;
      notifyListeners();
    }
  }
}

2. Notifier: o que interessa

  • ChangeNotifier é uma classe do Flutter com uma lista de ouvintes. notifyListeners() avisa-os; o Provider transforma isso em rebuilds.
  • O estado são três campos: aCarregar, erro, localidades. Amanhã substituímos por uma sealed class que impede combinações impossíveis (loading e erro ao mesmo tempo).
  • Duas notificações por carregamento: uma ao começar (mostra o loading) e outra no finally (mostra o resultado ou o erro).
  • O notifier não conhece widgets, BuildContext nem SnackBar. É por isso que se testa sem pumpWidget.
  • Uma mensagem de erro humana por defeito. A técnica (e.toString()) vai para o log, não para o ecrã.
Exercício 2 Cria DetalheNotifier com carregar(int localidadeId) que guarda uma Previsao?. O teste test/detalhe_notifier_test.dart verifica aCarregar antes e depois.

3. Provider: ligar as peças na raiz

void main() {
  final api = ApiClient(baseUrl: 'https://api.pdm.example'); // URL real na página API

  runApp(
    MultiProvider(
      providers: [
        Provider<PrevisaoRepository>(
          create: (_) => PrevisaoRepositoryApi(api),
        ),
        ChangeNotifierProvider(
          create: (context) =>
              PrevisaoNotifier(context.read<PrevisaoRepository>())..carregar(),
        ),
      ],
      child: const TempoApp(),
    ),
  );
}

A ordem importa: o notifier pede o repository com context.read, por isso o repository tem de vir antes na lista.

3. O ecrã só conhece o notifier

class LocalidadesScreen extends StatelessWidget {
  const LocalidadesScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final notifier = context.watch<PrevisaoNotifier>();

    if (notifier.aCarregar) {
      return const Center(child: CircularProgressIndicator());
    }
    if (notifier.erro != null) {
      return Center(
        child: FilledButton.icon(
          onPressed: () => context.read<PrevisaoNotifier>().carregar(),
          icon: const Icon(Icons.refresh),
          label: Text('${notifier.erro} · Tentar de novo'),
        ),
      );
    }
    return ListView(
      children: [
        for (final l in notifier.localidades)
          ListTile(title: Text(l.nome), subtitle: Text(l.ilha)),
      ],
    );
  }
}

3. Provider: o que interessa

  • context.watch<T>() subscreve: o widget reconstrói a cada notifyListeners. Só dentro de build.
  • context.read<T>() não subscreve: para chamar métodos em callbacks (onPressed, initState).
  • Consumer<T> limita a reconstrução a um subtree. Selector<T, R> só reconstrói quando R muda (por exemplo localidades.length).
  • Erros clássicos: watch dentro de onPressed lança exceção; read em build não atualiza; ProviderNotFoundException quando o widget está fora da árvore do Provider.
  • O ecrã voltou a ser StatelessWidget: o estado vive no notifier, o widget só o descreve.
Exercício 3 Liga o ecrã de detalhe ao DetalheNotifier. Usa Selector para que o cabeçalho com o nome da localidade não reconstrua quando só a previsão muda. Confirma com o inspector do DevTools ("Highlight repaints").
A dúvida do dia é watch vs read. Regra para dizer em voz alta: "watch em build, read em callbacks". Mostra a exceção ao vivo pondo um watch dentro de onPressed. Dá 15 minutos para o exercício 3.

4. Testar trocando o repository por um fake

class PrevisaoRepositoryFake implements PrevisaoRepository {
  PrevisaoRepositoryFake({this.falha = false});
  final bool falha;

  @override
  Future<List<Localidade>> localidades() async {
    if (falha) throw const ApiException('sem rede');
    return const [Localidade(id: 3, nome: 'Ponta Delgada', ilha: 'São Miguel')];
  }

  @override
  Future<Previsao> previsao(int id) => throw UnimplementedError();
}

void main() {
  test('carregar preenche localidades', () async {
    final n = PrevisaoNotifier(PrevisaoRepositoryFake());
    await n.carregar();
    expect(n.localidades, hasLength(1));
    expect(n.erro, isNull);
  });
  test('carregar guarda o erro quando o repository falha', () async {
    final n = PrevisaoNotifier(PrevisaoRepositoryFake(falha: true));
    await n.carregar();
    expect(n.erro, 'sem rede');
  });
}

4. Fakes: o que interessa

  • O fake implementa a mesma interface. O notifier não sabe que está a ser enganado: é exatamente esse o objetivo da interface.
  • Sem rede, sem pumpWidget, sem Provider: um teste unitário puro que corre em milissegundos.
  • Um fake por cenário (falha: true) testa o caminho de erro, que é o que ninguém testa à mão.
  • Na aula 25 substituímos fakes escritos à mão por mocktail. A ideia é a mesma.
  • O mesmo fake serve para desenvolver a UI sem backend: troca o create no main e a app corre em modo demo.
Exercício 4 Escreve o teste "carregar limpa o erro anterior": um notifier que falhou uma vez e depois carrega com sucesso tem de ficar com erro == null. Precisas de um fake que falha só na primeira chamada.

5. Favoritos em memória, partilhados entre dois ecrãs

class FavoritosNotifier extends ChangeNotifier {
  final Set<int> _ids = {};

  bool contem(int localidadeId) => _ids.contains(localidadeId);
  int get total => _ids.length;

  void alternar(int localidadeId) {
    if (!_ids.add(localidadeId)) _ids.remove(localidadeId);
    notifyListeners();
  }
}

// Na lista: um ícone que reage ao estado
IconButton(
  icon: Icon(context.watch<FavoritosNotifier>().contem(l.id)
      ? Icons.star
      : Icons.star_border),
  onPressed: () => context.read<FavoritosNotifier>().alternar(l.id),
)

// Noutro ecrã: um badge com o total, que só reconstrói quando o total muda
Selector<FavoritosNotifier, int>(
  selector: (_, f) => f.total,
  builder: (_, total, __) => Badge(label: Text('$total'), child: const Icon(Icons.star)),
)
Exercício 5 Regista FavoritosNotifier no MultiProvider, põe a estrela na lista e o badge no destino "Favoritos" da NavigationBar. Marca três localidades, muda de separador e volta: o estado tem de sobreviver. Na aula 16 passa a sobreviver também ao fecho da app.
