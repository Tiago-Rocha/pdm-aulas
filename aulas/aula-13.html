Arquitetura por camadas e gestão de estado

Hoje olhamos para uma classe que faz tudo sozinha, descobrimos juntos quantos trabalhos ela tem e partimo-la em camadas: dados, estado e UI. Amanhã pomos as mãos no código.

Repositório: pdm-aula-13
Aula teórica, com exercícios no quadro: a prática fica para amanhã. Ordem: a classe inteira em três slides (eles encontram as responsabilidades), as responsabilidades pintadas, a classe partida, as pastas, o restaurante, porque vale a pena, a IA, o código de cada camada e um exercício de "onde mexes". Quem quiser pode fazer clone e seguir no computador: o código de antes está no branch antes, o arrumado no main.

No fim desta aula consegues

  • Olhar para uma classe e dizer que trabalhos ela faz.
  • Partir uma classe em três camadas: dados, estado e UI.
  • Dizer em que pasta vive cada coisa: models/, data/, state/ e screens/.
  • Explicar porque é que isto importa num projeto de grupo, e ainda mais quando o código é escrito com IA.

class IslandsScreen extends StatefulWidget {
  const IslandsScreen({super.key, required this.api});

  final ApiClient api;

  @override
  State<IslandsScreen> createState() => _IslandsScreenState();

class _IslandsScreenState extends State<IslandsScreen> {
  late Future<List<Island>> _islands;

  @override
  void initState() {
    super.initState();
    _islands = _load();
  }

  Future<List<Island>> _load() async {
    final list = await widget.api.get('/v1/islands') as List<dynamic>;
    return list
        .map((item) => Island.fromJson(item as Map<String, dynamic>))
        .toList();
  }

Pergunta à turma Olha para o quadro. Junta o que escrevemos em grupos: quantos trabalhos diferentes faz esta classe?
Respostas às perguntas. Três grupos. Dados: recebe o ApiClient, pede /v1/islands, converte o JSON em Island. Estado: guarda o Future, decide entre a carregar, erro e dados, volta a pedir no "Tentar de novo". UI: desenha a AppBar, o erro, o botão e a lista. Uma classe, três trabalhos

Pergunta à turma Se partíssemos esta classe, em quantos ficheiros a partias? Que nome davas a cada um?
Respostas às perguntas. Três, um por cor: um que vai buscar os dados, um que guarda o estado, um que desenha. Os nomes que eles derem são bons se disserem o trabalho; os nossos estão no slide seguinte. A mensagem: não é código mal escrito, é código com trabalhos a mais. Hoje são 70 linhas; no projeto, este ecrã vai ter a previsão, os avisos e as favoritas, e passa das 400.

Partimos a classe: as mesmas linhas, arrumadas

Não se escreveu nada de novo: as mesmas linhas mudaram de sítio, e cada ficheiro ficou com uma cor só.

As linhas do _load foram para data/, as do Future e dos estados para state/, e o ecrã ficou só com o desenho. Repara que o total de linhas até aumentou um pouco (mais ficheiros, mais imports): arrumar não é encurtar. O ganho é cada ficheiro ter uma só razão para mudar. No repositório: git diff antes main.

Antes e depois: as pastas

As três cores do slide anterior são três pastas. models/ não é uma camada: são as classes que passam de mão em mão (Island, Forecast), usadas pelas três. O main.dart só arranca a app. O guia da equipa do Flutter usa nomes um pouco diferentes (ui/ e data/); o que importa é cada pasta ter um trabalho.

O restaurante: três postos

Conta como uma história, com um pedido real: o cliente pede as ilhas ao empregado (o ecrã); o empregado olha para o passe e vê "a preparar" (o notifier, isLoading); a cozinha (o repository) vai ao fornecedor (a API, pelo ApiClient), recebe os ingredientes em bruto (o JSON) e prepara o prato (Island); o prato chega ao passe, toca a campainha (notifyListeners) e o empregado serve. Se o fornecedor falhar, a cozinha avisa o passe, que mostra "esgotado" (error), e é o empregado que decide como o dizer ao cliente. Antes, era um restaurante de uma pessoa só: a mesma pessoa atendia, cozinhava e ia ao fornecedor.

Pergunta à turma Destas quatro, qual vos vai acontecer primeiro no projeto de grupo?
Respostas às perguntas. Não há resposta certa; a mais provável é a última, logo na primeira semana do projeto, que começa quarta-feira. Insiste numa ideia: nenhum destes problemas é um erro no código de hoje. A app funciona. São problemas de crescimento, e é por isso que se arruma antes de crescer. No restaurante: com duas mesas, uma pessoa chega; com vinte, ou no dia em que essa pessoa falta, o restaurante para.

E com IA, ainda mais

  • Uma IA escreve em segundos o que nós escrevíamos numa tarde. O problema deixou de ser escrever código: passou a ser ler e verificar código.
  • Sem pastas, a IA mete tudo onde calha, e o ecrã que faz tudo aparece sozinho, com 400 linhas que ninguém leu.
  • Com pastas, tu dizes onde: "cria um repository novo em data/ e não mexas em screens/". E quando ela acaba, vês logo que pastas mudaram.
  • A IA não dá sempre a mesma resposta. Cada camada sozinha dá: o repository a fingir devolve sempre as mesmas três ilhas. Consegues ver o resultado de cada passo e comparar com o que esperavas.
Regra para o projeto Se usares IA, és tu que decides a pasta e o ficheiro. Ela escreve, tu arrumas e verificas.
A ideia: a IA é probabilística, a mesma pergunta dá respostas diferentes. Uma app partida em camadas, com a saída de cada uma visível, torna o resultado de cada passo previsível e comparável. Pergunta-lhes se já usaram IA para o código das aulas e onde é que ela pôs as coisas. Liga ao projeto de grupo: quatro pessoas, cada uma com a sua IA, no mesmo ficheiro, é o pior dos dois mundos.

Cada camada só fala com a de baixo

Pergunta à turma O ecrã pode chamar a API diretamente? O repository pode mostrar uma mensagem de erro no ecrã?
Respostas às perguntas. Não e não. Se o ecrã chamar a API, voltamos ao restaurante de uma pessoa só: o empregado foi ao fornecedor. O repository não conhece widgets: quando algo falha, lança uma exceção; o notifier guarda-a como estado (error); e é o ecrã que decide como a mostrar. No restaurante: a cozinha não vai à mesa pedir desculpa, avisa o passe. Os nomes variam (MVVM, Clean Architecture, "camadas"), e o guia do Flutter chama ViewModel ao que aqui chamamos notifier; a ideia é a mesma.

Dados: o repository

/// What the app can ask for. The screens only see this.
abstract class ForecastRepository {
  Future<List<Island>> fetchIslands();
  Future<Forecast> fetchForecast(String islandId);
}
  • A interface diz o quê: as ilhas, a previsão de uma ilha. Como a ementa: diz os pratos, não as receitas.
  • Cada implementação diz como. O HttpForecastRepository pede à API; amanhã escreves um que devolve dados fixos.
  • O JSON não passa daqui para cima: sai daqui já em Island.
Analogia Pedes um prato à cozinha e recebes o prato pronto. Não sabes se o peixe veio do fornecedor de sempre, de um novo ou da arca.

Dados: HttpForecastRepository

/// How: HTTP to the course API, through the ApiClient.
class HttpForecastRepository implements ForecastRepository {
  HttpForecastRepository(this._api); // injected, not created here

  final ApiClient _api;

  @override
  Future<List<Island>> fetchIslands() async {
    final list = await _api.get('/v1/islands') as List<dynamic>;
    return list
        .map((item) => Island.fromJson(item as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Forecast> fetchForecast(String islandId) async {
    final json = await _api.get('/v1/islands/$islandId/forecast');
    return Forecast.fromJson(json as Map<String, dynamic>);
  }
}
Pergunta à turma Onde é que já vimos o fetchIslands?
Respostas às perguntas. É o _load do ecrã de antes, linha a linha, mudado de sítio: o widget.api.get passou a _api.get. implements obriga a escrever os dois métodos da interface; se faltar um, não compila. O fetchForecast fica pronto para mais à frente.

Estado: ForecastNotifier

class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repository); // injected, not created here

  final ForecastRepository _repository;

  bool isLoading = false;
  String? error;
  List<Island> islands = const [];

  Future<void> load() async {
    isLoading = true;
    error = null;
    notifyListeners(); // the screen shows the spinner
    try {
      islands = await _repository.fetchIslands();
    } catch (e) {
      error = '$e';
    } finally {
      isLoading = false;
      notifyListeners(); // the screen shows the islands or the error
    }
  }
}
Pergunta à turma Os três estados do FutureBuilder passaram a ser três campos. Quais? E o que é a campainha?
Respostas às perguntas. isLoading, error e islands. A campainha é o notifyListeners(): avisa quem está a ouvir que algo mudou. Toca duas vezes: quando o pedido parte (o ecrã mostra o "a carregar") e quando chega a resposta (as ilhas ou o erro). Não conhece widgets.

UI: o ecrã só conhece o notifier

class IslandsScreen extends StatelessWidget {
  const IslandsScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final forecast = context.watch<ForecastNotifier>();
    return Scaffold(
      appBar: AppBar(title: const Text('Tempo Açores')),
      body: _body(context, forecast),
    );
  }

  Widget _body(BuildContext context, ForecastNotifier forecast) {
    if (forecast.isLoading) {
      return const Center(child: CircularProgressIndicator());
    }
    // o erro: o Center de antes, com o botão Tentar de novo
    onPressed: () => context.read<ForecastNotifier>().load(),
    // os dados: o ListView.builder de antes, com forecast.islands
  }
}
Regra context.watch no build: o empregado de olho no passe. context.read no botão: um recado ao passe, sem ficar a olhar.
Deixou de ser StatefulWidget: sem State, sem Future, sem FutureBuilder, sem URL e sem JSON. Pergunta: o que acontecia com read no build? O ecrã ficava no "a carregar" para sempre, porque não ouvia a segunda campainha.

Exercício: onde mexes?

Para cada pedido, diz a pasta. Só uma.

  1. A API passa a dar as ilhas em /v2/islands.
  2. Queremos o nome de cada ilha a negrito.
  3. Ao carregar em "Tentar de novo", a lista deve esvaziar enquanto carrega.
  4. A API passa a mandar nome em vez de name.
  5. Queremos correr a app sem internet, com três ilhas fixas.
Respostas. 1: data/ (o HttpForecastRepository). 2: screens/ (o title do ListTile). 3: state/ (o load() põe islands = const []). 4: models/ (o fromJson da Island). 5: data/, um ficheiro novo, um repository a fingir: é a prática de amanhã. Pede respostas com o dedo no ar, uma pasta de cada vez; quem falhar, volta ao restaurante.

Pergunta à turma O cartão que abre e fecha precisa de Provider? E uma lista de ilhas favoritas, que aparece na lista e num ecrã de favoritas?
Respostas às perguntas. O cartão não: só ele quer saber se está aberto, e setState chega. As favoritas sim: dois ecrãs leem e mudam a mesma lista. É a prática de amanhã. O critério é quantos widgets precisam do estado, não o tamanho da app.

Onde ficámos

  1. Uma classe que faz tudo funciona, mas não cresce: dados, estado e UI misturados.
  2. Partimos em três camadas, uma pasta cada: data/, state/ e screens/, mais models/ para o que passa entre elas.
  3. Cada camada só fala com a de baixo.
  4. Com IA, as pastas dizem onde cada coisa vai e deixam verificar cada passo.
