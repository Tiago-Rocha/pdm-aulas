Analogia Três sítios numa casa. A gaveta da cozinha (shared_preferences) guarda coisas pequenas e pouco importantes, à mão. Deixar o token na gaveta é deixar a chave de casa debaixo do tapete.

Sandbox: onde ficam os ficheiros da app

  • Cada app tem a sua pasta privada. Outra app não a lê; o utilizador não a vê sem root. Android: /data/data/<package>/; iOS: Documents/, Library/, tmp/.
  • path_provider abstrai isto: getApplicationDocumentsDirectory() persiste e vai para o backup; getApplicationSupportDirectory() persiste sem aparecer ao utilizador; getTemporaryDirectory() pode ser limpa pelo sistema.
  • Atualizações mantêm tudo menos o temporário. Desinstalar apaga tudo, com uma exceção: o Keychain do iOS fica.
  • Backup: o iCloud copia Documents/; o Android Auto Backup copia até 25 MB. Cache e tokens devem ficar de fora (android:fullBackupContent, isExcludedFromBackup).
  • Exemplo: um jogo guarda o progresso em Documents (vai no backup) e as texturas descarregadas em Support (não vai, descarrega outra vez).

Para os testes: Documents persiste e vai no backup; tmp pode desaparecer a qualquer momento.

Keychain e Keystore: porque um token nunca vai para preferências

  • shared_preferences é um ficheiro XML (Android) ou plist (iOS) em texto. Num telemóvel com root lê-se com cat; nos backups vai em claro.
  • Keychain (iOS): cifrado com uma chave ligada ao hardware (Secure Enclave). Pode exigir o dispositivo desbloqueado. Sobrevive à desinstalação: cuidado com sessões fantasma.
  • Keystore (Android): as chaves vivem em hardware (TEE ou StrongBox) e nunca saem. flutter_secure_storage cifra os valores com AES e guarda a chave AES no Keystore.
  • Regra: token, refresh token, chaves do utilizador vão para secure storage. Nunca para preferências, nunca para a base de dados em claro.
  • Limite: quem tem o telemóvel desbloqueado tem acesso à app. Protege contra backups, outras apps, e ferramentas de extração.

Para os testes: um token nunca vai para shared_preferences; vai para Keychain ou Keystore via flutter_secure_storage.

Demonstração de 2 minutos que vale a matéria toda: com adb num emulador, `adb shell run-as com.exemplo.app cat shared_prefs/FlutterSharedPreferences.xml` e aparece tudo em claro. Depois o mesmo para o ficheiro do secure storage: lixo cifrado.

Por baixo do capô: um package, uma implementação por plataforma

  • Os dois são plugins federados: o package que pões no pubspec.yaml só tem a API em Dart. Puxa sozinho um package por plataforma (shared_preferences_android, shared_preferences_foundation, shared_preferences_web...).
  • O Dart não fala com o Keychain nem com o Keystore. Manda uma mensagem pelo canal de plataforma e o código nativo (Kotlin, Swift) responde. Por isso tudo é Future, e por isso o main chama WidgetsFlutterBinding.ensureInitialized() antes do primeiro plugin.
  • O mesmo write faz coisas muito diferentes: no Android cifra com uma chave guardada no Keystore; no iOS entrega ao Keychain; na web cifra com WebCrypto e guarda no browser, o que é bem menos seguro.
  • Um plugin novo ou mudado exige parar e voltar a correr a app. O hot reload não recompila Kotlin nem Swift.

Para os testes: o package dá uma só API; quem guarda de facto é o sistema de cada plataforma, através do canal de plataforma.

Se perguntarem porque o Chrome serve para a aula: serve para ver o fluxo, mas a segurança real só se vê no telemóvel ou no emulador. MissingPluginException quase sempre quer dizer que adicionaram o package com a app a correr: q e flutter run outra vez.

Cache-first, network-first, invalidação e migrações

EstratégiaFluxoQuando
Cache-firstMostra a cache, pede à rede em fundo, atualizaPrevisões, listas: rapidez percebida
Network-firstPede à rede; se falhar, mostra a cacheDados críticos que mudam: saldo, stock
Cache-only / Network-onlyNunca vai à rede / nunca guardaMapas descarregados / pagamentos
  • Invalidação por tempo: guarda obtidoEm e compara: previsão válida 30 min, avisos 5 min, localidades 24 h.
  • Migrações: a versão 1.2 da app muda a tabela, mas há utilizadores na 1.0 com a base antiga. schemaVersion + MigrationStrategy no drift; nunca apagar dados do utilizador sem aviso.

Para os testes: cache-first mostra rápido e atualiza depois; network-first garante dados frescos; a invalidação por tempo decide quando a cache expira.

Analogia O frigorífico. Mostra-se já o que há no frigorífico, com a data no rótulo (obtidoEm), e entretanto vai-se às compras (o pedido à rede em fundo); quando se volta, substitui-se o que lá estava. Sem rede, come-se o que há, e o rótulo diz de quando é. A validade no rótulo é a invalidação por tempo: dentro do prazo não se vai às compras.

Do ecrã ao cofre: o login em camadas

  1. O ecrã valida o formulário e chama login(email, password). Não espera pela resposta: desenha o que o notifier disser.
  2. O notifier liga o isLoading e pede ao AuthRepository.
  3. O repository faz o pedido pelo ApiClient.
  4. A resposta volta em JSON e o repository transforma-a numa Session.
  5. O notifier guarda o refresh token no SessionStore, que o entrega ao Keychain ou ao Keystore.
  6. Só depois põe a sessão no estado e chama notifyListeners. O main vê a sessão e troca o login pelas ilhas.
E com BLoC? O SessionNotifier passava a ser um Cubit<SessionState>: os mesmos passos, com emit(...) em vez de notifyListeners() e um estado imutável em vez de campos soltos. Repository e store ficam iguais. É isso que as camadas compram: muda-se a gestão de estado sem tocar nos dados.
Desenha isto no quadro antes de abrir o código: é o mapa para os três passos. A pergunta que vale a pena fazer: se amanhã o token passar para outro sítio, que ficheiros mudam? Resposta: só o SessionStore.

Um ecrã, quatro camadas: as ilhas

  1. models/: a classe com fromJson, só com o que a app usa.
  2. data/: o repository que pede à API pelo ApiClient e devolve modelos.
  3. state/: o notifier com carregamento, erro e dados.
  4. screens/: o ecrã que desenha o estado e chama o notifier.
  5. main.dart: cria as peças e liga-as com o Provider.
É a receita para cada requisito: avisos, trilhos e relatos são estes cinco passos. No repositório da aula está esta mesma pilha, com uma lista mais simples; o ecrã do projeto é este do Figma.

Para escrever, o mesmo caminho: os favoritos

  1. Toque no coração: o ecrã chama toggle('pico') e mais nada.
  2. O notifier muda já a lista e notifica: o coração enche antes de a API responder.
  3. O repository faz PUT (ou DELETE) com o token do utilizador.
  4. Se falhar, o notifier volta atrás e guarda o erro: o coração esvazia e aparece a mensagem, como no ecrã "Favorito sem rede" do Figma.
O token do utilizador nos pedidos é amanhã. Hoje fica a ideia: o ecrã não espera pela API para mudar o coração, e o notifier sabe desfazer.

Criar conteúdo: um relato com fotografia

  1. A fotografia vem do image_picker, outro plugin com uma implementação por plataforma. O ecrã guarda só o ficheiro escolhido.
  2. Publicar valida no ecrã (texto até 500 caracteres) e chama publish(...). Enquanto isSending, o botão fica desligado.
  3. O repository envia em multipart: os campos e a fotografia no mesmo pedido.
  4. Correu bem: o notifier põe o relato no topo do feed e o ecrã fecha. Falhou: o texto e a fotografia ficam e aparece o erro, como no ecrã "Erro ao publicar" do Figma.

AuthRepository: o pedido de login

class AuthRepository {
  AuthRepository(this._api); // injected, not created here

  final ApiClient _api;

  Future<Session> login(String email, String password) async {
    final json = await _api.post('/v1/auth/login', {
      'clientId': _api.clientId,
      'clientSecret': _api.clientSecret,
      'email': email,
      'password': password,
    });
    return Session.fromJson(json as Map<String, dynamic>);
  }
  • A app identifica-se com clientId e clientSecret; a pessoa com email e password. O register é igual, com mais o name.
  • A resposta traz o accessToken (15 min), o refreshToken (30 dias) e o user. Session.fromJson lê os três, em lib/models/user.dart.

SessionNotifier: quem está com sessão

  Future<void> login(String email, String password) =>
      _start(() => _auth.login(email, password));

  Future<void> register(String name, String email, String password) =>
      _start(() => _auth.register(name, email, password));

  Future<void> _start(Future<Session> Function() request) async {
    isLoading = true;
    error = null;
    notifyListeners();
    try {
      final s = await request();
      await _store.save(s.refreshToken); // before the UI knows
      session = s;
    } on ApiException catch (e) {
      error = e.message; // the API already writes it in Portuguese
    } catch (_) {
      error = 'Sem ligação. Tenta de novo.';
    } finally {
      isLoading = false;
      notifyListeners();
    }
  }
}
  • Login e registo partilham o _start: liga o spinner, faz o pedido, guarda a sessão ou o erro, desliga o spinner.
  • O refresh token vai para o cofre antes de a UI saber que há sessão.
  • As mensagens de erro da API já vêm em português ("Email ou password errados."). Sem rede, a nossa.

SessionStore: o refresh token no cofre

import 'package:flutter_secure_storage/flutter_secure_storage.dart';

/// The refresh token, in the Keychain (iOS) or the Keystore (Android).
/// Never in shared_preferences: it is a password that lasts 30 days.
class SessionStore {
  const SessionStore([this._storage = const FlutterSecureStorage()]);

  final FlutterSecureStorage _storage;
  static const _key = 'refreshToken';

  Future<String?> read() => _storage.read(key: _key);

  Future<void> save(String refreshToken) =>
      _storage.write(key: _key, value: refreshToken);

  Future<void> clear() => _storage.delete(key: _key);
}
  • Guarda-se o refresh token, não o access token: este dura 15 minutos e um novo sai do refresh.
  • A classe esconde o package: se amanhã o token mudar de sítio, só este ficheiro muda.

Ao arrancar: restore()

  Future<void> restore() async {
    try {
      final saved = await _store.read();
      if (saved != null) session = await _auth.refresh(saved);
    } on ApiException {
      await _store.clear(); // expired, logged out or account deleted
    } catch (_) {
      // offline: show the login, keep the token for the next start
    } finally {
      isRestoring = false;
      notifyListeners();
    }
  }
  • Com um token guardado, pede uma sessão nova a POST /v1/auth/refresh. Se a API recusar (expirou, logout, conta apagada), apaga-o.
  • Sem rede, guarda o token para a próxima vez. Enquanto isRestoring, o _Home mostra um spinner em vez do login.
  • No logout, o token sai do cofre e a API revoga-o.

Settings: o último email e o tema

class Settings extends ChangeNotifier {
  Settings(this._prefs);

  final SharedPreferences _prefs;

  static Future<Settings> load() async =>
      Settings(await SharedPreferences.getInstance());

  String get lastEmail => _prefs.getString('lastEmail') ?? '';

  // Enums are saved by name, never by index.
  ThemeMode get theme =>
      ThemeMode.values.byName(_prefs.getString('theme') ?? 'system');

  Future<void> saveLastEmail(String email) =>
      _prefs.setString('lastEmail', email);

  Future<void> saveTheme(ThemeMode mode) async {
    await _prefs.setString('theme', mode.name);
    notifyListeners(); // MaterialApp rebuilds with the new theme
  }
}
  • Leitura síncrona depois do getInstance(), escrita assíncrona.
  • Enums guardam-se pelo name e lêem-se com values.byName. Pelo índice, reordenar o enum estragava o que estava guardado.

Carregar antes do runApp

void main() async {
  WidgetsFlutterBinding.ensureInitialized(); // before any plugin
  final settings = await Settings.load();
  // ...
}
  • ensureInitialized() liga o motor do Flutter ao canal de plataforma. Sem ele, o primeiro plugin falha no main.
  • Carrega-se antes do runApp porque o tema tem de estar certo no primeiro frame.
  • O email não é segredo, mas a password é: essa nunca se guarda, nem aqui nem no cofre.

Projeto: Tempo Açores

O enunciado completo está em Projeto e a API em API. O essencial:

  • Uma app de tempo e trilhos para os Açores, por grupo, até ao fim do semestre. Todos os dados passam pela API do curso, incluindo os do IPMA.
  • Cada grupo tem uma app na API (clientId e clientSecret do grupo). Cada pessoa tem a sua conta dentro dessa app: registo, login, sessão, favoritos e relatos.
  • Sprints de duas semanas. A primeira acaba na segunda, 2 de novembro, às 16:00: registo e login com a sessão guardada, ilhas com pesquisa e previsão, camadas e estados.
  • Trabalho por pull request: um branch por tarefa, revisão de um colega, merge no main.
Percorre o enunciado no ecrã: requisitos mínimos, extras, sprints e avaliação. Não leias tudo; mostra onde está.

O design é o do Figma

  • Os ecrãs, o mapa da app, os fluxos e o design system estão no ficheiro do Figma: cores, tipografia, espaços e 25 componentes, cada um com medidas, estados e o código Flutter de referência.
  • Na página Mapa e fluxos, cada requisito do enunciado (R1, R2...) aponta para os ecrãs e os endpoints que o cumprem.
  • A app segue esse design, e isso faz parte da avaliação: cores e tipos certos, componentes iguais, estados (carregamento, erro, vazio) como estão desenhados.
Mostra a página Ecrãs, depois o Mapa e fluxos com a tabela dos requisitos, e por fim um componente, por exemplo o Botão, com a ficha completa.

Credenciais do grupo

  • Estão na issue #1 do repositório do grupo. São do grupo, não de uma pessoa.
  • Vão na linha de comandos, como as tuas. Nunca no código, nunca no git:
flutter run -d chrome --dart-define=CLIENT_ID=pdm-group \
  --dart-define=CLIENT_SECRET=group-secret

As contas criadas com as tuas credenciais não existem na app do grupo. No projeto, cada membro cria a sua conta outra vez, já na app do grupo.

Por onde começar

  1. Ler o enunciado e o Figma em grupo e dividir a sprint 1 em issues no repositório.
  2. O login primeiro: as camadas que vimos hoje, com o ecrã "Entrar" e o "Criar conta" do Figma.
  3. Em paralelo: a lista das ilhas com pesquisa e a previsão, noutro branch.
  4. Cada tarefa num branch e num pull request com uma captura do ecrã; outro membro revê e faz merge.
Ninguém faz commit direto no main. O código do repositório da aula pode ir para o projeto, mas o ecrã tem de seguir o Figma.

Onde ficámos

  1. Valores pequenos em preferências, dados que se consultam numa base local, segredos no Keychain ou no Keystore.
  2. Os packages têm uma API em Dart e uma implementação nativa por plataforma, ligadas pelo canal de plataforma.
  3. O login em camadas: ecrã, notifier, repository e store. O refresh token vai para o cofre antes de a UI saber.
  4. O projeto arrancou: enunciado, Figma e credenciais do grupo.

Amanhã: o access token nos pedidos (Authorization: Bearer), a renovação automática quando a API responde 401 e os favoritos guardados na conta.
