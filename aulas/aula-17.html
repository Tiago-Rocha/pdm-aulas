Autenticação com token e favoritos sincronizados

Teoria: autenticação em mobile: OAuth2 e OpenID Connect, JWT, tokens de acesso e refresh, biometria. Prática: favoritos guardados na conta de cada pessoa, com o token do utilizador, a renovação em 401 e a UI otimista.

Repositório: pdm-aula-17
Abre o jwt.io no projetor com um token de utilizador da API do curso colado (faz login no repositório da aula e copia-o do DevTools, separador Network, cabeçalho Authorization de um pedido aos favoritos): o payload aparece em claro, com o teu nome. É o gancho para os slides do JWT. O access token dura 15 minutos; na prática há um botão que o estraga, para o 401 aparecer sem esperar.

No fim desta aula consegues

  • Distinguir autenticação de autorização, e um 401 de um 403.
  • Ler um JWT e explicar cabeçalho, payload, assinatura e expiração.
  • Descrever o fluxo authorization code com PKCE e o papel do refresh token.
  • Enviar o token certo em cada pedido e renovar a sessão em 401, repetindo o pedido uma vez.
  • Guardar favoritos na conta, com UI otimista e rollback em caso de erro.

Autenticação vs autorização; cookies vs tokens

  • Autenticação: quem és (login, biometria, chave). Autorização: o que podes fazer (ler os teus favoritos, não os dos outros).
  • 401 Unauthorized = não sei quem és: token em falta ou expirado. 403 Forbidden = sei quem és, mas não podes.
  • Na web: sessão guardada no servidor e um cookie que o browser envia sozinho em cada pedido. O risco típico é CSRF.
  • Em mobile: não há browser a gerir cookies. A app guarda um token e envia-o explicitamente em Authorization: Bearer ….
  • Um token assinado é stateless: o servidor valida a assinatura sem ir à base de dados. Escala melhor; revogar é mais difícil.

Para os testes: 401 é autenticação, 403 é autorização; em mobile usam-se tokens Bearer, não cookies.

JWT (1 de 2): o que tem dentro

  • Três partes em base64url separadas por pontos: header.payload.signature.
  • Header: {"alg":"HS256","typ":"JWT"}. Payload: as claims: sub (quem), iss (quem emitiu), iat e exp (quando), e claims próprias de cada API.
  • Signature: HMAC (chave partilhada) ou RSA/ECDSA (par de chaves) sobre o header e o payload.

  • Base64 não é cifra: qualquer pessoa lê o payload. A app pode ler exp para saber que vai expirar sem fazer um pedido.

Para os testes: JWT = header.payload.signature; o payload é legível por todos, não é secreto.

JWT (2 de 2): assinatura, expiração e o que nunca lá vai

  • A assinatura garante integridade: se alguém mudar o uid para o de outra pessoa, a assinatura deixa de bater e o servidor rejeita.
  • Só o servidor valida. Com HS256 o cliente não tem a chave; com RS256 poderia validar com a chave pública, mas não precisa.
  • exp curto (15 min a 1 h): um token roubado vale pouco tempo. Sem exp é um token eterno, e isso é um bug de segurança.
  • Nunca no JWT: passwords, dados pessoais sensíveis, segredos. Vai em claro, em cada pedido, e acaba em logs.
  • Ataques reais do passado: "alg":"none" aceite pelo servidor, e chaves HS256 fracas quebradas por força bruta. Bibliotecas atuais rejeitam ambos.

Para os testes: a assinatura dá integridade, não confidencialidade; nunca se põem dados sensíveis num JWT.

Analogia Uma pulseira de festival. Diz quem és e até quando vale, e tem a assinatura do organizador; qualquer porteiro a verifica à porta sem telefonar à bilheteira (o servidor valida a assinatura sem ir à base de dados). Quem tentar alterar a data estraga a assinatura. E não se escreve nela nada que não se queira que todos leiam: a pulseira está à vista de toda a gente.
Pergunta: "se o payload é legível, porque é que não posso mudar o exp para daqui a um ano?" Deixa-os chegar à assinatura sozinhos. Depois: "e se o servidor não verificar a assinatura?" É o ataque alg none.

OAuth2 e OIDC em traços largos: authorization code + PKCE

  • O problema: a app quer aceder ao calendário Google do utilizador sem alguma vez conhecer a password do Google.
  • OAuth2 é autorização delegada: a app abre o browser do sistema, o utilizador entra no Google, o Google devolve um code por deep link, e a app troca o code por tokens.
  • PKCE: a app gera um code_verifier aleatório e envia o seu hash (code_challenge). Só quem tem o verifier troca o code. Obrigatório em apps móveis, porque não têm onde guardar um client secret.
  • OIDC = OAuth2 + identidade: devolve também um id_token (JWT) que diz quem é o utilizador. É o "Entrar com Google".
  • Em Flutter: flutter_appauth ou o SDK de cada fornecedor. Sempre Custom Tabs / ASWebAuthenticationSession, nunca um webview próprio (o utilizador não deve escrever a password dentro da tua app).

Para os testes: apps móveis não guardam passwords nem client secrets; usam authorization code com PKCE no browser do sistema.

Access token curto, refresh token longo, logout

Access tokenRefresh token
DuraçãoMinutos a uma horaDias a meses

Onde guardarMemória; secure storage se tiver de sobreviver ao arranqueSecure storage, sempre

  • Renovação: em 401, pede um access novo com o refresh e repete o pedido original uma vez. Se o refresh também falhar, logout.
  • Logout: apagar os dois do dispositivo, revogar o refresh no servidor, limpar a cache com dados do utilizador. Na API do curso, POST /v1/auth/logout revoga o refresh token.

Para os testes: access curto em cada pedido; refresh longo em secure storage, só para renovar; logout apaga ambos.

Analogia O access token é a pulseira do festival: mostra-se a cada porteiro e vale poucas horas. O refresh token é o bilhete que se troca por uma pulseira nova quando a antiga expira, sem voltar à fila da bilheteira (sem novo login). O bilhete fica guardado no bolso interior (secure storage) e só se mostra no balcão de troca; perdê-lo é grave, porque quem o tiver pode ir buscar pulseiras novas.

Biometria e Sign in with Apple

  • local_auth: Face ID, Touch ID, impressão digital. Devolve só "sim" ou "não" à app. Nunca fala com o servidor.
  • Uso certo: desbloqueio local. A app do banco já tem sessão (refresh token guardado); a biometria decide se a app o pode usar agora.
  • Uso errado: "autenticar no servidor com a biometria". O servidor nunca vê a biometria; se o refresh token não existir, a biometria não cria sessão nenhuma.
  • Sign in with Apple é obrigatório na App Store se a app oferece outro login social (Google, Facebook). Inclui email de relay para quem não quer dar o seu.
  • Passkeys (WebAuthn): a próxima etapa. Sem passwords, chave privada no dispositivo, desbloqueada por biometria. Já suportadas no Android e no iOS.

Para os testes: a biometria desbloqueia localmente; a autenticação no servidor continua a ser feita pelo token.

Dúvida frequente: "posso guardar a password no secure storage e usar a biometria para a reenviar?" Tecnicamente sim, é o que algumas apps antigas fazem, mas viola o princípio: a app não devia ter a password. Refresh token é a resposta.

Pergunta à turma Com o token da app, a lista das ilhas aparece e os favoritos dão 403. Porque não dá 401?
Respostas às perguntas. 401 seria "não sei quem és". Aqui o token é válido e a API sabe quem pede: a app. Só que os favoritos são de uma pessoa, e o token da app não diz que pessoa. Sei quem és, mas não podes: 403. É o slide da autenticação e da autorização, com um caso que vão ver no ecrã daqui a pouco.

Hoje, na app

  1. O token do utilizador nos pedidos: os favoritos passam a funcionar.
  2. A hora a que a sessão expira, lida de dentro do JWT.
  3. Em 401, um access token novo com o refresh token, e o pedido repete-se uma vez.
  4. O coração muda logo, sem esperar pela API, e volta atrás se ela falhar.
Quatro passos pequenos, cada um com uma mudança que se vê no ecrã. Se faltar tempo, o passo 2 é o que se corta: os outros não dependem dele. O passo 1 é uma linha e resolve o 403: é a vitória rápida do início.

1. Que token vai em cada pedido

Passo 1: o token do utilizador

Future<http.Response> _request(String method, String path) async {
  // the user's token when someone is logged in; otherwise, the app's
  final token = userToken ?? (_token ??= await _fetchToken());
  final request = http.Request(method, Uri.parse('$baseUrl$path'))
    ..headers['Authorization'] = 'Bearer $token';
  final streamed = await request.send().timeout(const Duration(seconds: 10));
  return http.Response.fromStream(streamed);
}

/// When the access token expires. The payload is the middle part of
/// the JWT, in base64: anyone can read it, no key needed.
DateTime get expiresAt {
  final payload = accessToken.split('.')[1];
  final text = utf8.decode(base64Url.decode(base64Url.normalize(payload)));
  final exp = (jsonDecode(text) as Map<String, dynamic>)['exp'] as int;
  return DateTime.fromMillisecondsSinceEpoch(exp * 1000); // seconds
}
  • split('.')[1]: o payload é a parte do meio de header.payload.signature.
  • base64Url.normalize repõe os = que o JWT tira do fim; utf8.decode e jsonDecode dão o mapa das claims.
  • exp vem em segundos; o DateTime quer milissegundos.
Faz Cola o getter em Session e acrescenta import 'dart:convert'; no topo do ficheiro.
Nenhuma chave foi precisa para ler o payload: é o slide do JWT a acontecer no código. A app lê o exp para mostrar; quem decide se o token vale é sempre o servidor, pela assinatura. Erro típico: esquecer o import do dart:convert (o base64Url fica a vermelho).

3. Em 401, renovar e repetir uma vez

  1. Um pedido sai com o access token. A resposta é 401: o token expirou.
  2. O ApiClient pede à sessão um access token novo: POST /v1/auth/refresh com o refresh token guardado.
  3. Se correu bem, repete o mesmo pedido, com o token novo. O utilizador não deu por nada.
  4. Se o refresh também falhar, o pedido falha com o 401 que já tinha. Nada de tentar outra vez.
  • O ApiClient não conhece a SessionNotifier: recebe uma função, renewSession, e quem a liga é o main.dart. As camadas continuam a só conhecer a de baixo.
  • Cada pedido é um http.Request novo: um pedido só pode ser enviado uma vez. Por isso o _request é chamado duas vezes.
Pergunta à turma Porque é que se repete só uma vez, e não até dar certo?
Respostas às perguntas. Se o refresh token também já não vale (logout noutro telemóvel, conta apagada, 30 dias passados), cada repetição volta a dar 401: a app ficava presa num ciclo de pedidos. Uma vez chega para o caso normal, que é o access token ter expirado. É o mesmo interceptor que o dio tem pronto; aqui fica à mão para se ver.

  var response = await _request(method, path);

Passo 3 (2 de 2): a sessão renova

/// After a 401: a new access token, from the refresh token.
Future<bool> renew() async {
  final current = session;
  if (current == null) return false;
  try {
    session = await _auth.refresh(current.refreshToken);
    notifyListeners(); // "Sessão até" moves on
    return true;
  } catch (_) {
    return false; // the request fails with the 401 it got
  }
}
api.renewSession = session.renew; // on a 401, the ApiClient asks here

4. UI otimista

  • Pessimista (o ponto de partida): toca, espera pela API, só depois muda o coração. Numa rede lenta, um segundo sem resposta: o utilizador toca outra vez.
  • Otimista: muda o coração já, envia o pedido e, se falhar, volta atrás e diz porquê.
  • Funciona porque quase todos os pedidos correm bem, e porque o PUT e o DELETE dos favoritos podem repetir-se sem estragar nada.
  • Não serve para tudo: um pagamento ou um envio de um relato esperam pela resposta.
Pergunta à turma O coração ficou vermelho e a API respondeu 500. O que vê o utilizador, e o que tem de acontecer ao estado?
Respostas às perguntas. Vê o coração voltar a vazio e o aviso com o erro. O estado tem de voltar a ser o que era antes do toque: senão a app mostra uma coisa e o servidor tem outra. É o rollback. Exemplos de apps que conhecem: o gosto do Instagram, a mensagem do WhatsApp com o relógio antes do visto.

/// The heart changes at once. If the API fails, it goes back.
Future<void> toggle(String islandId) async {
  final adding = !isFavorite(islandId);
  _mark(islandId, adding);
  error = null;
  notifyListeners(); // the heart changes now, before the API answers
  try {
    if (adding) {
      await _repository.add(islandId);
    } else {
      await _repository.remove(islandId);
    }
  } catch (e) {
    _mark(islandId, !adding); // undo
    error = _message(e);
    notifyListeners();
  }
}

void _mark(String islandId, bool favorite) {
  if (favorite) {
    ids.add(islandId);
  } else {
    ids.remove(islandId);
  }
}

Na app: no DevTools do Chrome (F12), separador Network, escolhe Slow 4G: o coração já não espera. Com Offline, fica como estava e o aviso diz "Sem ligação".

O notifyListeners() antes do try é o que faz o coração mudar logo. O segundo, no catch, é o do rollback. Sem rede, o pedido falha em milissegundos: o coração muda e volta antes de se ver, por isso mostra primeiro com Slow 4G e só depois com Offline. Num telemóvel, o modo de avião faz o mesmo. Se faltar tempo, este passo mostra-se no projetor com git checkout passo-4.

Onde ficámos

  1. O _request manda o token do utilizador quando há sessão, e o da app quando não há (passo 1).
  2. O exp lê-se do payload do JWT sem chave nenhuma: base64, não cifra (passo 2).
  3. Em 401, o ApiClient pede à sessão um access token novo com o refresh token e repete o pedido uma vez (passo 3).
  4. O coração muda antes da resposta e volta atrás se a API falhar (passo 4).
