Ephemeral state vs app state

Ask the class What about other apps? The cart in an online shop, the selected tab in a tab bar, the signed-in user, the half-typed text of a message: which is which?

For the tests: ephemeral state stays in the widget with setState; app state lives outside the tree and is shared.

Answers to the questions. Cart: app state, it shows on the top icon, in the product list and at checkout, and it has to survive navigation. Selected tab: ephemeral, only the tab bar cares (but if the app saves it on close, it becomes app state: the line is a design decision). Signed-in user: app state, almost every screen needs it. Half-typed message: ephemeral, it belongs to the text box; in a chat app that saves drafts, it becomes app state. On our screen the diagram already shows it: card open and search text are ephemeral, the °C/°F unit is app state. Today we do all three with setState, and the unit will show where that starts to cost.

The problem with passing by parameter

  • On our screen, the °C/°F unit will be chosen in the AppBar of ForecastScreen and used in CurrentConditions, in DetailCard and in DayChip, which sits inside DaysRow.
  • With setState alone, the variable has to live in the common ancestor (ForecastScreen) and travel down by parameter, constructor by constructor. DaysRow ends up receiving the unit only to hand it to DayChip. In a bigger app it is five or six levels: this is called prop drilling.
  • Every widget in between now depends on something that is not its own. Adding a new field means touching every constructor along the way.
  • And when the unit changes, setState in ForecastScreen rebuilds the whole screen, not just the texts with temperatures.

The answer to this problem is why state management libraries exist. They all solve the same thing: put the state somewhere reachable and rebuild only whoever reads it.

Go back to the question on the board: who needs to know about the unit? Draw the tree: WeatherApp → ForecastScreen → ListView → CurrentConditions, DaysRow → DayChip, DetailCard. In step 2 they only do CurrentConditions, and the days row stays in °C on purpose: it is the cost from this slide, in plain sight.

setState: when it is enough and when it stops being enough

  • Enough when the state belongs to one screen or one widget and nobody else needs it: a counter, a form, a card that opens and closes, a local search filter.
  • Enough for prototypes and isolated screens. It is not "bad practice"; it is the simplest tool and Flutter was designed for it.
  • Not enough when two unrelated screens need the same data, when the state must survive navigation, or when you want to test the logic without building widgets.
  • Not enough when build rebuilds a large tree because of one boolean.

For the tests: setState marks the widget as dirty and schedules a rebuild of its subtree on the next frame. It does not rebuild the whole app, but it rebuilds everything below.

ChangeNotifier, Provider and InheritedWidget

  • InheritedWidget is Flutter's own mechanism to put a value in the tree and let any descendant read it through context. The Theme.of(context) we use in every build is exactly this.
  • ChangeNotifier is a class with notifyListeners(). Your state extends it: class UnitSettings extends ChangeNotifier { bool fahrenheit = false; void toggle() { fahrenheit = !fahrenheit; notifyListeners(); } }.
  • Provider combines the two: it puts the notifier in the tree, and context.watch<UnitSettings>() rebuilds only the widget that called it when notifyListeners fires.
  • It solves the problem on the previous slide: DayChip reads the unit directly; DaysRow does not even know it exists.
  • The Flutter team recommends it to start with, and it is what we will use in the project.

For the tests: Provider is an InheritedWidget with sugar; ChangeNotifier tells its listeners; watch rebuilds, read does not.

BLoC, Cubit and Riverpod

ApproachWhat it addsWhen it makes sense
setStateNothing: it is Flutter's ownIsolated screen, few widgets, prototypes
Provider + ChangeNotifierAn observable object in the tree; watch rebuilds only readersSeveral screens share state; small teams; our project
BLoC / CubitImmutable states in a Stream; every transition predictable and testable; more filesLarge teams, strong testing requirements, banking apps
RiverpodGlobal, typed providers, no BuildContext; errors caught at compile timeThose who already know Provider and want more safety

Underneath they all do the same thing: an object that holds state and tells whoever is watching. The difference is in the ceremony and the guarantees.

Analogy Where the shopping list goes. A sticky note on a fridge in one bedroom: only people who go into that room see it (setState). A board in the kitchen that the whole house checks and that tells you when it changes (ChangeNotifier with Provider). A logbook with every change, dated and signed (BLoC: events and states). The board is enough for most homes.

Unidirectional flow and immutability

  • One direction: the UI triggers an action (tap, text) → the action changes the state → the UI rebuilds from the new state. The UI never changes the state directly and the state never touches the UI.
  • With one direction, any screen is a function of the state: same state, same screen. That is what makes testing and debugging possible.
  • Immutable: instead of changing a field of a DayForecast, you create a new one with copyWith. An object nobody changes can be shared, compared and kept in a history without surprises. The final fields of DayForecast in lib/data.dart are already this.
  • The UnitSettings from the previous slide is mutable inside (it is a ChangeNotifier), but what it exposes are values. BLoC and Riverpod take immutability all the way.

For the tests: unidirectional flow is action → state → UI; immutability means creating copies with copyWith instead of changing objects.

How to choose, and what we will use

  • How many screens share the state? One: setState. Several: Provider or beyond.
  • Do you need to test the logic without widgets? Then the logic has to live outside the widgets: Provider, BLoC or Riverpod.
  • Team and project size. Three people and 10 screens: Provider. Twenty people and 200 screens: BLoC or Riverpod, for the rules they enforce.
  • What the team already knows weighs more than what is fashionable.
  • In the project we use setState for ephemeral state and Provider with ChangeNotifier for the rest: it is simple, it is what Flutter's architecture guide recommends, and it can grow into BLoC later without a rewrite.
Today only setState. Provider comes in lesson 13, when we have API data to share.

1. StatelessWidget vs StatefulWidget

class DetailCard extends StatefulWidget {
  const DetailCard({super.key});

  @override
  State<DetailCard> createState() => _DetailCardState();
}

class _DetailCardState extends State<DetailCard> {
  bool _expanded = false;

  @override
  Widget build(BuildContext context) {
    // ... the build from before, which can now read and change _expanded
  }
}
  • The widget is still immutable. What changes is the State object, which Flutter creates once and keeps alive between rebuilds. That is why hot reload does not lose what is on screen.
  • setState(() { ... }) does two things: it runs the change and marks the widget to rebuild on the next frame. Changing the variable without setState changes the value, but the screen does not follow.
  • Only this widget's subtree is rebuilt. The lower the StatefulWidget sits, the less work.
Ask the class Why does _expanded live in _DetailCardState and not in DetailCard? What happens if you do _expanded = !_expanded without setState?
Answers to the questions. DetailCard is recreated on every rebuild of its parent (and it has a const constructor: its fields are final), so it cannot keep anything that changes. The State is created once and Flutter reuses it while the widget stays in the same place in the tree. Without setState the variable changes, but nobody asks for a new build: the screen stays the same until something else rebuilds it (a hot reload, for example, and then it "suddenly appears"). Worth showing live.

2. Lifting state up: the °C/°F unit

  • The unit is not one widget's: CurrentConditions shows temperatures, but the button to choose it sits in the AppBar, which belongs to ForecastScreen.
  • The setState rule: state lives in the closest common ancestor of whoever changes it and whoever shows it. Here that is ForecastScreen, which becomes a StatefulWidget.
  • Whoever only shows it receives the value as a parameter, in a final field, the way DayChip receives its forecast. It keeps nothing.
  • SegmentedButton is a controlled widget: it shows what is in selected and reports in onSelectionChanged. Switch, Checkbox and Slider work the same way.
Ask the class After this step, CurrentConditions shows °F. What about the days row and the detail card? What would we have to change for DayChip to show °F as well?
Answers to the questions. The days row and DetailCard stay in °C: they do not receive the unit. For DayChip to show °F you would add fahrenheit to the DaysRow constructor, pass it in ForecastScreen, add it to the DayChip constructor and pass it in the itemBuilder: two constructors changed, and DaysRow receives a value it does not use. That is the prop drilling from the theory slide, and exactly what Provider solves in lesson 13. It is left undone in the repository on purpose; early finishers can do it.

3. The State lifecycle

late final TextEditingController _search;

@override
void initState() {
  super.initState(); // once, before the first build
  _search = TextEditingController();
}

@override
void dispose() {
  _search.dispose(); // what initState creates, dispose frees
  super.dispose();
}
MethodWhen it runsWhat for
initStateOnce, when the State is createdCreate controllers, subscribe to streams, fire the first request
buildWhenever drawing is neededOnly describe the UI. No network requests here
didUpdateWidgetWhen the parent rebuilds with new parametersReact to a parameter that changed (a new location selected)
disposeOnce, when the widget leaves the treeRelease controllers, timers, subscriptions, focus nodes
Ask the class Why can the controller not be created inside build? And what happens if you forget dispose?

For the tests: whatever you create in initState you release in dispose; build can run many times and must have no side effects.

Answers to the questions. build runs on every setState, that is, on every key press: a new controller on each build loses the typed text and the cursor, and the box seems to "refuse" letters. Without dispose the controller stays in memory with its listeners after the screen is gone: a memory leak, invisible today but piling up in an app that opens and closes screens. late final tells Dart the field is filled once, later (in initState). If asked: there is also didChangeDependencies, which runs after initState and when an InheritedWidget (theme, locale) changes; it is where you read Theme.of if you need it outside build.

3. TextField and search: what matters

  • The TextEditingController holds the box's text. You need it to read the text somewhere else, clear it (X button) or set an initial value. And then, dispose.
  • onChanged runs on every key press. As the text is already in the controller, you only need to ask for a rebuild: setState(() {}).
  • The filtered list is a getter computed from the state. Do not store the filtered list as state: that is two values that can drift apart.
  • Filtering nine islands on every key press is instant. Filtering 100,000, or calling the API, means waiting for the user to stop typing (debounce, with a Timer).
  • InputDecoration controls the look: prefixIcon, suffixIcon, hintText, labelText, border and error text.

4. Form, TextFormField and validation

final _formKey = GlobalKey<FormState>(); // a field, never inside build
final _email = TextEditingController();

void _submit() {
  // validate() runs every validator and shows the errors
  if (_formKey.currentState!.validate()) {
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('Avisos enviados para ${_email.text}')),
    );
  }
}

child: Form(
  key: _formKey,
  • Form groups fields; the GlobalKey<FormState> gives the button access to the form. It is one of the few legitimate uses of GlobalKey.
  • Each TextFormField has a validator that returns the error message, or null if the value is fine. validate() runs them all, shows the errors under the fields and returns true if none failed.
  • autovalidateMode: AutovalidateMode.onUserInteraction validates each field while the user types in it. Without it, validation only happens on submit.
  • keyboardType: TextInputType.emailAddress and textInputAction: TextInputAction.next change the phone keyboard. On mobile, that is UX.
Ask the class Today, with no validators, what does "Subscrever" do with empty fields? Why does validate() return true?

For the tests: a validator returns null when the value is valid and a String with the error when it is not.

Answers to the questions. It shows the SnackBar "Avisos enviados para " with an empty e-mail. validate() returns true when no validator returns a message, and a field with no validator never returns anything: a form without validators is always valid. About the key: if the GlobalKey were created inside build, every rebuild would create a new key and the form would "forget" the errors already shown.
