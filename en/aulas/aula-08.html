State: from setState to architectures

Theory: what state is in an app, where it should live, and a comparison of setState, Provider, BLoC and Riverpod. Practice: StatefulWidget, the State lifecycle, text fields, forms with validation and searching a list.

Ephemeral state vs app state

Ephemeral (one widget's)App state (shared)
ExamplesSelected tab, half-typed text, scroll position, whether a card is expandedSigned-in user, favourites, temperature unit, loaded forecasts, shopping cart
Who needs itOne widget and its childrenSeveral screens, with no parent-child relationship
SurvivesRebuilds; dies with the widgetNavigation between screens; often the app being closed (persistence, lesson 16)
Where it livesIn the widget's State, with setStateIn an object outside the widget tree, observed by whoever needs it

For the tests: ephemeral state stays in the widget with setState; app state stays outside the tree and is shared.

Go back to the question on the board: the °C/°F switch. Is it ephemeral? No: the forecast screen, the detail and the home screen widget all need it. Practical example: ask where the "cart" lives in a shopping app. Everyone sees that it cannot be in the "add" button.

The five levels problem

  • The temperature unit is chosen in SettingsScreen and used in LocationCard, which is inside LocationList, inside ForecastScreen, inside Shell, inside TempoApp.
  • With setState alone, the variable has to move up to the common ancestor (TempoApp) and come down as a parameter through five constructors that have no use for it. This is called prop drilling.
  • Every widget in between now depends on something that is not its own. Adding a new field means touching five files.
  • And when the unit changes, setState in TempoApp rebuilds the whole app, not just the cards.

The answer to this problem is the reason state management libraries exist. They all solve the same thing: put the state somewhere reachable and rebuild only those who read it.

setState: when it is enough and when it stops being enough

  • It is enough when the state belongs to one screen or one widget and nobody else needs it: a counter, a form, a panel that opens and closes, a local search filter.
  • It is enough for prototypes and for isolated screens. It is not "bad practice"; it is the simplest tool and Flutter was designed for it.
  • It stops being enough when two unrelated screens need the same data, when the state has to survive navigation, or when you want to test the logic without building widgets.
  • It stops being enough when build rebuilds a large tree because of one boolean.

For the tests: setState marks the widget as dirty and schedules a rebuild of its subtree on the next frame. It does not rebuild the whole app, but it rebuilds everything below.

ChangeNotifier, Provider and InheritedWidget

  • InheritedWidget is Flutter's own mechanism for putting a value in the tree and letting any descendant read it with context. Theme.of(context) and MediaQuery.of(context) are this.
  • ChangeNotifier is a class with notifyListeners(). Your state extends it: class Settings extends ChangeNotifier { bool fahrenheit = false; void toggle() { fahrenheit = !fahrenheit; notifyListeners(); } }.
  • Provider joins the two: it puts the notifier in the tree, and context.watch<Settings>() rebuilds only the widget that called it when there is a notifyListeners.
  • It solves the five levels: LocationCard reads the unit directly; the widgets in between do not even know it exists.
  • It is recommended by the Flutter team as a starting point and it is what we will use in the project.

For the tests: Provider is an InheritedWidget with sugar; ChangeNotifier notifies the listeners; watch rebuilds, read does not.

BLoC, Cubit and Riverpod

ApproachHow it worksWhen it makes sense
setStateThe State holds the state and rebuilds the subtreeIsolated screen, few widgets, prototypes
Provider + ChangeNotifierObservable object in the tree; watch rebuilds only those who read itSeveral screens share state; small teams; our project
BLoC / CubitEvents go in, immutable states come out through a Stream; every transition is predictable and testable; more filesLarge teams, strong testing requirements, banking apps
RiverpodGlobal, typed providers that do not depend on BuildContext; errors caught at compile timeThose who already master Provider and want more safety and composition

They all do the same thing underneath: an object that holds state and notifies whoever observes it. The difference is in the ceremony and in the guarantees.

Analogy Where the shopping list is kept. A sticky note on the fridge in one room: only those who walk into that room see it (setState). A board in the kitchen that the whole house checks and that tells everyone when it changes (ChangeNotifier with Provider). A logbook with every change, dated and signed (BLoC: events and states). The board is enough for most houses.

Unidirectional flow and immutability

  • One direction: the UI triggers an action (tap, text) → the action changes the state → the UI rebuilds from the new state. The UI never changes the state directly and the state never touches the UI.
  • With one direction, any screen is a function of the state: given the same state, you see the same screen. This is what makes testing and debugging possible.
  • Immutable: instead of changing a field of Forecast, you create a new one with copyWith. An object that nobody modifies can be shared, compared and kept in a history without surprises.
  • The Settings class from the previous slide is mutable inside (it is a ChangeNotifier), but what it exposes are values. BLoC and Riverpod take immutability all the way.

For the tests: unidirectional flow is action → state → UI; immutability means creating copies with copyWith instead of modifying objects.

Analogy You do not scribble on the kitchen board. You write a new board with the change (copyWith) and replace the old one. Whoever was looking at the old one notices that it changed, because the object is a different one; and the old one can be kept in a history.

Criteria for choosing, and what we will use

  • How many screens share the state? One: setState. Several: Provider or above.
  • Do you need to test the logic without widgets? Then the logic has to live outside the widgets: Provider, BLoC or Riverpod.
  • Size of the team and of the project. Three people and 10 screens: Provider. Twenty people and 200 screens: BLoC or Riverpod, for the rules they enforce.
  • What the team already knows weighs more than what is in fashion.
  • In the project we use setState for ephemeral state and Provider with ChangeNotifier for the rest: it is simple, it is what the Flutter architecture guide recommends, and you can move to BLoC later without rewriting everything.
Today only setState. Provider comes in lesson 13, when we have API data to share.

1. StatelessWidget vs StatefulWidget

class UnitSelector extends StatefulWidget {
  const UnitSelector({super.key});

  @override
  State<UnitSelector> createState() => _UnitSelectorState();
}

class _UnitSelectorState extends State<UnitSelector> {
  bool _fahrenheit = false;                     // the state lives here, not in the widget

  @override
  Widget build(BuildContext context) {
    final t = _fahrenheit ? 21.0 * 9 / 5 + 32 : 21.0;
    return Column(
      children: [
        Text('${t.toStringAsFixed(0)} ${_fahrenheit ? '°F' : '°C'}'),
        Switch(
          value: _fahrenheit,
          onChanged: (v) => setState(() => _fahrenheit = v),   // change, ask for rebuild
        ),
      ],
    );
  }
}

1. Stateful: what matters

  • The widget is still immutable. What changes is the State object, which Flutter creates once and keeps alive between rebuilds. That is why hot reload preserves what you typed.
  • setState(() { ... }) does two things: it runs the change and marks the widget to rebuild on the next frame. Changing the variable without setState changes the value, but the screen does not follow.
  • Only this widget's subtree is rebuilt. The lower the StatefulWidget sits, the less work.
  • The Switch stores nothing: it shows value and reports in onChanged. All Material controls work like this: controlled widgets.
  • Shortcut in VS Code: type stful and press Tab.

2. The State lifecycle

class _SearchState extends State<Search> {
  late final TextEditingController _controller;
  Timer? _debounce;

  @override
  void initState() {
    super.initState();                       // 1. once, before the first build
    _controller = TextEditingController();
    _controller.addListener(_onChanged);
  }

  void _onChanged() {                        // 2. each key: wait 300 ms before filtering
    _debounce?.cancel();
    _debounce = Timer(const Duration(milliseconds: 300), () => setState(() {}));
  }

  @override
  void dispose() {
    _debounce?.cancel();
    _controller.dispose();                   // 4. release; without this, a memory leak
    super.dispose();
  }

  // 3. build runs between initState and dispose, as many times as needed
}
Call setState after dispose (a Timer that fires after leaving the screen) and show the error that appears. It is the most common crash in the projects of previous years. Give this block 10 minutes.

2. Lifecycle: what matters

MethodWhen it runsWhat for
initStateOnce, when the State is createdCreate controllers, subscribe to streams, fire the first request
didChangeDependenciesAfter initState and whenever an InheritedWidget you depend on changes (theme, locale)Read Theme.of or MediaQuery.of, which cannot be read in initState
buildWhenever something needs drawingOnly describe the UI. No network requests here
didUpdateWidgetWhen the parent rebuilds with new parametersReact to a parameter that changed (a new location selected)
disposeOnce, when the widget leaves the treeRelease controllers, timers, subscriptions, focus nodes

For the tests: everything you create in initState you release in dispose; build can run many times and must have no side effects.

3. TextField and searching a list

String _filter = '';                          // state: what the user typed

List<String> get _filtered => locations      // from lib/data.dart
    .where((l) => l.toLowerCase().contains(_filter.toLowerCase()))
    .toList();

@override
Widget build(BuildContext context) {
  return Column(
    children: [
      TextField(
        decoration: const InputDecoration(
          prefixIcon: Icon(Icons.search),
          hintText: 'Search location',
          border: OutlineInputBorder(),
        ),
        onChanged: (text) => setState(() => _filter = text),
      ),
      Expanded(
        child: ListView(
          children: [for (final l in _filtered) ListTile(title: Text(l))],
        ),
      ),
    ],
  );
}

3. Search: what matters

  • To react to the text, onChanged is enough. You need a TextEditingController when you want to read the text somewhere else, clear it (X button) or set an initial value. And then, dispose.
  • The filtered list is a getter computed from the state. Do not store the filtered list as state: those are two values that can get out of sync.
  • Filtering 100 locations on each key is instant. Filtering 100,000, or asking the API, needs the debounce from the previous slide.
  • The Expanded around the ListView is mandatory: without it, infinite height inside the Column.
  • InputDecoration controls the look: icon, hint, label, border, helper text and error text.

4. Form, TextFormField and validation

final _key = GlobalKey<FormState>();

Form(
  key: _key,
  child: Column(
    children: [
      TextFormField(
        decoration: const InputDecoration(labelText: 'Location name'),
        validator: (v) {
          if (v == null || v.trim().isEmpty) return 'Required';
          if (v.trim().length < 3) return 'At least 3 letters';
          return null;                                  // null means valid
        },
      ),
      FilledButton(
        onPressed: () {
          final form = _key.currentState!;
          if (form.validate()) {                        // runs every validator
            ScaffoldMessenger.of(context).showSnackBar(
              const SnackBar(content: Text('Form is valid')),
            );
          }
        },
        child: const Text('Save'),
      ),
    ],
  ),
)

4. Forms: what matters

  • Form groups fields; GlobalKey<FormState> gives access to the form's state from the button. It is one of the few legitimate uses of GlobalKey.
  • Each TextFormField has a validator that returns an error message or null. validate() runs them all, shows the errors below the fields and returns true if everything is fine.
  • autovalidateMode: AutovalidateMode.onUserInteraction validates while the user types, after the first attempt. Without it, validation only happens on submit.
  • keyboardType: TextInputType.number and textInputAction: TextInputAction.next change the phone's keyboard. On mobile, this is UX.
  • onSaved and form.save() copy the values into variables when you do not want one controller per field.

For the tests: a validator returns null when the value is valid and a String with the error when it is not.

5. Switch, Checkbox and Slider bound to state

bool _notifications = true;
double _radius = 25;
bool _fahrenheit = false;

SwitchListTile(
  title: const Text('Weather warnings'),
  value: _notifications,
  onChanged: (v) => setState(() => _notifications = v),
),
CheckboxListTile(
  title: const Text('Show in Fahrenheit'),
  value: _fahrenheit,
  onChanged: (v) => setState(() => _fahrenheit = v ?? false),
),
ListTile(
  title: Text('Search radius: ${_radius.round()} km'),
  subtitle: Slider(
    value: _radius,
    min: 5,
    max: 100,
    divisions: 19,
    label: '${_radius.round()} km',
    onChanged: (v) => setState(() => _radius = v),
  ),
),

They all follow the same contract: value comes from the state, onChanged changes the state with setState. The widget never stores anything.
