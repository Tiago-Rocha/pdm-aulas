Local persistence and offline cache

Theory: persistence options on mobile: key-value, SQLite, local NoSQL, files and secure storage; criteria for choosing. Practice: preferences with shared_preferences, a forecast cache in a local database with a cache-first strategy, and the token in secure storage.

Repository: pdm-aula-16
Five minutes for groups that did not manage the first request to the API on Wednesday: sort that out before the new material. Then open with a question: "where does the Spotify app keep the downloaded songs, and why can't you see them in the file explorer?" It is the sandbox, slide 4.

By the end of this lesson you can

  • Choose where to store each kind of data: preferences, database, files or secure storage.
  • Explain the app sandbox, what survives updates and what goes into the backup.
  • Justify why a token never goes into shared_preferences.
  • Implement a cache-first repository with drift and show the age of the data.

Where to store what

Kind of dataExample in Tempo AçoresTool
Key-value preferencesUnit °C/°F, theme, last locationshared_preferences (SharedPreferences on Android, NSUserDefaults on iOS)
Structured data with queriesCache of forecasts and warnings, historySQLite: sqflite (SQL by hand) or drift (typed, reactive)

SecretsAccess token, refresh tokenflutter_secure_storage (Keychain on iOS, Keystore on Android)

For the tests: preferences for small values, SQLite for data you query, secure storage for secrets.

Analogy Three places in a house. The kitchen drawer (shared_preferences) holds small, unimportant things, close at hand. The filing cabinet with folders (SQLite) holds many records that you look up by name or date. The safe (Keychain and Keystore) holds the token. Leaving the token in the drawer is leaving the house key under the doormat.

Sandbox: where the app's files live

  • Each app has its own private folder. Another app cannot read it; the user cannot see it without root. Android: /data/data/<package>/; iOS: Documents/, Library/, tmp/.
  • path_provider abstracts this: getApplicationDocumentsDirectory() persists and goes into the backup; getApplicationSupportDirectory() persists without being shown to the user; getTemporaryDirectory() can be cleared by the system.
  • Updates keep everything except the temporary folder. Uninstalling deletes everything, with one exception: the iOS Keychain stays.
  • Backup: iCloud copies Documents/; Android Auto Backup copies up to 25 MB. Cache and tokens should be left out (android:fullBackupContent, isExcludedFromBackup).
  • Example: a game stores progress in Documents (it goes into the backup) and the downloaded textures in Support (they do not, it downloads them again).

For the tests: Documents persists and goes into the backup; tmp can disappear at any moment.

Keychain and Keystore: why a token never goes into preferences

  • shared_preferences is an XML file (Android) or a plist (iOS) in plain text. On a rooted phone you read it with cat; in backups it goes unencrypted.
  • Keychain (iOS): encrypted with a key tied to the hardware (Secure Enclave). It can require the device to be unlocked. It survives uninstalling: watch out for ghost sessions.
  • Keystore (Android): the keys live in hardware (TEE or StrongBox) and never leave it. flutter_secure_storage encrypts the values with AES and keeps the AES key in the Keystore.
  • Rule: token, refresh token and the user's keys go into secure storage. Never into preferences, never into the database unencrypted.
  • Limit: whoever has the phone unlocked has access to the app. It protects against backups, other apps, and extraction tools.

For the tests: a token never goes into shared_preferences; it goes into Keychain or Keystore via flutter_secure_storage.

A 2-minute demonstration that is worth the whole topic: with adb on an emulator, `adb shell run-as com.example.app cat shared_prefs/FlutterSharedPreferences.xml` and everything shows up in plain text. Then the same for the secure storage file: encrypted rubbish.

Cache-first, network-first, invalidation and migrations

StrategyFlowWhen
Cache-firstShows the cache, asks the network in the background, updatesForecasts, lists: perceived speed
Network-firstAsks the network; if it fails, shows the cacheCritical data that changes: balance, stock
Cache-only / Network-onlyNever goes to the network / never storesDownloaded maps / payments
  • Time-based invalidation: store fetchedAt and compare: forecast valid for 30 min, warnings 5 min, locations 24 h.
  • Migrations: version 1.2 of the app changes the table, but there are users on 1.0 with the old database. schemaVersion + MigrationStrategy in drift; never delete the user's data without warning.

For the tests: cache-first shows quickly and updates afterwards; network-first guarantees fresh data; time-based invalidation decides when the cache expires.

Analogy The fridge. You show what is in the fridge right away, with the date on the label (fetchedAt), and in the meantime you go shopping (the network request in the background); when you come back, you replace what was there. With no network, you eat what there is, and the label says how old it is. The use-by date on the label is time-based invalidation: while it is in date you do not go shopping.

Size, clean-up and the "Clear data" button

  • There is no fixed limit, but the system shows "Storage: 480 MB" in the settings and the user clears it. On iOS, tmp/ is deleted when space runs low.
  • Order of magnitude: preferences in KB, database in MB, cached images with a limit (cached_network_image: 200 items or 7 days).
  • Your own clean-up: delete forecasts older than 7 days, a "Clear cache" option in the settings.
  • "Clear data" on Android deletes everything, including secure storage. On iOS only by uninstalling, and the Keychain stays.
  • The app has to start properly with everything empty: it is the first launch all over again. If it fails with no cache, the fault is in the app.

For the tests: the app has to work after the user clears the data, exactly as on the first launch.

1. shared_preferences: unit, theme, last location

class Settings {
  Settings(this._prefs);
  final SharedPreferences _prefs;

  static Future<Settings> load() async =>
      Settings(await SharedPreferences.getInstance());

  bool get useFahrenheit => _prefs.getBool('useFahrenheit') ?? false;
  ThemeMode get theme => ThemeMode.values.byName(_prefs.getString('theme') ?? 'system');
  int? get lastLocationId => _prefs.getInt('lastLocationId');

  Future<void> saveUnit({required bool fahrenheit}) =>
      _prefs.setBool('useFahrenheit', fahrenheit);
  Future<void> saveTheme(ThemeMode mode) => _prefs.setString('theme', mode.name);
  Future<void> saveLastLocation(int id) => _prefs.setInt('lastLocationId', id);
}

// main.dart: load before runApp, so the theme is right on the first frame
void main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final settings = await Settings.load();
  runApp(Provider.value(value: settings, child: const TempoApp()));
}

1. Preferences: what matters

  • Key-value with simple types: bool, int, double, String, List<String>. No large JSON here.
  • Reading is synchronous after getInstance(); writing is asynchronous. That is why we load before runApp: the theme has to be right on the first frame.
  • WidgetsFlutterBinding.ensureInitialized() is mandatory before any plugin in main.
  • Enums are stored by name and read with values.byName. Never by index: reordering the enum would break the stored preferences.
  • In the starter, SettingsNotifier wraps this class and calls notifyListeners so the UI reacts. Version 2.3+ of the package also has SharedPreferencesWithCache; the old API still works.

}

  int get schemaVersion => 1;

2. drift: insert, read, delete

extension ForecastCache on AppDatabase {
  Future<Forecast?> readForecast(int locationId) async {
    final row = await (select(forecasts)
          ..where((f) => f.locationId.equals(locationId)))
        .getSingleOrNull();
    if (row == null) return null;
    return Forecast.fromJson(jsonDecode(row.json) as Map<String, dynamic>)
        .copyWith(fetchedAt: row.fetchedAt);
  }

  Future<void> saveForecast(Forecast f) =>
      into(forecasts).insertOnConflictUpdate(ForecastsCompanion.insert(
        locationId: f.locationId,
        json: jsonEncode(f.toJson()),
        fetchedAt: DateTime.now(),
      ));

  Future<int> deleteOld({Duration maxAge = const Duration(days: 7)}) =>
      (delete(forecasts)
            ..where((f) => f.fetchedAt.isSmallerThanValue(DateTime.now().subtract(maxAge))))
          .go();
}

2. Database: what matters

  • One table per kind of cache, with the natural key (locationId) as the primary key and insertOnConflictUpdate for "save or replace".
  • Storing the whole JSON in one column is pragmatic for a cache: the structure of the forecast does not matter to SQL, only the key and the date.
  • drift generates forecasts, ForecastsCompanion and the column types. A wrong column name is a compile error, not a runtime one as in sqflite.
  • fetchedAt is what lets you say "from 12 min ago" and invalidate: without it the cache is eternal.
  • When you change the table: schemaVersion: 2 and a MigrationStrategy with onUpgrade. Never delete the database to "fix it".

3. Cache-first repository

class ForecastRepositoryCache implements ForecastRepository {
  ForecastRepositoryCache(this._api, this._db);
  final ForecastApiDataSource _api;   // Future<Forecast> forecast(int id), from lesson 12
  final AppDatabase _db;
  static const validity = Duration(minutes: 30);

  @override
  Stream<Forecast> forecast(int locationId) async* {
    final cached = await _db.readForecast(locationId);
    if (cached != null) yield cached;                         // 1. show what there is right away

    final valid = cached != null &&
        DateTime.now().difference(cached.fetchedAt) < validity;
    if (valid) return;                                        // 2. still fresh: stop here

    try {
      final fresh = await _api.forecast(locationId);          // 3. go to the network
      await _db.saveForecast(fresh);
      yield fresh.copyWith(fetchedAt: DateTime.now());
    } catch (_) {
      if (cached == null) rethrow;                            // no cache and no network: error
    }
  }
}

3. Cache-first: what matters

  • The repository returns a Stream because it can emit twice: the cache straight away, the fresh data later. With a Future there was only one answer.
  • async* and yield make this readable: it is sequential code that emits values along the way.
  • If the cache is recent, there is no network request. This is where time-based invalidation lives, not in the UI.
  • Network failure with cache: it is swallowed and the user is left with old data and the time. Network failure with no cache: error, as in lesson 14.
  • The notifier consumes the stream with await for and notifies on each emission:
Future<void> load(int id) async {
  try {
    await for (final f in _repo.forecast(id)) {
      state = Data(f, fetchedAt: f.fetchedAt);
      notifyListeners();
    }
  } catch (e) {
    if (state is! Data) state = Failure(messageFor(e));
    notifyListeners();
  }
}

5. flutter_secure_storage for the token

class TokenStorage {
  TokenStorage([FlutterSecureStorage? storage])
      : _storage = storage ??
            const FlutterSecureStorage(
              iOptions: IOSOptions(
                accessibility: KeychainAccessibility.first_unlock_this_device,
              ),
            );
  final FlutterSecureStorage _storage;
  static const _key = 'access_token';

  Future<String?> read() => _storage.read(key: _key);
  Future<void> save(String token) => _storage.write(key: _key, value: token);
  Future<void> delete() => _storage.delete(key: _key);
}
  • An API like an asynchronous map: read, write, delete. Underneath, Keychain on iOS and Keystore + AES on Android.
  • first_unlock_this_device: accessible after the first unlock and it does not migrate to another phone via backup. It is what you want for a token.
  • Tomorrow, AuthClient reads from here, renews on 401 and saves again. Today only the token from startup is kept.
Exercise 5 Save the token obtained at startup with TokenStorage and, at the next startup, use it without asking for another one. Confirm with adb shell run-as that there is no file with the token in plain text in the app's folder.
