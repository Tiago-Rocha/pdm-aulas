Where to store what

For the tests: preferences for small values, SQLite for data you query, secure storage for secrets.

Analogy Three places in a house. The kitchen drawer (shared_preferences) holds small, unimportant things, close at hand. The filing cabinet with folders (SQLite) holds many records that you look up by name or date. The safe (Keychain and Keystore) holds the token. Leaving the token in the drawer is leaving the house key under the doormat.

Sandbox: where the app's files live

  • Each app has its own private folder. Another app cannot read it; the user cannot see it without root. Android: /data/data/<package>/; iOS: Documents/, Library/, tmp/.
  • path_provider abstracts this: getApplicationDocumentsDirectory() persists and goes into the backup; getApplicationSupportDirectory() persists without being shown to the user; getTemporaryDirectory() can be cleared by the system.
  • Updates keep everything except the temporary folder. Uninstalling deletes everything, with one exception: the iOS Keychain stays.
  • Backup: iCloud copies Documents/; Android Auto Backup copies up to 25 MB. Cache and tokens should be left out (android:fullBackupContent, isExcludedFromBackup).
  • Example: a game stores progress in Documents (it goes into the backup) and the downloaded textures in Support (they do not, it downloads them again).

For the tests: Documents persists and goes into the backup; tmp can disappear at any moment.

Keychain and Keystore: why a token never goes into preferences

  • shared_preferences is an XML file (Android) or a plist (iOS) in plain text. On a rooted phone you read it with cat; in backups it goes unencrypted.
  • Keychain (iOS): encrypted with a key tied to the hardware (Secure Enclave). It can require the device to be unlocked. It survives uninstalling: watch out for ghost sessions.
  • Keystore (Android): the keys live in hardware (TEE or StrongBox) and never leave it. flutter_secure_storage encrypts the values with AES and keeps the AES key in the Keystore.
  • Rule: token, refresh token and the user's keys go into secure storage. Never into preferences, never into the database unencrypted.
  • Limit: whoever has the phone unlocked has access to the app. It protects against backups, other apps, and extraction tools.

For the tests: a token never goes into shared_preferences; it goes into Keychain or Keystore via flutter_secure_storage.

A 2-minute demonstration that is worth the whole topic: with adb on an emulator, `adb shell run-as com.example.app cat shared_prefs/FlutterSharedPreferences.xml` and everything shows up in plain text. Then the same for the secure storage file: encrypted rubbish.

Under the hood: one package, one implementation per platform

  • Both are federated plugins: the package you put in pubspec.yaml only has the Dart API. It pulls in one package per platform by itself (shared_preferences_android, shared_preferences_foundation, shared_preferences_web...).
  • Dart does not talk to the Keychain or the Keystore. It sends a message over the platform channel and the native code (Kotlin, Swift) answers. That is why everything is a Future, and why main calls WidgetsFlutterBinding.ensureInitialized() before the first plugin.
  • The same write does very different things: on Android it encrypts with a key kept in the Keystore; on iOS it hands the value to the Keychain; on the web it encrypts with WebCrypto and stores it in the browser, which is much less safe.
  • A new or changed plugin means stopping and running the app again. Hot reload does not recompile Kotlin or Swift.

For the tests: the package gives a single API; what actually stores the data is each platform's own system, through the platform channel.

If they ask why Chrome is fine for the lesson: it is fine to see the flow, but real security only shows on a phone or an emulator. MissingPluginException almost always means they added the package with the app running: q and flutter run again.

Cache-first, network-first, invalidation and migrations

StrategyFlowWhen
Cache-firstShows the cache, asks the network in the background, updatesForecasts, lists: perceived speed
Network-firstAsks the network; if it fails, shows the cacheCritical data that changes: balance, stock
Cache-only / Network-onlyNever goes to the network / never storesDownloaded maps / payments
  • Time-based invalidation: store fetchedAt and compare: forecast valid for 30 min, warnings 5 min, locations 24 h.
  • Migrations: version 1.2 of the app changes the table, but there are users on 1.0 with the old database. schemaVersion + MigrationStrategy in drift; never delete the user's data without warning.

For the tests: cache-first shows quickly and updates afterwards; network-first guarantees fresh data; time-based invalidation decides when the cache expires.

Analogy The fridge. You show what is in the fridge right away, with the date on the label (fetchedAt), and in the meantime you go shopping (the network request in the background); when you come back, you replace what was there. With no network, you eat what there is, and the label says how old it is. The use-by date on the label is time-based invalidation: while it is in date you do not go shopping.

Size, clean-up and the "Clear data" button

  • There is no fixed limit, but the system shows "Storage: 480 MB" in the settings and the user clears it. On iOS, tmp/ is deleted when space runs low.
  • Order of magnitude: preferences in KB, database in MB, cached images with a limit (cached_network_image: 200 items or 7 days).
  • Your own clean-up: delete forecasts older than 7 days, a "Clear cache" option in the settings.
  • "Clear data" on Android deletes everything, including secure storage. On iOS only by uninstalling, and the Keychain stays.
  • The app has to start properly with everything empty: it is the first launch all over again. If it fails with no cache, the fault is in the app.

For the tests: the app has to work after the user clears the data, exactly as on the first launch.

From the screen to the safe: the layered login

  1. The screen validates the form and calls login(email, password). It does not wait for the answer: it draws whatever the notifier says.
  2. The notifier turns on isLoading and asks the AuthRepository.
  3. The repository sends the request through the ApiClient.
  4. The answer comes back as JSON and the repository turns it into a Session.
  5. The notifier saves the refresh token in the SessionStore, which hands it to the Keychain or the Keystore.
  6. Only then does it put the session in the state and call notifyListeners. main sees the session and swaps the login for the islands.
And with BLoC? The SessionNotifier would become a Cubit<SessionState>: the same steps, with emit(...) instead of notifyListeners() and an immutable state instead of loose fields. Repository and store stay the same. That is what the layers buy you: you change the state management without touching the data.
Draw this on the board before opening the code: it is the map for the three steps. The question worth asking: if tomorrow the token moves somewhere else, which files change? Answer: only the SessionStore.

AuthRepository: the login request

class AuthRepository {
  AuthRepository(this._api); // injected, not created here

  final ApiClient _api;

  Future<Session> login(String email, String password) async {
    final json = await _api.post('/v1/auth/login', {
      'clientId': _api.clientId,
      'clientSecret': _api.clientSecret,
      'email': email,
      'password': password,
    });
    return Session.fromJson(json as Map<String, dynamic>);
  }
  • The app identifies itself with clientId and clientSecret; the person with email and password. register is the same, plus name.
  • The answer has the accessToken (15 min), the refreshToken (30 days) and the user. Session.fromJson reads all three, in lib/models/user.dart.

SessionNotifier: who is logged in

  Future<void> login(String email, String password) =>
      _start(() => _auth.login(email, password));

  Future<void> register(String name, String email, String password) =>
      _start(() => _auth.register(name, email, password));

  Future<void> _start(Future<Session> Function() request) async {
    isLoading = true;
    error = null;
    notifyListeners();
    try {
      final s = await request();
      await _store.save(s.refreshToken); // before the UI knows
      session = s;
    } on ApiException catch (e) {
      error = e.message; // the API already writes it in Portuguese
    } catch (_) {
      error = 'Sem ligação. Tenta de novo.';
    } finally {
      isLoading = false;
      notifyListeners();
    }
  }
}
  • Login and sign-up share _start: spinner on, request, keep the session or the error, spinner off.
  • The refresh token goes into the safe before the UI knows there is a session.
  • The API's error messages already come in Portuguese ("Email ou password errados."). Without a network, ours.

SessionStore: the refresh token in the safe

import 'package:flutter_secure_storage/flutter_secure_storage.dart';

/// The refresh token, in the Keychain (iOS) or the Keystore (Android).
/// Never in shared_preferences: it is a password that lasts 30 days.
class SessionStore {
  const SessionStore([this._storage = const FlutterSecureStorage()]);

  final FlutterSecureStorage _storage;
  static const _key = 'refreshToken';

  Future<String?> read() => _storage.read(key: _key);

  Future<void> save(String refreshToken) =>
      _storage.write(key: _key, value: refreshToken);

  Future<void> clear() => _storage.delete(key: _key);
}
  • We keep the refresh token, not the access token: that one lasts 15 minutes and a new one comes from the refresh.
  • The class hides the package: if the token moves somewhere else tomorrow, only this file changes.

On start: restore()

  Future<void> restore() async {
    try {
      final saved = await _store.read();
      if (saved != null) session = await _auth.refresh(saved);
    } on ApiException {
      await _store.clear(); // expired, logged out or account deleted
    } catch (_) {
      // offline: show the login, keep the token for the next start
    } finally {
      isRestoring = false;
      notifyListeners();
    }
  }
  • With a saved token, it asks POST /v1/auth/refresh for a new session. If the API refuses (expired, logged out, account deleted), it deletes it.
  • Without a network, it keeps the token for next time. While isRestoring, _Home shows a spinner instead of the login.
  • On logout, the token leaves the safe and the API revokes it.

Settings: the last email and the theme

class Settings extends ChangeNotifier {
  Settings(this._prefs);

  final SharedPreferences _prefs;

  static Future<Settings> load() async =>
      Settings(await SharedPreferences.getInstance());

  String get lastEmail => _prefs.getString('lastEmail') ?? '';

  // Enums are saved by name, never by index.
  ThemeMode get theme =>
      ThemeMode.values.byName(_prefs.getString('theme') ?? 'system');

  Future<void> saveLastEmail(String email) =>
      _prefs.setString('lastEmail', email);

  Future<void> saveTheme(ThemeMode mode) async {
    await _prefs.setString('theme', mode.name);
    notifyListeners(); // MaterialApp rebuilds with the new theme
  }
}
  • Reads are synchronous after getInstance(), writes are asynchronous.
  • Enums are saved by name and read with values.byName. By index, reordering the enum would break what was saved.
