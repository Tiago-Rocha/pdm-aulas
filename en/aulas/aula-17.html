Token authentication and synced favourites

Theory: authentication on mobile: OAuth2 and OpenID Connect, JWT, access and refresh tokens, biometrics. Practice: token kept in secure storage, renewal on 401 by an interceptor, and favourites synced with the server across devices.

Authentication vs authorisation; cookies vs tokens

  • Authentication: who you are (login, biometrics, key). Authorisation: what you can do (read your group's favourites, not those of the others).
  • 401 Unauthorized = I do not know who you are: token missing or expired. 403 Forbidden = I know who you are, but you are not allowed.
  • On the web: a session stored on the server and a cookie that the browser sends by itself on every request. The typical risk is CSRF.
  • On mobile: there is no browser managing cookies. The app stores a token and sends it explicitly in Authorization: Bearer ….
  • A signed token is stateless: the server validates the signature without going to the database. It scales better; revoking is harder.

For the tests: 401 is authentication, 403 is authorisation; on mobile you use Bearer tokens, not cookies.

JWT (1 of 2): what is inside

  • Three parts in base64url separated by dots: header.payload.signature.
  • Header: {"alg":"HS256","typ":"JWT"}. Payload: the claims: sub (who), iss (who issued it), iat and exp (when), and custom claims such as group or scope.
  • Signature: HMAC (shared key) or RSA/ECDSA (key pair) over the header and the payload.
{
  "sub": "group-07",
  "iss": "api.pdm.example",
  "iat": 1761494400,
  "exp": 1761495300,
  "scope": "forecast warnings favorites"
}
  • Base64 is not encryption: anyone can read the payload. The app can read exp to know it is about to expire without making a request.

For the tests: JWT = header.payload.signature; the payload is readable by everyone, it is not secret.

JWT (2 of 2): signature, expiry and what never goes in it

  • The signature guarantees integrity: if someone changes "sub": "group-07" to "group-01", the signature no longer matches and the server rejects it.
  • Only the server validates. With HS256 the client does not have the key; with RS256 it could validate with the public key, but it does not need to.
  • A short exp (15 min to 1 h): a stolen token is worth little time. Without exp it is an eternal token, and that is a security bug.
  • Never in the JWT: passwords, sensitive personal data, secrets. It travels in plain text, on every request, and ends up in logs.
  • Real attacks from the past: "alg":"none" accepted by the server, and weak HS256 keys broken by brute force. Current libraries reject both.

For the tests: the signature gives integrity, not confidentiality; you never put sensitive data in a JWT.

Analogy A festival wristband. It says who you are and until when it is valid, and it carries the organiser's signature; any doorman checks it at the door without phoning the ticket office (the server validates the signature without going to the database). Anyone who tries to change the date ruins the signature. And you do not write on it anything you do not want everyone to read: the wristband is in plain sight of everybody.
Question: "if the payload is readable, why can't I change exp to a year from now?" Let them get to the signature by themselves. Then: "and what if the server does not check the signature?" That is the alg none attack.

OAuth2 and OIDC in broad strokes: authorization code + PKCE

  • The problem: the app wants to access the user's Google calendar without ever knowing the Google password.
  • OAuth2 is delegated authorisation: the app opens the system browser, the user signs in to Google, Google returns a code through a deep link, and the app exchanges the code for tokens.
  • PKCE: the app generates a random code_verifier and sends its hash (code_challenge). Only whoever has the verifier can exchange the code. Mandatory in mobile apps, because they have nowhere to keep a client secret.
  • OIDC = OAuth2 + identity: it also returns an id_token (JWT) that says who the user is. It is "Sign in with Google".
  • In Flutter: flutter_appauth or each provider's SDK. Always Custom Tabs / ASWebAuthenticationSession, never your own webview (the user should not type the password inside your app).

For the tests: mobile apps do not store passwords or client secrets; they use authorization code with PKCE in the system browser.

Short access token, long refresh token, logout

Access tokenRefresh token
LifetimeMinutes to an hourDays to months
UseOn every request, as BearerOnly to ask for a new access token
Where to storeMemory; secure storage if it has to survive a restartSecure storage, always
If it is stolenIt is worth little timeSerious: revoke on the server
  • Renewal: on 401, ask for a new access token with the refresh token and repeat the original request once. If the refresh also fails, logout.
  • Logout: delete both from the device, revoke the refresh token on the server, clear the cache that holds user data. The course API has a single token (per group), but the pattern is the same.

For the tests: short access on every request; long refresh in secure storage, only to renew; logout deletes both.

Analogy The access token is the festival wristband: you show it to every doorman and it is valid for a few hours. The refresh token is the ticket you exchange for a new wristband when the old one expires, without going back to the ticket office queue (without a new login). The ticket stays in your inside pocket (secure storage) and is only shown at the exchange desk; losing it is serious, because whoever has it can go and fetch new wristbands.

Biometrics and Sign in with Apple

  • local_auth: Face ID, Touch ID, fingerprint. It only returns "yes" or "no" to the app. It never talks to the server.
  • Right use: local unlock. The bank app already has a session (refresh token stored); biometrics decide whether the app can use it now.
  • Wrong use: "authenticating on the server with biometrics". The server never sees the biometrics; if the refresh token does not exist, biometrics do not create any session.
  • Sign in with Apple is mandatory on the App Store if the app offers another social login (Google, Facebook). It includes a relay email for those who do not want to give their own.
  • Passkeys (WebAuthn): the next step. No passwords, a private key on the device, unlocked by biometrics. Already supported on Android and iOS.

For the tests: biometrics unlock locally; authentication on the server is still done by the token.

Frequent question: "can I keep the password in secure storage and use biometrics to resend it?" Technically yes, it is what some old apps do, but it violates the principle: the app should not have the password. The refresh token is the answer.

1. Obtain the token and store it securely

class AuthService {
  AuthService(this._api, this._storage);
  final ApiClient _api;
  final TokenStorage _storage;   // flutter_secure_storage, from lesson 16

  static const _clientId = String.fromEnvironment('PDM_CLIENT_ID');
  static const _secret = String.fromEnvironment('PDM_SECRET');

  Future<String> fetchToken() async {
    final json = await _api.post('/v1/auth/token', body: {
      'client_id': _clientId,
      'secret': _secret,
    });
    final token = json['access_token'] as String;
    await _storage.save(token);
    return token;
  }

  Future<String> currentToken() async =>
      await _storage.read() ?? await fetchToken();
}

1. Token: what matters

  • currentToken() returns what is stored or asks for a new one. There are never two paths to get a token: only this one.
  • The token goes into TokenStorage (Keychain/Keystore), never into shared_preferences nor into the database. That was the topic of lesson 16.
  • String.fromEnvironment is resolved at compile time: the value ends up in the binary. For the course API that is acceptable (a group token, revocable); in production the login belongs to the user.
  • A stored token may already be expired when the app starts. That is fine: the interceptor in step 2 handles the 401.
  • Optional: read exp from the payload (base64url of the second segment) and renew before it expires. It saves one 401 per session.
Exercise 1 Implement bool expiresWithin(String token, Duration margin), which decodes the payload and compares exp with DateTime.now(). Use it in currentToken() to renew when less than a minute is left. The test test/auth_service_test.dart comes with sample tokens.

2. AuthClient: Bearer on every request, renewal on 401

class AuthClient extends http.BaseClient {
  AuthClient(this._inner, this._auth);
  final http.Client _inner;
  final AuthService _auth;

  @override
  Future<http.StreamedResponse> send(http.BaseRequest request) async {
    if (request.url.path.endsWith('/auth/token')) return _inner.send(request);
    var response = await _sendWith(await _auth.currentToken(), request);
    if (response.statusCode == 401) {
      response = await _sendWith(await _auth.fetchToken(), request);  // renews once
    }
    return response;
  }

  Future<http.StreamedResponse> _sendWith(String token, http.BaseRequest original) {
    final request = http.Request(original.method, original.url)
      ..headers.addAll(original.headers)
      ..headers['Authorization'] = 'Bearer $token';
    if (original is http.Request) request.bodyBytes = original.bodyBytes;
    return _inner.send(request);
  }
}

// main.dart: ApiClient now uses AuthClient underneath
final api = ApiClient(baseUrl: baseUrl, client: AuthClient(http.Client(), auth));

2. Interceptor: what matters

  • BaseClient.send is the point every http request goes through. It is the interceptor from lesson 12, now with code.
  • The token request carries no token. Without the first line of send, currentToken() would call fetchToken(), which would go through send, which would call currentToken(): infinite recursion.
  • A BaseRequest can only be sent once. That is why _sendWith creates a new request with the same method, URL, headers and body.
  • It renews once. If the second request also gives 401, the problem is not the expired token: it is the wrong secret or the group revoked, and the app has to show that.
  • With dio it is a QueuedInterceptor with onError: the queue prevents ten parallel requests with 401 from asking for ten new tokens. Here, AuthService should keep the Future in progress for the same effect.

3. FavoritesRepository on top of /v1/me/favorites

abstract class FavoritesRepository {
  Future<List<int>> list();
  Future<void> add(int locationId);
  Future<void> remove(int locationId);
}

class FavoritesRepositoryApi implements FavoritesRepository {
  FavoritesRepositoryApi(this._api);
  final ApiClient _api;

  @override
  Future<List<int>> list() async {
    final json = await _api.get('/v1/me/favorites') as List<dynamic>;
    return json.map((e) => (e as Map<String, dynamic>)['locationId'] as int).toList();
  }

  @override
  Future<void> add(int locationId) =>
      _api.post('/v1/me/favorites', body: {'locationId': locationId});

  @override
  Future<void> remove(int locationId) =>
      _api.delete('/v1/me/favorites/$locationId');
}

3. FavoritesNotifier: optimistic UI with rollback

class FavoritesNotifier extends ChangeNotifier {
  FavoritesNotifier(this._repo);
  final FavoritesRepository _repo;
  Set<int> _ids = {};
  bool contains(int id) => _ids.contains(id);

  Future<void> load() async {
    _ids = (await _repo.list()).toSet();
    notifyListeners();
  }

  /// Returns false if the server refused and the change was undone.
  Future<bool> toggle(int id) async {
    final before = {..._ids};
    final adding = !_ids.contains(id);
    adding ? _ids.add(id) : _ids.remove(id);           // 1. the UI changes right away
    notifyListeners();
    try {
      await (adding ? _repo.add(id) : _repo.remove(id));   // 2. server
      return true;
    } catch (_) {
      _ids = before;                                    // 3. rollback
      notifyListeners();
      return false;
    }
  }
}

3. The favourite button with feedback in case of error

class FavoriteButton extends StatelessWidget {
  const FavoriteButton({super.key, required this.locationId});
  final int locationId;

  @override
  Widget build(BuildContext context) {
    final marked = context.select<FavoritesNotifier, bool>((f) => f.contains(locationId));
    return IconButton(
      icon: Icon(marked ? Icons.star : Icons.star_border),
      tooltip: marked ? 'Remove from favourites' : 'Add to favourites',
      onPressed: () async {
        final ok = await context.read<FavoritesNotifier>().toggle(locationId);
        if (!ok && context.mounted) {
          ScaffoldMessenger.of(context).showSnackBar(
            const SnackBar(content: Text('Could not save the favourite. Try again.')),
          );
        }
      },
    );
  }
}

3. Synced favourites: what matters

  • Optimistic UI: the star lights up the instant it is tapped, before the server's response. The user does not wait 800 ms for an icon.
  • Rollback: the previous state is kept (before); if the server refuses, it is restored and the user is told. There is never a lit star that the server does not know about.
  • toggle returns a bool instead of storing the message in the notifier: the widget that triggered the action is the one that shows the SnackBar, with context.mounted after the await.
  • context.select rebuilds the button only when this favourite changes, not when any of them changes.
  • The POST is not retried by ApiClient (lesson 14); if it fails, the rollback is the right answer. A repeated DELETE does no harm: it is idempotent.
Exercise 3 Register FavoritesRepositoryApi and the notifier in main, call load() at startup, and write the test "toggle rolls back when the repository fails" with a fake whose add throws.

4. Home screen with the same favourites on two phones

class FavoritesScreen extends StatelessWidget {
  const FavoritesScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final favorites = context.watch<FavoritesNotifier>();
    final all = context.watch<ForecastNotifier>().locations;
    final items = all.where((l) => favorites.contains(l.id)).toList();

    if (items.isEmpty) {
      return const EmptyState(message: 'Mark a location with the star to see it here.');
    }
    return RefreshIndicator(
      onRefresh: () => context.read<FavoritesNotifier>().load(),
      child: ListView(
        children: [
          for (final l in items)
            ListTile(
              title: Text(l.name),
              subtitle: Text(l.island),
              trailing: FavoriteButton(locationId: l.id),
              onTap: () => context.push('/location/${l.id}'),
            ),
        ],
      ),
    );
  }
}

5. Logout: delete token and cache

class SessionNotifier extends ChangeNotifier {
  SessionNotifier(this._storage, this._db, this._favorites);
  final TokenStorage _storage;
  final AppDatabase _db;
  final FavoritesNotifier _favorites;

  Future<void> signOut() async {
    await _storage.delete();            // 1. token out of the Keychain/Keystore
    await _db.deleteAll();              // 2. cache that may hold the group's data
    _favorites.clear();                 // 3. state in memory
    notifyListeners();                  // 4. the router takes you to the sign-in screen
  }
}
  • Order: first what is sensitive (token), then what is large (cache), then memory. If the app is killed halfway through, the token no longer exists.
  • With a refresh token there would be a step 0: POST /v1/auth/revoke on the server. A token that is only deleted on the client stays valid until it expires.
  • go_router observes SessionNotifier via refreshListenable and the redirect sends you to /sign-in when there is no session.
Exercise 5 A "Sign out" button in the settings. After pressing it: no token in secure storage, forecasts table empty, sign-in screen. On signing in again, the favourites come back from the server. Compare with solucao/.
