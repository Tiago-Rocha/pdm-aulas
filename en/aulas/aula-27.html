Workshop: signing the app and getting it to testers

Theory (30 minutes): why you distribute early, the three routes to testers and what signing an app means. Workshop: your group's app signed, in a GitHub Release and on three classmates' phones through Firebase App Distribution. Then: icon, launch screen, dark theme and two languages.

No lesson repository: everything happens in the group projectBreak at 10:20

For the tests: App Distribution and TestFlight come before the store; internal testing is already in the store.

What to say: all three do the same job, which is getting a build onto a tester's phone without going through the public store. App Distribution is the only one that covers both platforms and it is free, so it is today's. On iOS even it needs the paid Apple account, because the build has to be signed with a profile that lists each tester's iPhone. That is why anyone with an iPhone tests today on a classmate's Android phone or in the emulator. In TestFlight, team testers (up to 100) get the build straight away; external testers (up to 10,000) go through an Apple review, usually a day. Google Play internal testing has no long review and the app installs through the Play Store itself, with automatic updates, but it needs the developer account. Builds expire: 90 days in TestFlight, 150 in App Distribution.

Signing: the app says who made it

KeyWhere it livesWhat for
DebugOne per computer, from the Android SDKflutter run
Group upload keyA .jks file with a password, outside gitBuilds for testers and for the store
  • The phone only accepts an update signed with the same key as the installed app.
  • Each computer has its own debug key: a classmate's build on top gives "App not installed".
  • Lost key: testers uninstall, install again and lose their data.

For the tests: an app only updates with the same key; the .jks and its password never go into the repository.

What to say: the signature is how Android knows that version 2 comes from whoever made version 1. Without it, anyone could publish an "update" of someone's banking app. The debug key lives in ~/.android/debug.keystore and is created on the first build, one per computer: that is why, in a group, a classmate's APK will not install on top of yours. The store adds one more layer: Google keeps the app's final key (Play App Signing) and you only hold the upload key, so a lost upload key can be reset through support. Outside the store, like today, nobody can recover it. A .jks in a commit counts as published, even if it is deleted right after.

Two things that identify the app

FieldExampleRule
applicationIdpt.uac.pdm.tempo_acores.group1Unique, never changes once published
versionName0.3.0What the person reads in settings

  • In pubspec.yaml, version: 0.3.0+3 gives both versions: before and after the +.
  • The four apps in the class have the same applicationId today: to the phone, they are the same app.

For the tests: the versionCode has to go up with every build you distribute; Android refuses a lower version on top of a higher one.

What to say: the applicationId is the app's name on the phone and in the store, for example com.whatsapp or com.spotify.music. Two apps with the same id cannot live side by side: a tester with one group's app installed cannot install another group's (different signatures) and, if the key were the same, one would replace the other. So in step 1 each group adds its own suffix: lowercase letters, numbers and _, starting with a letter. The versionName is free (some teams use dates); the versionCode is what the system compares. Starting at 0.3.0 says it is the third sprint and not yet version 1.

WhereWhat it is

pdm.json at the root{"CLIENT_ID": "…", "CLIENT_SECRET": "…"}

What to say: there are two different passwords. Icon and launch screen

flutter_launcher_icons:
  android: true
  ios: true
  image_path: assets/icon.png
flutter_native_splash:
  color: "#0B4F6C"
  image: assets/logo.png
  • Install: flutter pub add --dev flutter_launcher_icons flutter_native_splash
  • Generate: dart run flutter_launcher_icons and dart run flutter_native_splash:create
What to say: both packages generate native files (the mipmap and drawable folders on Android, Assets.xcassets on iOS) from one image. The generated files go into the commit; whoever makes the next build does not need to run anything. The icon must be square, with no transparency for iOS; on Android 8 or later the system crops it into a circle or a rounded square, so keep the drawing away from the edges (the adaptive_icon_foreground option does it properly). The launch colour is the main colour of the design system. On Android 12 or later the launch screen is always the icon in the centre: the package handles that.

Dark theme and two languages

MaterialApp.router(
  theme: AppTheme.light,
  darkTheme: AppTheme.dark,
  themeMode: ThemeMode.system,
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,
  routerConfig: router,
)
  • AppTheme is your design system's theme, in light and in dark.
  • The strings: lib/l10n/app_pt.arb and app_en.arb; on screen, AppLocalizations.of(context)!.islands.
What to say: with ThemeMode.system the app follows the phone, no button needed. A dark theme is not inverted colours: it is the same ColorScheme with brightness: Brightness.dark, and with ColorScheme.fromSeed Flutter generates both from the same colour. For languages: flutter_localizations (from the SDK) and intl in pubspec.yaml, generate: true in the flutter section, and an l10n.yaml with arb-dir: lib/l10n and template-arb-file: app_pt.arb. flutter pub get generates the AppLocalizations class and the import is package:tempo_acores/l10n/app_localizations.dart. Island names and text that comes from the API are not translated.
