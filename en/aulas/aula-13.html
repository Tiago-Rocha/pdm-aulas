Layered architecture and state management

Today the app fetches the islands from the course API, with code you write. We start from a screen that does everything by itself (request, JSON and states) and put each job in its own layer: a repository for the data, a notifier for the state, and Provider to connect them to the screen.

Why layers

  • Swap the data source. The API moves to a new version, the data also starts coming from a cache on the phone: one file changes, and the screens stay the same.
  • Show it without a network. A fake repository, with fixed data, lets you build and demo the screen with no API and no credentials. Later on, it is also what makes automated tests possible.
  • Reuse. The list of islands appears in the list, in the favourites and, one day, on the map: only one place knows how to fetch it.
  • Each person in their own file. In the group project, whoever builds the screen and whoever writes the requests do not edit the same file at the same time.

In a large app (your bank's, Spotify) the screen asks for "the account" and does not know whether it came from the network, the cache or the disk.

For the tests: layers exist to isolate change; the screen must not know about HTTP or JSON.

The repository knows no widgets and no BuildContext: when something fails, it throws an exception; the notifier catches it and keeps it as state (error); and the screen decides how to show it, as text, a SnackBar or a button. The names vary (MVVM, Clean Architecture, "layers"), and the Flutter team's architecture guide calls ViewModel what we call a notifier here; the idea is the same.

Repository: one interface, several implementations

/// What the app can ask for. The screens only see this.
abstract class ForecastRepository {
  Future<List<Island>> fetchIslands();
  Future<Forecast> fetchForecast(String islandId);
}
  • The interface says what: the islands, the forecast of one island. An abstract class whose methods have no body.
  • Each implementation says how: HttpForecastRepository asks the API; FakeForecastRepository returns fixed data; later on, one with a cache on the phone.
  • Whoever uses it receives a ForecastRepository and does not know which of the three it is.
  • The JSON does not go above this layer. fromJson turns the API's shape (the DTO) into the app's shape (the model); if the API renames a field, fromJson changes and the rest of the app stays the same.
Analogy A shop counter. You ask the counter for "a forecast for Pico" and do not know whether it came from the stockroom (the cache) or the supplier (the API). The shop can change suppliers without you noticing; and in a training session, a pretend counter always gives the same answer.

For the tests: repository = one interface with several implementations; the screen depends on the interface, never on the implementation.

Dependency injection: whoever uses does not create

final ForecastRepository repository = useFake
    ? FakeForecastRepository()
    : HttpForecastRepository(
        ApiClient(clientId: clientId, clientSecret: clientSecret),
      );
  • HttpForecastRepository receives the ApiClient in its constructor; ForecastNotifier receives the repository in its constructor. Neither creates what it needs.
  • The one that creates is main, in a single place. That is where you choose the API or the fake, and the credentials.
  • The opposite, an ApiClient() created inside the notifier or a global variable everyone uses, is a hidden dependency: you cannot swap it, and you cannot see who depends on whom.
  • To carry the objects down to the widgets we use Provider. There are other tools (get_it, Riverpod); the constructor rule is the same.
Ask the class If HttpForecastRepository created its own ApiClient inside, what would no longer be possible?

For the tests: dependency injection = receive through the constructor instead of creating; it lets you swap a piece without touching whoever uses it.

Answers to the questions. Choosing the credentials (and the API address) from outside: they would have to be written inside the repository. Sharing a single ApiClient, and so a single token, between several repositories: each would ask for its own. And swapping the ApiClient for another one, for example one that answers without a network for a test. A quick analogy, if it helps: a coffee machine takes the capsule, it does not grow the coffee.

When Provider is the right tool

SituationChoice
State of a single widget: an open card, a search field, a tabsetState
Data from the network, or state shared by several screens, in a small teamChangeNotifier + Provider (the project)
Many events, strong testing rules, large teamsBLoC or Riverpod
  • Provider is the right tool when state leaves a single widget: when two screens need it, when it must survive navigation, or when the logic should live outside the widgets.
  • The Flutter team's recommendation: start simple, with layers and constructor injection, and only switch tools later if needed. With the layers in place, swapping ChangeNotifier for BLoC means changing one layer; without them, it means rewriting screens.
Ask the class Does the card that opens and closes need Provider? And the list of favourite islands, which appears in the list and on a favourites screen?

Answers to the questions. The card does not: only the card cares whether it is open, and setState is enough. The favourites do: two screens read and change the same list, and it has to still be there when you navigate from one to the other. That is today's step 4. The criterion is how many widgets need the state, not the size of the app.

ChangeNotifier and Provider: the pieces

PieceWhat it doesWhere it is used
ChangeNotifierHolds the state; notifyListeners() tells whoever is listeningThe state class: ForecastNotifier extends ChangeNotifier
ChangeNotifierProviderCreates the notifier once, puts it in the tree, disposes of it at the endAbove every screen that reads it: today, above the MaterialApp
context.watch<T>()Reads and subscribes: the widget runs build again on every notificationInside build
context.read<T>()Reads without subscribingIn callbacks: onPressed, onTap
Consumer<T>Like watch, but only rebuilds what is inside itIn a small part of a large screen
  • A rule to say out loud: watch in build, read in callbacks.
  • Provider is an InheritedWidget with less ceremony, the same mechanism as Theme.of(context): a value placed high in the tree, which any widget below finds through its context.

For the tests: notifyListeners notifies; watch rebuilds; read does not; the Provider must be above whoever reads it.

1. The repository: the request leaves the screen

/// How: HTTP to the course API, through the ApiClient.
class HttpForecastRepository implements ForecastRepository {
  HttpForecastRepository(this._api); // injected, not created here

  final ApiClient _api;

  @override
  Future<List<Island>> fetchIslands() async {
    final list = await _api.get('/v1/islands') as List<dynamic>;
    return list
        .map((item) => Island.fromJson(item as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Forecast> fetchForecast(String islandId) async {
    final json = await _api.get('/v1/islands/$islandId/forecast');
    return Forecast.fromJson(json as Map<String, dynamic>);
  }
}
  • fetchIslands is the screen's _load, moved: the path and the fromJson now live here.
  • implements ForecastRepository forces you to write both methods of the interface, with @override. If one is missing, the code does not compile.
  • fetchForecast is ready for later: nobody calls it today.
The interface (from the theory slide) goes in the same file, above this class, with the two imports: api_client.dart and models.dart. The underscore in _api makes it private: nothing outside the file can reach it, and the constructor HttpForecastRepository(this._api) still fills it in.

2. ForecastNotifier: the state leaves the screen

/// The state of the islands screen. Knows the repository, not the widgets.
class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repository); // injected, not created here

  final ForecastRepository _repository;

  bool isLoading = false;
  String? error;
  List<Island> islands = const [];

  Future<void> load() async {
    isLoading = true;
    error = null;
    notifyListeners(); // the screen shows the spinner
    try {
      islands = await _repository.fetchIslands();
    } catch (e) {
      error = '$e';
    } finally {
      isLoading = false;
      notifyListeners(); // the screen shows the islands or the error
    }
  }
}
  • The three states of the FutureBuilder become three fields: isLoading, error and islands.
  • The notifier knows no widgets and no BuildContext. It imports foundation.dart, not material.dart.
Ask the class Why are there two notifyListeners()? What does the user see after tapping "Tentar de novo" (try again) if you remove the first one?
Answers to the questions. The first shows the spinner as soon as the request leaves; the second, in finally, shows the result, whether that is the islands or the error. Without the first, after "Tentar de novo" the error message stays on screen until the response arrives: it looks as if the button did nothing, so the user taps again and makes two requests. '$e' shows the API's message (401: ...) or Dart's (a timeout); error messages written for people are for tomorrow.

2. Provider goes above the MaterialApp

void main() {
  final api = ApiClient(clientId: clientId, clientSecret: clientSecret);
  final repository = HttpForecastRepository(api);
  runApp(
    ChangeNotifierProvider(
      create: (_) => ForecastNotifier(repository)..load(),
      child: MaterialApp(
        title: 'Tempo Açores',
        theme: ThemeData(colorSchemeSeed: Colors.teal),
        home: const IslandsScreen(),
      ),
    ),
  );
}
  • create runs once: it creates the notifier with the repository, and ..load() fires the first request straight away. The .. calls load() and returns the notifier.
  • IslandsScreen no longer takes parameters: it gets the notifier from the Provider.
  • Everything below the ChangeNotifierProvider finds it. Above the MaterialApp, that means every screen in the app.

Answers to the questions. Today it would work: IslandsScreen is below the Provider. 3. A fake repository

/// Same interface, fixed data: no API and no credentials.
class FakeForecastRepository implements ForecastRepository {
  FakeForecastRepository({this.fail = false});

  final bool fail; // true: shows the error screen

  @override
  Future<List<Island>> fetchIslands() async {
    await Future.delayed(const Duration(seconds: 1)); // a slow network
    if (fail) throw Exception('Sem rede (fake)');
    return const [
      Island(id: 'corvo', name: 'Corvo', imageUrl: '$_img/corvo.jpg'),
      Island(id: 'faial', name: 'Faial', imageUrl: '$_img/faial.jpg'),
      Island(id: 'pico', name: 'Pico', imageUrl: '$_img/pico.jpg'),
    ];
  }

  @override
  Future<Forecast> fetchForecast(String islandId) {
    throw UnimplementedError(); // not used yet
  }
}

const _img = 'https://api-pdm.sublimecipher.com/static/islands';
  • It implements the same interface. The notifier receives a ForecastRepository and does not know this one is pretend.
  • The one-second wait lets you see the spinner; fail: true lets you see the error screen without turning off the Wi-Fi.
  • It is useful for building the screen before the API exists, for demoing the app without a network and, later on, for automated tests.

4. Favourites: state shared by two screens

/// Favourite islands, in memory. Shared by two screens.
class FavoritesNotifier extends ChangeNotifier {
  final Set<String> _ids = {};

  int get count => _ids.length;
  bool contains(String islandId) => _ids.contains(islandId);

  void toggle(String islandId) {
    if (!_ids.remove(islandId)) _ids.add(islandId);
    notifyListeners();
  }
}
    MultiProvider(
      providers: [
        ChangeNotifierProvider(
          create: (_) => ForecastNotifier(repository)..load(),
        ),
        ChangeNotifierProvider(create: (_) => FavoritesNotifier()),
      ],
  • It keeps only the island ids, in a Set: an island is a favourite or not, with no duplicates. The Set is private; from outside you can only ask (contains, count) and request (toggle).
  • MultiProvider is a list of providers instead of several nested inside each other. The child is still the MaterialApp.
Ask the class Mark two favourites, close the app and open it again. Are they still there? And after a hot reload?
Answers to the questions. Closing the app or doing a hot restart loses the favourites: they are only in memory and die with the app. With hot reload they stay, because Flutter keeps the objects alive. Saving them on the phone, so they survive the app closing, comes later; with the layers, it will be a new favourites repository, and the screen will not change.
