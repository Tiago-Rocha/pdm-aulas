Layered architecture and state management

Today we look at a class that does everything by itself, work out together how many jobs it has and split it into layers: data, state and UI. Tomorrow we get our hands on the code.

Repository: pdm-aula-13
Theory lesson, with exercises on the board: the practice is for tomorrow. Order: the whole class in three slides (they find the responsibilities), the responsibilities coloured in, the class split up, the folders, the restaurant, why it is worth it, AI, the code of each layer and a "where do you change it" exercise. Anyone who wants can clone and follow along on the computer: the code from before is on the antes branch, the organised code on main.

By the end of this lesson you can

  • Look at a class and say what jobs it does.
  • Split a class into three layers: data, state and UI.
  • Say which folder each thing lives in: models/, data/, state/ and screens/.
  • Explain why this matters in a group project, and even more when the code is written with AI.

Ask the class Look at the board. Put what we wrote into groups: how many different jobs does this class do?
Answers to the questions. Three groups. Data: receives the ApiClient, asks for /v1/islands, converts the JSON into Island. One class, three jobs

Ask the class If we split this class, how many files would you split it into? What would you call each one?
Answers to the questions. Three, one per colour: one that fetches the data, one that holds the state, one that draws. The names they give are good if they say the job; ours are on the next slide. The message: this is not badly written code, it is code with too many jobs. Today it is 70 lines; in the project, this screen will have the forecast, the warnings and the favourites, and will go past 400.

We split the class: the same lines, organised

Nothing new was written: the same lines moved, and each file ended up with a single colour.

The _load lines went to data/, the Future and state lines to state/, and the screen kept only the drawing. Note that the total number of lines actually went up a little (more files, more imports): organising is not shortening. The gain is that each file has a single reason to change. In the repository: git diff antes main.

Before and after: the folders

The three colours from the previous slide are three folders. models/ is not a layer: it holds the classes that pass from hand to hand (Island, Forecast), used by all three. main.dart only starts the app. The Flutter team's guide uses slightly different names (ui/ and data/); what matters is that each folder has one job.

The restaurant: three stations

Tell it as a story, with a real order: the customer asks the waiter (the screen) for the islands; the waiter looks at the pass and sees "being prepared" (the notifier, isLoading); the kitchen (the repository) goes to the supplier (the API, through the ApiClient), gets the raw ingredients (the JSON) and prepares the dish (Island); the dish reaches the pass, the bell rings (notifyListeners) and the waiter serves it. If the supplier lets them down, the kitchen tells the pass, which shows "sold out" (error), and it is the waiter who decides how to tell the customer. Before, it was a one-person restaurant: the same person waited on the tables, cooked and went to the supplier.

Ask the class Of these four, which will happen to you first in the group project?
Answers to the questions. There is no right answer; the most likely is the last one, in the very first week of the project, which starts on Wednesday. Stress one idea: none of these problems is a bug in today's code. The app works. They are growth problems, and that is why you organise before you grow. In the restaurant: with two tables, one person is enough; with twenty, or on the day that person is off, the restaurant stops.

And with AI, even more so

  • An AI writes in seconds what used to take us an afternoon. The problem is no longer writing code: it is reading and checking code.
  • Without folders, the AI puts everything wherever it lands, and the screen that does everything appears by itself, with 400 lines nobody has read.
  • With folders, you say where: "create a new repository in data/ and do not touch screens/". And when it finishes, you see straight away which folders changed.
  • The AI does not always give the same answer. Each layer on its own does: the pretend repository always returns the same three islands. You can see the result of each step and compare it with what you expected.
Rule for the project If you use AI, you decide the folder and the file. It writes, you organise and check.
The idea: AI is probabilistic, the same question gives different answers. An app split into layers, with the output of each one visible, makes the result of each step predictable and comparable. Ask them whether they have already used AI for the lesson code and where it put things. Link it to the group project: four people, each with their own AI, in the same file, is the worst of both worlds.

Each layer only talks to the one below

Ask the class Can the screen call the API directly? Can the repository show an error message on the screen?
Answers to the questions. No and no. If the screen calls the API, we are back to the one-person restaurant: the waiter went to the supplier. The repository knows no widgets: when something fails, it throws an exception; the notifier keeps it as state (error); and it is the screen that decides how to show it. In the restaurant: the kitchen does not go to the table to apologise, it tells the pass. The names vary (MVVM, Clean Architecture, "layers"), and the Flutter guide calls ViewModel what we call a notifier here; the idea is the same.

Many architectures, the same jobs

Ask the class In our app, which is the MVVM ViewModel? And the Model?
Answers to the questions. The ViewModel is ForecastNotifier; the Model is the repository and the classes in models/. The idea to get across: there is no single right architecture, there are several ways of organising the same responsibilities. MVC is the oldest (it comes from the web and desktop); MVVM is the one the official Flutter guide recommends, and it is practically ours; BLoC is a package in which state changes through events; Clean Architecture adds a layer in the middle (Domain, with the "use cases") for business rules, useful in large apps. The Flutter guide also has that layer, as optional. Anyone who understands the three responsibilities can read any of them.

Data: the repository

/// What the app can ask for. The screens only see this.
abstract class ForecastRepository {
  Future<List<Island>> fetchIslands();
  Future<Forecast> fetchForecast(String islandId);
}
  • The interface says what: the islands, the forecast of one island. Like the menu: it lists the dishes, not the recipes.
  • Each implementation says how. HttpForecastRepository asks the API; tomorrow you write one that returns fixed data.
  • The JSON does not go above this point: it leaves here already as Island.
Analogy You ask the kitchen for a dish and you get the finished dish. You do not know whether the fish came from the usual supplier, a new one or the freezer.

Data: HttpForecastRepository

/// How: HTTP to the course API, through the ApiClient.
class HttpForecastRepository implements ForecastRepository {
  HttpForecastRepository(this._api); // injected, not created here

  final ApiClient _api;

  @override
  Future<List<Island>> fetchIslands() async {
    final list = await _api.get('/v1/islands') as List<dynamic>;
    return list
        .map((item) => Island.fromJson(item as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Forecast> fetchForecast(String islandId) async {
    final json = await _api.get('/v1/islands/$islandId/forecast');
    return Forecast.fromJson(json as Map<String, dynamic>);
  }
}
Ask the class Where have we already seen fetchIslands?
Answers to the questions. It is the _load from the old screen, line by line, moved to a new place: widget.api.get became _api.get. implements forces you to write both methods of the interface; if one is missing, it does not compile. fetchForecast is ready for later on.

State: ForecastNotifier

class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repository); // injected, not created here

  final ForecastRepository _repository;

  bool isLoading = false;
  String? error;
  List<Island> islands = const [];

  Future<void> load() async {
    isLoading = true;
    error = null;
    notifyListeners(); // the screen shows the spinner
    try {
      islands = await _repository.fetchIslands();
    } catch (e) {
      error = '$e';
    } finally {
      isLoading = false;
      notifyListeners(); // the screen shows the islands or the error
    }
  }
}
Ask the class The three states of the FutureBuilder became three fields. Which ones? And what is the bell?
Answers to the questions. isLoading, error and islands. The bell is notifyListeners(): it tells whoever is listening that something changed. It rings twice: when the request goes out (the screen shows the spinner) and when the response arrives (the islands or the error). It knows no widgets.

UI: the screen only knows the notifier

class IslandsScreen extends StatelessWidget {
  const IslandsScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final forecast = context.watch<ForecastNotifier>();
    return Scaffold(
      appBar: AppBar(title: const Text('Tempo Açores')),
      body: _body(context, forecast),
    );
  }

  Widget _body(BuildContext context, ForecastNotifier forecast) {
    if (forecast.isLoading) {
      return const Center(child: CircularProgressIndicator());
    }
    // the error: the Center from before, with the Tentar de novo button
    onPressed: () => context.read<ForecastNotifier>().load(),
    // the data: the ListView.builder from before, with forecast.islands
  }
}
Rule context.watch in build: the waiter keeps an eye on the pass. context.read in the button: a quick message to the pass, without staying to watch.
It is no longer a StatefulWidget: no State, no Future, no FutureBuilder, no URL and no JSON. Ask: what would happen with read in build? The screen would stay on the spinner forever, because it never heard the second bell.

Exercise: where do you change it?

For each request, say the folder. Only one.

  1. The API now serves the islands at /v2/islands.
  2. We want each island's name in bold.
  3. When you tap "Tentar de novo" (try again), the list should empty while it loads.
  4. The API now sends nome instead of name.
  5. We want to run the app without internet, with three fixed islands.
Answers. 1: data/ (HttpForecastRepository). 2: screens/ (the title of the ListTile). 3: state/ (load() sets islands = const []). 4: models/ (the fromJson of Island). 5: data/, a new file, a pretend repository: that is tomorrow's practice. Ask for answers with hands up, one folder at a time; anyone who gets it wrong goes back to the restaurant.

Ask the class Does the card that opens and closes need Provider? And a list of favourite islands, which appears in the list and on a favourites screen?
Answers to the questions. The card does not: only the card cares whether it is open, and setState is enough. The favourites do: two screens read and change the same list. That is tomorrow's practice. The criterion is how many widgets need the state, not the size of the app.

Where we got to

  1. A class that does everything works, but it does not grow: data, state and UI mixed up.
  2. We split it into three layers, one folder each: data/, state/ and screens/, plus models/ for what passes between them.
  3. Each layer only talks to the one below.
  4. With AI, the folders say where each thing goes and let you check each step.
