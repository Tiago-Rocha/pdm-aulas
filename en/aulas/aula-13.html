Layered architecture and state management

Theory: splitting the app into layers (presentation, domain, data), the repository pattern and dependency injection; criteria for choosing between simple and complex architectures. Practice: repository, notifier and Provider connecting the interface to the data.

Repository: pdm-aula-13
Start by asking two students to show the detail screen from the homework. Ask: "where is the HTTP call?" The answer (inside the widget) is the problem this lesson solves. Do not spend more than five minutes here.

By the end of this lesson you can

  • Explain why to separate presentation, domain and data, and what each layer is allowed to know.
  • Write a repository with an interface and an implementation, and tell a DTO from a domain model.
  • Inject dependencies by constructor and distribute them with Provider, with no hidden singletons.
  • Model the state of a screen in a ChangeNotifier and connect it to the UI with watch, read, Consumer and Selector.
  • Test a notifier by swapping the repository for a fake.

Why layers

  • A widget that imports package:http is a warning sign: the UI knows too much.
  • Test without a network. A test that needs Wi-Fi is not a test, it is a lottery. With layers, you replace the data source with a fake.
  • Swap the source. API v1 to v2 (lesson 28), a local file in tests, a disk cache in lesson 16. The screens do not change.
  • Reuse. The list of locations appears on the home screen, in the favourites and on the map. One request, three screens.
  • Real example: in the Spotify or Nubank app the UI asks "give me the account" and does not know whether it came from the network, the cache or the disk.

For the tests: layers exist to isolate changes; the UI must not know about HTTP or JSON.

UI → Notifier → Repository → DataSource

LayerResponsibilityOnly knows
UI (widgets)Show the state, trigger actionsThe notifier
ViewModel / NotifierScreen state (loading, data, error) and presentation logicThe repository
RepositoryDecide where the data comes from, convert DTO to modelData sources
DataSourceTalk to the API, the database, the preferencesHTTP, SQL, files
  • Dependency rule: the arrows point down only. A layer never imports the one above it.
  • The names vary (MVVM, Clean Architecture, "layers"); the idea is the same: presentation, domain, data.

For the tests: the UI depends on the domain, never on the data; the repository is the boundary between the two.

Draw the four boxes on the board with arrows pointing down. Then ask: "can the widget call the ApiClient directly?" No. "Can the repository know about the BuildContext?" No. These two questions come up in the test.

Repository: one interface, several sources

  • One interface (abstract class ForecastRepository) and several implementations: remote, with cache, fake for tests.
  • The repository hides the origin: forecast(id) returns a Forecast, whether it comes from the network, the disk or memory.
  • DTO (Data Transfer Object): the shape of the JSON exactly as the API sends it. It changes when the API changes.
  • Domain model: the shape the app wants, with rich types (DateTime, enum, double). Stable.
  • The conversion lives in one place (ForecastDto.toDomain()). When API v2 renames fields, only the DTO changes.

For the tests: the DTO mirrors the API, the model mirrors the app; the repository converts one into the other.

Analogy A single counter. The screen asks the counter for "the forecast for Horta" and neither knows nor cares whether it came from the stockroom (the cache) or from the supplier (the API). Changing supplier does not change the screen. Testing is putting in a pretend counter (the fake) that always gives the same answer.

Dependency injection

  • Inject = whoever uses it does not create it. ForecastNotifier(repository) receives the repository by constructor instead of building it inside.
  • A hidden global singleton (ApiClient.instance) is an invisible dependency: it cannot be swapped in tests and nobody knows who depends on whom.
  • Provider: Provider<ForecastRepository>(create: …) at the root of the tree; widgets ask for it with context.read. It is what we use in the project.
  • get_it: a service locator. Simple, but it hides dependencies. Acceptable in small apps; avoid it in code you want to test.
  • Rule: constructor always; Provider to carry the instances to the widgets; never ApiClient() inside a notifier.

For the tests: constructor injection lets you swap the repository for a fake without touching the code under test.

Simple vs complex: when to scale up

SituationChoice
State of a single widget: active tab, checkbox, animationsetState
State shared by several screens, small teamChangeNotifier + Provider (our project)
Many events, auditable history, large teamsBLoC / Cubit
Typed global providers, no BuildContext, many derived valuesRiverpod
  • Google's architecture guide for Flutter recommends MVVM, repositories and constructor injection: "start simple, scale when you need to".
  • Moving from ChangeNotifier to BLoC later is easy if the layers exist. The opposite is harder.

For the tests: the right architecture is the simplest one that solves the current problem, with boundaries that leave room to grow.

Analogy Where the shopping list lives. A sticky note on the fridge in one room (setState: only that screen sees it); a board in the kitchen that the whole house checks and that tells everyone when it changes (ChangeNotifier + Provider); a ledger with every change dated and who made it (BLoC: events and states). The board is enough for most houses.
Ask the class: "does the settings form with two switches need Provider?" No, setState is enough. "And the favourites, which appear on three screens?" Yes. The criterion is how many screens share the state.

1. ForecastRepository: interface and implementation

abstract class ForecastRepository {
  Future<List<Location>> locations();
  Future<Forecast> forecast(int locationId);
}

class ForecastRepositoryApi implements ForecastRepository {
  ForecastRepositoryApi(this._api);   // injected by constructor

  final ApiClient _api;

  @override
  Future<List<Location>> locations() async {
    final json = await _api.get('/v1/locations') as List<dynamic>;
    return json
        .map((e) => Location.fromJson(e as Map<String, dynamic>))
        .toList();
  }

  @override
  Future<Forecast> forecast(int locationId) async {
    final json = await _api.get('/v1/forecast/$locationId') as Map<String, dynamic>;
    return Forecast.fromJson(json);
  }
}

1. Repository: what matters

  • The interface says what (locations, forecast); the implementation says how (HTTP, paths, JSON). The UI only sees the interface.
  • The ApiClient comes in through the constructor. In tests a MockClient comes in; in lesson 16 a database comes in too.
  • JSON does not leave this layer. Whoever calls locations() receives a List<Location> and never sees a Map.
  • In the starter the DTO and the model are the same class (fromJson). When the API changes shape, separate them.
  • The implementation name says the source: …Api, …Cache, …Fake. You will have all three.

2. ForecastNotifier: the state of the screen

class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repo);

  final ForecastRepository _repo;

  bool isLoading = false;
  String? error;
  List<Location> locations = const [];

  Future<void> load() async {
    isLoading = true;
    error = null;
    notifyListeners();
    try {
      locations = await _repo.locations();
    } on ApiException catch (e) {
      error = e.message;
    } catch (_) {
      error = 'Something went wrong. Try again.';
    } finally {
      isLoading = false;
      notifyListeners();
    }
  }
}

2. Notifier: what matters

  • ChangeNotifier is a Flutter class with a list of listeners. notifyListeners() tells them; Provider turns that into rebuilds.
  • The state is three fields: isLoading, error, locations. Tomorrow we replace them with a sealed class that rules out impossible combinations (loading and error at the same time).
  • Two notifications per load: one at the start (shows the loading) and another in the finally (shows the result or the error).
  • The notifier does not know about widgets, BuildContext or SnackBar. That is why it can be tested without pumpWidget.
  • A human error message by default. The technical one (e.toString()) goes to the log, not to the screen.
Exercise 2 Create DetailNotifier with load(int locationId) that stores a Forecast?. The test test/detail_notifier_test.dart checks isLoading before and after.

3. Provider: wiring the pieces at the root

void main() {
  final api = ApiClient(baseUrl: 'https://api.pdm.example'); // real URL on the API page

  runApp(
    MultiProvider(
      providers: [
        Provider<ForecastRepository>(
          create: (_) => ForecastRepositoryApi(api),
        ),
        ChangeNotifierProvider(
          create: (context) =>
              ForecastNotifier(context.read<ForecastRepository>())..load(),
        ),
      ],
      child: const TempoApp(),
    ),
  );
}

The order matters: the notifier asks for the repository with context.read, so the repository has to come first in the list.

3. The screen only knows the notifier

class LocationsScreen extends StatelessWidget {
  const LocationsScreen({super.key});

  @override
  Widget build(BuildContext context) {
    final notifier = context.watch<ForecastNotifier>();

    if (notifier.isLoading) {
      return const Center(child: CircularProgressIndicator());
    }
    if (notifier.error != null) {
      return Center(
        child: FilledButton.icon(
          onPressed: () => context.read<ForecastNotifier>().load(),
          icon: const Icon(Icons.refresh),
          label: Text('${notifier.error} · Try again'),
        ),
      );
    }
    return ListView(
      children: [
        for (final l in notifier.locations)
          ListTile(title: Text(l.name), subtitle: Text(l.island)),
      ],
    );
  }
}

3. Provider: what matters

  • context.watch<T>() subscribes: the widget rebuilds on every notifyListeners. Only inside build.
  • context.read<T>() does not subscribe: for calling methods in callbacks (onPressed, initState).
  • Consumer<T> limits the rebuild to a subtree. Selector<T, R> only rebuilds when R changes (for example locations.length).
  • Classic mistakes: watch inside onPressed throws an exception; read in build does not update; ProviderNotFoundException when the widget is outside the Provider's tree.
  • The screen is a StatelessWidget again: the state lives in the notifier, the widget only describes it.

4. Testing by swapping the repository for a fake

class ForecastRepositoryFake implements ForecastRepository {
  ForecastRepositoryFake({this.fails = false});
  final bool fails;

  @override
  Future<List<Location>> locations() async {
    if (fails) throw const ApiException('no network');
    return const [Location(id: 3, name: 'Ponta Delgada', island: 'São Miguel')];
  }

  @override
  Future<Forecast> forecast(int id) => throw UnimplementedError();
}

void main() {
  test('load fills locations', () async {
    final n = ForecastNotifier(ForecastRepositoryFake());
    await n.load();
    expect(n.locations, hasLength(1));
    expect(n.error, isNull);
  });
  test('load stores the error when the repository fails', () async {
    final n = ForecastNotifier(ForecastRepositoryFake(fails: true));
    await n.load();
    expect(n.error, 'no network');
  });
}

4. Fakes: what matters

  • The fake implements the same interface. The notifier does not know it is being fooled: that is exactly the point of the interface.
  • No network, no pumpWidget, no Provider: a pure unit test that runs in milliseconds.
  • One fake per scenario (fails: true) tests the error path, which is the one nobody tests by hand.
  • In lesson 25 we replace hand-written fakes with mocktail. The idea is the same.
  • The same fake is useful for developing the UI without a backend: swap the create in main and the app runs in demo mode.
Exercise 4 Write the test "load clears the previous error": a notifier that failed once and then loads successfully has to end up with error == null. You need a fake that fails only on the first call.

5. Favourites in memory, shared between two screens

class FavoritesNotifier extends ChangeNotifier {
  final Set<int> _ids = {};

  bool contains(int locationId) => _ids.contains(locationId);
  int get total => _ids.length;

  void toggle(int locationId) {
    if (!_ids.add(locationId)) _ids.remove(locationId);
    notifyListeners();
  }
}

// In the list: an icon that reacts to the state
IconButton(
  icon: Icon(context.watch<FavoritesNotifier>().contains(l.id)
      ? Icons.star
      : Icons.star_border),
  onPressed: () => context.read<FavoritesNotifier>().toggle(l.id),
)

// On another screen: a badge with the total, which only rebuilds when the total changes
Selector<FavoritesNotifier, int>(
  selector: (_, f) => f.total,
  builder: (_, total, __) => Badge(label: Text('$total'), child: const Icon(Icons.star)),
)
