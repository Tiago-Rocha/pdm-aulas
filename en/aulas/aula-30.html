Why size matters

  • A Google study with Play data (2017) measured it: for every extra 6 MB in the APK, 1% fewer completed installs. In markets with expensive data and full 32 GB phones, the first app to be deleted is the biggest one.
  • Store limits: Play accepts AABs up to 200 MB of compressed download (plus Play Asset Delivery for games); the App Store accepts up to 4 GB, but above 200 MB iOS asks for confirmation before downloading over mobile data. Many people never confirm.
  • Updates: Play sends deltas, but each release is a download for everyone. A 100 MB app with a weekly release uses up 400 MB a month for each user, and some people turn off automatic updates because of that.
  • Flutter: an empty app in release weighs 4 to 5 MB per architecture, most of which is the engine. The rest grows with packages, the plugins' native code, images and fonts. Tempo Açores with a map, fonts and background images reaches 20 to 30 MB if nobody is looking.
  • Two measures: download size (compressed, what the store shows) and installed size (uncompressed, what the user sees in the settings). The installed size is almost always double.

For the tests: size costs installs and updates; Play limits the AAB to 200 MB of download and iOS asks for confirmation on mobile data above 200 MB.

Ask two students to open their phone's settings and read out the installed size of WhatsApp and Instagram; it usually comes out at 200 to 500 MB, and nobody knew. Then ask how many apps they have already deleted for lack of space. Do not spend more than three minutes on this slide.

AAB and split per ABI

  • The universal APK (flutter build apk) carries the engine and the compiled Dart code for the three Android architectures: armeabi-v7a, arm64-v8a and x86_64. All of it goes to the phone, which only uses one.
  • flutter build apk --split-per-abi generates three APKs, one per architecture, each about a third of the size. It is the right format for Firebase App Distribution (lesson 27) and for installing with adb.
  • flutter build appbundle generates an AAB: Play receives the bundle and generates, signs and delivers the right APK for each phone (architecture, screen density, language). Mandatory for new apps on Play since 2021. Typical download: half of the universal APK.
  • On iOS, App Store Connect does the equivalent with App Thinning: each iPhone receives only its own architecture and the @2x or @3x assets it uses. There is nothing to configure.
  • Deferred components (Android only, via Play Feature Delivery): parts of the app in Dart and assets downloaded on demand. Worth it in large apps with rarely used modules (augmented reality, an editor); for Tempo Açores it is too much complexity.

For the tests: the AAB lets Play deliver only what each phone needs; the universal APK carries the three architectures; the split per ABI is the middle ground for distributing outside the store.

Tree shaking, images and fonts

  • Code tree shaking: the AOT compiler in release leaves out the Dart code that is never called. A large package from which you use one function weighs little; a package with native code (Kotlin, Swift) always weighs, because native code does not go through the Dart compiler.
  • Icon tree shaking: in release Flutter rebuilds MaterialIcons with only the icons used as const. Icons.wb_sunny costs bytes; the whole font would cost 1.6 MB. If you build icons dynamically with IconData(codePoint) the build fails and asks for --no-tree-shake-icons, which turns the optimisation off.
  • Images are the biggest contributor in most apps. A 4000 px PNG for a 300 px card is waste; WebP at quality 80 comes to a third; 2.0x and 3.0x variants only when the screen shows them; SVG for icons and logos; background photos served over the network with a cache. flutter build does not compress images for you.
  • Fonts: each weight of a family is 100 to 300 KB. Include only the weights you use (Regular and Bold, not all nine). google_fonts downloads at runtime by default: good for size, bad offline and at startup; for production bundle the fonts in pubspec.yaml.
  • Assets: everything under flutter: assets: goes into the bundle, referenced or not. Test JSON, design files, the whole assets/ folder declared out of laziness.

For the tests: unused Dart code and the Material icons drop out by themselves in release through tree shaking; images, fonts and assets do not: those you cut yourself.

Startup: up to the first frame

  • Cold, in order: the OS creates the process → shows the native splash (LaunchScreen.storyboard on iOS, the launch theme on Android) → the embedder initialises the engine and the Dart VM (100 to 300 ms in release) → main() → runApp → first build → first frame → data. Warm, the process already exists and the OS only brings the app to the front.
  • Reference values: Android Vitals flags a cold start above 5 s as excessive; iOS kills the app if startup takes more than about 20 s (watchdog). The target from lesson 26: under 2 s cold, measured on a mid-range phone, not on yours.
  • The native splash (flutter_native_splash, lesson 27) covers the gap between the tap and Flutter's first frame; without it there is a white screen. Do not prolong it with a second, 3 s animated splash inside Flutter: you double the perceived time.
  • Deferred work: in main() before runApp only the indispensable (WidgetsFlutterBinding.ensureInitialized(), reading small preferences). Firebase, database, Remote Config and HTTP requests start after the first frame, in parallel, with the UI showing the cache or a skeleton. An await http.get before runApp is the classic mistake.
  • Measuring: flutter run --profile --trace-startup writes build/start_up_info.json with timeToFirstFrameMicros; the Performance tab in DevTools shows the startup timeline; adb shell am start -W gives the total time on Android; on iOS, Instruments with the App Launch template. Never in debug.

For the tests: a cold start includes the engine and the Dart VM before main; the native splash covers that gap; the heavy work goes after the first frame.

Show live the start_up_info.json of your app in profile on your phone and then the same with an await Future.delayed(2 s) before runApp: the number goes up 2 seconds and the splash hangs there. Ask: "what is in your main before runApp?" Whoever answers "the token and the preferences" is fine; whoever answers "loading the locations" has a TODO.

OTA and code push: Shorebird

  • Through the store: build, upload, review (hours to days), rollout, and the user has to update; most take weeks. A critical bug released on a Tuesday can be live until the end of the following week.
  • Code push: the app downloads new Dart code and applies it on the next launch, without going through the store. Shorebird is the implementation for Flutter, created by former members of the Flutter team: shorebird release android publishes the base build, shorebird patch android sends the fix for that release. Expo Updates does the same in React Native; Microsoft's CodePush shut down in 2025.
  • What can change: Dart code, that is, logic, parsers, texts, layout. What cannot: native code (Kotlin, Swift, plugins with a native part), permissions, icon, Flutter version. For those, a new release through the store. A patch always belongs to one specific release.
  • Apple's rules: guideline 2.5.2 forbids downloading code that changes the app's features; the developer agreement allows interpreted code as long as it does not change the primary purpose. Shorebird complies because on iOS the patch runs in a Dart interpreter; you comply if you use patches for fixes, not for features hidden from review. Google has an equivalent rule.
  • Limits: the patch only reaches those who open the app with network; you can roll it back in the dashboard, but it has already run for those who received it; on iOS interpreted code is slower than AOT. It does not replace tests or the forced update.

For the tests: code push only changes Dart code, never native code or permissions; Apple allows it as long as it does not change the app's purpose.

Analogy Code push is swapping the contents of the newspaper without reprinting the front page. Only the Dart (the text on the pages) changes; the native "paper", the permissions and the icon stay the same, and that is why it does not go through a new review. Apple only accepts the swap if the newspaper's rules, its declared purpose, do not change.

Forced update and minimum versions

  • Why: v1 of the API is switched off on 09/12 (lesson 28) and anyone left on a version of the app that only speaks v1 starts seeing errors. Banks and Revolut force updates; WhatsApp expires old versions on a set date.
  • Mechanism: a value in remote config (Firebase Remote Config, lesson 26, or a /config endpoint of your own) with min_version, latest_version and a message. At startup the app reads its own version with package_info_plus and compares using version semantics (pub_semver), never as strings: as strings, "1.10.0" is less than "1.9.0".
  • Two levels: below latest_version, a dismissible notice ("update when you can"); below min_version, a blocking screen that does not close, with a button to the store (url_launcher to market://details?id=... or the App Store link). On Android, in_app_update uses Play to update without leaving the app; on iOS there is no API, only the link.
  • Fails open: if the config does not load (no network, server down), the app lets the user in. A user in airplane mode cannot be locked out by a bug of yours. And never set min_version above the version that is already approved in the store: you lock out every user with no alternative.
  • Supporting those who do not update: the backend keeps the old API during the deprecation window, the app ignores unknown fields, and the X-App-Version header (lesson 12) tells the backend who is still behind. Forcing is the last resort, once or twice a year; overused, it leads the user to uninstall.

For the tests: a forced update is a minimum version in remote config with a blocking screen; it fails open without network and never points to a version that is not in the store yet.

Tell a real case of an app that pointed the forced update to a version still in review and locked its users out for a day; if you do not have one of your own, one from a Portuguese bank will do. Ask: "does Tempo Açores need a forced update on 09/12?" Yes, if there is any tester with the v1 build installed; it is the example that this is not theoretical.

To analyze your app size in Dart DevTools, run the following command:
dart devtools --appSizeBase=apk-code-size-analysis_01.json
  • --analyze-size requires a single architecture, hence --target-platform android-arm64; it cannot be combined with --split-per-abi.
  • libflutter.so is the engine, fixed; libapp.so is your compiled Dart with the packages; classes.dex is the plugins' Kotlin and Java; flutter_assets/ is what you declared in pubspec.yaml. The "Dart AOT symbols" section says which packages weigh inside libapp.so.
  • In this example, a 5 MB background image is 27% of the app. As WebP at 1080 px it comes to 300 KB. google_fonts bundling nine weights of Inter is the second target.

Exercise: what to do with the number

  • Command run on the group's project, in release, for android-arm64, with no errors.
  • The biggest contributor that is not the engine identified: a file or a package, with its size and percentage of the total.
  • Decision made: compress, remove, replace with network plus cache, or accept with a written justification.
  • If it is an image or a font: fixed now, in a 10-minute PR, and measured again.
  • If it is a package: decided whether it is worth its weight, with the table from lesson 28.
  • README with an "App size" section: size before, biggest contributor, what you changed, size after.
Exercise Fifteen minutes. Run flutter build apk --analyze-size --target-platform android-arm64 on the group's project and find the biggest contributor that is not libflutter.so.
