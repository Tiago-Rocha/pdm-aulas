The programme: everyone takes one home

// flutter run --dart-define=CLIENT_SECRET=...
const clientSecret = String.fromEnvironment('CLIENT_SECRET');
  • --dart-define takes the secret out of the repository. It does not take it out of the APK: the value is compiled into libapp.so.
  • That is why an app secret is worth little: it only gets the visitor wristband. What protects Ana's account is her login.
Question for the class So what is --dart-define for, if the secret ends up in the APK?
Answers to the questions. It keeps the secret off GitHub, where it stays forever and where any collaborator, or a repository that one day goes public, exposes it. And each group gets its own without touching the code. The APK only reaches whoever installs it; the repository reaches everyone who ever has access to it. In production, apps carry no secret at all (yesterday's PKCE) and the server can revoke a secret that leaks.

The festival's memory: git

git log -S "the-group-secret" --oneline
  • Never in the repository: the clientSecret, the signing keystore (*.jks) and key.properties. The project's android/.gitignore already ignores the last two.
  • If a secret went into a commit, it counts as published: ask for a new one and switch to it. Deleting the commit is not enough: whoever already pulled has a copy.
git log -S finds the commits that added or removed that text. They will use it in a moment on the group repository, with the real secret. It works the same in PowerShell and in the Mac terminal.

The queue: speaking into the doorman's ear

  • HTTPS always. Android blocks http:// since version 9; so does iOS (App Transport Security). Turning this off "to test" is one of the most common mistakes.
  • Never accept any certificate: badCertificateCallback returning true lets a fake doorman in.
  • Certificate pinning: the app carries the real doorman's badge and checks it. It protects against whoever controls the network; it is expensive: when the server certificate changes, old apps stop working. Worth it for banks and health, not for Tempo Açores.
If they ask how someone reads the traffic: on open Wi-Fi anyone on the network sees the packets, and whoever runs the router sees everything. With HTTPS they see the server address but not what is said.

The bag check at the entrance: only what is needed

  • Ask for the permission when the person taps the feature, and say why in one sentence before the system prompt.
  • Ask for the smallest: approximate location is enough for "the nearest island". If the person says no, the app keeps working without it.
  • The stores reject permissions the app does not justify.
Watch out In debug, Flutter adds the INTERNET permission for you. In the release APK, it only has it if it is in android/app/src/main/AndroidManifest.xml. Without it, the APK you hand in has no network.
The INTERNET permission is not shown to the user (it is "normal", not "dangerous"), but it must be declared. The project template does not have it in the main manifest: they will add it in the sprint check.

Dart has one thread per isolate: the whole app runs on one barman. Everything he does in a row, without a break, the queue waits for. Come back to this table at the end of the performance part.

async does not call another barman

// before: the UI thread decodes 5 MB, the queue stops
return jsonDecode(response.body);

// after: a second isolate decodes it, the UI keeps going
return compute(jsonDecode, response.body);
  • await http.get(...) does not block: waiting for the network is not work, and the barman serves others meanwhile.
  • A 5 MB jsonDecode blocks, even inside an async function: it is 120 ms of sums in a row.
  • The second barman has his own till (separate memory): he receives text and numbers, and returns data. He does not see the BuildContext or the notifiers.
The classic test question: "does putting jsonDecode in an async function fix the jank?" No: async only frees the barman at the awaits. Creating an isolate costs a few milliseconds: for the course API responses, which are small, it is not worth it. It is for large JSON, images, calculations.

Glasses already poured: const and small widgets

  • setState and notifyListeners rebuild the widget and everything below it. The higher up, the more work.
  • Split the screen into small widgets: what changes lives in a widget of its own.
  • const Text('Islands') is created once and never rebuilt. flutter analyze tells you where it is missing.
  • With Provider: context.select instead of context.watch, to rebuild only when the value the widget uses changes.
DevTools shows how many times each widget is rebuilt (Rebuild stats, in the Performance tab). Not for today; just so they know it exists.

Security check: 5 minutes, on the group repository

git log -S "the-group-clientSecret" --oneline
git grep -n "http://"
git grep -n "uses-permission" -- android
  1. The first command must show nothing. If it shows a commit, the secret was published: ask for a new one in the credentials issue.
  2. The second one neither: everything on https://.
  3. The third must show INTERNET in android/app/src/main/AndroidManifest.xml. If it only shows up in debug and profile, release is missing it.
Do Run the three commands. If INTERNET is missing, add it in a PR, right after <manifest ...>: <uses-permission android:name="android.permission.INTERNET"/>
The commands are git commands and work in PowerShell. The secret goes in quotes, without writing it anywhere else. The project template only has INTERNET in the debug and profile manifests, so every group will need the line.
