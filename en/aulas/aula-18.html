Secrets: what an attacker gets out of an APK in 5 minutes

  • An APK is a zip: unzip app.apk, strings libapp.so | grep -i secret. jadx decompiles the Kotlin; Dart compiled AOT still has its strings readable.
  • Consequence: everything that goes into the binary is public. A "secret" on the client is not a secret, it is obfuscation.
  • Never in the repository: .env.json in .gitignore; --dart-define-from-file=.env.json in development; in CI they come from GitHub Secrets.
  • If it has already been committed, it is compromised: rotate the secret (ask the teacher for another one). Deleting it from the history is not enough: someone has already cloned.
  • What can go on the client: restricted public keys (Maps limited to the package), identifiers with no power. What cannot: API keys with write access, passwords, OAuth client secrets.

For the tests: everything in the APK is public; secrets live on the server or come in through dart-define, and never in git.

Analogy An APK is a zip: anyone can open it and see what is inside. Putting a secret in the code is writing the password on a piece of paper and sticking it to the door. Obfuscating is writing the paper in small letters: it is still on the door. The only place where the password is not in plain sight is on the inside, on the server.
An awkward question that is worth asking: "so the group's client id and secret, which go in through dart-define, also end up in the APK?" Yes. That is why the course API issues short-lived tokens per group and can revoke them: the group's secret is a classroom secret, not a production one. In production the login belongs to the user, not to the app.

HTTPS always; certificate pinning when it is worth it

  • HTTPS is mandatory: Android has blocked cleartext traffic since version 9; iOS requires TLS 1.2+ through App Transport Security. Turning this off "to test" is mistake M5.
  • HTTPS protects you from whoever is in the middle (the café Wi-Fi), but trusts any CA installed on the system. A proxy with an installed certificate (Charles, mitmproxy) sees everything.
  • Pinning: the app only accepts the certificate or the public key it knows. The proxy stops working; so does a compromised CA.
  • Cost: when the certificate rotates, old versions of the app stop connecting. It needs a backup pin, a rotation plan and forced update (lesson 30).
  • Who does it: banks, health, apps facing targeted attacks. A weather app does not need it. In Flutter: SecurityContext or http_certificate_pinning.

For the tests: pinning protects against compromised CAs and proxies, at the cost of maintenance every time the certificate rotates.

Minimal permissions, requested at the right moment

  • Each permission is a question to the user and a line in the store review. Request only what the feature needs: approximate location is enough for "nearest location".
  • At the right moment: when the user taps "Near me", not at launch. A screen that explains before the system dialog (pre-prompt) raises the acceptance rate.
  • Mandatory justification: NSLocationWhenInUseUsageDescription on iOS and the usage declaration on Google Play. Vague text ("we need your location") is grounds for rejection.
  • Denial: the app keeps working (full list instead of "near me"). Permanent denial: a button that opens Settings, without insisting.
  • What the stores reject: permissions with no visible feature, background location without a strong reason, SMS and call log outside the default apps.

For the tests: minimal permission, requested in context, with a justification, and the app works if it is denied.

Privacy: GDPR, ATT, labels and data safety

  • GDPR: a legal basis for each piece of data collected, minimisation, the right to erasure. Explicit consent, not pre-ticked, for analytics and marketing.
  • App Tracking Transparency (iOS 14.5+): a mandatory dialog before tracking the user across apps. No "Allow", no IDFA. Apple rejects anyone who tries to get round it.
  • Privacy nutrition labels (App Store) and the Data safety form (Play): you declare what you collect and why. A false declaration is grounds for removal.
  • In practice: a privacy policy with a public URL, even for a weather app. Logs and crash reports with no personal data.
  • In Tempo Açores: location used once for the nearest location and not stored; favourites tied to the group, not to people.

For the tests: ATT is requested before tracking; the labels and the data safety form have to match what the app does.

Show the privacy page of a well-known app on the App Store (Instagram's is the most impressive). Then the one for a well-made weather app. Two minutes, and the difference is clear.

Obfuscation and root detection in one sentence each

  • flutter build apk --obfuscate --split-debug-info=build/symbols renames the Dart symbols. It makes the binary harder to read; it does not hide strings or secrets.
  • Keep the split-debug-info folder for each version: without it the stack traces of production crashes are unreadable (lesson 26).
  • Android minification (R8) is on by default in release. Some plugins need ProGuard rules; flutter build warns you.
  • Root and jailbreak: detect a compromised device and limit features. Banks do it; it can be bypassed; it does not replace any of the defences above.

For the tests: obfuscation makes reverse engineering harder but does not protect secrets; root detection is an extra layer, not a guarantee.

Isolates: separate memory, heavy work off the UI

  • Dart runs on one thread with an event loop. async/await frees the thread while it waits (network, disk), but frees nothing while it computes.
  • An isolate is another thread with its own memory. It does not share objects: what goes in and out is copied by message.
  • compute(function, argument) (or Isolate.run) creates an isolate, runs the function and returns the result as a Future.
  • Use it for: large JSON (hundreds of KB), sorting or filtering thousands of items, processing images, encrypting.
  • What cannot pass between isolates: BuildContext, controllers, sockets, plugin instances. Pass plain data and models.
import 'dart:convert';
import 'package:flutter/foundation.dart';

List<Forecast> _parseForecasts(String body) {
  final items = jsonDecode(body) as List<dynamic>;
  return items.map((e) => Forecast.fromJson(e as Map<String, dynamic>)).toList();
}

// The function has to be top-level or static: it will run in another isolate.
Future<List<Forecast>> parseForecasts(String body) => compute(_parseForecasts, body);

For the tests: async/await solves waiting; isolates solve computation. A 5 MB parse with await still blocks the interface.

Analogy Two cooks in separate kitchens, each with their own pots (the memory). They share nothing; they pass dishes through the hatch, and what passes is a copy (the messages between isolates). The cook who serves the dining room (the main isolate) never leaves the room empty: while the other one peels the 5 MB JSON, this one keeps serving the customers, which are the frames.
Ask: "if I put jsonDecode inside an async function, does the UI stop blocking?" Most say yes. Explain that async only yields the thread at the awaits, and jsonDecode has no await inside it. Creating an isolate costs a few milliseconds: for small JSON it does not pay off.

Rebuilds: cheap, but not free

  • setState rebuilds the whole widget and everything below it. If the whole screen is one StatefulWidget, a counter changing rebuilds the entire list.
  • const: a const widget is created once and reused; the framework skips it on rebuild. The prefer_const_constructors lint points out the candidates.
  • Splitting widgets: what changes goes in a small widget with its own state; what does not change stays outside.
  • Selector and context.select: rebuild only when the field that matters changes, not on every notifyListeners().
  • Keys: ValueKey(location.id) on list items that get reordered or removed, so the framework reuses the right state.
  • To see them: DevTools → Inspector → Track widget builds; Android Studio → Flutter Performance → rebuild counts.

For the tests: build running many times is normal; the problem is rebuilding many widgets that did not change.

Frames: measure in profile, never in debug

  • 60 fps gives 16.6 ms per frame; 120 fps gives 8.3 ms. Each frame goes through the UI thread (Dart, build, layout) and the raster thread (painting). If one of them goes over budget, the frame is skipped: jank.
  • Performance overlay (P in the flutter run terminal, or showPerformanceOverlay: true): two graphs, raster on top and UI below. Red bar = slow frame.
  • Debug mode runs JIT, with asserts and extra checks: it is 2 to 5 times slower and represents nothing. Measure with flutter run --profile on a real phone.
  • Shaders: with Impeller (the default on current iOS and Android) first-animation jank has practically disappeared; the old SkSL warm-up was a patch for Skia.
  • DevTools → Performance: frame timeline, what took time in each one, and the Enhance tracing button to see builds and layouts.

For the tests: performance is only measured in profile or release mode, on a physical device.

Analogy The screen asks for a new image 60 times a second, and each request has 16 ms to be served. An 80 ms jsonDecode is a customer who holds up the counter for five requests in a row: the others are left waiting and the screen stutters. That is the jank the overlay shows in red.
Show the overlay on your app with the phone projected. Scroll fast through a list with uncached images and let red bars appear. Then turn on cached_network_image and repeat. Two minutes, and the class understands what to look for in the exercise.

Battery and network

  • The radio (Wi-Fi, 4G/5G) is one of the biggest consumers. Each request wakes it up and keeps it on for a few seconds: batch requests instead of making ten in a row.
  • No polling. Asking the server "anything new?" every 30 seconds drains the battery. Alternatives: push (lesson 19), background sync with constraints (lesson 23), refresh on open.
  • Location only when needed, with the minimum accuracy that will do. GPS on continuously drains a phone in a few hours (lesson 21).
  • Respect battery saver mode and Data Saver: fewer animations, fewer images, no preloading.
  • Examples: Instagram preloads images in batches while the radio is already awake; Google Maps only turns on high-accuracy GPS during navigation.

For the tests: the cost of a request is not just the bytes; it is waking up the radio.

20-minute exercise: measure your app

  1. Run in profile with the phone connected by cable: 
    flutter run --profile
  2. Turn on the overlay: press P in the terminal. Scroll the list of locations, open a detail, go back. Look for red bars.
  3. Open DevTools (v in the terminal) → Inspector → enable Track widget builds. Interact again and see which widgets rebuild on each tap.
  4. Find an unnecessary rebuild: a widget that rebuilds without its data changing. Fix it with const, by extracting a widget, or with Selector.
  5. Find a widget that can be const and is not yet. Run flutter analyze: the prefer_const_constructors lint helps.
Exercise 1 Open a PR with the two fixes and, in the description, a screenshot of the overlay before and after. A colleague from another group reviews it. If your app does not have a list with real data yet, measure the solucao/ from lesson 14.

What matters when you are measuring

  • A single red bar when a screen opens is normal (first build). Red bars in a row during scrolling are what you are looking for.
  • If the top graph (raster) is high, the problem is painting: large images, shadows, Opacity in lists, ClipRRect on every item.
  • If the bottom graph (UI) is high, the problem is Dart: heavy build, parsing on the main thread, logic inside build.
  • A whole screen rebuilding when only one text changed means the setState or the watch is too high up in the tree.
  • Do not optimise what you have not measured. One const too many does no harm; an architecture twisted for an imaginary gain does.
Frequent question: "the overlay shows red on the emulator". Explain that the emulator rasterises in software and does not count. Anyone without a phone uses one from a colleague in the group. Give 20 minutes and then ask two groups to show the before and after.

Homework: audit of secrets and permissions

  1. Secrets in the history and in the code. Run in the group's repository: 
    git log -p | grep -inE 'secret|token|password|api_key' | head -20
grep -rniE 'secret|password' lib/ android/app/src/main/ ios/Runner/
    Any result with a real value is a finding. A variable name is not.
  2. .gitignore has to include .env.json, *.jks, key.properties and *.keystore. Confirm with git check-ignore -v .env.json.
  3. AndroidManifest.xml: list each <uses-permission>. For each one, is there a feature that uses it? Also check android:allowBackup and usesCleartextTraffic.
  4. Info.plist: does each NS…UsageDescription key have a real, specific text? Is there no NSAllowsArbitraryLoads?
  5. Record the result in the "Security audit" issue: what was found, what was fixed, who fixed it. Close it through a PR.

It takes 15 minutes per group. Do it at home, or at the end of the lesson if the measurement exercise finishes early.
