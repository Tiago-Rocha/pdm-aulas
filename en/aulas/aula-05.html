Anatomy of a Flutter project and first app

Theory: what the flutter create command generates, the role of each folder, pubspec.yaml and the differences between debug and release. Practice: cloning the course's first repository and building the first screen of the Tempo Açores app on the phone.

Repository: pdm-aula-05

By the end of this lesson you can

  • Read and change a pubspec.yaml: dependencies, versions with ^, assets, and the role of pubspec.lock.
  • Tell the debug, profile and release modes apart and choose the right one for each situation.

What flutter create generates

Folder or fileWhat it is for
lib/Your Dart code. Everything you write lives here, starting with main.dart.
test/Automated tests. flutter test runs everything in here (tests in a later lesson).
android/ and ios/The native projects that wrap the app: Gradle and Kotlin on one side, Xcode and Swift on the other. You only go there for permissions, icons, signing.
web/, macos/, linux/, windows/The same for the other platforms. You can delete the ones you do not use.
pubspec.yamlThe project's identity card: name, version, dependencies, assets, fonts.

For the tests: the app's code is in lib/; android/ and ios/ are generated native projects that Flutter wraps.

Open a freshly created project in VS Code and walk through the folders live. Show the size of the android/ folder vs lib/. Ask: why is there a whole Android project if we write Dart? Answer: the embedder we talked about last week.

What gets committed and what does not

  • flutter create already generates a correct .gitignore. Do not delete it.
  • Never in the repository: build/ (binaries, hundreds of MB), .dart_tool/ (compiler cache), .idea/ and *.iml (IDE), android/local.properties (paths on your laptop).
  • Always in the repository: lib/, test/, pubspec.yaml, pubspec.lock, analysis_options.yaml, the native folders, assets/.
  • pubspec.lock is committed in apps (everyone builds with the same versions) and is not committed in published packages.
  • Secrets (API keys, the signing key.properties) never go into git. We come back to this in a later lesson.
Warning sign If git status shows hundreds of files in build/, the .gitignore is not working. Fix it before the first commit.

pubspec.yaml

name: tempo_acores
description: Previsão meteorológica para os Açores.
publish_to: 'none'
version: 1.0.0+1                # versionName + versionCode (class 31)

environment:
  sdk: ^3.11.0

dependencies:                   # ships inside the app
  flutter:
    sdk: flutter
  google_fonts: ^8.2.1
  intl: ^0.20.3

dev_dependencies:               # development and tests only
  flutter_test:
    sdk: flutter
  flutter_lints: ^6.0.0

flutter:
  uses-material-design: true
  assets:
    - assets/img/

pubspec.yaml: what matters

  • dependencies go into the final binary; dev_dependencies (lints, tests, code generators) do not.
  • ^6.2.1 means "any 6.x.y from 6.2.1 onwards, but not 7". This is semver: the major version changes when the API breaks compatibility.
  • flutter pub get resolves and downloads; flutter pub add name adds to the pubspec and does the get; flutter pub upgrade moves up to the newest versions allowed; flutter pub outdated shows what is behind.
  • pubspec.lock pins the exact version that was resolved. With it, you and your classmates build exactly the same code.
  • The flutter: section declares assets and fonts. An image that is not listed here does not exist for the app.

For the tests: ^1.2.3 accepts up to <2.0.0; pubspec.lock pins exact versions.

Build modes

ModeHow it compilesWhat it is for
DebugJIT on the Dart VM. Asserts on, hot reload, DevTools, "DEBUG" banner in the corner.Developing. Slow and large; never any good for measuring performance.
ProfileAOT, like release, but keeps the telemetry for DevTools.Measuring performance on a real phone (later on).
ReleaseOptimised AOT, no asserts, no DevTools, tree shaking.What goes to the store and to the testers.

An app that seems slow in debug can be perfectly fast in release. The opposite never happens.

For the tests: debug uses JIT and allows hot reload; release uses AOT and is the only mode that gets distributed.

Run flutter run --release on your phone live and show the difference in startup. Stress this: a DEBUG banner in the README screenshots earns a comment in the assessment.

The command line

CommandWhat it does
flutter runBuilds in debug and installs on the chosen device. In VS Code it is F5, with the device chosen in Flutter: Select Device; saving a file does a hot reload and the ↻ button does a hot restart. In the terminal: r hot reload, R hot restart, q quit. -d chooses the device, --release the mode.
flutter build apk / appbundle / ipaGenerates the release binary. The .aab is what goes to Google Play.
flutter analyzeRuns the static analyser and the lints without compiling. Zero warnings is the rule for the project.
flutter testRuns the tests in test/.
flutter doctor / flutter devicesState of the environment / connected devices and available emulators.

VS Code and Android Studio call exactly these commands underneath their buttons.

DevTools

  • A set of tools in the browser, connected to the app in debug or profile. With flutter run a link appears in the terminal; in VS Code, the "Flutter: Open DevTools" command.
  • Widget Inspector: the widget tree, live. "Select widget mode" lets you tap the screen and see which widget it is. The Layout Explorer shows the constraints (tomorrow).
  • Performance: frame chart; every bar above the 16 ms line is jank. It shows excess rebuilds.
  • Network: all HTTP requests with headers, body and timings. You will use it when the app talks to the API.
  • Memory and Logging: memory leaks and the output of debugPrint.

For the tests: the inspector is for layout, the Performance tab is for jank, and neither of them works in release.

Anatomy of an app

  • main() is the entry point. It calls runApp(widget), which attaches the widget to the root of the screen and starts the engine.
  • MaterialApp is the root of almost every app: it defines the theme, routes, localisation and title. There is one per app.
  • Scaffold is the structure of a screen: appBar at the top, body in the middle, floatingActionButton, drawer, bottomNavigationBar. There is one per screen.
  • Inside the body, your widgets: text, icons, images, lists, cards.
  • Every screen in Gmail or Spotify follows exactly this structure: bar at the top, content, navigation at the bottom.

For the tests: one MaterialApp per app, one Scaffold per screen, and runApp is called only once.

1. Reading main.dart together

void main() {
  runApp(const WeatherApp());

      home: Scaffold(
        appBar: AppBar(title: const Text('Tempo Açores')),

        ),

1. main.dart: what matters

  • import 'package:flutter/material.dart' brings in the whole of Material Design. Almost every UI file starts like this.
  • WeatherApp is a StatelessWidget: it has no state of its own, it only describes. build returns the tree.
  • colorSchemeSeed generates a whole Material 3 palette from one colour. Change it to Colors.deepOrange and hot reload.
  • const in front of a widget tells Flutter that this subtree never changes: it can reuse it instead of rebuilding. Use it whenever the compiler lets you.
  • Center centres its child; Text draws text. They are the two simplest widgets there are.
Shortcut In VS Code, Ctrl+. (or Cmd+.) on a widget gives you "Wrap with Padding", "Wrap with Center", "Remove this widget".

2. Basic widgets: what matters

  • Text with a style from the textTheme respects the theme and the user's font size. Avoid a fixed fontSize: 24.
  • Icon uses the built-in Material icons (Icons.*). You do not need to download anything.
  • Image.asset reads a file declared in pubspec.yaml under the assets: section. If you forget, the error is at runtime, not at compile time.
  • Container combines colour, padding, border, radius and size in one widget. Padding and SizedBox are lightweight versions for when you only need space.
  • Column stacks children vertically; tomorrow we look at layout in depth.

3. The location card

class LocationCard extends StatelessWidget {
  const LocationCard({super.key, required this.name, required this.temperature});

  final String name;
  final double temperature;

  @override
  Widget build(BuildContext context) {
    final textTheme = Theme.of(context).textTheme;
    return Card(
      child: Padding(
        padding: const EdgeInsets.all(16),
        child: Row(
          children: [
            const Icon(Icons.wb_sunny, size: 40, color: Colors.orange),
            const SizedBox(width: 16),
            Text(name, style: textTheme.titleLarge),
            const Spacer(),
            Text('${temperature.round()} °C', style: textTheme.headlineMedium),
          ],
        ),
      ),
    );
  }
}
Write this widget live, from scratch, with the stless shortcut in VS Code. Show the compiler error when the required is missing and when you try to put const on a Text with a variable. Give this block 20 minutes; it is the heart of the lesson.

3. The card: what matters

  • A custom widget is a class with final fields, a const constructor with named parameters and a build. It is exactly the data model you wrote in DartPad with one extra method.
  • You use it like any other: const LocationCard(name: 'Horta', temperature: 19.4). The const is only possible because the constructor is const and the arguments are literals.
  • Card gives elevation and the theme's rounded corners. Row puts the children side by side; Spacer pushes the rest to the right.
  • One file per widget once it goes past 20 lines. main.dart imports it with import 'location_card.dart';.

4. Hot reload and hot restart in practice

  1. With the app running, change Colors.teal to Colors.indigo and save the file: VS Code hot reloads on save. The colour changes, the rest stays the same. This is hot reload: new code, old state.
  2. Change the temperature of a card and hot reload. It changes. build was called again with the new code.
  3. Change main() to runApp(const OtherApp()) (create an OtherApp that only has a Text). Hot reload is not enough: main only runs at startup. Hot restart: the ↻ button on the debug toolbar.
  4. Add a new image to assets/img/ and to pubspec.yaml. Neither saving nor the ↻ button is enough: stop the app (■) and F5 again.

For the tests: hot reload keeps the state and calls build again; hot restart restarts the app; changing pubspec.yaml requires a new flutter run.

Let them do the four steps on their own: 8 minutes. The typical question: "I changed it and nothing happened". It is almost always an unsaved file, or a change in main. Ask the class what hot reload preserves and why (answer: the State objects, which we see in a later lesson).
