How to answer multiple choice

  • Read the question to the end before the options. Underline the word that changes everything: always, never, guarantees, mandatory, only.
  • First eliminate the two that are clearly from another topic or too absolute. Two remain: one right and one "almost right".
  • The "almost right" one is usually true in another context (Android instead of iOS, debug instead of release, web instead of mobile). Ask yourself "for this platform and this scenario?".
  • There is no penalty for a wrong answer: answer all of them. A question you still cannot answer after 90 seconds, mark it and come back at the end.
  • 40 questions in 75 minutes gives less than two minutes per question. Time is not the problem if you do not get stuck.

Question 1 · Location

Tempo Açores wants to open on the location nearest to the user when they open the app. Which permission should it request?

  1. Always location, so that it also works in the background.
  2. When in use location, with approximate accuracy being enough.
  3. Background location with a foreground service so that it does not fail.
  4. None: GPS coordinates are public and do not need a permission.
Answer: B. The app only needs the position while it is open; requesting always is rejected by the stores without a justification and scares the user. To choose the nearest location among nine islands, approximate accuracy is enough. A is the classic "always vs when-in-use" mistake; C confuses background with reliability; D is false, location is sensitive data and always requires a runtime permission.

Question 2 · Deep links

Why should a "magic login" link sent by email not use a custom scheme such as tempoacores://login?token=...?

  1. Because custom schemes do not work on Android.
  2. Because any installed app can register the same scheme and receive the link with the token.
  3. Because iOS only allows schemes registered on the App Store.
  4. Because custom schemes require HTTPS and a certificate.
Answer: B. A scheme has no owner: there is no domain verification, so another app can claim tempoacores:// and grab the token. Universal Links and App Links solve this because the domain proves, with the AASA and assetlinks.json, that the app belongs to it. A and C are false; D mixes up schemes with HTTPS links. Classic mistake: "custom scheme as secure".

Question 3 · Background

You configure WorkManager to refresh the forecast cache every 6 hours. What does Android guarantee?

  1. That the task runs exactly every 6 hours, even in Doze.
  2. That the task runs at least once in each period, when the constraints allow it, and survives restarts.
  3. That the task runs only while the app is in the foreground.
  4. That the same configuration works on iOS with the same guarantee.
Answer: B. WorkManager guarantees execution, not a time: the period is a minimum and the system batches tasks into maintenance windows, especially in Doze and in the App Standby buckets. It survives a reboot. A is the classic "WorkManager with a guaranteed time" mistake. C describes the opposite of what it is for. D is false: on iOS it is BGTaskScheduler, with even fewer guarantees.

Question 4 · Hardware

An app wants to scan for Bluetooth Low Energy devices on a current Android. What does it need?

  1. Nothing: BLE scanning is unrestricted because it does not identify the user.
  2. Only the NFC permission, because BLE and NFC share the radio.
  3. The BLUETOOTH_SCAN permission (Android 12 and later) and, on earlier versions, the location permission.
  4. The camera permission, because scanning uses the code reader.
Answer: C. Up to Android 11, BLE scanning required location, because beacons make it possible to locate people; since 12 there are dedicated Bluetooth permissions (SCAN, CONNECT) with the option to declare that location is not derived. A ignores the privacy risk; B and D are plausible nonsense for anyone who did not study. Links to lesson 24.

Question 5 · Tests

In the test pyramid there are many unit tests and few integration or E2E tests. Why?

  1. Because unit tests are fast, cheap and point directly at the cause of the failure.
  2. Because Flutter does not support integration tests.
  3. Because unit tests test the interface and E2E tests only test the logic.
  4. Because golden tests replace E2E tests.
Answer: A. A unit test runs in milliseconds and says "fromJson fails with a missing field"; an E2E test takes minutes, needs a device and says "the screen went blank". B is false, integration_test exists. C is the wrong way round. D confuses pixel comparison with a complete flow. Reinforce: in the project, parsing, notifier with a fake repository and one widget test per state.

Question 6 · Observability

Crashlytics shows "crash-free users: 99.2%" for the last week. What does this mean?

  1. That 0.8% of sessions ended in a crash.
  2. That 99.2% of crashes have already been fixed.
  3. That 0.8% of users had at least one crash in that period.
  4. That 0.8% of the app's code has bugs.
Answer: C. The metric is per user and per period: of everyone who used the app, 0.8% saw at least one crash. A confuses users with sessions (crash-free sessions exists, it is a different metric). B and D are impossible readings. Then ask: "and is this good?" It depends on the product; above 99% is the normal expectation, and Play starts penalising at around 1.1% of user-perceived crashes.

Question 7 · Distribution to testers

What is the essential difference between distributing a build to external testers through TestFlight and through Firebase App Distribution?

  1. Firebase App Distribution only works for iOS.
  2. External TestFlight goes through a beta review by Apple; Firebase delivers the file with no review.
  3. TestFlight has no limit on testers; Firebase is limited to 25.
  4. There is no difference: both install through the App Store.
Answer: B. External TestFlight (up to 10,000 testers) requires a beta review, lighter than the store's but it exists; internal testers (up to 100, team members) do not go through it. Firebase App Distribution delivers an APK/AAB or an ad hoc IPA directly, with no review, and on iOS requires the tester's UDID to be in the profile. A and D are false; C inverts the limits.

Question 8 · Platform channels

Which types can you send directly over a MethodChannel between Dart and Kotlin or Swift?

  1. Any Dart object, because the channel serialises automatically using reflection.
  2. Only String; everything else has to go as JSON.
  3. Primitives, String, lists and maps supported by the StandardMessageCodec; your own objects are converted to maps.
  4. Widgets, so that the native side can draw them.
Answer: C. The StandardMessageCodec supports null, bool, int, double, String, Uint8List and the like, List and Map. A Forecast class goes as a Map (toJson) and is rebuilt on the other side. A does not exist in Dart AOT; B is what many people do out of laziness, but it is not mandatory; D confuses platform views with channels. Remind them of the MissingPluginException on the web and of EventChannel for streams.

Question 9 · Stores and monetisation

Tempo Açores starts selling a "10-day forecast" subscription inside the iOS app. What does Apple require?

  1. Nothing: the app can accept card payments with any payment provider.
  2. That the purchase of digital content uses Apple's in-app purchase system, with the corresponding commission.
  3. That the subscription is sold only on the website and the app never mentions it.
  4. That the app is paid in the store instead of having a subscription.
Answer: B. Digital content and features consumed in the app go through StoreKit (15% or 30%). Physical goods and services outside the app (a trip, a taxi) can use another processor. In the EU, the DMA forced Apple to allow alternatives with their own conditions; the general rule for the exam is still B. C describes the "reader" model with restrictions; D has nothing to do with it.

Question 10 · Build and versioning

You uploaded an app bundle with versionCode 7 to the internal testing track. You fix a bug and want to upload to production. What does the new bundle need?

  1. Nothing: tracks are independent and 7 can be repeated.
  2. versionCode 7 and a different versionName.
  3. versionCode 8 or higher; the versionName can be the same.
  4. A new keystore, because the test key is no good for production.
Answer: C. The versionCode is unique per app on Play, across all tracks, and only goes up. The versionName is for humans and can be repeated. A and B are the classic "same versionCode" mistake. D is serious: changing keystore would prevent updates for everyone who already has the app; the key is always the same, and with Play App Signing so is the upload key.

Frequent mistakes in the test

The mistakeWhy it is wrong
Requesting always location "to be safe"The app does not need it, the stores reject it without a justification and the user denies it. When in use is enough for almost everything.
Treating a custom scheme as secureIt has no owner and no domain verification. For tokens and login, Universal/App Links.
Counting on WorkManager at a fixed timeIt guarantees execution within constraints, not a time. The OS batches and defers work because of battery.
Thinking code push changes everything without the storeOnly Dart code; nothing native, no assets, no permissions. And Apple requires that it does not change the purpose of the app.
Reusing the versionCodePlay refuses the upload and the phone refuses the downgrade. It always goes up; it is the versionName that can repeat.

For the tests: when an option promises an absolute guarantee (always, exactly, without limits) on a mobile system, be suspicious.

Finishing workshop: submission checklist

  • Minimum requirements working on the phone: locations with search, 5-day forecast, warnings, synced favourites, working without network with "data from X ago", loading, error and empty states on every screen.
  • Chaos mode switched on for 5 minutes without the app failing.
  • Green CI on main: flutter analyze with no warnings and at least five tests passing.
  • No secrets in the repository: git log -p | grep -i secret clean, key.properties and keystore kept out.
  • README complete (next slide).
  • Signed build 1.0.0+N, distributed through Firebase App Distribution to at least 3 testers outside the group, and through TestFlight for those who have iOS.
How it will go 10:35 to 10:50: each group goes through the checklist and marks what is missing in the milestone. 10:50 to 12:00: work, with the teacher circulating. 12:00 to 12:30: uploads and cross-checking with another group.
Cross-checking is the part that pays off most: group A installs group B's build through the App Distribution link, turns on airplane mode and tries to break the app for 5 minutes, and vice versa. Record what they find as issues in the other group's repo. It is the "real tester" of the rubric.

README and documentation: what has to be there

  1. Header: name of the app, the members with their GitHub username, and a screenshot or GIF of the app running on the phone.
  2. How to run: Flutter version, flutter pub get, what to put in --dart-define or in env/dev.json, and how to get the client-id (not the secret itself).
  3. Architecture in ten lines: layers, folders per feature, where the state lives, how the cache works. A simple diagram is worth more than ten paragraphs.
  4. What is done and what is not: the minimums, the extras, the "Later" milestone. Honesty here is assessed; hiding a known bug is not.
  5. How to get the build: App Distribution invitation link, current version, and who has the keystore.
  6. Retrospective: the two sentences from lesson 32.
Exercise Swap READMEs with another group. Without talking to them, try to run the app using only what is written there. Each thing you had to ask about is a line that is missing.

Signed final build and upload to App Distribution

  1. Bump the build number in pubspec.yaml: version: 1.0.0+N, with N greater than the last one you distributed.
  2. Build the release APK with the prod flavor and the prod configuration. 
    flutter build apk --release --flavor prod --dart-define-from-file=env/prod.json
  3. Upload it with the Firebase CLI, to the class tester group you created in lesson 27. 
    firebase appdistribution:distribute \
  build/app/outputs/flutter-apk/app-prod-release.apk \
  --app 1:123456789012:android:0123456789abcdef \
  --groups pdm-class \
  --release-notes "v1.0.0 (N): final build for the defence"
  4. Confirm on another group's phone that the App Distribution notification arrived and that the app installs over the previous one, without uninstalling.
Exercise Build distributed to at least 3 testers outside the group, with the release link pasted into the README. If installing over the previous one fails, the cause is in lesson 31: key or versionCode.

TestFlight, for those who have iOS

  1. Paid account and a Mac. The teacher does the upload with their own account for the groups whose app compiles on iOS; the bundle id must be the one agreed with the teacher.
  2. Build the .ipa file and open it in Xcode or in Transporter. 
    flutter build ipa --release --flavor prod --dart-define-from-file=env/prod.json
open build/ios/archive/Runner.xcarchive
  3. Distribute App → App Store Connect → Upload. The build shows as "Processing" for a few minutes.
  4. Internal testers need no review: add your classmates' Apple IDs to the internal testing group, and they receive the invitation in the TestFlight app.
  5. No Mac: there is no way. State in the README that the iOS build was not distributed and why; it is not penalised.
Do a live upload to your App Store Connect if at least one group has iOS; otherwise show TestFlight with a build of yours and the list of testers. Check that the "Missing Compliance" (encryption) message is answered, it is the usual reason builds get stuck.
