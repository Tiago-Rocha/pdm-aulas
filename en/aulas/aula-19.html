How a push reaches the screen

  1. The app registers with the platform's service: APNs (Apple Push Notification service) on iOS, FCM (Firebase Cloud Messaging) on Android. It receives a device token: a long string that identifies this installation on this phone.
  2. The app sends the token to your server, associated with the user. Without this, the server does not know who to send to.
  3. The server sends the payload to FCM/APNs (never directly to the phone), authenticated with a server key.
  4. FCM/APNs delivers to the operating system, which decides: show it, wake the app, or discard it.
  • The token changes: reinstall, restore from backup, clearing data. The app has to listen to onTokenRefresh and send it again.
  • On iOS, FCM also works: it wraps APNs, and needs the APNs key configured in the Firebase project.

For the tests: your server never talks to the phone; it talks to FCM or APNs, which talk to the operating system.

Analogy The post office. The app does not stand at the door waiting for the postman: it registers its address, the device token, with the platform's post office, FCM or APNs. The server hands the letter to the post office with that address, and the post office delivers it when the phone can be reached. A single connection from the phone to the post office serves every installed app, and that is why the battery copes.
Draw the four boxes on the board: server → FCM/APNs → OS → app. Ask: "and if the user has the app on two phones?" Two tokens, two sends. "And if they uninstalled it?" FCM returns an error and the server should delete the token.

Permissions: ask at the right moment

  • iOS always asks, with a system dialog that only appears once. If the user says no, the only way back is in Settings.
  • Android 13+ (API 33) also asks at runtime: POST_NOTIFICATIONS. On earlier versions notifications come turned on by default.
  • Asking at app launch is the fastest way to get a "no": the user does not yet know what it is for.
  • Ask in context: after the user marks Ponta Delgada as a favourite, "Do you want to be notified when IPMA issues a warning for Ponta Delgada?", and only then the system dialog.
  • iOS has provisional authorisation: quiet notifications in Notification Centre, with no dialog, until the user decides.
  • Industry studies point to about half of users accepting on iOS and quite a lot more on Android; the difference comes from when and how you ask.

For the tests: a permission request is explained before it appears, and is made when the user already sees the benefit.

Payload: notification vs data

App stateNotification message (notification)Data message (data)
ForegroundDelivered to your code; by default nothing appears. The app decides whether to show it.Delivered to your code.
BackgroundThe system shows it in the tray without running the app. On tap, the app opens with the data.Wakes the app for a moment to process it (with limits).
TerminatedSame as background: the system handles it.Android: can wake the app. iOS: only if it is silent and the system allows it.
  • The payload has title, body and a data map of strings, for example {"type": "warning", "locationId": "3"}. It is through data that the app knows which screen to open.
  • Practical limit: 4 KB. You do not send the whole forecast; you send an identifier and the app fetches it.

For the tests: with the app in background, a notification-only message is shown by the system without executing any app code.

Channels, categories, sound, badge and silence

  • Channels (Android 8+): every notification belongs to a channel with a name and an importance. The user turns channels off in the system settings, one by one: "Weather warnings" on, "News" off. An app with a single channel forces all or nothing.
  • Categories (iOS): they define the action buttons ("See forecast", "Mute for 24h") and grouping.
  • Sound and badge: the number on the icon (badge) is managed by the app on iOS and by the launcher on Android. Custom sounds have to be bundled in the app.
  • Silent notifications (content-available on iOS, a data message with priority on Android): they show nothing; they wake the app to sync. iOS limits them to a few per hour and does not guarantee delivery.
  • Example: WhatsApp uses a silent one to download the message and then shows the notification with the text already in it.

For the tests: channels belong to Android and let the user choose which types of notification they want.

Ask someone to open the notification settings for Instagram or YouTube on an Android phone and read the list of channels out loud. It is the best demonstration possible.

In lesson 22 we do local notifications: the app detects a new warning for a favourite when it refreshes, and schedules the next day's forecast. Remote push requires a Firebase project per group; it stays as an extra for the project.

Analogy A local notification is a reminder the app itself leaves on the fridge: it writes it and schedules it on the phone, without going through the post office. A remote push is a letter that comes from outside, and only the post office (FCM or APNs) knows how to deliver it. To the reader, the note on the fridge and the letter look the same.

Good practice

  • Do not overdo it. One useless notification costs the permission for all the ones after it. Duolingo is personalised and frequent, and even so a lot of people mute it.
  • Personalise. "Orange warning for strong wind in Angra do Heroísmo until 18:00" instead of "There are new warnings".
  • Deep link to the content. Tapping the notification opens the location's screen, not the home page.
  • Let the user turn them off by type inside the app, and respect quiet hours.
  • Group and replace. Three warnings for the same location are one updated notification, not three.
  • Work without them. The app cannot depend on a push arriving; iOS discards them whenever it likes.

For the tests: a notification with no deep link to the content is a badly made notification.

Sample questions (1 of 3)

Method Read the question to the end. Cross out the two options that are clearly wrong. Between the two that are left, choose the one that uses the exact vocabulary from the lessons; the other is usually "almost true".

1. You changed the body of main() and pressed r. The app does not reflect the change. Why?

  1. Hot reload only works in release mode.
  2. Hot reload does not run main() again; a hot restart is needed.
  3. You forgot to run flutter pub get.
  4. The phone is in airplane mode.

2. A 2-second computation inside build makes the app…

  1. stay smooth, because Dart is multithreaded by default.
  2. freeze, because the interface runs on a single thread.
  3. be terminated immediately by the operating system.
  4. fail to compile.

3. Where does the state of a StatefulWidget live?

  1. In the widget itself, which is therefore mutable.
  2. In the State object, which survives the widget's rebuilds.
  3. In the BuildContext.
  4. In the MaterialApp.
For each question: 30 seconds in silence, a show of hands per option, and only then the answer. Ask those who voted for the wrong one to say what drew them to it; that is where you learn to eliminate.

Sample questions (2 of 3)

4. With go_router, what is the difference between context.go('/x') and context.push('/x')?

  1. go replaces the stack with the route; push stacks on top of the current one.
  2. They are equivalent; push is the old name.
  3. push only works on the web.
  4. go only works with Navigator.push.

5. The course API returns 429. What should the app do?

  1. Retry immediately until it gets 200.
  2. Wait the time given in Retry-After and retry with backoff.
  3. Show a fatal error and close the app.
  4. Swap the POST method for GET.

6. Which of these requests should you not retry automatically after a timeout?

  1. GET /v1/locations
  2. GET /v1/forecast/3
  3. POST /v1/me/favorites
  4. GET /v1/warnings

7. Where do you store the API access token?

  1. In shared_preferences, because it is fast.
  2. In a file in getApplicationDocumentsDirectory().
  3. In flutter_secure_storage, which uses the Keychain and the Keystore.
  4. In a constant in the code, so it does not get lost.

Sample questions (3 of 3)

8. A JWT…

  1. is encrypted; nobody can read the content.
  2. is signed; anyone can read the content, but cannot change it without invalidating the signature.
  3. never expires.
  4. should contain the user's password to renew the session.

9. To parse a 5 MB JSON response without jank, you use…

  1. setState after the parse.
  2. Future.delayed to give the interface time.
  3. compute() or Isolate.run.
  4. async/await, which frees the thread during the parse.

10. A push with only a notification field, without data, arrives with the app in background. What happens?

  1. The app is woken up and decides what to show.
  2. The operating system shows it in the tray without executing any app code.
  3. It is discarded.
  4. It is kept until the app is opened manually.

Answers and why

  1. b. Hot reload injects code and calls build again; main and global variables only with R.
  2. b. One UI thread, one event loop. Heavy computation blocks until it finishes.
  3. b. The widget is immutable; the State is the object that persists.
  4. a. go is declarative navigation to a location; push stacks a screen that can be closed with back.
  5. b. 429 means "slow down"; retrying immediately makes it worse and can get you blocked.
  1. c. POST is not idempotent: retrying can create the favourite twice. GETs can be retried without risk.
  2. c. shared_preferences is a file that can be read on a rooted phone; secrets go into the system's secure storage.
  3. b. Base64 is not encryption. The signature guarantees integrity, not confidentiality. It expires through exp.
  4. c. await only yields the thread on waiting operations; jsonDecode is pure computation.
  5. b. Notification messages in background are handled by the system; only on tap does the app receive the data.
Places where the class usually goes wrong: 6 (they think a timeout is always safe to retry) and 9 (they think async solves computation). Spend more time on these two. If there are doubts about 8, show a decoded JWT on jwt.io live.

Frequent mistakes in the test

MistakeWhy it is wrong
Confusing hot reload with hot restartReload keeps state and does not re-run main; restart starts the app again and loses the state. A full rebuild is something else: flutter run again.
A "mutable" widget with fields that changeWidgets are immutable and recreated on every build; what changes is the State or the app state in a notifier.
! as the solution to null safetyIt forces a value that may be null and moves the error from the compiler to a crash in production. Use ?., ??, if or patterns.
Token in shared_preferencesReadable text on disk; on a rooted phone or in a backup it is exposed. Keychain and Keystore exist for this.
Automatic retry on POSTA non-idempotent POST repeated creates duplicates. Retry only on operations that are safe to repeat, with backoff and a limit.

For the tests: when two options look right, the right one is the one without a word too many ("always", "never", "only on iOS").
