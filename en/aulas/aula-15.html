MVP: the minimum that gets installed and used

  • The minimum viable product is the smallest version that someone installs and gets value from. It is not a prototype, nor a demo.
  • In Tempo Açores: list of locations, forecast for a location, favourites, and carrying on working with no network using old data.
  • Cut features, not quality. One screen with the four states handled is worth more than three half-done screens.
  • Ask for each feature: "if this does not exist, is the app useless?" If the answer is no, it goes on the "later" list.
  • Real examples: Instagram v1 only had photos with a filter and a feed; WhatsApp v1 was a status app. They grew later.

For the tests: the MVP cuts scope, never quality; every feature that stays, stays complete.

Backlog in issues

  • Title: verb + object. "Show the 5-day forecast for the location", not "Forecast".
  • Body: context in one sentence and acceptance criteria as a checklist, in the format "given X, when Y, then Z".
  • Rough estimate: S (half a day), M (one day), L (two or more). An L issue is split into two M issues before it enters the sprint.
  • Labels and assignee: sprint-1, ui, data, bug; one person per issue; linked to the project board.
  • Example of a criterion: "With no network, the screen shows the last saved forecast and the time it was fetched."

For the tests: a good issue has a title with a verb, verifiable acceptance criteria and an estimate.

Write a bad issue on the board ("Do the detail screen") and ask the class to fix it out loud. Two minutes. Then show a real issue from an open source Flutter project with acceptance criteria.

Definition of done

An issue is done when the PR that closes it meets all of this. If one point fails, it is not done, however much "it works on my laptop".

  • It runs on the phone, not only on the emulator.
  • flutter analyze with no warnings and flutter test green.
  • PR reviewed and approved by another member of the group.
  • Loading, error, empty and data states handled in every screen touched.
  • No secrets in the code (lesson 18) and the issue closed by the PR (Closes #12).

For the tests: "done" is an objective list, not an opinion.

Flow: issue → branch → PR → review → merge

  1. Issue assigned to one person, in the "In progress" column of the board.
  2. Branch from an up-to-date main: git switch -c feat/12-forecast-5-days. The issue number in the name.
  3. Small commits with conventional commits: feat(forecast): show 5 days, fix(api): handle 429.
  4. Small PR (fewer than 300 lines), with a description, a screenshot from the phone and Closes #12.
  5. Review by a colleague: at least one useful comment; the author replies or fixes.
  6. Merge (squash) done by the reviewer; branch deleted. main is protected: nobody pushes directly.

For the tests: protected main, small PR and review by a colleague is the minimum flow of a team.

Golden rule The minimum requirements first, complete. An extra only enters the backlog when all the minimum requirements are in the "Done" column.
Read the rubric out loud, section by section, and stop for questions. The usual ones: "can we use package X?" (yes, if you can explain it), "can we change the design?" (yes, if it respects the states and accessibility), "what if a member does not work?" (the defence is individual and PRs have an author).

Groups, GitHub Classroom and client-id

  1. Groups of 2 to 3. Group name and members in the Moodle form. No groups of 1 or of 4.
  2. Accept the assignment in GitHub Classroom (link on Moodle). The first member creates the team, the others join. The repository is created from the tempo-acores-template template.
  3. Clone and run. The template already has ApiClient, theme, navigation and the state widgets from lessons 12 to 14. 
    git clone https://github.com/pdm-daw-2026/tempo-acores-group-07.git
cd tempo-acores-group-07

  4. Receive the group's client-id and secret in person. The secret never goes into the repository: it is passed through --dart-define or through a .env.json ignored by git.
  5. First request: the template app shows the list of locations from GET /v1/locations with the group's token. If a 401 appears, the secret is mistyped.

Sprint 1 backlog and board

  • Project board with the columns Backlog, Sprint 1, In progress, In review, Done.
  • Between 6 and 10 issues in sprint 1, each with acceptance criteria and an S/M/L estimate. The minimum requirements first.
  • Suggested split: list of locations and search · detail with 5 days · navigation, theme and settings · local favourites · error states and messages · README and basic CI.
  • Each member responsible for 2 to 3 issues. Nobody is left with only "UI" or only "data": everyone touches both layers.
  • An empty "Security audit" issue, for lesson 18.

First PR and what the teacher does

  • The group's first PR: README.md with names, the initial split of work and a screenshot of the template running on the phone. Opened by one member, reviewed and merged by another. It is there to test the flow before there is any code.
  • Branch protection on main: the teacher enables it in every repository by tomorrow. From then on code only gets in through an approved PR.
  • The teacher today: validates groups and repositories, hands out client-ids, goes round each group to see the backlog and the first request to the API on the phone.
  • The teacher during the sprint: comments on PRs, follows the API telemetry per group, answers on the Moodle forum. Does not write code for the group.
Exercise 2 First PR opened, reviewed and merged before leaving the room. Confirm that the reviewer left at least one comment, even if it is "LGTM, the screenshot is missing".
