The navigation stack

  • The screens of an app are a stack: push puts a new screen on top, pop removes the top one and goes back to the previous one. The islands grid → Pico → the map: three screens on the stack.
  • The screen underneath stays alive, with its State, its scroll and the text typed in it. When you pop, it is exactly as you left it.
  • The screen that leaves with pop is destroyed: dispose runs and the state is lost. If the user needs what was there, you have to return it to the previous screen or keep it outside.
  • A screen can return a result when it leaves: the island screen calls pop(context, true) when you tap the star, and whoever opened it receives the true in the await.
  • Very deep stacks (10 screens) are a symptom: the user is lost. Well-designed apps rarely go beyond 3 or 4.

For the tests: push keeps the previous screen alive; pop destroys the current screen and can return a value.

Analogy A pile of sheets of paper on the desk. push puts a sheet on top; pop takes the top one off and throws it away. The sheet underneath stays on the desk with everything that was written on it. The Android back button is a pop.

Back: the Android button, the iOS gesture, and state

  • Android: the system back button or gesture, from either edge. Since Android 14, predictive back shows a preview of the previous screen before you let go. Flutter supports it with PopScope.
  • iOS: there is no system button. The user swipes from the left edge or taps the arrow in the bar. Flutter handles the gesture by itself in MaterialPageRoute on iOS.
  • Back at the root of the app: on Android it leaves the app (or minimises it); on iOS it does not exist. Never put an "exit" button in an app.
  • A half-filled form and the user presses back: everything is lost. PopScope with canPop: false and a "Discard changes?" dialog is the pattern. Gmail does this with drafts.
  • When the app is killed in the background and reopened, the stack goes back to the start unless you restore it (lesson 4, state restoration). Users hate going back to the home screen.

For the tests: "back" belongs to the system, not to the app; the app can intercept it with PopScope, but it cannot ignore it.

Imperative vs declarative routes

  • Imperative (Navigator.push): you say what to do, screen by screen. Simple, but the stack only exists in memory: it has no name, and it cannot be shared or restored.
  • Declarative (go_router): you declare a map of routes with paths, as on a website: /, /island/:id, /settings. Navigating is changing the URL; the stack is derived from it.
  • URL as state: the same app on Flutter Web shows the URL in the address bar; on the phone, a deep link opens /island/pico directly; an automated test starts on a screen without tapping five buttons.
  • go_router is maintained by the Flutter team and handles the back button, tabs with independent stacks and redirects (login screen).
  • The two live together: you can use showDialog and showModalBottomSheet (imperative) inside an app with go_router.

For the tests: declarative routes describe the screens as URLs and derive the stack from the URL; they are the basis of deep links and of the web.

Deep links in one sentence

A deep link is a URL that opens the app directly on a specific screen, instead of on the home screen.

  • https://tempoacores.pt/island/pico in an SMS, in a notification or in the browser: if the app is installed, it opens on the Pico screen; if not, it opens the website.
  • With go_router, the URL received is handled exactly like context.go('/island/pico'). That is why route paths should be designed as if they were public.
  • It needs native configuration (Android App Links, iOS Universal Links) and a file on the server proving that the domain is yours.
Details, configuration and testing in lesson 22. In this lesson we only define the structure of the paths.
Analogy A full address, with street, number, floor and door, instead of "go to the city and look around". The URL takes you to the app and to the right screen, and the path segments (/island/pico) are the number and the door.

Themes (1 of 2): ThemeData and ColorScheme

  • ThemeData is the set of colours, typography, shapes and component styles for the whole app. It lives in the MaterialApp and any widget reads it with Theme.of(context).
  • ColorScheme.fromSeed(seedColor: ...) generates, from one colour, the 30-odd colours of Material 3: primary, secondary, tertiary, error, surface, the on* ones for text on top, the *Container ones for soft backgrounds. It guarantees contrast between pairs.
  • Material widgets use the scheme by themselves: a FilledButton is primary with onPrimary text; a Card is surfaceContainer. If you do not set colours by hand, the app is coherent for free.
  • Typography comes from the textTheme: displayLarge down to labelSmall. Use them instead of fixed fontSize values.

For the tests: ColorScheme.fromSeed generates the whole Material 3 palette from one colour; widgets read the theme with Theme.of(context).

Themes (2 of 2): light, dark and consistency

  • theme and darkTheme in the MaterialApp; themeMode decides which one: ThemeMode.system follows the phone, light and dark force one.
  • A dark theme is not the light one inverted: dark grey surfaces (not pure black), lighter and less saturated primary colours, shadows replaced by tones. fromSeed with brightness: Brightness.dark takes care of this.
  • Fixed colours (Colors.white, Color(0xFF...)) in a widget break in dark mode. Rule: colours only from the colorScheme; exceptions (the yellow of a weather warning) declared in one place only.
  • Dark mode is the most used accessibility preference and saves battery on OLED screens. The stores expect it.
  • Consistency: one theme, one place to change it, all screens alike. The moment a screen "looks like it is from another app" is a theme bug.

For the tests: ThemeMode.system follows the system preference; fixed colours in widgets are the classic dark mode mistake.

1. Navigator: push and pop with a result

IconButton(
  icon: const Icon(Icons.star_border),
  tooltip: 'Adicionar aos favoritos',
  onPressed: () => Navigator.pop(context, true), // close, return true
),
  • Navigator.push puts a new screen on top of the stack and returns a Future: it completes when that screen leaves. The value given to pop is the result.
  • If the user leaves with the AppBar arrow, the back button or the iOS gesture, the result is null. That is why the code checks favorite == true.
  • MaterialPageRoute gives each platform's transition and the back gesture on iOS. The AppBar arrow appears on its own when there is a screen underneath.
  • After an await, the widget may no longer exist. context.mounted checks that it still does before using the context; the use_build_context_synchronously lint warns you if you forget.

2. go_router: a path for each screen

import 'package:go_router/go_router.dart';

import 'forecast_screen.dart';
import 'island_screen.dart';

/// Every screen of the app, with its path, like the pages of a site.
final router = GoRouter(
  initialLocation: '/',
  routes: [
    GoRoute(
      path: '/',
      builder: (context, state) => const ForecastScreen(),
      routes: [
        GoRoute(
          path: 'island/:id', // /island/pico
          builder: (context, state) =>
              IslandScreen(id: state.pathParameters['id']!),
        ),
      ],
    ),
  ],
);
  • Each GoRoute links a path to a screen. :id is a parameter: in /island/pico, state.pathParameters['id'] is 'pico'.
  • The island/:id route is inside the / route: opening /island/pico puts the grid underneath and Pico on top, even when you come in directly from a link. The back arrow works.
  • context.push('/island/pico') stacks on top and returns a result, like Navigator.push. context.go('/island/pico') replaces the stack with the one for the path. For "open and come back", push.
Ask the class Why does the path carry the island's id and not the whole Island?
Answers to the questions. A path is text: it has to fit in a URL, in a link in an SMS or in a notification. An object does not fit in a URL. With the id, the destination screen fetches the rest from the data, and the same path works wherever it comes from. That is also why IslandScreen handles an id that does not exist: a mistyped link has to give "Ilha não encontrada", not a red error. In Chrome, type /island/xyz in the address bar to show it.

3. Navigation bar with independent stacks

StatefulShellRoute.indexedStack(
  builder: (context, state, shell) => Scaffold(
    body: shell, // the current tab, with its own stack
    bottomNavigationBar: NavigationBar(
      selectedIndex: shell.currentIndex,
      onDestinationSelected: (i) =>
          shell.goBranch(i, initialLocation: i == shell.currentIndex),
      destinations: const [
        NavigationDestination(
          icon: Icon(Icons.wb_sunny_outlined),
          label: 'Previsão',
        ),
        // and Avisos (Icons.warning_amber), Definições (Icons.settings_outlined)
      ],
    ),
  ),
  branches: [
    // one StatefulShellBranch per tab
  ],
),
  • StatefulShellRoute draws a Scaffold shared by all tabs, with the NavigationBar at the bottom. shell is the current tab.
  • Each StatefulShellBranch is a tab with its own stack. indexedStack keeps all three alive: switching tabs does not pop. It is the Instagram pattern.
  • Tapping the tab that is already active (i == shell.currentIndex) goes back to that tab's root. It is what users expect.
  • NavigationBar is the Material 3 one; BottomNavigationBar is the old one. Three to five destinations, with icon and label.
Ask the class Each tab has a Scaffold with its own AppBar, and shell has another Scaffold with the bar. Two Scaffolds one inside the other: is that a mistake?
Answers to the questions. It is not a mistake, it is normal with tabs: the outer Scaffold only has the bottom bar, and the inner one has the AppBar and the body of each screen. The SnackBar still appears because there is only one ScaffoldMessenger, created by MaterialApp. On tablets the bottom bar is swapped for a NavigationRail on the left; that is for the adaptive layouts lesson.

4. Light and dark theme

/// The same theme for light and dark: only the brightness changes.
ThemeData buildTheme(Brightness brightness) {
  return ThemeData(
    colorScheme: ColorScheme.fromSeed(
      seedColor: Colors.teal,
      brightness: brightness,
    ),
    useMaterial3: true,
    // Inter, on top of the text colours of this brightness
    textTheme: GoogleFonts.interTextTheme(
      ThemeData(brightness: brightness).textTheme,
    ),
  );
}
/// The theme chosen by the user. A ValueNotifier holds one value and tells
/// whoever listens when it changes: WeatherApp listens, in main.dart.
final themeMode = ValueNotifier(ThemeMode.system);
  • theme and darkTheme in the MaterialApp, and themeMode chooses: ThemeMode.system follows the phone, light and dark force one.
  • The mode is chosen in settings, but the one who uses it is MaterialApp, at the top. Passing it by parameter does not work: the router is in between. A ValueNotifier keeps the value in one place and tells whoever is listening. It is the small version of the ChangeNotifier from the lesson 8 theory.
  • ValueListenableBuilder listens to the ValueNotifier and rebuilds what is in its builder every time the value changes.
Ask the class Why does buildTheme pass ThemeData(brightness: brightness).textTheme to interTextTheme, instead of GoogleFonts.interTextTheme() as until now?
Answers to the questions. GoogleFonts.interTextTheme() with no argument starts from the light text theme, which has dark colours. In dark mode that gives dark text on a dark background, unreadable. Passing the text theme of the same brightness keeps the Inter font with the right colours. It is the classic mistake from the theory slide, a fixed colour breaking dark mode, only hidden inside a function. Whoever wants to see it swaps to GoogleFonts.interTextTheme() and switches to Escuro. In lesson 13 the ValueNotifier becomes a ChangeNotifier with Provider, and in a later lesson the mode is saved.
