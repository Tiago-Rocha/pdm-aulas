Navigation and themes

Theory: how screens are organised in a stack, what the back button does to state, and routes declared as URLs. Practice: Navigator, go_router with parameters, a navigation bar with three tabs and a light and dark Material 3 theme.

The navigation stack

  • The screens of an app are a stack: push puts a new screen on top, pop removes the top one and goes back to the previous one. The locations list → the detail → the map: three screens on the stack.
  • The screen underneath stays alive, with its State, its scroll and the text typed in it. When you pop, it is exactly as you left it.
  • The screen that leaves with pop is destroyed: dispose runs and the state is lost. If the user needs what was there, you have to return it to the previous screen or keep it outside.
  • A screen can return a result when it leaves: the location picker screen calls pop(context, location) and the caller receives it in the await.
  • Very deep stacks (10 screens) are a symptom: the user is lost. Well-designed apps rarely go beyond 3 or 4.

For the tests: push keeps the previous screen alive; pop destroys the current screen and can return a value.

Analogy A pile of sheets of paper on the desk. push puts a sheet on top; pop takes the top one off and throws it away. The sheet underneath stays on the desk with everything that was written on it. The Android back button is a pop.
Draw the stack on the board with three stacked rectangles. Ask for the result of the screen count you asked for at the start: usually between 3 and 6. Discuss for 2 minutes why banking apps go deep (transfer flows) and Instagram does not.

Back: the Android button, the iOS gesture, and state

  • Android: the system back button or gesture, from either edge. Since Android 14, predictive back shows a preview of the previous screen before you let go. Flutter supports it with PopScope.
  • iOS: there is no system button. The user swipes from the left edge or taps the arrow in the bar. Flutter handles the gesture by itself in MaterialPageRoute on iOS.
  • Back at the root of the app: on Android it leaves the app (or minimises it); on iOS it does not exist. Never put an "exit" button in an app.
  • A half-filled form and the user presses back: everything is lost. PopScope with canPop: false and a "Discard changes?" dialog is the pattern. Gmail does this with drafts.
  • When the app is killed in the background and reopened, the stack goes back to the start unless you restore it (lesson 4, state restoration). Users hate going back to the home screen.

For the tests: "back" belongs to the system, not to the app; the app can intercept it with PopScope, but it cannot ignore it.

Imperative vs declarative routes

  • Imperative (Navigator.push): you say what to do, screen by screen. Simple, but the stack only exists in memory: it has no name, and it cannot be shared or restored.
  • Declarative (go_router): you declare a map of routes with paths, as on a website: /, /location/:id, /settings. Navigating is changing the URL; the stack is derived from it.
  • URL as state: the same app on Flutter Web shows the URL in the address bar; on the phone, a deep link opens /location/horta directly; an automated test starts on a screen without tapping five buttons.
  • go_router is maintained by the Flutter team and handles the back button, tabs with independent stacks and redirects (login screen).
  • The two live together: you can use showDialog and showModalBottomSheet (imperative) inside an app with go_router.

For the tests: declarative routes describe the screens as URLs and derive the stack from the URL; they are the basis of deep links and of the web.

Deep links in one sentence

A deep link is a URL that opens the app directly on a specific screen, instead of on the home screen.

  • https://tempoacores.pt/location/horta in an SMS, in a notification or in the browser: if the app is installed, it opens on the detail for Horta; if not, it opens the website.
  • With go_router, the URL received is handled exactly like context.go('/location/horta'). That is why route paths should be designed as if they were public.
  • It needs native configuration (Android App Links, iOS Universal Links) and a file on the server proving that the domain is yours.
Details, configuration and testing in lesson 22. In this lesson we only define the structure of the paths.
Analogy A full address, with street, number, floor and door, instead of "go to the city and look around". The URL takes you to the app and to the right screen, and the path segments (/location/horta) are the number and the door.

Themes (1 of 2): ThemeData and ColorScheme

  • ThemeData is the set of colours, typography, shapes and component styles for the whole app. It lives in the MaterialApp and any widget reads it with Theme.of(context).
  • ColorScheme.fromSeed(seedColor: ...) generates, from one colour, the 30-odd colours of Material 3: primary, secondary, tertiary, error, surface, the on* ones for text on top, the *Container ones for soft backgrounds. It guarantees contrast between pairs.
  • Material widgets use the scheme by themselves: a FilledButton is primary with onPrimary text; a Card is surfaceContainer. If you do not set colours by hand, the app is coherent for free.
  • Typography comes from the textTheme: displayLarge down to labelSmall. Use them instead of fixed fontSize values.

For the tests: ColorScheme.fromSeed generates the whole Material 3 palette from one colour; widgets read the theme with Theme.of(context).

Themes (2 of 2): light, dark and consistency

  • theme and darkTheme in the MaterialApp; themeMode decides which one: ThemeMode.system follows the phone, light and dark force one.
  • A dark theme is not the light one inverted: dark grey surfaces (not pure black), lighter and less saturated primary colours, shadows replaced by tones. fromSeed with brightness: Brightness.dark takes care of this.
  • Fixed colours (Colors.white, Color(0xFF...)) in a widget break in dark mode. Rule: colours only from the colorScheme; exceptions (the yellow of a weather warning) declared in one place only.
  • Dark mode is the most used accessibility preference and saves battery on OLED screens. The stores expect it.
  • Consistency: one theme, one place to change it, all screens alike. The moment a screen "looks like it is from another app" is a theme bug.

For the tests: ThemeMode.system follows the system preference; fixed colours in widgets are the classic dark mode mistake.

Show the Tempo Açores solution changing theme when you change the system setting on the phone, without restarting. Then show a widget with Colors.white in dark mode: white text on white. It is an image that sticks.

1. Navigator.push and pop with a result

// On the list screen: push the detail and wait for a result
onTap: () async {
  final favorite = await Navigator.push<bool>(
    context,
    MaterialPageRoute(builder: (_) => DetailScreen(location: l)),
  );
  if (favorite == true && context.mounted) {         // the screen may no longer exist
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('${l.name} added to favourites')),
    );
  }
},

// On the detail screen: go back and return the result
AppBar(
  title: Text(location.name),
  actions: [
    IconButton(
      icon: const Icon(Icons.star_border),
      tooltip: 'Add to favourites',
      onPressed: () => Navigator.pop(context, true),
    ),
  ],
)

1. Navigator: what matters

  • Navigator.push returns a Future that completes when the new screen calls pop. The value passed to pop is the result; if the user goes back with the gesture, it is null.
  • MaterialPageRoute gives the platform transition: sliding up from the bottom on Android, from the right on iOS, with the back gesture included.
  • After an await, the widget may have been destroyed. context.mounted avoids using a dead context; the lint use_build_context_synchronously forces you to check.
  • The back arrow in the AppBar appears by itself when there is a screen underneath. Do not draw it by hand.
  • Navigator.pop(context) with no value is for "Cancel".

2. go_router: routes with parameters

import 'package:go_router/go_router.dart';

final router = GoRouter(
  initialLocation: '/',
  routes: [
    GoRoute(
      path: '/',
      builder: (context, state) => const LocationsScreen(),
      routes: [
        GoRoute(
          path: 'location/:id',                         // /location/ponta-delgada
          builder: (context, state) {
            final id = state.pathParameters['id']!;
            return DetailScreen(id: id);
          },
        ),
      ],
    ),
    GoRoute(path: '/settings', builder: (_, __) => const SettingsScreen()),
  ],
);

// in main.dart, in place of MaterialApp(home: ...)
MaterialApp.router(routerConfig: router, theme: theme);

2. go_router: what matters

  • Nested routes (routes: inside a GoRoute) build the stack: opening /location/horta from a deep link puts the list underneath and the detail on top. Back works.
  • :id is a path parameter, read from state.pathParameters. Query strings (?day=2) are in state.uri.queryParameters. Pass identifiers, not objects: the detail screen looks up the location by its id.
  • context.go('/settings') replaces the stack with the one for the new URL. context.push('/settings') stacks on top of the current stack and can return a result, like the Navigator.
  • Rule of thumb: go to change section (tabs, deep links, after login); push to "open on top and come back".
  • The starter's tests navigate by URL. That is the advantage of screens having names.

For the tests: go replaces the stack; push stacks. Path parameters come in pathParameters.

3. NavigationBar with independent stacks

StatefulShellRoute.indexedStack(
  builder: (context, state, shell) => Scaffold(
    body: shell,                                    // the current tab, with its own stack
    bottomNavigationBar: NavigationBar(
      selectedIndex: shell.currentIndex,
      onDestinationSelected: (i) => shell.goBranch(i, initialLocation: i == shell.currentIndex),
      destinations: const [
        NavigationDestination(icon: Icon(Icons.wb_sunny_outlined), label: 'Forecast'),
        NavigationDestination(icon: Icon(Icons.warning_amber), label: 'Warnings'),
        NavigationDestination(icon: Icon(Icons.settings_outlined), label: 'Settings'),
      ],
    ),
  ),
  branches: [
    StatefulShellBranch(routes: [GoRoute(path: '/', builder: (_, __) => const LocationsScreen())]),
    StatefulShellBranch(routes: [GoRoute(path: '/warnings', builder: (_, __) => const WarningsScreen())]),
    StatefulShellBranch(routes: [GoRoute(path: '/settings', builder: (_, __) => const SettingsScreen())]),
  ],
)

3. Navigation bar: what matters

  • ShellRoute wraps a set of routes in a common widget (the bar). StatefulShellRoute.indexedStack goes further: each tab has its own stack and its own state, preserved when you switch tabs. It is the Instagram pattern.
  • The detail route goes in as a child of the / route inside the first branch: the detail opens on top of the list and the bar stays visible.
  • initialLocation: true when tapping the already active tab goes back to the root of that tab. It is the behaviour users expect.
  • NavigationBar is Material 3; BottomNavigationBar is the old Material 2. Three to five destinations, with icon and label.
  • On tablets, swap it for a NavigationRail on the left with a LayoutBuilder.

4. Light and dark Material 3 theme

const seed = Color(0xFF0B63C9);

MaterialApp.router(
  routerConfig: router,
  theme: ThemeData(colorScheme: ColorScheme.fromSeed(seedColor: seed), useMaterial3: true),
  darkTheme: ThemeData(
    colorScheme: ColorScheme.fromSeed(seedColor: seed, brightness: Brightness.dark),
    useMaterial3: true,
  ),
  themeMode: _mode,                            // ThemeMode.system, .light or .dark
)

// Manual toggle: _mode lives in a StatefulWidget above the MaterialApp
SegmentedButton<ThemeMode>(
  segments: const [
    ButtonSegment(value: ThemeMode.system, label: Text('System')),
    ButtonSegment(value: ThemeMode.light, label: Text('Light')),
    ButtonSegment(value: ThemeMode.dark, label: Text('Dark')),
  ],
  selected: {_mode},
  onSelectionChanged: (s) => setState(() => _mode = s.first),
)

4. Theme: what matters

  • Two lines of fromSeed and the app has coherent light and dark modes. From there on, avoid fixed colours: no Colors.white in the widgets.
  • In the widgets, final colors = Theme.of(context).colorScheme; and then colors.primaryContainer for the background and colors.onPrimaryContainer for the text on top. The x / onX pairs guarantee contrast.
  • The SegmentedButton is on the settings screen, but _mode has to be above the MaterialApp. Today it goes up through a callback (the five levels problem); in lesson 13 it moves to a ChangeNotifier and in lesson 16 it is saved.
  • Component styles (cardTheme, appBarTheme, inputDecorationTheme) are defined once in the ThemeData, not widget by widget.
  • Always test both modes: turn on the phone's dark mode and go through every screen.
