The navigation stack

  • push puts a screen on top; pop removes it and goes back to the one underneath.
  • The screen underneath stays alive: scroll, search and State as you left them.
  • The screen that leaves is destroyed (dispose).

For the tests: push keeps the previous screen alive; pop destroys the current screen.

Draw the stack on the board as three stacked rectangles. Ask for the result of the screen count you asked for at the start: usually between 3 and 6. Very deep stacks are a sign the user got lost; well-designed apps rarely go beyond 3 or 4. Analogy, if it helps: a pile of sheets on a desk; push puts a sheet on top, pop takes the top one and throws it away, and the one underneath still has everything written on it.

Back: the Android button, the iOS gesture, and state

  • The AppBar arrow appears on its own when there is a screen underneath; the iOS gesture comes with MaterialPageRoute.
  • Form half filled in? PopScope asks "Discard changes?" before leaving.

For the tests: "back" belongs to the system, not the app; the app can intercept it with PopScope, but cannot ignore it.

On Android, the back button or gesture works from either edge and, since Android 14, predictive back shows a preview of the previous screen. On iOS there is no system button. Back at the root of the app: on Android it leaves (or minimises); on iOS it does not exist; never add an "exit" button. When the app is killed in the background and reopened, the stack goes back to the start unless you restore it (state restoration). A PopScope example: Gmail with a half-written draft.

Navigation patterns

  • Examples: e-mail (list → detail), Instagram and YouTube (tabs), composing an e-mail (modal), sharing (bottom sheet), "Delete conversation?" (dialog).
Tabs with independent stacks: you open a video in Home on YouTube, go to Subscriptions, come back and the video is still there; tapping the active tab again goes back to its root. Modal: a full screen with "Cancel" and "Save", like creating an event in Calendar. Bottom sheet: the rest of the screen stays visible and dimmed, like the Airbnb filters. Dialog: interrupts with a question and two actions at most, like permission requests.

Imperative vs declarative routes

dependencies:                   # vai para dentro da app
  flutter:
    sdk: flutter
  go_router: ^18.0.2
  google_fonts: ^8.2.1
  • go_router does not come with Flutter: it is a package from pub.dev, like google_fonts. flutter pub add go_router adds the line to pubspec.yaml and flutter pub get downloads it. In today's repository it is already there.

For the tests: declarative routes describe screens as URLs and derive the stack from the URL; they are the basis of deep links and the web.

With paths, the same app on Flutter Web shows the URL in the address bar, a deep link opens /island/pico directly, and a test starts on a screen without tapping five buttons. go_router is maintained by the Flutter team and handles the back button, tabs with independent stacks and redirects (login screen). The two ways live together: showDialog and showModalBottomSheet are imperative and are used inside an app with go_router. Show the repository's pubspec.yaml in VS Code: ^18.0.2 means "18.0.2 or newer, without moving to 19".

Deep links in one sentence

A deep link is a URL that opens the app directly on a specific screen, instead of on the first screen.

Setup and testing in lesson 22. Today we only design the paths.
If the app is not installed, the same link opens the website. That is why route paths are designed as if they were public. It needs native setup (Android App Links, iOS Universal Links) and a file on the server proving the domain is yours. Analogy: a full address, with street, number and door, instead of "go to the town and look around".

2. go_router: a path for each screen

import 'package:go_router/go_router.dart';

import 'forecast_screen.dart';
import 'island_screen.dart';

/// Every screen of the app, with its path, like the pages of a site.
final router = GoRouter(
  initialLocation: '/',
  routes: [
    GoRoute(
      path: '/',
      builder: (context, state) => const ForecastScreen(),
      routes: [
        GoRoute(
          path: 'island/:id', // /island/pico
          builder: (context, state) =>
              IslandScreen(id: state.pathParameters['id']!),
        ),
      ],
    ),
  ],
);
  • Each GoRoute links a path to a screen. :id is a parameter: in /island/pico, state.pathParameters['id'] is 'pico'.
  • The island/:id route is inside the / route: opening /island/pico puts the grid underneath and Pico on top, even when you come in directly from a link. The back arrow works.
  • context.push('/island/pico') stacks on top, like Navigator.push. context.go('/island/pico') replaces the stack with the one for the path. For "open and come back", push.
Ask the class Why does the path carry the island's id and not the whole Island?
Answers to the questions. A path is text: it has to fit in a URL, in a link in an SMS or in a notification. An object does not fit in a URL. With the id, the destination screen fetches the rest from the data, and the same path works wherever it comes from. That is also why IslandScreen handles an id that does not exist: a mistyped link has to give "Ilha não encontrada", not a red error. In Chrome, type /island/xyz in the address bar to show it.

3. Navigation bar with independent stacks

StatefulShellRoute.indexedStack(
  builder: (context, state, shell) => Scaffold(
    body: shell, // the current tab, with its own stack
    bottomNavigationBar: NavigationBar(
      selectedIndex: shell.currentIndex,
      onDestinationSelected: (i) =>
          shell.goBranch(i, initialLocation: i == shell.currentIndex),
      destinations: const [
        NavigationDestination(
          icon: Icon(Icons.wb_sunny_outlined),
          label: 'Previsão',
        ),
        // and Avisos (Icons.warning_amber), Definições (Icons.settings_outlined)
      ],
    ),
  ),
  branches: [
    // one StatefulShellBranch per tab
  ],
),
  • StatefulShellRoute draws a Scaffold shared by all tabs, with the NavigationBar at the bottom. shell is the current tab.
  • Each StatefulShellBranch is a tab with its own stack. indexedStack keeps all three alive: switching tabs does not pop. It is the Instagram pattern.
  • Tapping the tab that is already active (i == shell.currentIndex) goes back to that tab's root. It is what users expect.
  • NavigationBar is the Material 3 one; BottomNavigationBar is the old one. Three to five destinations, with icon and label.
Ask the class Each tab has a Scaffold with its own AppBar, and shell has another Scaffold with the bar. Two Scaffolds one inside the other: is that a mistake?
Answers to the questions. It is not a mistake, it is normal with tabs: the outer Scaffold only has the bottom bar, and the inner one has the AppBar and the body of each screen. The SnackBar still appears because there is only one ScaffoldMessenger, created by MaterialApp. On tablets the bottom bar is swapped for a NavigationRail on the left; that is for the adaptive layouts lesson.
