Build and signing

Signing: why it exists (1 of 2)

  • Signing means computing a digest (hash) of the package and encrypting it with a private key. The certificate with the public key travels inside the package.
  • It proves two things: who built the app (the same key is the same author) and that the package was not changed after it was signed.
  • The operating system only accepts an update if the package name and the key are the same as those of the installed version. This is what stops a fake app from replacing yours.
  • It does not prove that the app is safe, or that the code is any good. It proves identity and integrity, nothing more.
  • Every app installed on a phone is signed, including debug ones: Flutter uses ~/.android/debug.keystore, generated on the first build, different on each machine.

For the tests: the signature proves authorship and integrity; it does not prove quality or security.

Analogy The signature is a notary's seal. It proves who made the app (the same key is the same author) and that nobody changed it along the way (the hash matches). It says nothing about the content of the document: a bad contract with a seal is still a bad contract.
A real example that has already caught groups out: colleague A installs the debug app on colleague B's phone; then B tries to run flutter run and gets INSTALL_FAILED_UPDATE_INCOMPATIBLE, because each laptop's debug key is different. The solution is to uninstall. This is the signature doing its job.

Analogy The keystore is the notary's stamp itself. Whoever loses it can never again sign an update as being the same app: to the system, an app with another stamp is another app. Play App Signing is Google keeping a copy of the final stamp; your upload key is a secondary stamp that, if lost, gets replaced.

Android: keystore, key.properties, signingConfigs

  • Keystore (.jks): a file with the key pair, protected by a password. Each key inside it has an alias. You create it once with keytool.
  • android/key.properties: four lines with the path of the keystore, the alias and the passwords. Gradle reads it. It goes into .gitignore.
  • signingConfigs in android/app/build.gradle.kts: tells Gradle that the release build type signs with that key.
  • Without this, flutter build appbundle signs with the debug key and the Play Console refuses the upload.
  • In CI, the keystore comes in as a secret in base64 and key.properties is written at build time.

For the tests: the keystore signs; key.properties only says where it is and how to open it. Neither of them goes into git.

An AAB cannot be installed with adb install. To test locally from a bundle you use Google's bundletool, or you generate an APK as well.

iOS: certificates and provisioning profiles (1 of 2)

  • Development certificate: per developer, to run on your iPhone. Distribution certificate: per team, for TestFlight and the App Store. Both issued by Apple from a request (CSR) and valid for one year.
  • The certificate's private key stays in the Keychain of the Mac that made the request. For another machine or for CI you export it as .p12.
  • App ID / bundle identifier: registered on developer.apple.com, in reverse DNS notation (pt.uac.tempoacores). The capabilities (push, associated domains) are attached to it.
  • Provisioning profile = certificate + App ID + list of devices (in development and ad hoc) + entitlements. It is embedded in the .ipa.
  • A free Apple ID is enough to run on your own iPhone: 7-day profile, no TestFlight and no store. The paid account costs 99 USD a year.
Analogy On iOS there is also Apple's notarial register. The certificate is the notary's identity (who you are); the provisioning profile is the record of which devices and which app the seal is valid for. Without both, Xcode does not sign, and the final seal that reaches the store is Apple's own.

iOS: bundle id and automatic signing (2 of 2)

  • Automatically manage signing in Xcode creates certificates, App ID and profiles for you. It is enough for almost every project, including yours.
  • Manual signing only when you need to control the profile: CI, extensions (widgets, rich notifications), several teams. In that world people use fastlane match, which keeps the certificates encrypted in a private repository.
  • The bundle id is unique in the world and does not change once published. Choose it well the first time.
  • flutter build ipa generates the .ipa file; the upload is done with Transporter or with xcrun altool. Only on macOS.
  • Versioning is the same as on Android: it comes from pubspec.yaml, as you will see next.

For the tests: on iOS the one who signs the app that reaches the store is Apple; your distribution certificate only authorises you to upload.

Show Xcode: Runner → Signing & Capabilities → Team. Also show developer.apple.com → Certificates, IDs & Profiles with your account, so they see that the three objects really exist. Do not spend more than 5 minutes: whoever has no Mac is not going to do this.

Versioning: version: 1.2.3+45

In pubspec.yamlAndroidiOSWho sees it
1.2.3 (before the +)versionNameCFBundleShortVersionStringThe user, in the store and in the settings
45 (after the +)versionCodeCFBundleVersionThe store, to order builds
  • Flutter copies both values to Gradle (flutter.versionName, flutter.versionCode) and to Xcode (Generated.xcconfig) on every build. The pubspec is the single source.
  • On the command line you can override them: --build-name=1.2.4 --build-number=46. That is what CI does with the run number.
  • Follow semver in the name: major when you break compatibility, minor when you add, patch when you fix.

Versioning: store rules

  • Play: the versionCode is an integer that has to be strictly greater than any already uploaded for the app, on any track. Maximum 2,100,000,000. It is never reused.
  • App Store: within the same version (1.2.3) the build number has to go up; TestFlight refuses a repeated build. A new version can restart the build at 1, but nobody does that.
  • The version name can repeat between uploads (several builds of 1.2.3 in testing); the code never.
  • On the phone, installing a versionCode lower than the installed one gives INSTALL_FAILED_VERSION_DOWNGRADE. It is the same mechanism that stops a user from being "updated" backwards.
  • A simple strategy for the project: 1.0.0+N, with N going up on every build that leaves the laptop for another person.

For the tests: versionName is for humans and can repeat; versionCode is for the store and can never go down or repeat.

Flavors and environments

  • Why: the dev app talks to the dev API, the prod one to the prod API; the two install side by side on the same phone; the icon says which is which; the prod one has no logs and no hidden menus.
  • Android: productFlavors in Gradle, with applicationIdSuffix (.dev) and source sets per flavor (src/dev/res) for icon and name.
  • iOS: schemes and configurations (Debug-dev, Release-prod) with .xcconfig files. More manual work; there are packages that automate it.
  • Flutter: flutter run --flavor dev. The flavor name has to exist on both platforms if you build both.
  • Two environments are enough for the project. In companies you see dev, staging and prod, rarely more.

For the tests: a flavor changes the identity of the app (id, name, icon) and the build configuration; it does not change the Dart code.

--dart-define for configuration and build secrets

  • --dart-define=API_URL=https://... on the command line and String.fromEnvironment('API_URL') in the code. It is a compile-time constant: there are also bool.fromEnvironment and int.fromEnvironment.
  • With many keys: --dart-define-from-file=env/prod.json. The prod file goes into .gitignore and into the CI secrets.
  • The value goes into the binary as text. Obfuscation (--obfuscate) makes it harder but does not stop someone from extracting it from an APK. It is for configuration and low-risk keys (URL, maps key restricted by package), not for secrets that would give access to data.
  • The group's secret for the course API stays where it already is: obtained at runtime and kept in flutter_secure_storage, as we did in lesson 17.
  • Flavor and dart-define combine: the flavor changes the identity of the app, the dart-define changes what Dart reads.

For the tests: --dart-define injects values at compile time; everything that goes into the binary can be read by whoever decompiles it.

1. Create the keystore and key.properties

  1. Generate the key, outside the project folder. Keep both passwords in the group's password manager. 
    keytool -genkey -v -keystore ~/tempo-acores-upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
  2. Write key.properties inside android/, with the absolute path of the keystore. 
    storePassword=your-password
keyPassword=your-password
keyAlias=upload
storeFile=/Users/me/tempo-acores-upload.jks
  3. Protect both in git before you make any commit. 
    android/key.properties
**/*.jks
**/*.keystore

2. signingConfigs in build.gradle.kts

import java.util.Properties
import java.io.FileInputStream

val keystoreProperties = Properties()
val keystorePropertiesFile = rootProject.file("key.properties")
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(FileInputStream(keystorePropertiesFile))
}

android {
    // ...namespace, compileSdk, defaultConfig stay as they are
    signingConfigs {
        create("release") {
            keyAlias = keystoreProperties["keyAlias"] as String
            keyPassword = keystoreProperties["keyPassword"] as String
            storeFile = keystoreProperties["storeFile"]?.let { file(it) }
            storePassword = keystoreProperties["storePassword"] as String
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")   // TODO 1: was "debug"
        }
    }
}

3. Generate, install and verify the release

  1. App bundle for the store. It ends up in build/app/outputs/bundle/release/app-release.aab. 
    flutter build appbundle --release
  2. Release APK to install on the phone. Uninstall the debug version first: the key is different and Android refuses the update. 
    flutter build apk --release
adb uninstall pt.uac.tempoacores
adb install build/app/outputs/flutter-apk/app-release.apk
  3. Verify who signed it. keytool reads the certificate from inside the APK. Compare the SHA-256 with the one from your keystore. 
    keytool -printcert -jarfile build/app/outputs/flutter-apk/app-release.apk
keytool -list -v -keystore ~/tempo-acores-upload.jks -alias upload

5. Dev and prod flavors on Android

android {
    // ...
    flavorDimensions += "environment"
    productFlavors {
        create("dev") {
            dimension = "environment"
            applicationIdSuffix = ".dev"          // pt.uac.tempoacores.dev
            versionNameSuffix = "-dev"
            resValue("string", "app_name", "Tempo Açores DEV")
        }
        create("prod") {
            dimension = "environment"
            resValue("string", "app_name", "Tempo Açores")
        }
    }
}
  • In AndroidManifest.xml, android:label="@string/app_name" now uses the flavor's value.
  • Different icon: copy android/app/src/main/res/mipmap-* to android/app/src/dev/res/mipmap-* and swap the images. The flavor's source set overrides main.
  • Run with flutter run --flavor dev. The two apps stay installed at the same time, with different names and icons.
