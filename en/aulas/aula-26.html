Observability and sprint 2 review

Theory (30 minutes): observability in production: crash reports, analytics, feature flags and remote config, metrics to keep an eye on. Practice: sprint 2 review, retrospective and sprint 3 planning.

Sprint 3: 19/11 to 02/12
Prepare the order of the demos (drawn at random) and a visible timer. Say right at the start that the review begins at 16:35 sharp, so that the groups get their phones ready during the theory. Test the projector cable or scrcpy before you start. If there are more than 7 groups, cut the theory to 25 minutes.

By the end of this lesson you can

  • Explain what a crash report contains and why the symbols and the app version are indispensable.
  • Compare Crashlytics and Sentry and hook up Flutter's two error capture points.
  • Define meaningful analytics events and say what is never recorded.
  • Use feature flags and remote config to ship switched off, switch off remotely and force an update.
  • Present sprint 2 in 5 minutes and plan sprint 3 with what goes in and what stays out.

Without observability you do not know the app is broken

  • On the web, the server has logs and you see the error in seconds. On mobile, the code runs on a stranger's phone, sometimes offline, on a version that is no longer the current one.
  • A crash report brings: stack trace, version and build number, device model and OS version, free memory, breadcrumbs (the last screens and actions) and whether the app was in the foreground.
  • Symbols: in release the code is AOT and may be obfuscated; without the symbol files (dSYM on iOS, mapping on Android, and Flutter's own with --split-debug-info) the stack trace is a list of addresses. They are uploaded at build time.
  • Grouping: the service gathers identical crashes into one issue, counts affected users and says "started in 1.4.2". That is what decides whether you hotfix today or in the next version.
  • A real example: a crash only on the Samsung A12 with Android 11 and the Samsung keyboard. Without reports, you would never reproduce it on your own phone.

For the tests: without symbols a release crash report is unreadable; without the app version you do not know whether the bug still exists.

Analogy Crash reports and metrics are the airplane's black box and instrument panel. Without them, you only find out the plane has crashed when someone phones, and without the flight data (version, device, breadcrumbs) you do not know why. The black box records what happened; the panel shows, in flight, whether everything is within limits.
Ask: "how many of you have given an app 1 star because it crashed?" Then: "and how many wrote to the developer to explain?" That is the whole argument of the lesson. Show a real crash from your Crashlytics, with the list of devices.

Non-fatal errorsrecordErrorcaptureException
FlutterError.onError = (details) {
  FlutterError.presentError(details);                 // still shows up in the console
  crash.record(details.exception, details.stack);     // build, layout and paint errors
};
PlatformDispatcher.instance.onError = (error, stack) {
  crash.record(error, stack, fatal: true);            // Futures with no catch, outside the tree
  return true;                                        // handled: the app does not die
};

For the tests: FlutterError.onError catches framework errors; PlatformDispatcher.instance.onError catches the asynchronous ones. Both SDKs hook up both for you.

Analytics: meaningful events

  • An event is a name and parameters: forecast_opened {location: "horta", source: "favorites"}. Firebase Analytics, Mixpanel, Amplitude, PostHog.
  • A meaningful event answers a product question: "how many reach the detail?", "how many add a favourite in the first session?". If nobody is going to look at the chart, do not record it.
  • Funnel: a sequence of events (open → list → detail → favourite) and the percentage that gives up at each step. That is how you decide what to improve next.
  • What not to record: name, email, exact location, the contents of text fields, anything that identifies a person without consent. GDPR, App Tracking Transparency on iOS and the Play data safety form (lesson 18).
  • Spotify knows at which second you skip the song. Your app needs to know whether anyone opens the map. Different scale, same logic.

For the tests: analytics records product events, not personal data; a funnel shows where users give up.

A 2-minute exercise: each group names one event it would record in Tempo Açores and the question it answers. Reject events with no question ("button_pressed") and events with personal data ("search_text" with the text).

Feature flags and remote config

  • A feature flag is a value the app reads at startup that decides whether it shows the feature. Firebase Remote Config, LaunchDarkly, or a /config endpoint of your own.
  • Ship switched off: the map code goes out in 1.5 with the flag set to false. You switch it on for 10% of users, watch the crashes, switch it on for everyone. No new store submission.
  • Kill switch: the broken feature is switched off in minutes; a fix through the store takes days, and some people never update.
  • A/B: half see the blue button, half the green one, and analytics says which converts. It only makes sense with volume; with 50 users it is noise.
  • Forced update: the config says "minimum version 1.4.0"; versions below it show a blocking screen with a link to the store. Mandatory when you change the API in an incompatible way (lesson 28).
  • Rule: the app works with the default values if the config does not arrive. The first launch may be offline.

For the tests: a feature flag switches features on or off without going through the store; the forced update blocks versions below the minimum.

Analogy A feature flag is a switch on the instrument panel that can be turned off in flight, without landing. A fix through the store is landing, repairing and taking off again: it takes days, and some passengers never catch the next flight. The switch turns off the broken feature in minutes, in the version that is already installed.

Metrics, alerts and logs

MetricWhat it isHealthy value
Crash-free usersPercentage of users with no crash in the periodAbove 99.5%
ANR (Android)"App Not Responding": the UI thread blocked for 5 secondsBelow 0.47% of sessions, the Play threshold
Startup timeFrom the tap on the icon to the first useful frameBelow 2 s on a cold start (lesson 30)
Adoption per versionPercentage of users on each versionMost on the latest after two weeks
  • The stores watch this: Play lowers the visibility of apps above the thresholds (Android vitals); the App Store shows crashes in the Xcode Organizer.
  • A useful alert: "crash-free dropped below 99% in the new version" → a message on Slack. An alert nobody reads is noise.
  • Logs: dart:developer or the logging package instead of print; levels; never tokens or personal data.

For the tests: crash-free users and ANR are the metrics the stores watch; above the thresholds, the app's visibility drops.

Sprint 2 review

  • 5 minutes per group, with a timer. Demo on the projected phone (scrcpy or mirroring), never on the emulator.
  • Structure: 30 s on what you promised for the sprint; 3 min of demo; 1 min on what was left undone; 30 s of questions.
  • Show: the app running from main, airplane mode switched on halfway through, favourites synced between two phones, the green CI in the README.
  • Those watching: each group notes one good thing and asks the next group one question. The teacher takes notes for the rubric.
If the demo fails Say what should have happened and move on. Nobody is penalised for a crash in the demo; you are penalised for not being able to explain it.
Order drawn at random. Cut at 5 minutes with no exceptions: it is a skill. Note per group: does offline work? favourites? error states? CI? and one UX comment. With 6 to 8 groups, set aside 45 minutes and keep the retro and the planning in the last 40.

Retro and sprint 3 planning

Retro (15 min)

  • Each member writes three sticky notes: start, stop, continue.
  • The group picks one of each and shares it with the class in one minute.
  • Typical theme: "stop leaving PRs open for three days"; "start testing on a colleague's phone".

Sprint 3, the last one (19/11 to 02/12)

  • Goes in: the missing minimum requirements, at most one extra per group, tests and CI, the polish and Friday's distribution.
  • Stays out: new features while the minimums are not done, big refactors, changing architecture.
  • Done in sprint 3: installable by a tester outside the group, README with screenshots, green CI.

Sprint 3 backlog in issues by Friday. Sprint 3 review on 02/12; freeze on 09/12.

The typical mistake in this planning is ambition: groups with favourites half done planning earthquakes and a map. Go round each group and ask "what happens if you only do half of this?". The answer has to be "we still have the minimums".

Teacher demo: Sentry in a Flutter project in 5 minutes

  1. Project on sentry.io of type Flutter; copy the DSN. Then flutter pub add sentry_flutter.
  2. Initialisation wrapping runApp: 
    Future<void> main() async {
  await SentryFlutter.init(
    (options) {
      options.dsn = const String.fromEnvironment('SENTRY_DSN');
      options.environment = kReleaseMode ? 'production' : 'dev';
      options.tracesSampleRate = 0.2;   // 20% of sessions with performance
    },
    appRunner: () => runApp(const TempoApp()),
  );
}
  3. Run with flutter run --dart-define=SENTRY_DSN=https://... and press a button that does throw StateError('crash test').
  4. See the issue in Sentry: readable stack trace, device, breadcrumbs with the screens visited. Mark it as resolved in the next version.
The DSN is not a critical secret It only allows sending events, but it goes through --dart-define all the same: what stays in the repository is its absence.
Do this in your own demo app, not in a group's. If the classroom network fails, you have the screenshot of the issue. Finish with the next slide and with the reminder that Friday is 4 hours and starts at 08:30.
