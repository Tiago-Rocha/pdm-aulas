Resilience: UI states, retry and chaos mode

Theory: network failures, 500 and 429 responses, unexpected JSON; offline-first, HTTP cache and pagination. Practice: modelling the four states of each screen, retry with backoff, pull-to-refresh and testing the app with the API's chaos mode switched on.

Repository: pdm-aula-14
Open the lesson with the phone in airplane mode and yesterday's app: a red screen with a raw exception. That is the "before". Announce right away that chaos mode will be switched on at around 10:00 and that it is announced, not a prank.

By the end of this lesson you can

  • List the ways a request fails on mobile and what the app should do in each one.
  • Explain offline-first, HTTP cache with ETag and Cache-Control, pagination and rate limiting.
  • Model the state of a screen as a sealed class and handle it with an exhaustive switch.
  • Implement retry with exponential backoff and jitter, and know when not to retry.
  • Build error, empty and loading screens the user understands, with pull-to-refresh and the age of the data.

Everything fails

  • No network: airplane mode, a tunnel, a garage. SocketException within milliseconds.
  • Slow network: weak 3G, café Wi-Fi with a login portal. A 20-second request, or a TimeoutException.
  • Server down: 500, 502, 503. Or 429 because the app asked too much.
  • Unexpected JSON: a field set to null, a string where a number should be, an empty list. FormatException or TypeError.
  • Examples: Spotify in offline mode keeps playing what it downloaded; Google Maps shows the cached map; the bank app says "no connection" but shows the last balance.
  • The worst possible result: a blank screen or a crash. The second worst: "Error: SocketException…".

For the tests: on mobile a network failure is not an exception, it is a normal case; the app is designed for it.

Analogy A counter always has one of four signs on display: "being prepared", "nothing available", "out of order, try again", or the dish on the counter. It is never left without a sign. A screen is the same: it is loading, it is empty, it failed or it has data; the blank screen is the counter with no sign at all.

Offline-first

  • Show what there is first. If there was ever any data, never show an empty screen: show the cache, then refresh.
  • Mark it as old. "Updated 12 min ago", an icon, a colour. The user decides whether to trust it.
  • Sync when possible. When the app opens, when the network comes back, when the list is pulled. Not every second.
  • Offline writes: a favourite marked with no network goes into a queue and is uploaded when there is a connection. Conflicts are resolved with rules (last one wins, or the server wins).
  • Detecting the connection: connectivity_plus says whether there is Wi-Fi or mobile data, not whether there is Internet. The only proof is a request that gets a response.

For the tests: offline-first is cache first, network second, and always telling the user the age of the data.

Question: "which apps do you use with no network?" Spotify, Maps, Notes, Kindle. Then: "and what annoys you when there is no network?" Usually: endless spinners. Use that to justify the slide.

HTTP cache: ETag, Cache-Control, 304

  • ETag is a fingerprint of the response. The client stores it and sends If-None-Match: "abc" in the next request. If nothing changed, the server replies 304 Not Modified with no body.
  • Cache-Control: max-age=600 allows the client to reuse the response for 10 minutes without asking. no-store forbids storing it (sensitive data).
  • 304 saves data and battery, but there is still a request. max-age avoids the request altogether.
  • Cache on the client (the app stores it) and cache on the server or CDN (stored for all users) coexist.
  • The http package does not cache by itself. Options: dio + dio_cache_interceptor, or our local database (lesson 16).

For the tests: ETag + If-None-Match give 304 "not changed"; Cache-Control says for how long the response is valid.

Pagination and rate limiting

PaginationHowPros and cons
Offset?page=3&size=20Simple; skips or repeats items when the list changes between requests
Cursor?after=eyJpZCI6NDJ9Stable (Twitter, Instagram); cannot jump to page 7
Infinite scrollRequest the next page when the scroll gets close to the endNatural on mobile; needs a loader at the end of the list and handling of an error halfway through
  • Rate limiting: the server limits requests per client (for example 100 per minute) and replies 429 Too Many Requests with Retry-After: 30.
  • The app respects Retry-After. Retrying straight away makes it worse and can get the token blocked.

For the tests: 429 asks for a wait, not an immediate retry; Retry-After says how long.

Retry with exponential backoff and jitter

  • Exponential backoff: wait 1 s, 2 s, 4 s, 8 s between attempts. A maximum number of attempts (3) and a ceiling on the wait (30 s).
  • Jitter: a random part in each wait. Without it, a thousand phones that failed at the same time retry at the same time and bring the server down again (thundering herd).
  • Retry: timeouts, connection failures, 5xx, 429 (respecting Retry-After).
  • Do not retry: 4xx (the request is wrong, it will fail again) and a non-idempotent POST: creating two favourites, paying twice.
  • If a POST really has to be retried, use an idempotency key (Idempotency-Key), like Stripe: the server ignores the repetition.

For the tests: retry only transient failures, only idempotent requests, with exponential backoff and jitter.

Do the sum on the board: 3 attempts with 1, 2, 4 s are 7 s of waiting in the worst case, plus 3 timeouts of 10 s. Is that too much? It depends: for a forecast yes, which is why the retry timeout should be shorter than that of the first request.

1. State as a sealed class

sealed class ForecastState {
  const ForecastState();
}

class Loading extends ForecastState {
  const Loading();
}

class Failure extends ForecastState {
  const Failure(this.message, {this.canRetry = true});
  final String message;
  final bool canRetry;
}

class Empty extends ForecastState {
  const Empty();
}

class Data extends ForecastState {
  const Data(this.locations, {required this.fetchedAt});
  final List<Location> locations;
  final DateTime fetchedAt;
}

1. The notifier now has a single field

class ForecastNotifier extends ChangeNotifier {
  ForecastNotifier(this._repo);
  final ForecastRepository _repo;

  ForecastState state = const Loading();

  Future<void> load({bool silent = false}) async {
    if (!silent) {
      state = const Loading();
      notifyListeners();
    }
    try {
      final items = await _repo.locations();
      state = items.isEmpty
          ? const Empty()
          : Data(items, fetchedAt: DateTime.now());
    } on ApiException catch (e) {
      state = Failure(messageFor(e), canRetry: e.transient);
    } catch (e) {
      state = Failure(messageFor(e));
    }
    notifyListeners();
  }
}

1. Exhaustive switch in the UI

@override
Widget build(BuildContext context) {
  final state = context.watch<ForecastNotifier>().state;

  return switch (state) {
    Loading() => const ListSkeleton(),
    Empty() => EmptyState(
        message: 'No locations yet.',
        action: 'Refresh',
        onAction: () => context.read<ForecastNotifier>().load(),
      ),
    Failure(:final message, :final canRetry) => ErrorState(
        message: message,
        onRetry: canRetry
            ? () => context.read<ForecastNotifier>().load()
            : null,
      ),
    Data(:final locations, :final fetchedAt) => LocationList(
        locations: locations,
        fetchedAt: fetchedAt,
      ),
  };
}

1. States: what matters

  • sealed closes the hierarchy: only these four subclasses exist. The compiler knows it and forces the switch to handle all of them.
  • Add a Partial state and build stops compiling until you handle it. It is impossible to forget a case.
  • With three booleans (isLoading, error, items) there were eight combinations, four of them impossible. Now there are four states, all of them possible.
  • Failure(:final message) is an object pattern: it extracts the field in the case itself.
  • The data lives inside the state (Data.locations): there is no list "left hanging" when the state is Failure.
Exercise 1 Migrate DetailNotifier to DetailState with the same four cases and an exhaustive switch in the detail screen. The test test/detail_state_test.dart checks each transition.
Frequent question: "why not an enum?" Because an enum does not carry data: Failure needs the message, Data needs the list. Show the compile error when you delete a case from the switch: it is the strongest argument for sealed.

2. Error, empty and loading widgets

class ErrorState extends StatelessWidget {
  const ErrorState({super.key, required this.message, this.onRetry});
  final String message;
  final VoidCallback? onRetry;

  @override
  Widget build(BuildContext context) {
    return Center(
      child: Column(
        mainAxisSize: MainAxisSize.min,
        children: [
          const Icon(Icons.cloud_off, size: 48),
          const SizedBox(height: 12),
          Text(message, textAlign: TextAlign.center),
          if (onRetry != null) ...[
            const SizedBox(height: 12),
            FilledButton.icon(
              onPressed: onRetry,
              icon: const Icon(Icons.refresh),
              label: const Text('Try again'),
            ),
          ],
        ],
      ),
    );
  }
}

2. Visual states: what matters

  • Error: an icon, a human message and a "Try again" button only when it makes sense (a null onRetry hides it). A 404 is not retried.
  • Empty: it is not an error. "No warnings yet" with a calm icon and, if possible, an action ("Refresh", "Add favourite").
  • Loading: a skeleton instead of a spinner in the centre: Skeletonizer(enabled: true, child: LocationList(locations: Location.sample)) draws the shape of the list in grey.
  • All three are reusable widgets in lib/core/widgets/: every screen of the project uses the same ones.
  • States are part of the design (lesson 6): they are designed with the same care as the screen with data.

3. Retry with backoff in ApiClient

Future<dynamic> get(String path, {int attempts = 3}) async {
  var delay = const Duration(seconds: 1);
  for (var i = 1; ; i++) {
    try {
      return await _getOnce(path);               // the get from lesson 12
    } on ApiException catch (e) {
      if (!e.transient || i >= attempts) rethrow;
      await Future.delayed(e.retryAfter ?? _withJitter(delay));
    } on TimeoutException catch (_) {
      if (i >= attempts) rethrow;
      await Future.delayed(_withJitter(delay));
    } on SocketException catch (_) {
      if (i >= attempts) rethrow;
      await Future.delayed(_withJitter(delay));
    }
    delay *= 2;                                    // 1 s, 2 s, 4 s
  }
}

Duration _withJitter(Duration base) =>
    base + Duration(milliseconds: Random().nextInt(300));

// In ApiException: 429 and 5xx are transient; 4xx are not
bool get transient => statusCode == 429 || (statusCode ?? 0) >= 500;

3. Human messages for each kind of failure

String messageFor(Object error) => switch (error) {
      SocketException() => 'No connection. Check the network and try again.',
      TimeoutException() => 'The server is taking too long. Try again shortly.',
      ApiException(statusCode: 429) => 'Too many requests in a row. Wait a few seconds.',
      ApiException(statusCode: 401) => 'The session has expired. Sign in again.',
      ApiException(statusCode: final c?) when c >= 500 =>
        'The service is having problems. We are showing the latest data we have.',
      FormatException() => 'We received unexpected data. We are already working on it.',
      _ => 'Something went wrong. Try again.',
    };
  • Only get retries: post and delete fail on the first attempt, because they are not idempotent.
  • retryAfter comes from the Retry-After header in seconds; the starter already reads it in _getOnce.
  • One message per kind of failure, with no jargon, and saying what the user can do. The original exception goes to the log.

4. Pull-to-refresh and the age of the data

class LocationList extends StatelessWidget {
  const LocationList({super.key, required this.locations, required this.fetchedAt});
  final List<Location> locations;
  final DateTime fetchedAt;

  @override
  Widget build(BuildContext context) {
    final minutes = DateTime.now().difference(fetchedAt).inMinutes;
    return RefreshIndicator(
      onRefresh: () => context.read<ForecastNotifier>().load(silent: true),
      child: ListView.builder(
        physics: const AlwaysScrollableScrollPhysics(),
        itemCount: locations.length + 1,
        itemBuilder: (_, i) {
          if (i == 0) {
            return ListTile(
              dense: true,
              leading: const Icon(Icons.schedule, size: 18),
              title: Text(minutes == 0 ? 'Updated just now' : 'Data from $minutes min ago'),
            );
          }
          return ListTile(title: Text(locations[i - 1].name), subtitle: Text(locations[i - 1].island));
        },
      ),
    );
  }
}

4. Refresh: what matters

  • RefreshIndicator calls onRefresh and keeps the circle visible until the Future completes. That is why load returns Future<void>.
  • silent: true does not go through Loading: the list stays visible during the refresh. Without it, the skeleton replaced the list and the gesture looked broken.
  • AlwaysScrollableScrollPhysics lets you pull even when the list fits on the screen.
  • "Data from 12 min ago" only makes sense if fetchedAt lives in the state. That is why it is in Data, not in the widget.
  • A refresh that fails with data on screen shows a SnackBar and keeps the data: it never swaps valid data for an error screen.
Exercise 4 When load(silent: true) fails and the current state is Data, keep the data and store the message in a refreshWarning field. The screen shows it in a SnackBar only once.

5. Chaos mode: observe, fix, repeat

  1. The teacher switches on chaos mode for your group: 3 s of latency on half the requests, 20% of 500 responses, a 429 every ten requests with Retry-After: 5.
  2. Use the app for two minutes like a user: open the list, go into a detail, pull to refresh, go back. Note down everything you see and should not see.
  3. Fix in order of severity: crash or blank screen, then raw messages, then retry hammering the 429, then valid data replaced by an error.
  4. Repeat until the app withstands five minutes of chaos with no crash, no blank screen and no technical message.
