A URL opens a screen: the three types

TypeExampleWithout the app installedWho can claim the link
Custom schemetempoacores://location/3Nothing happens (Android) or "cannot open" (iOS). Dead link.Any app. Two apps with the same scheme: a conflict with no rule.
App Links (Android 6+)https://tempoacores.pt/location/3Opens the website in the browser.Only whoever proves the domain with assetlinks.json.
Universal Links (iOS 9+)https://tempoacores.pt/location/3Opens the website in Safari.Only whoever proves the domain with apple-app-site-association.
https without verification (Android)The same URL, without autoVerifyBrowser.Android asks "open with…" and the user chooses.

A deep link is a URL that opens the app on a specific screen instead of the home screen. All three types do that; they differ in who can register them and in what happens without the app.

For the tests: App Links and Universal Links are ordinary https URLs that the system hands to the app after verifying the domain; a custom scheme is a URL that belongs only to the app, with no verification.

Analogy A deep link is a full address, with street, number, floor and door, instead of "go to the city and look around". Opening the app from its icon is arriving in the city; the URL takes you to the app and to the right screen, with the id of the location already in the path.
Ask who has tapped an Instagram link in an email and seen the app open instead of the website. Then ask what happens to that same link on a phone without Instagram: it opens the website. That is the difference custom schemes cannot give you.

Custom scheme vs https: security and fallback

  • Any app can declare tempoacores://. With two apps claiming the same scheme, Android asks "open with" and iOS picks one with no documented rule. That is why no bank sends tokens through a custom scheme.
  • Without the app, the custom scheme dies. The https link falls back to the website: the same link works in an email, an SMS, a QR code or an ad, with or without the app installed.
  • Verified https has a cost: a domain, a file served at /.well-known/, and on iOS the Associated Domains entitlement, which requires a paid developer account.
  • A custom scheme is fine for prototypes and lessons, internal apps, and the OAuth callback (com.googleusercontent.apps.123:/oauth2redirect), because the PKCE from lesson 17 protects the code even if another app catches it.
  • Example: Spotify has spotify:track:… and https://open.spotify.com/track/…. The share button always uses the second.

For the tests: nobody verifies a custom scheme and it has no fallback; an App Link or Universal Link proves domain ownership and falls back to the website when the app is not installed.

Analogy tempoacores:// is a nickname: any app can claim it and nobody checks who answers. https://tempoacores.pt/... is a registered address: the system confirms on the domain, through assetlinks.json or the AASA, that the app really owns the address; and if the app is not installed, the letter still arrives, at the website.

Domain verification: AASA and assetlinks.json

  • iOS: https://tempoacores.pt/.well-known/apple-app-site-association, JSON with no extension, served as application/json over HTTPS with no redirects. It lists appIDs (Team ID + bundle id) and the paths. The app declares applinks:tempoacores.pt in the entitlement.
  • The iPhone does not go to your server: it downloads the file through Apple's CDN at install time and every now and then. A change takes hours to arrive; in development use ?mode=developer in the entitlement.
  • Android: https://tempoacores.pt/.well-known/assetlinks.json with package_name and the SHA-256 of the signing certificate. The intent-filter carries android:autoVerify="true". Verified at install time.
  • Keys: debug, release and Play App Signing have different SHA-256 values. The file can list all three; ./gradlew signingReport shows them.
  • When it fails, nobody tells you: iOS opens Safari, Android opens the browser or asks. Diagnosis: adb shell pm get-app-links pt.uac.tempoacores; on iOS, Settings → Developer → Universal Links.

For the tests: verification is done by the system at install time, against a file in /.well-known/ on the domain; failure is silent and the link falls back to the browser.

Classic production mistake: the signing key changes (or they move to Play App Signing) and the App Links stop opening the app without anyone noticing, because the browser keeps showing the website. Tell it as a story; it comes up in the test.

Deferred deep links, attribution and use cases

  • Deferred deep link: the user taps the link, does not have the app, installs it, opens it, and lands on the right content. The stores do not pass the URL to the app; a service (Branch, AppsFlyer, Adjust) records the tap (IP, model, time) and does the match on first open.
  • Campaign attribution: knowing which ad or poster each install came from. That is the business of those services; ATT on iOS (lesson 18) limits the match. Firebase Dynamic Links shut down in August 2025.
  • Play Install Referrer: the only official mechanism, Android only and Play Store only: the store hands a string to the app on first open.
  • Use cases: notification → content (today); sharing ("see the forecast for Horta"); marketing (QR code on the festival poster); email verification and magic login; OAuth callback.
  • Magic login only with an App Link or Universal Link. With a custom scheme, the wrong app can catch the token that travels in the URL.

For the tests: a deferred deep link survives the install and needs an external service, because the stores do not hand the link to the app.

From the URL to the screen: the router decides

  • The OS hands the URL to the app. Android: an Intent with ACTION_VIEW, in onCreate if it was closed or onNewIntent if it was running. iOS: application(_:open:), or continue userActivity for Universal Links.
  • Flutter wraps it in a RouteInformation and MaterialApp.router hands it to go_router. For the router it is the same as context.go(url). Designing the routes as public URLs in lesson 9 pays off here.
  • Three situations: app in the foreground (it just navigates); in the background (it comes back to the screen and navigates); closed (cold start: the URL is the initial route and nothing else exists yet, neither token nor cache).
  • So the destination screen loads itself from the id, without depending on the user having gone through the list. And it validates: the id comes from outside and may not exist.
  • Testing with no website and no server: adb shell am start -a android.intent.action.VIEW -d "tempoacores://location/3" on Android; xcrun simctl openurl booted "tempoacores://location/3" on the iOS simulator.

For the tests: a deep link is handled by the router like any navigation; what changes is where the URL comes from and whether the app was already running.

Step 2: initialise the plugin and create the channel

import 'package:flutter_local_notifications/flutter_local_notifications.dart';

class NotificationService {
  final _plugin = FlutterLocalNotificationsPlugin();
  static const warningsChannel = AndroidNotificationChannel(
    'warnings', 'Weather warnings',
    description: 'IPMA warnings for your favourite locations',
    importance: Importance.high, // shows as heads-up, with sound
  );

  Future<void> initialize({required void Function(String route) onTap}) async {
    await _plugin.initialize(
      const InitializationSettings(
        android: AndroidInitializationSettings('@mipmap/ic_launcher'),
        iOS: DarwinInitializationSettings( // do not ask yet: we ask in context
          requestAlertPermission: false, requestBadgePermission: false, requestSoundPermission: false),
      ),
      onDidReceiveNotificationResponse: (response) {
        if (response.payload case final route?) onTap(route); // tap with the app running
      },
    );
    await _plugin.resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()
        ?.createNotificationChannel(warningsChannel); // once; the user manages it in the system
  }
}
The @mipmap/ic_launcher icon is fine for the lesson; in release, Android paints the small icon white and you get a square. Say that the project should have a monochrome ic_notification in res/drawable. Show the channel appearing in the system settings after the first launch.

Step 3: ask for permission in context and show

/// Ask when the user turns on "Notify me" in the settings, never at launch.
Future<bool> requestPermission() async {
  final android = _plugin.resolvePlatformSpecificImplementation<
      AndroidFlutterLocalNotificationsPlugin>();
  if (android != null) {
    return await android.requestNotificationsPermission() ?? false; // 13+; before that, true
  }
  final ios = _plugin.resolvePlatformSpecificImplementation<
      IOSFlutterLocalNotificationsPlugin>();
  return await ios?.requestPermissions(alert: true, badge: true, sound: true) ?? false;
}

Future<void> showWarning(Warning w) => _plugin.show(
      w.id, // stable id: the same warning replaces the notification, no duplicate
      'Warning ${w.level}: ${w.locationName}',
      w.description,
      NotificationDetails(
        android: AndroidNotificationDetails(warningsChannel.id, warningsChannel.name,
            channelDescription: warningsChannel.description,
            importance: Importance.high, priority: Priority.high),
        iOS: const DarwinNotificationDetails(),
      ),
      payload: '/location/${w.locationId}', // the route the router opens on tap
    );

Local notifications: what matters

  • A notification has an id, title, body, per-platform details and a payload. The id is its identity: show with the same id replaces it. Use the id of the warning, not a counter.
  • Channel: created once, with a name the user will read in the system settings. Importance.high gives heads-up. Changing the importance after it is created has no effect: the channel now belongs to the user.
  • Permission in context: on the "Notify me" button, never in main. On Android 13+ it is a runtime permission; before that it is automatic. iOS asks once and never again: the second attempt goes to the settings.
  • Foreground: Android always shows it; iOS shows it by default and lets you tune alert, sound and badge in DarwinNotificationDetails.
  • The payload is a route, not data: /location/3. Whoever opens the screen fetches the rest from the repository.
  • Android small icon: monochrome, in res/drawable. The ic_launcher becomes a white square in release.

Step 4: detect a new warning for a favourite

class WarningsNotifier extends ChangeNotifier {
  WarningsNotifier(this._repository, this._favorites, this._notifications);
  final WarningsRepository _repository;     // GET /v1/warnings (lessons 14 and 16)
  final FavoritesNotifier _favorites;       // lesson 17
  final NotificationService _notifications;

  List<Warning> _warnings = [];
  bool _hasLoaded = false;
  List<Warning> get warnings => _warnings;

  Future<void> refresh() async {
    final known = _warnings.map((w) => w.id).toSet();
    _warnings = await _repository.fetchWarnings();
    notifyListeners();

    final firstTime = !_hasLoaded;
    _hasLoaded = true;
    if (firstTime) return; // at launch, nothing is "new"

    for (final w in _warnings) {
      final isNew = !known.contains(w.id) && _favorites.contains(w.locationId);
      if (isNew) await _notifications.showWarning(w);
    }
  }
}

Step 5: from the payload to the route, with the app running or closed

/// null if the app opened normally; the payload route if a tap launched it.
Future<String?> launchRoute() async {
  final details = await _plugin.getNotificationAppLaunchDetails();
  if (details?.didNotificationLaunchApp != true) return null;
  return details!.notificationResponse?.payload;
}

// lib/main.dart
Future<void> main() async {

Step 6: the router with an initial route and URLs from outside

late final GoRouter router; // created in main(), once the initial route is known

GoRouter createRouter({String initialRoute = '/'}) => GoRouter(
      initialLocation: initialRoute,
      redirect: (context, state) {
        final uri = state.uri;
        // tempoacores://location/3: "location" is the host and "/3" the path, and
        // go_router only matches the path. We normalise to /location/3.
        if (uri.scheme == 'tempoacores') return '/${uri.host}${uri.path}';
        return null; // https://tempoacores.pt/location/3 already has the right path
      },
      routes: [
        GoRoute(
          path: '/',
          builder: (context, state) => const LocationsScreen(),
          routes: [
            GoRoute(
              path: 'location/:id', // the id comes from outside: validate it
              builder: (context, state) =>
                  DetailScreen(id: int.tryParse(state.pathParameters['id'] ?? '')), // null → "not found"
            ),
          ],
        ),
      ], // ...plus warnings, map and settings in the StatefulShellRoute from lessons 9 and 21
    );

From the tap to the screen: what matters

  • Two paths, one destination. Running: onDidReceiveNotificationResponse → router.go. Closed: getNotificationAppLaunchDetails → initialLocation. If you only handle the first, a tap with the app closed opens the list.
  • WidgetsFlutterBinding.ensureInitialized() before touching plugins in main. Without it, MissingPluginException.
  • The redirect normalises URLs that come from outside before the router looks for routes: scheme, host, prefixes. A single place for every format.
  • The id comes from outside: int.tryParse and a "location not found" screen with a button to the list. Never !.
  • Detecting what is new: save the known ids before refreshing and compare afterwards; the first load does not notify. Extra: persist the ids already seen in shared_preferences to survive restarts. Tomorrow's workmanager will need that.
  • To test without waiting for IPMA, the starter has a WarningsRepositoryFake that returns one extra warning on the second call.

Step 9: tomorrow's forecast at 20:00 with zonedSchedule

import 'package:timezone/timezone.dart' as tz; // tz.local set in initialize()

Future<void> scheduleTomorrowForecast(Location l, Forecast tomorrow) =>
    _plugin.zonedSchedule(
      1000 + l.id, // one id per location: rescheduling replaces, it does not pile up
      'Tomorrow in ${l.name}',
      '${tomorrow.tMin.round()}° to ${tomorrow.tMax.round()}°, ${tomorrow.type.description}',
      _next20h(),
      const NotificationDetails(
        android: AndroidNotificationDetails('forecast', "Tomorrow's forecast",
            channelDescription: 'Every day at 20:00, for your favourites'),
        iOS: DarwinNotificationDetails(),
      ),
      androidScheduleMode: AndroidScheduleMode.inexactAllowWhileIdle, // no exact alarm
      payload: '/location/${l.id}',
    );

/// Today at 20:00 if it has not passed yet; otherwise tomorrow at 20:00. Always in tz.local.
tz.TZDateTime _next20h() {
  final now = tz.TZDateTime.now(tz.local);
  final today = tz.TZDateTime(tz.local, now.year, now.month, now.day, 20);
  return today.isAfter(now) ? today : today.add(const Duration(days: 1));
}

Scheduled notifications: what matters

  • zonedSchedule takes a TZDateTime, not a DateTime: the time belongs to a time zone. In initialize(): tz.initializeTimeZones() and tz.setLocalLocation(tz.getLocation('Atlantic/Azores')). Without this tz.local is UTC and the 20:00 one fires at 19:00 in winter. For the phone's time zone, flutter_timezone.
  • Inexact vs exact: inexactAllowWhileIdle can be minutes late (Doze, tomorrow). exactAllowWhileIdle requires SCHEDULE_EXACT_ALARM on Android 12+, and on 14 only alarm clocks and calendars have it by default. For a forecast, inexact is enough.
  • The same id replaces: each forecast refresh reschedules with fresh text. Tomorrow, workmanager does that every 6 hours without opening the app.
  • Android: without RECEIVE_BOOT_COMPLETED and the receiver from step 1, a restart wipes the schedule. iOS: it keeps the 64 nearest pending ones and discards the rest.
  • Debugging: pendingNotificationRequests() lists what is scheduled; cancel(id) and cancelAll(). To test, schedule for now + 10 s and go back to 20:00 afterwards.
  • Switch turned off in the app settings: cancel all of them. Channel turned off in the system: it does not fire and there is no error; the app never finds out.
