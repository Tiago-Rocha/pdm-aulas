Automated tests and CI

Theory: the test pyramid, what is worth testing on mobile, mocks and fakes, golden tests and continuous integration. Practice: unit tests with mocktail, widget tests, and a GitHub Actions workflow that blocks pull requests with failures.

Repo: pdm-aula-25
Start by asking who has ever written an automated test in any language. It is usually fewer than half. Say that by the end of the lesson each of them will have a workflow running on GitHub and a badge in the README, and that Wednesday's review rewards a green CI. Confirm that everyone has the lesson repo cloned before starting the theory.

By the end of this lesson you can

  • Draw the test pyramid and state the cost and speed of each level.
  • Choose what to test in a mobile app (parsing, state logic, UI states) and what is not worth it.
  • Replace a repository with a fake or with a mocktail mock and test a notifier without a network.
  • Write a widget test with pumpWidget, find, tap and pumpAndSettle.
  • Configure GitHub Actions to run flutter analyze and flutter test on every PR and protect main.

The test pyramid

LevelWhat it checksHow manySpeedMaintenance cost
UnitA Dart function or class, without Flutter: fromJson, calculations, the notifierManyMillisecondsLow
WidgetA widget or screen in a test tree, without a phone: the text appears, the button does what it shouldSomeTenths of a secondMedium: breaks when the UI changes
Integration / E2EThe whole app on a phone or emulator, with a real or simulated networkFewMinutesHigh: fragile, slow, needs a device
  • Unit tests catch most logic bugs. Widget tests catch "the button disappeared". E2E tests catch "the app won't start on Android 12".
  • An inverted pyramid (E2E only) is the classic mistake: each test takes minutes, fails for reasons unrelated to the code, and nobody runs it.

For the tests: many unit tests, some widget tests, few integration tests; the higher up the pyramid, the slower and the more expensive.

Analogy Quality control in a car factory. Testing each bolt as it leaves the machine (unit) is fast, cheap and catches almost everything. Assembling the dashboard and pressing every button (widget) catches the fitting problems. Driving the complete car on the road (integration) is the most realistic test and the most expensive, so it is done few times and at the end.
Ask: "if you had 30 minutes to write tests for Tempo Açores, where would you spend them?" Steer towards: fromJson of the three models, notifier states, a widget test of the forecast screen. No E2E.

What to test on mobile

  • Parsing: fromJson with real JSON from the API, with missing fields, with null, with wrong types. That is where the app crashes in production when the backend changes.
  • State logic: the notifier goes from Loading to Data; to Failure when the repository fails; to Empty with an empty list. No UI, no network.
  • UI states: the screen shows the spinner, the error message, the "Try again" button, the list. One widget test per state.
  • Business rules: temperature range, warning colour, "Updated 12 min ago", °C/°F conversion.
What is not worth it Testing that a Text has the theme colour, testing trivial getters, testing the http package, or writing E2E for every screen. Test your code, not Flutter's.

For the tests: on mobile you test parsing and state logic first, because that is what fails when the API changes or the network drops.

Mocks and fakes: testing without a network

  • The notifier depends on a ForecastRepository. In the test, you inject another implementation. This is what we made the interface for in lesson 13.
  • Fake: a class of your own that implements the interface with simple logic (returns a fixed list, or throws). Readable, no package, enough for most cases.
  • Mock with mocktail: class MockRepo extends Mock implements ForecastRepository {}; you program responses with when(() => repo.forecast(any())).thenAnswer(...) and check calls with verify.
  • Mocktail needs no code generation (unlike mockito with build_runner). That is why we use it.
  • Never let a test hit the course API: it is slow, depends on the network, and fills the group's telemetry with test requests.

For the tests: a fake is a simplified implementation written by hand; a mock is programmed inside the test itself and records the calls.

Golden tests

  • A golden test renders a widget and compares the pixels with a reference image stored in the repo (matchesGoldenFile('forecast_card.png')).
  • It catches visual regressions that no find.text catches: padding that changed, a wrong colour in the dark theme, text cut off with a large font.
  • When they are used: design systems, components reused on many screens, apps where the look is the product. Flutter uses them for its own Material widgets.
  • When they get in the way: font rendering differs between macOS, Linux and the CI, and every legitimate UI change forces you to regenerate the images (flutter test --update-goldens). Without review, the reference images are updated without being checked.

For the tests: golden tests compare pixels with a reference image; they are valuable for visual components and fragile across different machines.

Continuous integration

  • CI: a server runs flutter analyze and flutter test on every push and on every PR. If it fails, the PR turns red and cannot go into main.
  • The green badge in the README is the definition of done made visible: "runs on the phone, no warnings, PR reviewed" now includes "green CI".
  • GitHub Actions is free for public repos and for Classroom ones; it uses subosito/flutter-action to install Flutter on the runner.
  • iOS builds need macOS: on Actions, runs-on: macos-latest costs 10 times more minutes. Alternatives made for mobile: Codemagic and Bitrise, with Mac machines, signing and upload to the stores included.
  • Rule: the CI runs what you run locally. If flutter analyze warns on your laptop, it warns on the CI.

For the tests: CI runs analyze and test on every PR; iOS builds require a macOS runner, which GitHub charges more for and Codemagic includes.

Show a real PR of yours with red checks and then green ones. Frequent question: "and does the CI build the app?" Only if you ask it to (flutter build apk), and that takes 5 to 8 minutes; in the lesson we do only analyze and test.

1. Unit test of the model

import 'dart:convert';
import 'package:flutter_test/flutter_test.dart';
import 'package:tempo_acores/models/forecast.dart';

const sample = '''
{"locationId": "3420300", "forecastDate": "2026-11-16",
 "tMin": 14.2, "tMax": 19.8, "weatherType": "rain", "precipProb": 65}
''';

void main() {
  group('Forecast.fromJson', () {
    test('reads the fields of the API v1 JSON', () {
      final p = Forecast.fromJson(jsonDecode(sample) as Map<String, dynamic>);
      expect(p.locationId, '3420300');
      expect(p.day, DateTime(2026, 11, 16));
      expect(p.type, WeatherType.rain);
    });

    test('computes the temperature range', () {
      final p = Forecast.fromJson(jsonDecode(sample) as Map<String, dynamic>);
      expect(p.range, closeTo(5.6, 0.001));
    });
  });
}

1. Unit test: what matters

  • A file in test/ that ends in _test.dart, with a main(). flutter test finds them all; flutter test test/models runs just one folder.
  • group groups, test is one case, expect(value, matcher) checks. Useful matchers: equals, isA<T>(), closeTo, isNull, throwsA, contains.
  • Never compare a double with ==: 19.8 - 14.2 is not exactly 5.6. Use closeTo.
  • One test, one reason to fail. If the test name contains "and", it is probably two.
  • The test JSON comes from the real API: copy a response from Swagger into a constant, do not invent fields.
Exercise 1 Make the two tests above pass and write the third: without tMax in the map, Forecast.fromJson throws a FormatException with a useful message (expect(() => Forecast.fromJson(withoutTMax), throwsA(isA<FormatException>())); TODO 1 in the model). Then a fourth: an unknown weatherType falls back to WeatherType.unknown, without throwing.
Give them 15 minutes. The usual question is the cast of jsonDecode: explain that it returns dynamic and that the "as Map<String, dynamic>" is mandatory. Anyone who finishes early writes the test for Location.fromJson.

2. Testing the notifier with a fake (1 of 2)

import 'package:flutter_test/flutter_test.dart';
import 'package:tempo_acores/data/forecast_repository.dart';
import 'package:tempo_acores/models/forecast.dart';
import 'package:tempo_acores/state/forecast_notifier.dart';

class FakeForecastRepository implements ForecastRepository {
  FakeForecastRepository({this.response = const [], this.error});
  final List<Forecast> response;
  final Object? error;

  @override
  Future<List<Forecast>> forecast(String locationId) async {
    if (error != null) throw error!;
    return response;
  }
}

final testForecast = Forecast(
  locationId: '3420300', day: DateTime(2026, 11, 16),
  tMin: 14.2, tMax: 19.8, type: WeatherType.rain,
);

2. Testing the notifier with a fake (2 of 2)

void main() {
  test('loading → data when the repository responds', () async {
    final notifier = ForecastNotifier(FakeForecastRepository(response: [testForecast]));
    final states = <ForecastState>[];
    notifier.addListener(() => states.add(notifier.state));

    await notifier.load('3420300');

    expect(states.first, isA<Loading>());
    expect(states.last, isA<Data>());
    expect((states.last as Data).items, hasLength(1));
  });

  test('loading → empty when the list comes back empty', () async {
    final notifier = ForecastNotifier(FakeForecastRepository());
    await notifier.load('3420300');
    expect(notifier.state, isA<Empty>());
  });
}

2. The same with mocktail: loading → failure

import 'package:flutter_test/flutter_test.dart';
import 'package:mocktail/mocktail.dart';
import 'package:tempo_acores/data/api_exception.dart';
import 'package:tempo_acores/data/forecast_repository.dart';
import 'package:tempo_acores/state/forecast_notifier.dart';

class MockForecastRepository extends Mock implements ForecastRepository {}

void main() {
  late MockForecastRepository repo;
  late ForecastNotifier notifier;

  setUp(() {
    repo = MockForecastRepository();
    notifier = ForecastNotifier(repo);
  });

  test('loading → failure when the API fails', () async {
    when(() => repo.forecast(any()))
        .thenAnswer((_) async => throw ApiException('No connection', canRetry: true));
    await notifier.load('3420300');
    expect(notifier.state, isA<Failure>().having((e) => e.message, 'message', 'No connection'));
    verify(() => repo.forecast('3420300')).called(1);
  });
}

2. Notifier: what matters

  • The test knows nothing about HTTP, JSON or Flutter. It only exists because the notifier receives the repository through the constructor.
  • Recording the states with addListener lets you assert the sequence (first Loading, then Data), not just the end.
  • when(...).thenAnswer((_) async => ...) for asynchronous methods; thenThrow throws synchronously and can escape your try. any() accepts any argument.
  • verify(...).called(1) catches the notifier calling the API twice by mistake. verifyNever catches the opposite.
  • A fake for simple, readable scenarios; a mock when you want to check calls or vary the responses within the same test.
Exercise 2 TODO 2: make the three tests pass. Then write the fourth: load called twice in a row does not leave the state in Loading at the end. Tip: verify(...).called(2) and expect(notifier.state, isNot(isA<Loading>())).
15 minutes. Where they get stuck: forgetting the "late" with setUp, and registerFallbackValue when the argument is not a primitive type (here it is a String, so it is not needed; tell them they will need it when they pass a Location object).

3. Widget test (1 of 2)

import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:mocktail/mocktail.dart';
import 'package:provider/provider.dart';
import 'package:tempo_acores/state/forecast_notifier.dart';
import 'package:tempo_acores/ui/forecast_screen.dart';
import 'package:tempo_acores/ui/widgets/forecast_card.dart';
import '../helpers.dart'; // MockForecastRepository, testForecast, ApiException

Widget testApp(MockForecastRepository repo) => ChangeNotifierProvider(
      create: (_) => ForecastNotifier(repo)..load('3420300'),
      child: const MaterialApp(home: ForecastScreen(locationId: '3420300')),
    );

void main() {
  testWidgets('shows the error message and the Try again button', (tester) async {
    final repo = MockForecastRepository();
    when(() => repo.forecast(any()))
        .thenAnswer((_) async => throw ApiException('No connection', canRetry: true));
    await tester.pumpWidget(testApp(repo));
    await tester.pumpAndSettle();
    expect(find.text('No connection'), findsOneWidget);
    expect(find.widgetWithText(FilledButton, 'Try again'), findsOneWidget);
  });
}

3. Widget test (2 of 2): the tap

  testWidgets('Try again loads again and shows the list', (tester) async {
    final repo = MockForecastRepository();
    when(() => repo.forecast(any()))
        .thenAnswer((_) async => throw ApiException('No connection', canRetry: true));
    await tester.pumpWidget(testApp(repo));
    await tester.pumpAndSettle();

    // From here on the API "recovers"
    when(() => repo.forecast(any())).thenAnswer((_) async => [testForecast]);

    await tester.tap(find.text('Try again'));
    await tester.pumpAndSettle();              // until there are no more scheduled frames

    expect(find.text('No connection'), findsNothing);
    expect(find.byType(ForecastCard), findsOneWidget);
    verify(() => repo.forecast('3420300')).called(2);
  });

3. Widget test: what matters

  • pumpWidget builds the tree; it needs a MaterialApp around it, otherwise there is no theme, text direction or Navigator.
  • The Provider goes into the test as it does in the app: the screen does not know that the repository is a mock.
  • pump() advances one frame; pumpAndSettle() advances until the tree settles. If the screen has an infinite animation (the spinner) and the state never changes, pumpAndSettle fails with a timeout: use pump(const Duration(seconds: 1)).
  • find.text, find.byType, find.byKey, find.widgetWithText. For repeated elements, give them a Key.
  • To test the Loading state, make the mock return a Completer<List<Forecast>>().future that you never complete, do one pump() and look for the CircularProgressIndicator. If you let the mock answer straight away, the loading would go by between two frames and you would not catch it.
  • The mock and testForecast live in test/helpers.dart, shared by all the tests. A widget test runs on the laptop, without an emulator, in tenths of a second.
Exercise 3 TODO 3: make the two tests pass. Then write the one for the Empty state: with an empty list "No forecasts for this location" appears and no ForecastCard appears.
20 minutes. The most frequent failure is "A RenderFlex overflowed" in the test: the test screen is 800x600 by default; tell them to use tester.view.physicalSize if they need a phone. The second is forgetting the await before pumpAndSettle.

4. GitHub Actions: the workflow

name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4

      - uses: subosito/flutter-action@v2
        with:
          channel: stable
          cache: true

      - run: flutter --version
      - run: flutter pub get
      - run: dart format --output=none --set-exit-if-changed lib test
      - run: flutter analyze --fatal-infos
      - run: flutter test --reporter expanded

4. CI: protect main and show the badge

  1. Commit the workflow on a branch, open the PR. In the Checks tab you see the verify job running; the first run takes 3 to 4 minutes (after that the cache speeds it up).
  2. Settings → Branches → Add branch ruleset for main: turn on "Require a pull request before merging" and "Require status checks to pass", and choose the verify check. From here on a red PR has no merge button.
  3. Badge in the README: 
    ![CI](https://github.com/pdm-daw-2026/tempo-acores-group-01/actions/workflows/ci.yml/badge.svg)
    Replace it with the name of your repo. Green in the README is the definition of done, visible to anyone passing by.
  4. Break it on purpose: comment out a line of fromJson, push, watch the PR turn red, restore it. Now you know what the CI does for you.

The subosito cache stores the SDK; the first run without a cache takes longer. Final exercise: one test per state

The project app has four states on each screen (lesson 14). Each state deserves a widget test that proves the UI does what the design says.

StateThe test asserts
LoadingThere is a CircularProgressIndicator or skeleton and there is no list
FailureThe human message and the "Try again" button appear; the tap calls the repository again
EmptyThe empty text appears with the suggested action
DataAs many cards appear as there are forecasts; the first has the right temperature
