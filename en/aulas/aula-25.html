Bug hunt: tests, CI and logs

Tempo Açores is on your phone and it has six bugs that have already turned into complaints. First, the three nets that catch them: tests, continuous integration and logs. Then the hunt: a test that fails, the fix, a pull request with a green CI, and the fix showing up on everyone's phone.

By the end of this lesson you can

  • Say what flutter analyze, tests and logs catch, and what each one lets through.

  • Read what the CI says about a pull request and decide whether it can go into main.
  • Read a log line and say where, to whom and in which version the error happened.
What to say: no new Flutter today. This is how teams work on an app that is already in people's hands: someone complains, the team finds it, proves it, fixes it and ships it without breaking something else. Everything you do today is used in sprint 3 of the project, where CI becomes mandatory.

Answer: none. The code compiles, the types match and there are no warnings. Analyze checks that the code is well written; it does not know what the app should do. Three nets, three different holes

  • Real world: the Flutter repository does not accept a pull request without tests; Instagram and Spotify get crashes from millions of phones through Crashlytics and Sentry.
  • The test says the bug exists; the log says who it happened to, where and in which version.
What to say: analyze is the spell checker, it catches what is badly written. The test is the proofreader who knows what the text should say. The log is the reader who calls to say page 40 makes no sense: you only find out after publishing, but you learn what no test predicted. Question for the class: which of the three nets is the cheapest? Analyze, because it runs by itself. And the most expensive? The log, because the bug has already reached someone. That is why you try to catch things as early as possible.

The test pyramid

  • Real world: Google aims for 70% unit, 20% integration between parts and 10% end to end; Firebase Test Lab runs the top ones on dozens of real phones.
What to say: the pyramid is a way of spending time well. A unit test runs in milliseconds and says exactly where the error is; an integration test starts the app on a phone, takes minutes and, when it fails, it might be the network, the GPS or the code. In today's repository: unit tests in test/models, test/location and test/state, widget tests in test/screens. The 12 tests all run in about a second. The top ones, in Flutter, are the integration_test package. There are also golden tests: they take a picture of a widget and compare it with the saved one, pixel by pixel; they are useful for a design system and annoying when the font changes. Question for the class: the minimum and maximum bug, which layer catches it? Unit: it is fromJson. And "Tentar de novo"? Widget: it needs a tap.

Where the magic happens: a test in three parts

test('offline, load keeps the error for the screen', () async {
  final repository = FakeForecastRepository()..failing = true;
  final notifier = ForecastNotifier(repository);

  await notifier.load();

  expect(notifier.error, contains('Sem ligação'));
});

The idea: Prepare, do, check. The name says, as a sentence, what should happen.

It is in test/state/forecast_notifier_test.dart. The three parts are separated by a blank line; when it fails, you read the name and know what broke. Prepare: a fake repository that fails, like a phone with no network, and the notifier with it. Do: one thing only, load. Check: the error was kept for the screen to show. expect compares what happened with what should have happened; contains, isNull, isTrue, closeTo are the matchers. No network, no screen, no phone: it runs in milliseconds. Question for the class: if load did not catch the exception, what would the test say? It would fail with the exception and the test name, not with "expected ... but was null".

Where the magic happens: a fake repository

class FakeForecastRepository implements ForecastRepository {
  bool failing = false;
  int islandCalls = 0; // how many times the islands were asked for
  @override
  Future<List<Island>> fetchIslands() async {
    islandCalls++;
    if (failing) throw Exception('Sem ligação');
    return islands;
  }

The idea: It answers straight away, always the same, and fails on demand.

The notifier gets its repository from outside, so the test gives it a fake one; islandCalls counts how many times it was called. It is in test/fakes.dart, together with FakeFavoritesRepository and the test islands (São Miguel, Terceira and Corvo, with their real coordinates). This is where splitting into layers pays off: since ForecastNotifier receives a ForecastRepository and does not create an HttpForecastRepository inside, the test swaps it without touching the app code. A fake is a real implementation, just a simple one; a mock (mocktail) is generated and each test says what it answers. For us a fake is enough and reads better. Question for the class: what is islandCalls for? To prove that a button asked for the islands again. It will come in handy for one of the bugs.

Where the magic happens: a screen in a test

testWidgets('offline, shows the error and a button', (tester) async {
  final repository = FakeForecastRepository()..failing = true;

  await pumpScreen(tester, const IslandsScreen(), forecast: repository);

  expect(find.textContaining('Sem ligação'), findsOneWidget);
  expect(find.text('Tentar de novo'), findsOneWidget);
});

The idea: The screen drawn in memory; find searches like a pair of eyes.

It is in test/screens/islands_screen_test.dart; pumpScreen is in test/fakes.dart and does what main.dart does, with fake parts: fake data and Ana logged in. A widget test has no phone: Flutter draws the screen in memory, and the tester moves time forward. pumpAndSettle waits for animations and futures to finish. To tap: await tester.tap(find.text('Tentar de novo')) and then pumpAndSettle. If find finds nothing, the tap fails saying there is no such widget. Question for the class: this test passes today, with the "Tentar de novo" bug inside. Why? Because it only checks that the button shows up, not what it does when tapped.

Red first, then green

You fixed the bug and only then wrote the test. It passed first time. What guarantee do you have that it catches the bug?

Answer: none. It might be testing something else, or the same path that already worked. Hence the order: watch it fail with the bug, fix, watch it pass. From then on the test stays in the repository for good: if someone breaks the same thing a year from now, the CI goes red before it reaches people. It is called a regression test. Each test file already has a test next to the bug; the quickest way is to copy that one and change the case. If the new test does not fail with the bug, it is not testing the bug: go back to the log and the issue.

Continuous integration: the CI

  • Real world: GitHub Actions, Codemagic and Bitrise for Flutter; for iPhone the CI needs a Mac.

It is 17:55, the review is at 18:00 and the CI on your PR is red. Do you merge?

The file is .github/workflows/ci.yml, in two parts. The first, test, runs on every pull request and every push to main: installs Flutter, flutter pub get, flutter analyze, flutter test. The second, deploy, only runs after a merge and only if the first passed: flutter build web with the clientId of this lesson's app and the version set to the commit, and publishes to GitHub Pages. The published version is the commit: in the logs, the version column changes when the fix arrives. The secrets (clientId and clientSecret) are in the repository settings, not in the code. Show a PR with the green tick and one with the red cross on GitHub, and the Actions tab with the log of a failing test. Answer to the question: no. A red merge breaks main for every teammate, and in the review what counts is what works. Better to show less, and green. In the projects, CI comes in sprint 3: it is this file, with only the test part.

Never in the log: passwords, tokens, the exact position, what the person typed.

A log just says "Error!". What is missing for you to fix it?

Answer: everything. Which error, on which screen, with which data, for whom, in which version. With the lines in the table you know it happened on the forecast screen, on Corvo, in a specific version; run ties together the lines from the same phone, in order. Real world: Crashlytics and Sentry group identical lines into one problem and tell you how many people hit it; Datadog and OpenObserve keep individual lines and let you search them. Ours is OpenObserve, installed on our own server: you only pay for the server. The "Onde estou?" log says the island and the kilometres, not where the person is. Privacy is the law: GDPR treats an email or a position in a log as personal data. Your name shows up today because this is a lesson and you chose it; in a real app it would be an id.

Where the magic happens: no silent errors

FlutterError.onError = (details) {
  FlutterError.presentError(details); // still red in the console
  log.error(details.exception, details.stack, {
    'where': details.context?.toDescription() ?? details.library,
  });
};

The idea: A widget breaks: the error goes to the console and to the log.

It is in lib/main.dart, which does the same for errors from futures that nobody caught (platformDispatcher.onError). In debug, a widget that breaks turns red with the error; in release (the published app) it turns grey, with no message: the person sees an empty screen and does not know why. Without this function, nobody on the team would know. The log is in lib/telemetry/app_log.dart: it batches lines, sends them every five seconds and, with no network, keeps them until there is one. The app never talks to OpenObserve: it sends to the course API (POST /v1/logs), which adds the name and the app and passes it on to OpenObserve. That way the log server's password never goes inside the app, where anyone could read it. It is what Crashlytics and Sentry do internally, with more care.
