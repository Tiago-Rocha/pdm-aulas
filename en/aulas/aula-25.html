Someone opens an island's forecast and the app crashes. Is that log or analytics?

At 16:40, before they pick up the app. Two minutes. Both travel down the same pipe: the app gathers the lines, sends them in batches to the course API and the API passes them on to OpenObserve, in the same apps stream. What sets them apart is the kind field: log or event. You do not need two servers to have both; you need to tell them apart in the code, so you do not end up with a pile of lines where the error gets lost among the taps. Events have one name per action, in the past tense, in snake_case, always the same: that is what you count by. Big apps use different tools for each side: Spotify or Revolut measure with analytics what people do and catch crashes with Crashlytics or Sentry. Answer: both. Opening the forecast is an analytics event (forecast_opened, with the island). The crash is an error, a log line. And the error line carries last_event: what the person had just done.

The idea: One line, in the forecast screen's initState. The rest is added along the way, and that is what lets you count and filter in OpenObserve.

It is in lib/screens/forecast_screen.dart: initState runs once, when the screen opens, and that is where you say "they opened the forecast for this island". The name is in the past tense and in snake_case, always the same: that is how you count it. How it works inside (lib/telemetry/analytics.dart and telemetry.dart), for whoever asks. Besides these fields, each line carries version (the deploy commit), platform and run (one per launch): analytics.event puts the line in the same queue as the logs, with kind event; the queue adds the version, the platform and the run and goes to the API in batches every five seconds; offline, it keeps them. The API adds who sent it and passes it on to OpenObserve. analytics also keeps the last event as text (forecast_opened island=corvo): if an error follows, the error line carries last_event. That is what Sentry calls a breadcrumb, the trail of crumbs. log.info('islands loaded', {'count': islands.length}) does the same with kind log. Question for the class: is "Tentar de novo" with no network an event or a log? The "islands failed" warning is a log (warn: something went wrong and the app held up); the tap on the button would be an event, and it does not exist: it stays as an idea for whoever finishes.

Where the magic happens: a test in three parts

test('offline, load keeps the error for the screen', () async {
  final repository = FakeForecastRepository()..failing = true;
  final notifier = ForecastNotifier(repository);

  await notifier.load();

  expect(notifier.error, contains('Sem ligação'));
});

The idea: Prepare, do, check. The name says, as a sentence, what should happen.

It is in test/state/forecast_notifier_test.dart. The three parts are separated by a blank line; when it fails, you read the name and know what broke. Prepare: a fake repository that fails, like a phone with no network, and the notifier with it. Do: one thing only, load. Check: the error was kept for the screen to show. expect compares what happened with what should have happened; contains, isNull, isTrue, closeTo are the matchers. No network, no screen, no phone: it runs in milliseconds. Question for the class: if load did not catch the exception, what would the test say? It would fail with the exception and the test name, not with "expected ... but was null".

Red first, then green

You fixed the bug and only then wrote the test. It passed first time. What guarantee do you have that it catches the bug?

Answer: none. It might be testing something else, or the same path that already worked. Hence the order: watch it fail with the bug, fix, watch it pass. From then on the test stays in the repository for good: if someone breaks the same thing a year from now, the CI goes red before it reaches people. It is called a regression test. Each test file already has a test next to the bug; the quickest way is to copy that one and change the case. If the new test does not fail with the bug, it is not testing the bug: go back to the log and the issue.

Continuous integration: the CI

  • Real world: GitHub Actions, Codemagic and Bitrise for Flutter; for iPhone the CI needs a Mac.

It is 17:55, the review is at 18:00 and the CI on your PR is red. Do you merge?

The file is .github/workflows/ci.yml, in two parts. The first, test, runs on every pull request and every push to main: installs Flutter, flutter pub get, flutter analyze, flutter test. The second, deploy, only runs after a merge and only if the first passed: flutter build web with the clientId of this lesson's app and the version set to the commit, and publishes to GitHub Pages. The published version is the commit: in the logs, the version column changes when the fix arrives. The secrets (clientId and clientSecret) are in the repository settings, not in the code. Show a PR with the green tick and one with the red cross on GitHub, and the Actions tab with the log of a failing test. Answer to the question: no. A red merge breaks main for every teammate, and in the review what counts is what works. Better to show less, and green. In the projects, CI comes in sprint 3: it is this file, with only the test part.
