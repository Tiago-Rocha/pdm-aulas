Network layer and the course API

HTTP in 10 minutes (1 of 2): methods and idempotency

  • A request is method + URL + headers + body (optional). The response is code + headers + body.
  • GET reads and never changes anything. POST creates or executes. PUT replaces. PATCH changes a part. DELETE deletes.
  • Idempotent: repeating the request gives the same result. GET, PUT and DELETE are; POST is not.
  • That is why a GET that failed can be repeated blindly. A repeated POST can create two favourites, or charge twice.
  • Real example: the IPMA app does a GET for the forecast; an MB WAY payment is a POST that the app never repeats on its own.

For the tests: idempotency decides what the app can repeat automatically when the network fails.

Analogy A restaurant. The menu is the API documentation (the OpenAPI contract); the order is the request, with method, URL and headers; the kitchen is the server. The dish arrives in a labelled box (the JSON response, Content-Type: application/json) with a code on the lid: 200 all is well, 404 there is none, 500 the kitchen broke down, 429 too many orders. The app does not eat from the box: it moves the contents onto the plate, which is the Dart model.
Ask: "if the payment request timed out, did the money leave or not?" The answer is "you don't know", and that is what makes POST dangerous to repeat. We come back to this in lesson 14 with idempotency keys.

HTTP in 10 minutes (2 of 2): codes, headers, JSON

CodeMeansWhat the app does
2xx (200, 201, 204)It went well; 204 carries no bodyUse the data
400, 404, 422The request is wrong or the resource does not existOur bug or an empty state; do not repeat
401, 403No valid token / no permissionRenew the token or log in; 403 is not worth repeating
429Too many requestsWait for the Retry-After and repeat
5xxServer errorRepeat with backoff, show old data
  • Everyday headers: Content-Type: application/json, Accept, Authorization, Cache-Control, ETag.
  • The body is JSON in UTF-8: objects, lists, numbers, strings, booleans and null. Anything that comes from outside may be missing.

For the tests: 4xx is the request's fault, 5xx is the server's fault, 429 is nobody's fault: it is a limit.

API catalogue and OpenAPI

  • Contract: an openapi.yaml file describes routes, parameters, data schemas and response codes. It is the source of truth.
  • Swagger UI: a page generated from the contract where you try out each route without writing code. The course API has one at /docs.
  • Client generation: openapi-generator produces the Dart code from the contract. We write it by hand to understand what is inside.
  • Versioning in the URL: /v1. When something changes in an incompatible way, /v2 is born and /v1 lives a few more months. You will migrate in lesson 28.
  • Catalogue: a company has dozens of APIs (Apigee, Postman, Backstage). As a client, you read the contract before writing the first line.

For the tests: client code that does not match the OpenAPI contract is a client bug.

Show the course API's Swagger live: expand GET /v1/locations, press "Try it out", show the response. Two minutes that save many questions in the practical part.

Timeouts, retries and cancellation

  • On the web, a hanging request is a tab that spins. On mobile it is a "dead" app and a one-star review.
  • Timeout: without it a request can wait for minutes. Typical values: 10 s to connect, 15 to 30 s in total.
  • Retry with backoff: 1 s, 2 s, 4 s, with randomness. Only for transient failures (timeout, 5xx, 429) and only on idempotent requests. Details in lesson 14.
  • Cancellation: the user left the screen; the response arrives for a widget that no longer exists. It is the origin of the error setState() called after dispose().
  • Why more so on mobile: the network changes (Wi-Fi to 4G halfway through), tunnels, locked screen, the system suspends the app with the request in flight.

For the tests: timeout limits the wait, retry repeats transient failures, cancellation avoids work for screens that no longer exist.

Interceptors and a single HTTP client

  • An interceptor sees every request and response in one place: it adds headers, writes logs, renews the token, measures times.
  • Common headers: Authorization: Bearer …, X-Platform (android/ios), X-App-Version. They let the backend know which version is failing and where.
  • A single client in the app: it reuses connections (keep-alive), keeps the configuration in one place and is swapped for a fake in tests.
  • With http: a subclass of BaseClient that overrides send. With dio: InterceptorsWrapper with onRequest, onResponse, onError.
  • Logging only in debug. A token printed to the release console ends up in a crash report.

For the tests: the interceptor is the single point everything passes through; it is where authentication, logs and retries live.

From JSON to a Dart object

The response arrives as text: a String with JSON in the body and Content-Type: application/json in the header. Before it becomes an object the app can use, it always goes through the same two steps: decode and type.

// The body of GET /v1/forecast/3 is text. A forecast, abridged:
// {
//   "locationId": 3,
//   "updatedAt": "2026-10-12T15:00:00Z",
//   "days": [ { "date": "2026-10-12", "tMin": 17.2, "tMax": 22.8, "type": "rain" } ]
// }
final body = utf8.decode(response.bodyBytes);         // String
final forecast = Forecast.fromJson(                   // Forecast, typed
  jsonDecode(body) as Map<String, dynamic>,           // Map, no types checked
);
forecast.days.first.tMin;                             // double, not dynamic
Analogy JSON is text with labels, like a form filled in by hand. jsonDecode turns the text into a dictionary (Map<String, dynamic>): you can already read it by key, but nothing is checked. Forecast.fromJson copies the form out neatly onto a typed record card: each field in the right place, with the right type, and a clear error if something is missing. From then on the rest of the app works with record cards, never with text.

1. A request with the http package

import 'dart:convert';
import 'package:http/http.dart' as http;

const baseUrl = 'https://api.pdm.example'; // real URL on the API page

Future<List<Location>> fetchLocations() async {
  final uri = Uri.parse('$baseUrl/v1/locations');
  final response = await http.get(uri).timeout(const Duration(seconds: 10));

  if (response.statusCode != 200) {
    throw ApiException('GET /v1/locations returned ${response.statusCode}',
        statusCode: response.statusCode);
  }

  final json = jsonDecode(utf8.decode(response.bodyBytes)) as List<dynamic>;
  return json
      .map((e) => Location.fromJson(e as Map<String, dynamic>))
      .toList();
}

1. A request: what matters

  • http.get returns a Future<Response>. Only with await do you have the statusCode and the body.
  • .timeout(…) throws TimeoutException if the response does not arrive. Without this, a tunnel leaves the app waiting forever.
  • jsonDecode returns dynamic: a List or a Map<String, dynamic>. The as confirms what you expect and fails early if it is not.
  • utf8.decode(bodyBytes) instead of body avoids broken accents when the server does not declare the charset.
  • Always check the status code before touching the body. A 500 also has a body, and it is not the one you expect.

2. Models from JSON, with validation

class Location {
  final int id;
  final String name;
  final String island;

  const Location({required this.id, required this.name, required this.island});

  factory Location.fromJson(Map<String, dynamic> json) {
    final id = json['id'];
    final name = json['name'];
    if (id is! int || name is! String) {
      throw const FormatException('Location without id or name');
    }
    return Location(id: id, name: name, island: json['island'] as String? ?? 'unknown');
  }

  Map<String, dynamic> toJson() => {'id': id, 'name': name, 'island': island};
}

class ApiException implements Exception {
  const ApiException(this.message, {this.statusCode});
  final String message;
  final int? statusCode;
  @override
  String toString() => 'ApiException($statusCode): $message';
}

2. Models: what matters

  • fromJson is a factory: it validates and builds. If the JSON is wrong, it throws FormatException with a message that says what was missing.
  • is! promotes the type: after the if, the compiler knows that id is an int. No !, no blind as.
  • Optional fields get a default value (?? 'unknown'); mandatory fields fail early. Decide case by case.
  • The custom exception (ApiException) carries the statusCode: in lesson 14 the UI chooses the message by code.
  • Rule: the app must never fail because the server sent one field too many or too few. Test with broken JSON.

3. FutureBuilder: the first screen connected to the API

class _LocationsScreenState extends State<LocationsScreen> {
  late final Future<List<Location>> _future = fetchLocations();

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<Location>>(
      future: _future,
      builder: (context, snapshot) {
        if (snapshot.connectionState != ConnectionState.done) {
          return const Center(child: CircularProgressIndicator());
        }
        if (snapshot.hasError) {
          return Center(child: Text('Could not load: ${snapshot.error}'));
        }
        final items = snapshot.data ?? const <Location>[];
        return ListView.builder(
          itemCount: items.length,
          itemBuilder: (_, i) => ListTile(
            title: Text(items[i].name),
            subtitle: Text(items[i].island),
          ),
        );
      },
    );
  }
}

3. FutureBuilder: what matters

  • connectionState is waiting while the Future runs and done when it finishes, with hasData or hasError.
  • The Future is created once, in a field of the State. If you create it inside build, every rebuild makes a new request to the API.
  • snapshot.data is nullable. ?? const [] instead of !.
  • Showing the raw snapshot.error is fine for learning; in production the message is chosen by the app (lesson 14).
  • FutureBuilder is enough for an isolated screen. On Monday we move this to a notifier, to share between screens and test without a network.
Exercise 3 Show the number of locations in the AppBar title when the data arrives, and in the error state a "Try again" button that recreates the Future with setState.

4. ApiClient: base URL, headers and timeout in one place

class ApiClient {
  ApiClient({required this.baseUrl, http.Client? client, this.token})
      : _client = client ?? http.Client();

  final String baseUrl;
  final http.Client _client;
  String? token;

  Map<String, String> get _headers => {
        'Accept': 'application/json',
        'X-Platform': defaultTargetPlatform.name,
        'X-App-Version': '1.0.0',
        if (token != null) 'Authorization': 'Bearer $token',
      };

  Future<dynamic> get(String path) async {
    final response = await _client
        .get(Uri.parse('$baseUrl$path'), headers: _headers)
        .timeout(const Duration(seconds: 10));
    if (response.statusCode >= 400) {
      throw ApiException('GET $path failed', statusCode: response.statusCode);
    }
    return jsonDecode(utf8.decode(response.bodyBytes));
  }
}

4. ApiClient: what matters

  • One instance for the whole app, created in main and passed by constructor to whoever needs it. On Monday Provider takes care of the distribution.
  • The http.Client is injectable: in tests you pass a MockClient from the http/testing package and there is no network.
  • defaultTargetPlatform.name (from package:flutter/foundation.dart) gives android or iOS. The version comes from package_info_plus in the project.
  • 4xx and 5xx errors become an ApiException with a statusCode. TimeoutException and SocketException (no network) pass through as they are. We handle all three in lesson 14.
  • The token is mutable on purpose: today it is assigned at startup; in lesson 17 it will be renewed by an interceptor.

5. Class token and the forecast for a location

// In ApiClient
Future<Map<String, dynamic>> post(String path, {Object? body}) async {
  final response = await _client
      .post(Uri.parse('$baseUrl$path'),
          headers: {..._headers, 'Content-Type': 'application/json'},
          body: jsonEncode(body))
      .timeout(const Duration(seconds: 10));
  if (response.statusCode >= 400) {
    throw ApiException('POST $path failed', statusCode: response.statusCode);
  }
  return jsonDecode(utf8.decode(response.bodyBytes)) as Map<String, dynamic>;
}

5. Token and forecast: what matters

  • POST /v1/auth/token receives JSON with client_id and secret and returns access_token: a JWT that expires. We look at what is inside it in lesson 17.
  • The secret comes in through the command line with --dart-define and String.fromEnvironment. Never in the code, never in git. Why, in lesson 18.
  • With the token in the ApiClient, every following request carries Authorization: Bearer with no extra code.
  • A 401 means a missing or expired token. Today you solve it by restarting the app; in lesson 17 it becomes automatic.
  • Spread {..._headers, 'Content-Type': …}: a new map with the common headers plus one. Idiomatic in Dart.
