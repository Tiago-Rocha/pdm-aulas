Futures, HTTP and JSON

How an app fetches data from a server without freezing: Future and async/await, HTTP requests, JSON turned into Dart objects, and FutureBuilder. Along the way, we read the course API's Swagger documentation together and try requests in the browser.

Theory lesson, with no hands-on work for the students and no homework. Reference times: Future and HTTP until 16:30; the course API and Swagger until 16:45; practice in Swagger (part 1, the token, until 16:55; part 2, bug hunt and review, until 17:25); JSON, parsing, FutureBuilder and Streams until the end. Today the students write no code: they use the API in the browser or in Postman. The Trilhos mini-project closed at 16:00, at the start of this lesson.

By the end of this lesson you can

  • Explain what a Future is and why a network request must never block the app.
  • Read an HTTP request and response: method, URL, headers, body and status code.
  • Turn JSON into Dart objects with fromJson and know where parsing usually breaks.
  • Read an API's Swagger documentation: operations, parameters, responses, schemas and errors.
  • Show data from the network with FutureBuilder: loading, error and data.
  • Tell a Future (one value) from a Stream (many values over time).

A value that has not arrived yet

  • A network request takes 50 ms on the school Wi-Fi and 5 s in a tunnel. The app cannot sit there waiting.
  • Dart runs your app on a single thread of execution, which also draws the screen. If it waits, the screen freezes: no scrolling, no animations, no taps.
  • That is why http.get does not return the response: it returns a Future<Response>, a promise that the response will come later.
  • A Future is in one of three states: uncompleted, completed with a value or completed with an error.
print('1. before the request');
final future = http.get(url); // the request goes out, the app carries on
print('2. the request has gone out');
final response = await future; // the function waits here for the response
print('3. arrived: ${response.statusCode}');
Ask the class While this function is stopped at the await, can the user scroll in the app?
Answers to the questions. Yes. await suspends this function, not the app: the thread goes back to the event loop and keeps drawing frames and handling taps. When the response arrives, the function resumes on the next line. It is the same as async/await in JavaScript, which many have already used with fetch: a Future is a Promise.

async and await

Future<List<Island>> fetchIslands(String token) async {
  final response = await http.get(
    Uri.parse('$baseUrl/v1/islands'),
    headers: {'Authorization': 'Bearer $token'},
  );
  final list = jsonDecode(response.body) as List<dynamic>;
  return list
      .map((item) => Island.fromJson(item as Map<String, dynamic>))
      .toList();
}
  • async marks the function: it always returns a Future, even when the return gives back a list.
  • await can only be used inside an async function. It reads top to bottom like normal code.
  • An error inside the function (no network, wrong JSON) completes the Future with an error. You catch it with try/catch around the await.
  • Forgetting the await is the most common mistake: you end up holding a Future instead of the response.
Show the forgotten-await mistake: final response = http.get(...) followed by response.body does not compile, because Future has no body. The compiler catches most of these cases; the dangerous one is a function returning Future<void> called without await, which runs "in parallel" with nobody seeing the error. The unawaited_futures lint warns about it.

HTTP in 10 minutes (1 of 2): request and response

  • GET reads and never changes anything. POST creates. PUT replaces. DELETE deletes.
  • Idempotent: repeating the request gives the same result. GET, PUT and DELETE are; POST is not. A failed GET can be repeated; a repeated POST can create two reports, or charge twice.

For the tests: idempotency decides what the app may repeat on its own when the network fails.

Open the Chrome developer tools (Network tab) on any page and show a real request: method, URL, headers, code and body. DAW students have already seen this on the web; mobile uses exactly the same protocol. Ask: "if the payment request timed out, did the money leave or not?" The answer is "you don't know", and that is what makes a POST dangerous to repeat.

Reading Swagger (1 of 4): the map of the API

  • Swagger is a page generated from the OpenAPI contract (/openapi.json): a file that describes every route, its parameters, its data and its errors. It is the source of truth.
  • Operations are grouped by topic. Each row is a method and a path: GET /v1/islands.
  • The padlock says the operation needs a token. The Authorize button keeps the token for every request on the page.
Open https://api-pdm.sublimecipher.com/docs on the projector and go through the page from top to bottom: the four groups (Autenticação, Ilhas e trilhos, Previsão, Relatos) and, at the end, the Schemas section. Click /openapi.json to show that Swagger is just a nice way of reading that file. Tools like openapi-generator generate the client code from it; we write it by hand to understand what is in there. The API's texts are in Portuguese.

Reading Swagger (2 of 4): one operation

  • Parameters: what you have to send. id is required (* required), it is text and it goes in the path: /v1/islands/sao-miguel/forecast. Others go in the query: /v1/trails?islandId=faial.
  • Try it out and Execute make the real request. Swagger shows the curl, the URL, the status code and the response body. If the curl has no Authorization: Bearer line, Authorize was missed.
  • Responses: one entry per possible code (200, 401, 404, 502), each with an example. It is the list of cases your app has to handle.
Live: Try it out on POST /v1/auth/token with the Docente account (~/.config/pdm-api/docente.json; do not show the secret on screen), copy the accessToken, Authorize, then Execute on GET /v1/islands/pico/forecast. Show the generated curl: it is the same request the Dart code will make, with the Authorization header. Careful: the curl shows the token on screen; it lasts one hour and only belongs to the Docente account.

Reading Swagger (3 of 4): the schema

  • Schema (next to Example Value) is the exact shape of the response. The red * means the field is always there.
  • The types tell you how to read each field in Dart: string, integer, number, objects inside objects ({ }) and lists ([Day]). Enum is the closed list of values: it becomes an enum in Dart.
Link it to the model: this schema is, field by field, the DayForecast we are about to write. Ask: "is tMin integer or number?" It is number, so in Dart it is read as num and turned into a double (the "Where parsing breaks" slide explains why). category has the same five values as the WeatherType enum from the lessons.

Reading Swagger (4 of 4): the errors

  • Every code the operation can return has an entry: for /v1/islands/{id}/forecast they are 200, 401, 404 and 502.
  • Errors always have the same shape: code for the program to decide (not_found, unauthorized...), message to show to the person.
  • The list of codes is the list of cases the screen has to handle. If Swagger says a 502 can come back, the app needs something to show when it does.
The 502 happens when IPMA does not answer and the API has no stored forecast: it is not the app's or the student's fault, and the app should say "try again in a moment". All the API's error codes are on the site's API page, in the errors table.

From JSON to a Dart object

The response arrives as text. Before it becomes an object the app can use, it always goes through the same two steps: decode and give it types.

The two steps are always the same, whatever the API. jsonDecode knows nothing about forecasts or islands; fromJson, which we write for each model, does.

One island: from JSON to Island

{
  "id": "sao-miguel",
  "name": "São Miguel",
  "imageUrl": "https://api-pdm.sublimecipher.com/static/islands/sao_miguel.jpg",
  "trailCount": 3
}
factory Island.fromJson(Map<String, dynamic> json) {
  return Island(
    id: json['id'] as String,
    name: json['name'] as String,
    imageUrl: json['imageUrl'] as String,
  );
}
trailCount comes in the JSON and the model ignores it: fromJson reads only what the app uses. If the API adds fields, the app does not break; if it removes or changes one the app reads, it breaks. Frequent question: "why not use json_serializable or freezed?" You can, in the project: they generate this code. Today we write it by hand to understand what the generator does.

JSON with objects inside objects

{
  "date": "2026-10-14",
  "weatherType": {
    "id": 7,
    "description": "Aguaceiros/chuva fracos",
    "category": "rain"
  },
  "tMin": 20.0,
  "tMax": 24.2,
  "rainChance": 57,
  "wind": {
    "direction": "SW",
    "class": 2,
    "description": "Moderado"
  }
}
  • An object inside another is one more Map; a list is a List<dynamic> that you walk through with map.
  • JSON has no dates and no enums: they come as text, and fromJson converts them (DateTime.parse, values.byName).

One day: DayForecast.fromJson

factory DayForecast.fromJson(Map<String, dynamic> json) {
  final weather = json['weatherType'] as Map<String, dynamic>;
  final wind = json['wind'] as Map<String, dynamic>;
  return DayForecast(
    date: DateTime.parse(json['date'] as String),
    type: WeatherType.values.byName(weather['category'] as String),
    tMin: (json['tMin'] as num).toDouble(),
    tMax: (json['tMax'] as num).toDouble(),
    rainChance: json['rainChance'] as int,
    windClass: wind['class'] as int,
  );
}
  • The app's model does not have to match the JSON. IPMA does not give the wind in km/h, only its class: the lessons' windKmh becomes windClass.
Link it to the WeatherType enum from lessons 5 to 11: the names (sunny, partlyCloudy, cloudy, rain, storm) were chosen to match the API's category, which is why byName works with no conversion table. The whole forecast is a Forecast with location and a days list, each one a DayForecast.fromJson.

The full request, with errors

void _check(http.Response response) {
  if (response.statusCode >= 200 && response.statusCode < 300) return;
  final body = jsonDecode(response.body) as Map<String, dynamic>;
  final error = body['error'] as Map<String, dynamic>;
  throw ApiException(response.statusCode, error['message'] as String);
}

Future<List<Island>> fetchIslands(String token) async {
  final response = await http
      .get(
        Uri.parse('$baseUrl/v1/islands'),
        headers: {'Authorization': 'Bearer $token'},
      )
      .timeout(const Duration(seconds: 10));
  _check(response);
  final list = jsonDecode(response.body) as List<dynamic>;
  return list
      .map((item) => Island.fromJson(item as Map<String, dynamic>))
      .toList();
}
  • http does not throw on a 404 or a 500: the response arrives anyway. Checking the statusCode is your job.
  • Without a timeout, a request in a tunnel can hang for minutes. With it, after 10 s the Future completes with an error.
Show the real result of the two errors, which are in the demo code: GET /v1/islands/atlantida/forecast gives "404: Não há nenhuma ilha com o id "atlantida"." (there is no island with that id) and a token request with the wrong secret gives "401: clientId ou clientSecret errados." (wrong clientId or clientSecret). ApiException is our own class with statusCode and message; later on the app decides what to do for each code (resilience lesson).

The token and the secret

Future<String> fetchToken(String clientId, String clientSecret) async {
  final response = await http.post(
    Uri.parse('$baseUrl/v1/auth/token'),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode({'clientId': clientId, 'clientSecret': clientSecret}),
  );
  _check(response);
  final json = jsonDecode(response.body) as Map<String, dynamic>;
  return json['accessToken'] as String;
}
const clientId = String.fromEnvironment('CLIENT_ID');
const clientSecret = String.fromEnvironment('CLIENT_SECRET');
flutter run -d chrome \
  --dart-define=CLIENT_ID=pdm-ab12cd \
  --dart-define=CLIENT_SECRET=your-secret
  • In a POST the body goes as JSON: jsonEncode does the opposite of jsonDecode.
  • The secret does not go into the code or into git. --dart-define passes it in when you run the app.
Honest warning: --dart-define keeps the secret out of git, but it stays inside the compiled app, and anyone who opens the APK can read it. In a real app the user logs in and the secret is never on the phone; that is the authentication lesson. For the course it is enough, because each student has their own and the API knows who made each request.

FutureBuilder: the screen that waits

class _IslandsScreenState extends State<IslandsScreen> {
  late final Future<List<Island>> _islands;

  @override
  void initState() {
    super.initState();
    _islands = fetchIslands(widget.token); // once, not in build
  }

  @override
  Widget build(BuildContext context) {
    return FutureBuilder<List<Island>>(
      future: _islands,
      builder: (context, snapshot) {
        if (snapshot.connectionState != ConnectionState.done) {
          return const Center(child: CircularProgressIndicator());
        }
        if (snapshot.hasError) {
          return Center(child: Text('${snapshot.error}'));
        }
        final islands = snapshot.data!;
        return ListView.builder(
          itemCount: islands.length,
          itemBuilder: (context, i) => ListTile(
            leading: Image.network(islands[i].imageUrl, width: 56),
            title: Text(islands[i].name),
          ),
        );
      },
    );
  }
}

FutureBuilder: what matters

  • The builder runs again every time the Future changes state. The snapshot tells you which state it is in.
  • Three branches, always: loading (connectionState), error (hasError, error) and data (data). The three states of the Future, drawn on screen.
  • The Future is created once, in initState. If you write future: fetchIslands(token) inside build, every rebuild makes a new request.
  • Image.network instead of Image.asset: the photo also comes from the network, and Flutter caches it.
  • To ask again (a "Try again" button), assign a new Future inside setState.
Ask the class How many times does a screen's build run? And how many requests would the server get if the Future were created in there?
Answers to the questions. Many times, with no control: every setState, every change of theme or text size, every time the keyboard opens or the screen rotates, and every hot reload. With the Future in build, each of those is a new request and the screen goes back to "loading". Live demo: change future: _islands to future: fetchIslands(widget.token), hot reload three times and show the repeated requests in Chrome's Network tab.

Demo code in ../pdm-aula-12 (local, no remote). Run it with flutter run -d chrome --dart-define=CLIENT_ID=... --dart-define=CLIENT_SECRET=... using the Docente account from ~/.config/pdm-api/docente.json.

What if the data never stops coming?

Future<T>Stream<T>
How many valuesOne, onceMany, over time
How you waitawaitawait for or listen
WidgetFutureBuilderStreamBuilder
ExamplesToday's forecast, the token, a photoThe GPS position, chat messages, stock prices, a moving bus
  • A Future is a parcel: it arrives once. A Stream is a subscription: it arrives every time there is a new issue, until you cancel.
  • Where real-time data comes from: polling (the app asks every X seconds), Server-Sent Events or WebSockets (the server sends when there is something new).
  • StreamBuilder has the same snapshot as FutureBuilder, but the builder runs again for every new value.
Polling is the simplest and the most wasteful: with 1000 phones asking every 5 seconds, that is 200 requests per second, almost all with the same answer. With WebSockets, the server asks once and sends to everyone. It is one of the questions to ask when designing a real-time app.
