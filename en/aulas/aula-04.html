Lifecycle, asynchrony and Dart II

Theory: the lifecycle of a mobile app, with the states imposed by the operating system, and the execution model on a single thread with 16 milliseconds per frame. Practice: the asynchronous part of Dart: Future, async/await, Stream, error handling and JSON.

States of an app

StateWhat the user seesWhat the OS does
Foreground (active)The app on screen, responding to touchGives it priority for CPU, network and GPS
Inactive (in transition)Incoming call, notification panel, app switcherPauses animations; the app is still visible
BackgroundAnother app on screenLimits CPU and network; after a few seconds, suspends
SuspendedNothing; it appears in the list of recent appsKeeps it in memory, but runs no code
DeadNothing, or a launch screen when it comes backHas freed the memory; the next launch is a cold start

For the tests: in the background the app can be killed at any moment and without warning. What you did not save, you lost.

Analogy A shop in a shopping centre. Open and with customers is the foreground. With the lights off but the stock in place is the background and suspension. In the middle of the night, the shopping centre can evict the shop without warning to give the space to another one: that is the process being killed. When the customer comes back, the shop has to reopen as if nothing had happened, and whatever was not stored in the stockroom (the disk) is lost.
Ask: how many apps do you have "open" on your phone right now? Most of the ones that show up in the recents list are dead; the OS only shows a screenshot. Example: opening Instagram after a few hours and seeing the launch screen is a cold start. Give this slide 5 minutes.

AppLifecycleState in Flutter

class _ForecastScreenState extends State<ForecastScreen> {
  late final AppLifecycleListener _lifecycle;

  @override
  void initState() {
    super.initState();
    _lifecycle = AppLifecycleListener(
      onResume: _refreshForecasts,            // back on screen: the data may be stale
      onPause: _saveDraft,                    // going to the background: save now
      onStateChange: (state) => debugPrint('lifecycle: $state'),
    );
  }

  @override
  void dispose() {
    _lifecycle.dispose();
    super.dispose();
  }

  void _refreshForecasts() { /* ask the API if more than 10 min have passed */ }
  void _saveDraft() { /* shared_preferences, lesson 16 */ }
}

The states are resumed, inactive, paused, hidden and detached. For the tests: resumed is the moment to refresh; paused is the last safe moment to save.

A single UI thread

  • Your app's Dart code runs in a single isolate, with a single thread. It is the same one that draws the interface and responds to touch.
  • An event loop takes tasks from two queues: microtasks (continuations of Futures: then, await) and events (touches, timers, network responses, the request to draw the next frame). It always empties the microtasks before moving on to the next event.
  • await does not block: it suspends the function, hands the thread back to the loop, and the continuation joins the queue when the value arrives.
  • A heavy synchronous computation (decoding a 5 MB JSON, a loop of millions of iterations, resizing a photo) holds the thread until it finishes. Meanwhile nothing is drawn and no touch is handled.

For the tests: async/await does not create threads. It is for waiting on network and disk without blocking; it is not for speeding up computation.

Analogy The event loop is someone serving at a counter who takes one order at a time, in the order they arrived. await is that person setting an order aside while the coffee comes out of the machine and serving the next customer; they do not stand there staring at the machine. When the coffee is ready, the order goes back into the queue.
Draw the two queues on the board and the loop alternating between them. Ask: "if I run a for loop of 100 million iterations inside an async function, does the UI keep responding?" Most say yes. No: async is not parallelism. This is the number one confusion in the tests.

Jank: 16 milliseconds per frame

  • A 60 Hz screen shows a new image every 16.6 ms; at 120 Hz (iPhone Pro, many recent Android phones) every 8.3 ms.
  • In that time Flutter has to run build, layout, painting and hand over to the GPU. If your code holds the thread for longer than that, the frame is dropped.
  • The user sees: stuttering scroll, an animation that jumps, a button that only reacts half a second later. It is called jank and it is the number one reason for one-star reviews.
  • Long blocks are worse: Android shows "App isn't responding" (ANR) after 5 s; iOS kills the app if startup takes too long.
  • Where it happens in practice: parsing a large JSON at startup, lists with heavy widgets, images at their original size.

For the tests: 60 fps means a budget of 16 ms per frame; a missed frame is jank.

Analogy The screen asks for a new image 60 times a second, and each request has 16 ms to be served. An 80 ms jsonDecode is a customer who holds up the counter for five orders: the others are left waiting and the screen freezes.
Ask whether anyone has felt this in a well-known app; almost always someone mentions a banking app or the tax office app. If you have an app to hand with a synchronous sleep, show the performance overlay in 2 minutes; otherwise it waits for lesson 18.

Isolates: the answer to heavy work

  • An isolate is a thread with its own memory. Two isolates do not share objects; they communicate through messages, which are copies.
  • Isolate.run(() => jsonDecode(text)) or compute(parse, text) runs the function in another isolate and returns the result as a Future. The UI stays at 60 fps.
  • With no shared memory there are no race conditions and no locks. In exchange, passing large data costs copying time.
  • You cannot touch widgets or call plugins from another isolate.
  • Real cases: decoding the API response with a thousand forecasts, compressing a photo before sending it, searching a list of 50,000 items.
Today it is just the idea. In lesson 18 we measure with DevTools and move work to an isolate.
Analogy Two cooks in separate kitchens, each with their own pans (the memory). They share nothing; they pass dishes through the hatch, and each dish is a copy (the messages). The cook serving the dining room, the main isolate, never leaves the room empty: the heavy work goes to the other kitchen.

1. Future and async/await

import 'dart:math';

Future<double> readTemperature(String location) async {
  await Future.delayed(const Duration(seconds: 1));     // simulates waiting for the network
  return 15 + Random().nextInt(10) + Random().nextDouble();
}

void main() async {
  print('Requesting Ponta Delgada...');
  final t = await readTemperature('Ponta Delgada');     // waits here, without blocking
  print('Ponta Delgada: ${t.toStringAsFixed(1)} °C');

  final future = readTemperature('Horta');              // no await: it is just a future value
  print('Requested Horta and carried on');
  future.then((t) => print('Horta: ${t.toStringAsFixed(1)} °C'));
  print('End of main (Horta arrives later)');
}

1. Future: what matters

  • Future<T> is the promise of a value T that does not exist yet. async marks the function; await waits for the value without stopping the thread.
  • An async function always returns a Future, even if you write return 21.0.
  • You can only use await inside an async function. If you do not await, the Future runs all the same; you just do not wait for it.
  • then is what await does underneath. Prefer await: it reads from top to bottom.

For the tests: await suspends the function, not the thread.

2. Errors: try, on, catch, finally

class ApiException implements Exception {
  const ApiException(this.code, this.message);
  final int code;
  final String message;
  @override
  String toString() => 'ApiException($code): $message';
}

Future<double> readTemperature(String location) async {
  await Future.delayed(const Duration(milliseconds: 500));
  if (location == 'Atlantis') throw const ApiException(404, 'unknown location');
  return 21.0;
}

void main() async {
  for (final l in ['Horta', 'Atlantis']) {
    try {
      print('$l: ${await readTemperature(l)} °C');
    } on ApiException catch (e) {
      print('The API refused: ${e.message} (${e.code})');   // expected error: handle it
    } finally {
      print('--- request "$l" finished');                   // always runs
    }
  }
}
Show what happens if you remove the try: the exception goes up to main and the program ends. It is the equivalent of the app crashing. Then show the order: specific on first, generic catch after.

2. Errors: what matters

  • on Type catch (e) catches only that type; catch (e) catches everything. The order matters: from the most specific to the most general.
  • finally always runs, with or without an error. It is where you turn off the loading indicator and close what you opened.
  • A custom exception (implements Exception) with a code and a message lets the UI decide: 404 shows "not found", 500 shows "try again later".
  • An await that fails throws the exception at the place of the await. With no try around it, it goes up until it ends the app with an error.

For the tests: expected errors (network, API) are handled with on; programming errors (ArgumentError, ! on a null) should fail early, in development.

3. Parallel requests and timeouts

import 'dart:async';

void main() async {
  final locations = ['Ponta Delgada', 'Angra do Heroísmo', 'Horta'];
  final stopwatch = Stopwatch()..start();

  for (final l in locations) {
    await readTemperature(l);                          // one at a time: 3 × 1 s
  }
  print('In sequence: ${stopwatch.elapsedMilliseconds} ms');

  stopwatch.reset();
  final temps = await Future.wait(locations.map(readTemperature));
  print('In parallel: ${stopwatch.elapsedMilliseconds} ms → $temps');   // ~1 s, same order

  try {
    final t = await readTemperature('Flores').timeout(const Duration(milliseconds: 300));
    print('Flores: $t');
  } on TimeoutException {
    print('Slow network: show the old data and try again later');
  }
}
  • Future.wait starts them all at the same time and returns a list in the original order. If one fails, the await throws.
  • .timeout throws TimeoutException if the value does not arrive in time. Without a timeout, the app stays "loading" forever inside a tunnel.

4. Stream: values over time

import 'dart:async';

Stream<double> readings() async* {
  for (var i = 0; i < 5; i++) {
    await Future.delayed(const Duration(milliseconds: 400));
    yield 18 + i * 0.5;                                // emits a value and carries on
  }
}

Stream<DateTime> clock() =>
    Stream.periodic(const Duration(seconds: 1), (_) => DateTime.now());

void main() async {
  await for (final t in readings()) {                  // consumes until the stream closes
    print('Reading: $t °C');
  }

  final subscription = clock().listen(
    (now) => print('${now.hour}:${now.minute}:${now.second}'),
  );
  await Future.delayed(const Duration(seconds: 3));
  await subscription.cancel();                         // an infinite stream has to be cancelled
  print('End');
}
  • A Stream is a sequence of values over time: readings from a sensor, GPS position, messages from a WebSocket, the clock on the screen.
  • async* and yield create; await for consumes; listen returns a subscription that you have to cancel in dispose (lesson 8).

5. JSON (1 of 2): the model

import 'dart:convert';

class Forecast {
  const Forecast({required this.location, required this.day, required this.tMin, required this.tMax});

  final String location;
  final DateTime day;
  final double tMin;
  final double tMax;

  factory Forecast.fromJson(Map<String, dynamic> json) => Forecast(
        location: json['location'] as String,
        day: DateTime.parse(json['day'] as String),
        tMin: (json['tMin'] as num).toDouble(),        // the API may send 17 or 17.0
        tMax: (json['tMax'] as num).toDouble(),
      );

  Map<String, dynamic> toJson() => {
        'location': location,
        'day': day.toIso8601String(),
        'tMin': tMin,
        'tMax': tMax,
      };
}
This is the pattern that will show up in every model of the project. Insist on (x as num).toDouble(): it is the most common bug when the API changes 17.0 to 17. Ask: what happens if the tMax field does not come? Leave the answer for the homework.

5. JSON (2 of 2): decoding and serialising

const body = '''
[
  {"location": "Horta", "day": "2026-09-23", "tMin": 17, "tMax": 22.5},
  {"location": "Horta", "day": "2026-09-24", "tMin": 16, "tMax": 21}
]''';

void main() {
  final raw = jsonDecode(body) as List<dynamic>;           // does not know what it is yet
  final forecasts = raw
      .map((e) => Forecast.fromJson(e as Map<String, dynamic>))
      .toList();

  print(forecasts.length);                                     // 2
  print(forecasts.first.tMax);                                 // 22.5
  print(forecasts.map((f) => f.day.day).toList());             // [23, 24]

  final text = jsonEncode(forecasts.map((f) => f.toJson()).toList());
  print(text);                                                 // ready to send or save
}

Pipeline: String (response body) → jsonDecode → Map / List → fromJson → Forecast → List<Forecast> → widgets

Analogy JSON is text with labels, like a form filled in by hand. jsonDecode turns that text into a dictionary (Map<String, dynamic>): you can already read it by key, but nothing is checked. Forecast.fromJson copies the form out neatly onto a typed record card: each field in the right place, with the right type, and a clear error if something is missing. From then on the rest of the app works with record cards, never with text.

5. JSON: what matters

  • jsonDecode returns dynamic: a Map<String, dynamic> for objects, a List<dynamic> for lists. You do the cast and then build your own objects.
  • fromJson is a factory: it takes the map and returns an instance. toJson goes the other way. This pair will exist in every model of the project.
  • Numbers: JSON does not distinguish 17 from 17.0; in Dart the first is an int. (x as num).toDouble() avoids a crash.
  • If a field is missing, json['tMax'] as num throws a TypeError. Validating this is the homework.

For the tests: in Dart, JSON is decoded into generic Map and List; the conversion to classes is your code (or generated with json_serializable).

6. Enums with values and extension methods

enum WeatherType {
  sun('☀️', 'Clear sky'),
  cloudy('☁️', 'Cloudy'),
  rain('🌧️', 'Rain'),
  thunderstorm('⛈️', 'Thunderstorm');

  const WeatherType(this.icon, this.description);
  final String icon;
  final String description;

  static WeatherType fromApi(String code) =>
      values.firstWhere((t) => t.name == code, orElse: () => cloudy);
}

extension Temperature on double {
  String get celsius => '${toStringAsFixed(1)} °C';
  double get fahrenheit => this * 9 / 5 + 32;
}

void main() {
  final t = WeatherType.fromApi('rain');
  print('${t.icon} ${t.description}');   // 🌧️ Rain
  print(21.456.celsius);                 // 21.5 °C
  print(21.0.fahrenheit);                // 69.8
}

6. Enums and extensions: what matters

  • An enum can have fields, a const constructor, getters and static methods. values is the list of all of them; name is the identifier as text.
  • firstWhere with orElse turns the string from the API into an enum value without failing when a new value turns up.
  • extension X on Type adds methods to types that are not yours (double, DateTime, String). It has to be imported in the file where you use it.
  • In Flutter you will see extensions on BuildContext (context.theme) and on num in many pub.dev packages.

For the tests: an enum in Dart 3 is a class with a fixed number of instances; it can have fields and methods, but it cannot be extended.
