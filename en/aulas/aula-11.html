Quality: lints, organisation and git flow

Theory: code quality: lints, organisation by feature, widget extraction and code review; git flow for teams with a branch per task, small pull requests and review by a teammate. Practice: guided refactor of the mini-project and resolving a merge conflict.

Repository: pdm-aula-11

By the end of this lesson you can

  • Organise a Flutter project by feature and say what it gains over organisation by layer.
  • Extract reusable widgets with named parameters and const constructors.
  • Review a classmate's code with useful comments on names, errors, dispose and null safety.

Lints: the compiler that knows you

  • The Dart analyser catches type errors. Lints go further: they catch code that compiles but is wrong, slow or going to cause problems. They are rules, and you choose which ones.
  • flutter_lints comes with flutter create: the rules recommended by the Flutter team. Few, uncontroversial, no false positives.
  • very_good_analysis (Very Good Ventures) is the strict set used in industry: 200-odd rules, including style, documentation and trailing commas. More noise at the start, fewer arguments in code review.
  • The configuration lives in analysis_options.yaml at the root. VS Code shows the warnings as you type; flutter analyze shows them all; the CI (lesson 25) rejects PRs with warnings.
  • Zero warnings is the definition of done in the project. Not because every warning is serious, but because a project with 200 warnings hides the 3 that matter.

For the tests: lints are static analysis rules configured in analysis_options.yaml; flutter_lints is the base set, very_good_analysis the strict one.

Open the solution mini-project with very_good_analysis turned on and show the list of warnings: there are dozens. Ask which ones the students think matter. Then show the same with flutter_lints: almost none. The difference is the conversation of this slide and the next.

analysis_options.yaml

include: package:flutter_lints/flutter.yaml   # or package:very_good_analysis/analysis_options.yaml

analyzer:
  language:
    strict-casts: true          # no dynamic passing as a String without an explicit cast
    strict-inference: true
    strict-raw-types: true      # List without <T> is a warning
  errors:
    unused_import: error        # raised from warning to error
    use_build_context_synchronously: error
  exclude:
    - "**/*.g.dart"             # generated code is not analysed

linter:
  rules:
    prefer_const_constructors: true
    prefer_final_locals: true
    avoid_print: true
    require_trailing_commas: true
    always_declare_return_types: true
    avoid_dynamic_calls: true

include inherits a set; analyzer.errors changes the severity; linter.rules turns rules on or off one by one. The full list is at dart.dev/tools/linter-rules.

Warnings that matter, and why

RuleWhy it exists
prefer_const_constructorsA const widget is created once and reused in every rebuild. Less work per frame; less jank.
use_build_context_synchronouslyUsing the context after an await can point to a widget that no longer exists. Intermittent crash, hard to reproduce.
avoid_printprint stays in the release binary and goes to the system logs. Use debugPrint or a logger that turns itself off in production.
strict-casts and avoid_dynamic_callsJSON is dynamic; without explicit casts the error shows up at runtime on the user's phone, not at compile time.
unused_import, unused_local_variable, dead_codeNoise that hides bugs and confuses the reader. If it is not used, delete it.

For the tests: use_build_context_synchronously exists because the widget may have been destroyed during the await; const avoids rebuilds.

Organisation: by layer or by feature

By layer

lib/
  models/      forecast.dart, location.dart, warning.dart
  services/    local_forecasts.dart, api_client.dart
  ui/          list_screen.dart, detail_screen.dart,
               warnings_screen.dart, settings_screen.dart
  widgets/     forecast_card.dart, day_chip.dart

Simple to start with. With 30 screens, each feature is spread over four folders and one change touches all of them.

By feature

lib/
  app/           app.dart, router.dart, theme.dart
  forecast/      models/, data/, ui/
  warnings/      models/, data/, ui/
  settings/      ui/
  shared/        widgets/, extensions/, l10n/

Each folder is a complete feature, with its layers inside. One team per folder; deleting a feature is deleting a folder.

For the tests: by layer groups by the kind of code; by feature groups by what the app does. The project uses by feature with layers inside each one, which is what the Flutter architecture guide recommends.

Reusable widgets

  • Extract when it repeats or when a build goes past 50 lines. A 300-line build cannot be read, cannot be tested and rebuilds everything every time.
  • Class, not method. Widget _card() inside the State looks shorter, but it cannot be const, always rebuilds, and does not show up in the inspector. class ForecastCard extends StatelessWidget solves all three.
  • Named parameters and required: ForecastCard(forecast: f, onTap: open) reads without opening the class. Input data as final fields; actions as VoidCallback or ValueChanged<T> callbacks.
  • const constructor whenever the fields are final. The prefer_const_constructors lint tells you where you can use it.
  • Small files: one public widget per file, file name in snake_case matching the class name. forecast_card.dart holds ForecastCard.
  • The widget does not know where the data comes from or where navigation goes. It receives values and returns events. That is what makes it reusable and testable.

For the tests: extract widgets into classes, not methods: they allow const, avoid rebuilds and show up in the inspector.

Code review: what to look for

Look forExample comment
Names that say what the thing is"list2 → filteredLocations? That way the reader does not need to open the where."
Error and empty states handled"If the JSON fails, the FutureBuilder stays blank. A Text with the message and a retry button?"
dispose for every controller, timer and subscription"The _controller created in initState is never released. Memory leak every time the screen opens."
Null checks with ! and casts hiding problems"This json['tMax']! fails when the field is missing. ?? 0 or a FormatException with the field name?"
Large widgets and repeated code"This build has 140 lines and the card appears three times. Extract ForecastCard?"
Project a 150-line file from the starter and do the review live with the class: they point, you write the comment. 5 minutes. Note that every comment ends with a question or a concrete suggestion, never with "this is wrong".

Code review: how to comment

  • Comment on the code, not the person. "This method does two things" instead of "you did this wrong".
  • Ask before asserting. "Is there a reason for the Future to be created in build?" Sometimes there is, and you learn; sometimes there is not, and the author fixes it without feeling attacked.
  • Suggest, with code when it helps. GitHub has "suggestion" blocks that the author accepts with one click.
  • Separate what blocks from what is taste. "blocking: crash with no network" vs "nit: I prefer final here". A PR does not sit waiting because of commas.
  • Praise what is good. A review with only problems teaches less than one that says "this extraction came out clean, do the same in the detail screen".
  • Reviewing is reading carefully, not rushing. If you do not understand a block, the comment is "I did not understand this; can you explain or simplify it?". Probably nobody else understands it either.

For the tests: a good review separates blocking from optional, comments on the code and not the author, and ends with a concrete suggestion.

Git for teams (1 of 2): branches and pull requests

  • main protected. Nobody pushes directly. Everything enters through a reviewed pull request. On GitHub: Settings → Branches → "Require a pull request before merging". In the group project it is mandatory.
  • One branch per task, short, with a name that says what it is: feat/warning-detail, fix/overflow-landscape, chore/lints. It is born from main and dies after the merge.
  • Small PR. Fewer than 300 lines, one thing only. A 2000-line PR is not reviewed; it is approved without being read. Split it before opening.
  • Description: what, why, how to test, a screenshot if it is UI. The title becomes the merge commit message.
  • Review by a teammate before it goes in. The author does not approve their own PR. The CI (lesson 25) runs analyze and test and blocks if they fail.

For the tests: a branch per task starting from main, a small PR reviewed by someone else, main protected with no direct push.

Analogy A commit is a photograph of the whole project with a caption and a date; none is ever deleted and you can go back to any of them. A branch is a separate notebook where you experiment without spoiling the main notebook. The pull request is asking a teammate to read the notebook before its contents are copied into the main one.

Git for teams (2 of 2): commits, rebase and conflicts

  • Conventional commits: type(scope): description in the imperative, up to 72 characters. Types: feat, fix, refactor, docs, test, chore. Example: feat(warnings): add warning detail with affected locations. It lets you generate changelogs and understand the history without opening diffs.
  • Merge joins two histories with a merge commit: it preserves everything, but the graph ends up with loops. Rebase rewrites your commits on top of the current main: linear history, but never on commits that have already been shared.
  • Project rule: git pull --rebase on your branch to update; "Squash and merge" on GitHub to enter main. One clean commit per PR.
  • Conflicts happen when two branches change the same lines. They are not an error: they are git asking you to decide. You open the file, choose, delete the markers, git add, carry on.
  • Large conflicts are a symptom of large PRs or of two members working on the same file. Split the work by feature (folder) and almost all of them disappear.

For the tests: rebase rewrites history and is not done on shared commits; a conflict is resolved by editing the file, deleting the markers and running git add.

1. Turn on strict lints and fix

flutter pub add --dev very_good_analysis
flutter analyze
dart fix --dry-run          # what dart can fix on its own
dart fix --apply
flutter analyze
include: package:very_good_analysis/analysis_options.yaml

linter:
  rules:
    public_member_api_docs: false     # documenting everything is too much for an app; for packages
    lines_longer_than_80_chars: false # the formatter takes care of the lines
  • dart fix fixes the mechanical part: missing const, unused imports, trailing commas. The rest is fixed by hand, one warning at a time.
  • Turning a rule off is legitimate when you have a reason and you write it next to it. Turning a rule off because it produces many warnings is not a reason.

2. Extract widgets

class ForecastCard extends StatelessWidget {
  const ForecastCard({
    required this.forecast,
    this.selected = false,
    this.onTap,
    super.key,
  });

  final Forecast forecast;
  final bool selected;
  final VoidCallback? onTap;                     // action: whoever uses it decides what it does

  @override
  Widget build(BuildContext context) {
    final colors = Theme.of(context).colorScheme;
    return Card(
      color: selected ? colors.primaryContainer : null,
      child: InkWell(
        onTap: onTap,
        child: Padding(
          padding: const EdgeInsets.all(12),
          child: Text('${forecast.day.day}: ${forecast.tMin.round()}° to ${forecast.tMax.round()}°'),
        ),
      ),
    );
  }
}

2. Extract: what matters

  • VS Code does the extraction: select the widget, Ctrl+. → "Extract Widget", give it a name. Then you move the result to the right file and replace the captured fields with parameters.
  • Parameter order: the required ones first, the optional ones after, super.key at the end. It is the very_good_analysis convention.
  • The widget does not import go_router or data.dart. It receives a Forecast and an onTap. Whoever uses it decides where to navigate.
  • After extracting, the screen's build is left with 30 lines that read like a table of contents: header, row of days, card for the day. That is the goal.

  forecast/

4. Simulate and resolve a conflict

git switch main
git pull
git switch -c feat/title-pt      # change the title in lib/app/app.dart to 'Tempo Açores' and commit
git switch main
git switch -c feat/title-en      # change the SAME line to 'Azores Weather' and commit
git switch main
git merge feat/title-pt                             # goes in without conflict
git merge feat/title-en                             # CONFLICT (content): lib/app/app.dart
      title: 'Tempo Açores',
<<<<<<< HEAD
      // version that is on main
=======
      title: 'Azores Weather',
>>>>>>> feat/title-en
  1. Open the file. VS Code shows "Accept Current", "Accept Incoming", "Accept Both". Decide: here, the title comes from the .arb, so neither of the two is right.
  2. Write the final version, delete the three markers, save. flutter analyze to confirm it compiles.
  3. git add lib/app/app.dart and git commit. If you were in a rebase: git rebase --continue.
Exercise 4 Cause and resolve the conflict above in your repository. Then delete the two branches. If you get lost halfway: git merge --abort goes back to the previous state, always.
Let them cause the conflict on their own; it is the moment they realise it is not serious. Walk around and show git merge --abort to anyone who panics. Give 15 minutes. If there is time left, show the same with rebase and --force-with-lease on the push.

5. dart format and format-on-save

dart format lib test                 # formats everything; with no arguments, the whole project
dart format --set-exit-if-changed .  # in CI: fails if anything is not formatted
{
  "editor.formatOnSave": true,
  "[dart]": {
    "editor.formatOnSave": true,
    "editor.rulers": [80],
    "editor.codeActionsOnSave": { "source.fixAll": "explicit" }
  },
  "dart.lineLength": 80
}
  • The Dart formatter has no style options. The arguments about braces and indentation are over: everyone has the same code.
  • The trailing comma decides the format: with a comma at the end, one argument per line; without it, everything on one line. That is why require_trailing_commas is turned on.
  • Commit .vscode/settings.json: the whole team gets the same configuration.
Exercise 5 Turn on format-on-save, run dart format . on the mini-project and commit the result in a PR of its own, chore: format with dart format. It is a small PR and simple to review.
