Why the system limits the background

  • One battery, many apps. Every app that "just checks one thing" each minute wakes the CPU and the radio. Ten apps like that drain a phone in an afternoon, and the user blames the phone.
  • Privacy and control. The user wants to know what runs without them seeing it. That is why iOS shows "used your location in the background" and Android 14 makes you declare the type of every foreground service.
  • On leaving the screen: iOS suspends the app within seconds (about 30 s of grace with beginBackgroundTask); Android keeps the process until it needs memory, and then kills it without notice.
  • What dies: Timer, streams, animations, an await http.get in flight, isolates. The app is not told; next time it starts from zero, in main().
  • What survives: what is on disk (lesson 16) and what the system agreed to schedule for you: notifications (lesson 22), WorkManager tasks, alarms.
  • Examples: WhatsApp does not keep running, it is the push that wakes it; Spotify runs because it has an audio foreground service, with a visible notification.

For the tests: an app in the background is not running; it is suspended or dead, and the code that was in flight does not finish.

Analogy An app is a shop in a shopping centre. Open and with customers is the foreground; with the lights off but the stock in place is the background or suspension. In the small hours, the shopping centre can evict the shop without notice to give the space to another: that is the process being killed. When the customer comes back, the shop reopens as if nothing had happened, and whatever was not kept in the storeroom (the disk) is lost.
Ask: "if you have a Timer.periodic refreshing the forecast every minute, what happens when you lock the phone?" Most think it carries on. On iOS it stops within seconds; on Android it carries on until the process dies, and nobody knows when. Neither answer is any good for designing an app.

Android: WorkManager, foreground services, Doze and buckets

MechanismWhat it isWhat your app needs to know
WorkManagerDeferred or periodic work, with constraints (network, charger, battery). Survives restarts.Minimum 15 min between runs. The system picks the time. The task must be short and idempotent.
Foreground serviceA running process with a permanent visible notification.Only for what the user sees happening: music, navigation, upload. Android 14 requires a declared type and its own permission.
AlarmManagerWaking the app at a given time.Exact requires SCHEDULE_EXACT_ALARM (12+); on 14 only alarm clocks and calendars have it by default. Inexact can be minutes late.
DozeScreen off and phone still: network, jobs and alarms deferred to maintenance windows that get further and further apart.Your "every 6 hours" task may run at 8 or at 9. There is no way round it, and that is how it should be.
App Standby bucketsActive, working set, frequent, rare, restricted, depending on how much the user uses the app.An app that is rarely opened: few jobs per day. The user can also set it to "restricted" in the battery settings.

For the tests: WorkManager guarantees that the task runs, not when; Doze and the buckets decide the when.

Analogy Registering a task with WorkManager is leaving a note for the caretaker of the building, the operating system: "when you can, go and water the plants". The caretaker decides the time, batches the notes from several residents to save trips, and if the building is in power-saving mode (Doze) only comes by in the small hours. No resident can demand "at 20:00 sharp"; that is what the alarm and the scheduled notification are for.

iOS: BGAppRefreshTask, BGProcessingTask and silent push

  • BGAppRefreshTask: up to 30 s, to "refresh before the user opens the app". The system learns what time you open the app and wakes it a little earlier. You ask for an earliestBeginDate, not a time.
  • BGProcessingTask: minutes, for heavy maintenance. It typically runs at night, while charging. You can require network and charger.
  • No guarantees: if the user rarely opens the app, iOS hardly ever wakes it. If they turn off "Background App Refresh" in Settings, never.
  • Silent push (content-available: 1, lesson 19): the server wakes the app when there is something new. Also limited: a few per hour, with no delivery guarantee.
  • UIBackgroundModes in Info.plist: fetch, processing, remote-notification, audio, location, voip. Each one is reviewed by Apple; audio without playing sound means rejection.
  • Testing: there is no adb. With the app paused in the Xcode debugger, e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"..."].

For the tests: on iOS there is no periodic task with a set time; the system learns the user's habits and decides when to wake the app.

In Flutter: workmanager, background_fetch and the isolate

  • workmanager: WorkManager on Android and BGTaskScheduler on iOS, with a single API. Periodic tasks with a frequency only on Android; on iOS you register identifiers and the system calls when it wants.
  • background_fetch: the same space, with background fetch on iOS and headless mode on Android. flutter_background_service: a foreground service with an isolate running.
  • The callback runs in a new isolate, opened by native code, without the app: separate memory, main() has not run, no widget exists.
  • It can use: pure Dart, http, shared_preferences, drift, flutter_secure_storage, flutter_local_notifications. It cannot use: BuildContext, Provider, setState, plugins that need an Activity (permission dialogs, image_picker), the app's in-memory state.
  • @pragma('vm:entry-point') on the top-level function: in release, tree-shaking removes whatever no Dart code calls, and this one is called by native code.
  • With the app open at the same time there are two isolates using the same database. The disk is the only meeting point: drift copes, an in-memory Map does not.

For the tests: the background callback runs in a new isolate, with no widget tree and without the app's state; only the disk is shared.

Link to lesson 18: compute() creates an isolate from the app; here it is the system that creates the isolate and the app may not even exist. The rules are the same (no BuildContext, data copied), made worse by the fact that main() has not run: whoever wants the token has to read it from secure storage again.

Patterns: sync in the small hours, do not poll, respect the user

  • Sync when it pays off: with network and battery not low (constraints), while charging for what is heavy, in the small hours for what can wait.
  • Do not poll. "Anything new?" every 15 minutes is what WorkManager allows, and it is almost always the wrong answer: push (lesson 19) for what the server knows, refresh on open for the rest.
  • Short and idempotent: it can be killed halfway and repeated. Save "last sync" and do no more than one per window; return false lets WorkManager retry with backoff.
  • Respect the user: a switch in the settings, respect battery saver mode, no waking the phone for the sake of analytics.
  • Measure: Battery Historian and adb shell dumpsys batterystats; the Energy gauge in Xcode. The user sees "used 12% in the background" in the battery settings, and uninstalls.
  • Examples: Gmail syncs by push, not by polling; Spotify downloads playlists at night while charging; weather apps use the system refresh and a home screen widget.

For the tests: background work is short, idempotent and tolerates being deferred or repeated; if it needs an exact time, it is not background work, it is an alarm or a scheduled notification.

Demo (1 of 2): register the periodic task on Android

import 'package:workmanager/workmanager.dart';
import 'background/background_tasks.dart'; // callbackDispatcher and cacheTask

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Workmanager().initialize(callbackDispatcher); // top-level function: next slide

  // Android: every 6 hours, only with network and battery not low. The system picks the time.
  // The unique name avoids duplicates: registering again under it keeps the existing one.
  await Workmanager().registerPeriodicTask(
    cacheTask, // uniqueName: to cancel and not duplicate
    cacheTask, // taskName: what reaches the callback
    frequency: const Duration(hours: 6),
    constraints: Constraints(
      networkType: NetworkType.connected,
      requiresBatteryNotLow: true,
    ),
    backoffPolicy: BackoffPolicy.exponential, // failed? retry with a growing delay
  );

  // Test right away, in development only: registerOneOffTask('test', cacheTask, initialDelay: 10 s)
  runApp(/* ...as in lesson 22 */);
}

Demo (2 of 2): the top-level callback, in an isolate without the app

import 'package:workmanager/workmanager.dart';
const cacheTask = 'pt.uac.tempoacores.refreshCache';

/// Called by native code in a new isolate, without the app: top-level, and with
/// the pragma so that tree-shaking does not remove it in release.
@pragma('vm:entry-point')
void callbackDispatcher() {
  Workmanager().executeTask((task, data) async {
    if (task != cacheTask) return true; // unknown task: do not retry
    try { // no Provider or BuildContext: we build what we need by hand
      final token = await const FlutterSecureStorage().read(key: 'token');
      if (token == null) return true; // no session, nothing to do
      final api = ApiClient(token: token);
      final cache = ForecastCache(AppDatabase()); // drift, lesson 16
      final favorites = await LocalFavorites.ids(); // shared_preferences
      for (final id in favorites) {
        await cache.save(id, await api.forecast(id)); // GET /v1/forecast/{id}
      }
      await BackgroundWarnings(api, cache).checkAndNotify(favorites); // lesson 22
      return true;
    } catch (e) {
      return false; // WorkManager retries with exponential backoff
    }
  });
}

Demo: what matters

  • Unique name vs task name: the first identifies the registration (cancel with cancelByUniqueName, do not duplicate); the second reaches the callback so it knows what to do.
  • 6 hours is a request. With Doze and buckets it can be 7 or 9. Minimum 15 minutes. If you need a set time, it is zonedSchedule (yesterday) or an alarm.
  • Same database, two isolates: drift opens another connection. The open app sees the new data when the user refreshes, or straight away if it observes the table with watch().
  • return true is done; return false is retry with backoff; an uncaught exception is a silent failure in release. Catch everything and log it.
  • See and force: adb shell dumpsys jobscheduler | grep tempoacores lists what is scheduled; registerOneOffTask with an initialDelay of 10 s runs right away. The print calls from the isolate show up in the normal flutter run.
  • iOS: BGTaskSchedulerPermittedIdentifiers and UIBackgroundModes in Info.plist, registration in the AppDelegate, and the system calls executeTask when it wants. Not part of the project.
