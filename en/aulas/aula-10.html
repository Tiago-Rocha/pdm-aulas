Accessibility is mandatory, and it is good engineering

  • Law: the European Accessibility Act has been in force since June 2025. Apps for commerce, banking, transport and consumer services in the EU have to be accessible. Fines and removal from the market are real.
  • Stores: Apple and Google assess accessibility in featuring reviews and in rejections. Apple has published "Accessibility Nutrition Labels" since 2025.
  • People: about 1 in 6 people has some disability. And we all use the phone in the sun, with one hand, with a cracked screen, or with the system text size turned up.
  • Engineering: an accessible app has widgets with names, a clear structure and no colour as the only signal. That is the same as an app that is testable and easy to maintain.
  • Flutter already does a lot by itself: buttons, texts and fields get semantics automatically. You take care of what is missing.

For the tests: the European Accessibility Act (2025) requires consumer service apps in the EU to be accessible; semantics in Flutter are generated automatically for Material widgets and completed with Semantics.

Semantics in Flutter

// Flutter generates semantics for Text, buttons and fields. You add what is missing:
IconButton(
  icon: const Icon(Icons.star_border),
  tooltip: 'Add to favourites',              // read by the screen reader and shown on long press
  onPressed: add,
),

Semantics(
  label: 'Ponta Delgada, 21 degrees, clear sky',
  button: true,
  child: ExcludeSemantics(                   // the icon and the texts are already in the label
    child: LocationCard(forecast: p),
  ),
),

Image.asset('assets/img/sao_miguel.jpg', semanticLabel: 'Lagoa das Sete Cidades'),

MergeSemantics(                              // two texts read as one
  child: Row(children: const [Text('Min '), Text('17°')]),
),
  • Focus order: the reader follows the order of the tree. If the visual layout does not match, Semantics(sortKey: OrdinalSortKey(1)) fixes it.
  • Test with TalkBack (Android: Settings → Accessibility) or VoiceOver (iOS: triple-click the side button). Five minutes of use with the screen covered reveal more than reading the documentation.
Analogy The screen reader is a guide who describes the room to someone who cannot see. A button with only an icon is an object with no name: the guide says "button" and nothing else. The semantic label (tooltip, label) gives it its name; MergeSemantics joins several pieces into one description.
Ask: what does the screen reader say on a card with a sun icon, "Ponta Delgada" and "21°"? Without Semantics: three separate elements, the icon with no name. With the label: one sentence. Show "Show semantics" in DevTools so they can see the semantics tree.

Contrast, touch and large text

  • Contrast: 4.5:1 for normal text, 3:1 for large text and icons (WCAG AA). ColorScheme.fromSeed guarantees the x/onX pairs; colours set by hand are the source of the problems. Check with Accessibility Scanner (Android) or the Xcode inspector.
  • Touch targets: 48 dp minimum. IconButton and ListTile already comply; a GestureDetector around a 20 dp icon does not. MaterialTapTargetSize.padded is the theme's default value.
  • Large text: the user can set the text to 200%. MediaQuery.textScalerOf(context) tells you the factor. Layouts with fixed heights (SizedBox(height: 40) around a Text) break; use Wrap, Expanded, FittedBox or leave the height free.
  • Test with the system text size at maximum. If a card ends up with cut-off text, it is a bug, not an odd preference.
  • Colour is not a signal: a "red" warning also needs an icon or text. Colour blindness affects 8% of men.

For the tests: minimum contrast 4.5:1, minimum target 48 dp, and the layout has to survive a textScaler of 2.0.

i18n (1 of 2): gen-l10n and .arb files

# pubspec.yaml
dependencies:
  flutter_localizations:
    sdk: flutter
  intl: any                     # the version the SDK pins
flutter:
  generate: true                # runs gen-l10n on every pub get

# l10n.yaml (at the project root)
arb-dir: lib/l10n
template-arb-file: app_pt.arb
output-localizations-file: app_localizations.dart
{
  "@@locale": "pt",
  "appTitle": "Tempo Açores",
  "search": "Pesquisar localidade",
  "forecastDays": "{n, plural, =1{Previsão para 1 dia} other{Previsão para {n} dias}}",
  "@forecastDays": {"placeholders": {"n": {"type": "int"}}},
  "updatedAgo": "Atualizado há {minutes} min",
  "@updatedAgo": {"placeholders": {"minutes": {"type": "int"}}}
}
Analogy You do not write the text on the wall; you write it on a sign that can be swapped. The .arb files are the signs in each language, and gen-l10n builds the holder the sign slots into (AppLocalizations). The phone's locale picks the sign.

i18n (2 of 2): using the strings

import 'l10n/app_localizations.dart';                       // generated in lib/l10n/

MaterialApp.router(
  routerConfig: router,
  localizationsDelegates: AppLocalizations.localizationsDelegates,
  supportedLocales: AppLocalizations.supportedLocales,     // [pt, en], from the .arb files
  onGenerateTitle: (context) => AppLocalizations.of(context)!.appTitle,
)

// in a widget
final l10n = AppLocalizations.of(context)!;
Text(l10n.appTitle);
Text(l10n.forecastDays(5));                                  // Previsão para 5 dias
Text(l10n.updatedAgo(12));                                 // Atualizado há 12 min
  • The template file (app_pt.arb) defines the keys; every other language is an .arb with the same keys. A missing key gives a warning when generating, not a crash at runtime.
  • Plurals with ICU: =0, =1, other. In Portuguese "1 dia" and "2 dias"; other languages have more forms, and the format handles them.
  • The language comes from the system. To force one, locale: const Locale('en') in the MaterialApp (useful for testing).

For the tests: the strings live in .arb files, one language per file; gen-l10n generates the AppLocalizations class; there is never visible text hard-coded in the widgets.

Formats with intl, and RTL in one sentence

import 'package:intl/intl.dart';
import 'package:intl/date_symbol_data_local.dart';

await initializeDateFormatting('pt_PT');               // once, in main, before runApp

final today = DateTime(2026, 10, 6);
DateFormat.EEEE('pt_PT').format(today);                // terça-feira
DateFormat('d MMM', 'pt_PT').format(today);            // 6 out.
DateFormat.yMMMMd('en').format(today);                 // October 6, 2026
NumberFormat('0.0', 'pt_PT').format(21.456);           // 21,5
NumberFormat.decimalPattern('en').format(1234.5);      // 1,234.5

// Better: the screen's locale, not a fixed one
final locale = Localizations.localeOf(context).toString();
DateFormat.EEEE(locale).format(today);
  • Dates, numbers, currencies and units change from language to language: the decimal comma, the day/month order, the name of the day. Never assemble them by hand with '$day/$month'.
  • RTL: Arabic and Hebrew are written from right to left; Flutter mirrors the layout by itself if you use EdgeInsetsDirectional and start/end instead of left/right.

For the tests: intl formats dates and numbers by locale; initializeDateFormatting is mandatory for locales other than English.

Step 1: loading JSON from the assets

import 'dart:convert';
import 'package:flutter/services.dart';

class LocalForecasts {
  Future<List<Location>> load() async {
    final text = await rootBundle.loadString('assets/forecasts.json');
    final json = jsonDecode(text) as Map<String, dynamic>;
    final items = json['locations'] as List<dynamic>;
    return items
        .map((e) => Location.fromJson(e as Map<String, dynamic>))
        .toList();
  }
}

// on the list screen
FutureBuilder<List<Location>>(
  future: _future,                              // created once in initState, never in build
  builder: (context, snapshot) {
    if (snapshot.hasError) return Text('Error: ${snapshot.error}');
    if (!snapshot.hasData) return const Center(child: CircularProgressIndicator());
    final locations = snapshot.data!;
    return LocationList(locations: locations);
  },
)
Classic mistake: creating the Future inside build; on every rebuild it reads the file again and the screen flickers. Show it on purpose and fix it with initState. Second mistake: the file is not declared in pubspec.yaml and loadString throws "Unable to load asset".

Step 1: what matters

  • rootBundle.loadString reads a file declared in pubspec.yaml in the assets: section. It is asynchronous because in release the assets come from inside the binary.
  • The Location and Forecast models with fromJson are the ones from lesson 4, with the validation from the homework: a missing field throws a FormatException with the name of the field.
  • FutureBuilder draws the states of the Future: loading, with an error, with data. It is the minimal version of the four states from lesson 6; in lesson 14 we do better.
  • The Future is created once (initState) and kept in a field. Creating it in build repeats the read on every rebuild.
  • The LocalForecasts class is the only one that knows where the data comes from. In lesson 12 it is swapped for one that talks to the API without touching the screens.
