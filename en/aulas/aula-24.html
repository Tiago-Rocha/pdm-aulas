Camera and gallery

  • image_picker opens the system camera or gallery and returns a file. It is enough for most cases: a profile photo, attaching an image to a form. It is what WhatsApp does when you attach a photo.
  • camera gives you the live preview inside the app, control of focus, flash and video. You need it to read QR codes or apply filters. It costs more code and more permissions.
  • Permissions: Android 13+ uses the Photo Picker and does not ask for permission to choose from the gallery; the camera requires CAMERA. iOS requires NSCameraUsageDescription and NSPhotoLibraryUsageDescription in Info.plist, with a justification text, or the app crashes.
  • Size: a 12 MP photo is 4 to 6 MB. Before sending, shrink it with maxWidth and imageQuality from image_picker or with flutter_image_compress. A 6 MB upload on 3G fails; a 300 KB one does not.

For the tests: image_picker delegates to the system and has no preview; camera has a preview and costs more permissions and code.

Ask: for an app to report potholes in the road, image_picker or camera? Answer: image_picker, they only need the photo. Insist on compression: anyone who has had uploads fail on a weak network gets it straight away.

Motion sensors

  • sensors_plus exposes each sensor as a Stream: accelerometerEventStream(), gyroscopeEventStream(), magnetometerEventStream(), barometerEventStream(). No permissions on either platform.
  • A stream at 100 Hz keeps the CPU awake. Choose the samplingPeriod, cancel the subscription in dispose and when the app goes to the background.

For the tests: motion sensors do not ask for permission, but they cost battery; cancel the stream when nobody is looking.

Analogy The sensors are the phone's senses. The accelerometer and the gyroscope are the inner ear: they give balance and movement without asking anyone's leave. The camera is sight. NFC is touch: it only works within centimetres and in an instant. BLE is the voice: it reaches tens of metres and holds a conversation. Each sense has its own permission and its own cost in battery.

NFC

  • NDEF tags are the common language of tags: text, URL, vCard, Wi-Fi configuration. Reading and writing with nfc_manager. Examples: tags in museums, business cards, stickers that open an app.
  • Android: reads and writes tags in the background, with no system screen; it needs android.permission.NFC in the manifest, with no prompt to the user. It does HCE (Host Card Emulation): the phone pretends to be a card, with a native service.
  • iOS: reads since iOS 11 and writes since 13, but always in a session with the system sheet visible ("Ready to Scan"); it needs NFCReaderUsageDescription and the capability in Xcode. HCE only since iOS 17.4, only in the EU and with Apple's authorisation.
  • Payments (Apple Pay, Google Wallet) use NFC with a Secure Element. An ordinary app cannot imitate that; a home-made "transport card" is not possible.

For the tests: in NFC, Android does reading, writing and HCE; iOS reads and writes in a system session and HCE is a special case.

Show the "Ready to Scan" sheet on your iPhone; Android users find it odd that there is no silent mode. Frequent question: "can I make a gym access card?" Only if the reader accepts NDEF or HCE; transport cards require a Secure Element and agreements with the operator.

Bluetooth Low Energy

  • Central is whoever scans and connects (the phone). Peripheral is whoever advertises (the wristband, the temperature sensor, the lock). The phone can also be a peripheral, but it is rarely worth it.
  • Flow: scan for advertisements → connect → discover services → read, write or subscribe to characteristics. Each characteristic is a UUID with bytes; the meaning comes from the standard (Heart Rate Service 0x180D) or from the manufacturer.
  • flutter_blue_plus: scan with filters, connection, read(), write() and lastValueStream per characteristic.
  • Permissions: up to Android 11 the scan requires location permission, because beacons reveal where you are. Android 12+ has BLUETOOTH_SCAN and BLUETOOTH_CONNECT, with the neverForLocation flag. iOS asks for NSBluetoothAlwaysUsageDescription.
  • Examples: Mi Band, home weather stations, AirTags, the contact tracing system from the pandemic.

For the tests: BLE on old Android asks for location in order to scan; it is not a bug, it is privacy.

Biometrics, haptics, home screen widgets

  • local_auth: Face ID, Touch ID, fingerprint, with authenticate(localizedReason: ...). It unlocks something local: showing the stored token, entering a sensitive screen. It does not replace authentication on the server (lesson 17).
  • Haptics: HapticFeedback.lightImpact(), mediumImpact(), heavyImpact(), selectionClick(). No permission, no package, and it is one of the details that most make an app feel native. iOS has the Taptic engine; on Android it depends on the hardware.
  • Home screen widgets: home_widget bridges to App Widgets (Android) and WidgetKit (iOS). The widget's UI is native; Flutter only writes the data. The perfect case: today's forecast for the favourite location.
  • Live Activities (iOS 16.1+) and Dynamic Island in one sentence: a live notification whose data you update; Swift code is mandatory. Examples: deliveries, flights, sports results.

For the tests: biometrics is local unlocking; a home screen widget is drawn in native code and Flutter only gives it data.

Ask the class where a haptic would make sense in Tempo Açores. Good answers: when adding a favourite, when completing the pull-to-refresh, when a red warning arrives. Common question: "does biometrics prove to the server who I am?" No: it proves it to the phone, and the server still only sees the token.

Demo: read an NFC tag and vibrate

On the teacher's phone. The code is short, and what matters is the sequence: check availability, open a session, handle the tag, close the session.

import 'package:flutter/services.dart';
import 'package:nfc_manager/nfc_manager.dart';
import 'package:nfc_manager_ndef/nfc_manager_ndef.dart';

class NfcService {
  Future<void> readTag({required void Function(String) onRead}) async {
    if (!await NfcManager.instance.isAvailable()) {
      throw StateError('NFC unavailable or turned off on this phone');
    }
    await NfcManager.instance.startSession(
      pollingOptions: {NfcPollingOption.iso14443, NfcPollingOption.iso15693},
      onDiscovered: (NfcTag tag) async {
        final message = await Ndef.from(tag)?.read();
        final record = message?.records.firstOrNull;
        final text = record == null
            ? 'tag with no NDEF content'
            : String.fromCharCodes(record.payload.skip(3)); // skips the Text Record header
        await HapticFeedback.heavyImpact();
        onRead(text);
        await NfcManager.instance.stopSession();
      },
    );
  }
}

Demo: what matters

  • isAvailable() first: without NFC, or with NFC turned off in the settings, the session never opens. Show a message, not a crash.
  • On Android, onDiscovered fires silently. On iOS the system sheet appears and the session closes by itself after 60 seconds.
  • The payload of a Text Record starts with a status byte and the language code (pt, en): hence the skip(3).
  • Configuration: <uses-permission android:name="android.permission.NFC"/> in AndroidManifest.xml; on iOS, NFCReaderUsageDescription in Info.plist and the "Near Field Communication Tag Reading" capability in Xcode.
  • The HapticFeedback.heavyImpact() is the feedback: the user feels that the read happened before reading the screen.
Exercise 1 If your project has a gesture that deserves feedback (adding a favourite, finishing the pull-to-refresh, receiving a red warning), open a five-line PR with HapticFeedback.selectionClick() or mediumImpact() at that point. Test on the phone, not on the emulator: the emulator does not vibrate.
