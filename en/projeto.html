Tempo Açores

A weather and trails app for the Azores, built in groups on the course API: 5-day forecast and IPMA weather warnings for each island, hiking trails, class reports with photos and synced favourites.

Why this app

Because it has everything a real mobile app has: lists and details, data that changes, a network that fails, data worth keeping for when there is no network, authentication, photos, notifications and location. And because the data is from here: the islands, the trails and the forecast are those of the Azores.

The course API

The app does not talk to IPMA directly. It talks to the course API, which fetches the data from IPMA, tidies it up and caches it. It is the same API as mini-project 2, with the same authentication: you exchange a clientId and a clientSecret for a token, and send the token with every request.

DataRequest
Accounts: sign up, log in, renew the session, log out and delete/v1/auth/… and DELETE /v1/me
The nine islands, with photo and coordinatesGET /v1/islands
5-day forecast for an island (IPMA)GET /v1/islands/{id}/forecast
Yellow, orange and red weather warnings (IPMA)GET /v1/warnings
Trails, for all islands or oneGET /v1/trails
Class reports: read, create, edit and delete/v1/reports
The user's favourites: read, add and remove/v1/me/favorites
Sea state near the island (IPMA)GET /v1/islands/{id}/sea
Weather now at the island's stations (IPMA)GET /v1/islands/{id}/observations
Earthquakes in the last 30 days (IPMA)GET /v1/earthquakes
  • Each group gets its own clientId and clientSecret, in an issue in the group repository, which is private. They identify the group's app.
  • Inside the app, each person creates their own account (email, password and name) and logs in with it. Favourites and reports belong to each user; reports appear to the class with the group's name and the name of whoever wrote them. The API stores the email and name of each account, and the password only as a hash. The email does not need to be real: the API sends no emails.
  • The clientSecret never goes into the repository: it is passed at build time with --dart-define.
  • The interactive documentation is at api-pdm.sublimecipher.com/docs: try each request in the browser before you write it in Dart.
  • If the API gets a version 2 during the semester (lesson 28), the migration is part of the sprint 3 work.

Design

The app follows the reference design. This counts in the user experience criterion (visual consistency): colours, type, components and states as they are drawn.

  • Figma: the design system (colours, typography, spacing and 25 components with measurements, states and Flutter code) and the screens.
  • App map and flows (in Portuguese, like the app): which screens exist, how you reach each one, which API requests each one makes and which requirement it covers.
  • Screens (in Portuguese): every screen, with the loading, error and empty states, and the extras.

Groups and repository

  1. Groups of 2 to 3. Formed in lesson 15 (21/10). Anyone not in the lesson is placed in a group by the teacher. Groups do not change after the sprint 1 review.
  2. Group repository. One member opens the template, clicks Use this template and creates a private repository called pdm-projeto- plus the surnames (e.g. pdm-projeto-silva-costa). In Settings, Collaborators they invite the rest of the group and the teacher (Tiago-Rocha). The repository starts with an app that already runs, the layer folders, the lints and CI.
  3. API credentials. The group's clientId and clientSecret arrive in an issue in the repository. You make the first request to the API in the lesson on Mon 26/10.
  4. First pull request. README with each member's name and student number, the initial split of the work and a screenshot of the template app running.

How you work

  • Backlog in issues. Each feature is an issue with a short title (verb and object) and acceptance criteria. The sprint's issues sit on a GitHub Projects board.
  • Everything by pull request. One issue, one branch, one small PR, reviewed by another member of the group before it goes into main. Nobody pushes straight to main.
  • Definition of done. An issue only closes when it runs on the phone, has no flutter analyze warnings, handles the error states and the PR has been reviewed and approved.
  • Everyone's work. Each member must have their own PRs and their own reviews in every sprint. The GitHub history is the evidence.

Sprints

Three sprints of about two weeks. Each one ends with a review in class: each group has 5 minutes to show the app on the phone and say what is still to do. What counts is what is on main at the time of the review.

Distribution to testers

From lesson 27 (20/11), the app must be installed on the phones of people from outside the group. On Android, through Firebase App Distribution; on iOS, through TestFlight, if the group has a Mac and a developer account. At least three testers from outside the group, for example colleagues from other groups. The feedback they give goes into the backlog as issues, and each new build gets a new version number.

Freeze and defences

  • Freeze: Wed 09/12 at 18:30. The group creates the v1.0.0 tag on main. That is the version that is assessed. After the freeze only the README can change.
  • Order of the defences drawn in lesson 35 (09/12), where each group also does a 5-minute rehearsal.
  • Defences: Mon 14/12 (16:00 to 18:00) and Wed 16/12 (08:30 to 10:30). A 10-minute presentation by the group, with 3 slides at most and a live demo on the phone, then questions aimed at each member.
  • In the questions, each person answers alone for the code they wrote and for any part of the app. This is where the oral defence mark comes from, and it is individual.
  • Bring a plan B: a short video of the app working, in case the network or the phone fails.

What you deliver

Everything in the group repository, at the v1.0.0 tag:

  • The app code, with green CI on that commit.
  • A README with: the members' names and numbers, what the app does, screenshots, how to run the app (including the --dart-define for the credentials), the extras done and who did what.
  • The install link for testers (Firebase App Distribution or TestFlight) and the list of who tested.
  • The defence slides as a PDF, in the docs/ folder.
  • The history of issues, branches and pull requests from the three sprints.
Never in the repository The clientSecret, the signing keystore and key.properties. A secret that went into a commit counts as published, even if it is deleted in the next commit.
