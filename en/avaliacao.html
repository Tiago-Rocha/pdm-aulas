How you are assessed

Two components: a final group project, built in sprints over the semester, and one or two multiple-choice written tests on the theory part of the lessons (number and dates to be confirmed).

Draft The weights and rules below are the teacher's proposal and become final in the first lesson, once confirmed with the programme coordination. What does not change is the structure: group project plus multiple-choice written tests.

Written tests

  • On paper, multiple choice, closed book. Each question has four options and only one is correct.
  • Test 1 (04/11): theory from lessons 1 to 19. Mobile ecosystem, Flutter and Dart, lifecycle, UX, state, navigation, accessibility, network layer, architecture, resilience, persistence, security, authentication, performance, push notifications.
  • Test 2 (07/12): theory from lessons 21 to 32. Location and maps, deep links, background work, hardware, tests, observability, distribution to testers, platform channels, stores and monetisation, size and startup, build and signing, store consoles.
  • There is a revision lesson with questions and answers before each test (02/11 and 04/12).

Final group project

Groups of 2 to 3 people. The app connects to a public API: the main proposal is Tempo Açores, on the IPMA API through the course API; another open API can be considered. The full brief, the minimum requirements and the extras are published before the kickoff, in week 7.

Individual mark within the group

The project mark belongs to the group, adjusted per person based on three signals: each person's pull requests (authorship and reviews), the oral defence with questions aimed at each member, and the distribution of commits in the history. The individual mark depends on each member being able to explain the code they delivered.

Monitoring during the semester

Every week, group by group, the teacher follows the commits and pull requests on GitHub and the use of the course API (each group has its own client-id). This is for giving feedback early, not for counting requests. A group that has not yet called the API by week 8 gets a warning from the teacher.

Transparency Requests to the course API are logged (group, endpoint, status, time, platform and app version). No personal content is stored. We talk about this in the first lesson.

Rules

  • The project code lives in the group repository created by GitHub Classroom. Code outside the repository does not count.
  • Using AI (Copilot, ChatGPT, Claude, etc.) is allowed and encouraged, on one condition: you must be able to explain every line you deliver. That is what the defence is for.
  • Plagiarism between groups voids the component for those involved.
  • Sprint deadlines are fixed. Late deliveries are assessed, but the delay counts in the process criterion.
